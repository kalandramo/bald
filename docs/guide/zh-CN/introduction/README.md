# Bald 入门简介

## 前言

多数框架材料停在「怎么用」：跟着示例敲完能跑，但装配开始膨胀时不知道往哪收、新业务域接不进去时不知道为什么、框架升级弄坏你写的代码时只能翻源码。缺的不是又一篇操作教程，而是一张认知地图——这个框架解决什么问题、为什么长成现在的形状、哪些概念是主干、哪些是可以整页跳过的高级面。所谓装配，指把配置、日志、存储、传输面这些能力接进一个进程的那层代码——它不实现任何业务，却决定业务能不能跑起来。

bald 的对应故事是现成的，而且它不回避自己曾经的样子。2026-10 的一次装配层评估直面了原始痛点——**装配复杂度的主要来源是框架结构，而不是示例用法**：装配一个服务要理解太多框架内部。装配编排层默认可见 147 个导出符号；资源注册要经 13 张逐行同构的注册表；「契约段 → 消费者」靠人工枚举表维系，配了一个框架并不消费的配置段（`script` 段全仓零消费者），框架静默忽略、不报错。

此后批 1 落下第一批改造，批 2 到批 5 的四批演进把装配收敛到判据可量化的形态：新增业务域 3 个手写文件、装配改动 0；装配行数不随域增长；业务代码不 import 装配层；新服务 30 分钟内可跑。这些不是口号，是带实测数据的验收判据，本文「为什么要用 Bald」一节给出数字与出处。

写作方式上有一条铁律：**本篇只讲概念与动机。**命令、配置键、API 签名等操作细节一律链接到[用户手册](../README.md)与设计文档，本篇不复述——双源必然漂移，细节以操作页为准。

## Bald 是什么

一句话定位：

> **bald 是一个用 Go 把服务装配「工程化」的框架：装配写成段驱动的 Provider 契约，业务域是一等公民，代码生成器用三道门守住生成物，高级机制面整体收进 mech。**

这句话里的每个名词在后文都有对应的小节，先把它当作整份文档的目录读。四个名词对应四个反复出现的结构：

- **段驱动装配**：任何能力接进装配面都是同一个动作——声明你消费哪个契约段。段在才构建，段缺失跳过，没人消费的段启动报错。
- **域一等公民**：一组业务功能（路由、gRPC service、对配置段的消费）声明成一个 `Domain` 值，自持接线，引擎按声明消费。新增域不碰装配文件。
- **代码生成三道门**：从一份声明文件生成整套可编译骨架；生成器不产出错误的配置键、不覆盖你的手写文件——三道门与三态文件归属把这个保证机械化。
- **mech 机制层**：效应账本、能力声明、期望态协调这些高级原语收进独立子包，业务默认看不见，需要时一行 import。

四个结构有一个共同取向：把装配知识从散落的手写代码收拢到可声明、可校验、可生成的形态。

在这个骨架之上，是服务绕不开的常见能力。它们的共同点：接入姿势统一（Provider + 契约段），不随能力数量膨胀——

- **配置**：四源优先级链（flag > env > 本地文件 > 契约源层 > 远程桥），配置键即 proto 契约字段路径，写错键名启动即报——[Bald 配置系统](../Bald%20配置系统.md)。
- **可观测**：日志 slog 默认零代码、五后端可换——[Bald 日志使用](../Bald%20日志使用.md)；指标埋点两套体系、三后端——[Bald 指标埋点使用](../Bald%20指标埋点使用.md)；metrics/trace 经 observability-otlp 桥接双通道输出。
- **审计**：log 后端内置零注册、store/stream 引依赖即用，自动埋点四类——[Bald 审计使用](../Bald%20审计使用.md)。
- **缓存与存储**：local/redis 可并存装配、8 方法缓存契约、loadable 回源组合器——[Bald 缓存使用](../Bald%20缓存使用.md)；泛型 store 经 store-gorm 段 Provider 接入。
- **传输面**：一个进程同时承载 HTTP 与 gRPC（可经 grpc-gateway 转码复用同一份 proto），五阶段优雅停机，注册中心可插拔（inmemory 内置；etcd/consul/nacos/kubernetes 直连 SDK）——起步见[快速入门](../quickstart/README.md)。
- **授权**：生成物产数据（默认策略行与别名表）、casbin 桥产行为——[Bald 授权使用](../Bald%20授权使用.md)。

## 为什么要用 Bald

传统装配方式在业务增长后会得三种工程病，bald 的诊断文档对每一种都给了实测数字。

**第一种病：装配随域线性膨胀。**每接一个新能力，注册表、访问器、装配函数要同步改多处。实测：每个业务域约 14 处装配引用；新增一个域要动 8 个文件（其中装配 4 个），全栈域 15–17 个文件（装配 6–7 个）。参考示例 bald-admin 的装配面 19 个文件、3,787 行，占非生成非测试代码的 20.7%——其中注释占非空行 40%，那不是啰嗦，是一个没有文档就读不懂的装配层。

**第二种病：业务被迫 import 框架内部。**13 张资源注册表逐行同构，接一个后端要经「New 注册表 + MustRegister + With* 注入」的固定三步；登录限流阈值、审计后端集合这些业务决策住在装配目录里；装配编排层默认可见 147 个导出符号——你只想写业务，却要先理解框架内部。

**第三种病：破坏面不可控。**「契约段 → 消费者」靠人工枚举表维系，配了不生效是静默的（`script` 段实证）；生成器固化示例的旧装配路径、还漏掉后来补的修复；配置键写错运行期静默吞掉。装配层的正确性没有闸门，全靠人盯。

bald 的解法是四件事的组合，各自对准一种病：

1. **声明式契约**：appspec.json 单一真相源 + bconf 契约段，声明面只有一处。
2. **段驱动 Provider**：Segments 声明契约段、同段末者胜、无消费者的顶层段启动即报（L3，fail-closed）。
3. **域声明值**：Domain 三槽位自持接线，gen domain 确定性重写域生成物。
4. **生成器三道门**：Gate1 生成期 schema、Gate2 生成期契约键回读、Gate3 运行期未知键报错。

对应关系大致是：域声明值对准第一种病（装配不随域增长），段驱动 Provider 对准第二种病（业务不再经注册表触碰框架内部），声明式契约与三道门对准第三种病（正确性由闸门保证，不再靠人盯）。

疗效用四条判据量化（批 3 收口），全部有实测：

| 判据 | 实测结果 |
|---|---|
| ① 新增业务域 3 个手写文件、装配改动 0 | proto + 域包 + 域声明共 3 个文件，gen domain 重写清单 |
| ② 装配不随域增长 | 装配面收敛为 Provider 声明 + 域清单（bald-admin：15 个 Provider 声明即全部装配）；装配面 3,787 → 1,514 行（−60%） |
| ③ 业务不 import 装配层 | 业务层对装配层零依赖；layering AST 守卫随生成物下发，违规编译期可见 |
| ④ 新服务 30 分钟可跑 | 端到端计时（生成 → tidy → 构建 → 就绪 → 优雅退出）：批 3 首点 76.8s，正式存档 v1 46.16s，判据口径 ≤ 1800s |

数字出处：[装配层评估](../../../devel/zh-CN/装配层评估.md)（§0 一句话结论、§3 归因、§11–§13 批次实施记录）与[性能基准](../../../devel/zh-CN/性能基准.md)（正式存档 v1）。配套证据：v0.24.0 与 v0.25.0 的四项对照基准分配剖面逐字节一致——这轮重构只动装配期，没有碰运行期路径。

## 关键特性

### 段驱动装配

**它是什么**：能力经统一的 Provider 契约接入装配面。Provider 声明自己消费哪些契约段路径（`Segments`），框架按段路由：段存在才构建，段缺失跳过（合法），同段精确路径**末者胜**（后声明的接管，框架默认后端由此可被顶替），契约里出现而无消费者的顶层段启动即报错（L3，fail-closed）。框架自有后端收敛成一个 `std.Standard()`，第三方后端各带自己的 Provider。段的清单不需要任何人手工维护——框架从契约的 protobuf 描述符反射枚举，多出来的段与少掉的段都会被看见。

**解决什么**：13 张注册表和两张手工段枚举表消失；「配了不生效」从静默 bug 变成启动报错；接一个新后端 = 实现一个 Provider，不再碰任何注册表样板。

**一句代码印象**——能力作为变参项直接进装配入口：

```go
appkit.MustServe(ctx, std.Standard(), storegorm.AppProvider(), loggerProvider{})
```

**深读**：[Provider 接入 - contract.AppProvider 与段 Provider](../Provider%20接入%20-%20contract.AppProvider%20与段%20Provider.md)。

### Domain 一等公民

**它是什么**：业务域包导出一个 `appkit.Domain` 值，三个槽位自持——Routes（HTTP 路由）、Services（gRPC 注册）、Wire（域自我接线：读自己的配置段、构造自己的能力、持有自己的端口）。引擎在 Wire 之后、server 构建之前消费域声明。域的生成物（域清单、逐域 gRPC 注册/REST 挂载/授权动作投影、授权别名表）由 `bald gen domain` 确定性重写。域导入清单必须由生成文件承载：Go 没有运行期包发现，这份清单总要有个家——从手写文件变成生成物，是「新增域装配改动 0」能成立的前提。域的授权动作投影也从 proto 的 service/method 派生，策略行不用手写。

**解决什么**：业务阈值与构造知识搬回域包，装配层不再出现业务配置段的知识；新增域 = 手写 proto、域包、域声明三个文件，装配改动 0（判据①）；装配面不随域数量增长（判据②）。

**一句代码印象**——main 的装配面里，域只是一个声明值：

```go
appkit.MustServe(ctx, std.Standard(), greetv1.Domain)
```

**深读**：[新增业务域 - Domain 与 gen domain](../新增业务域%20-%20Domain%20与%20gen%20domain.md)。

### 代码生成三道门

**它是什么**：appspec.json 是声明的单一真相源，`bald gen app` 据此生成整套可编译骨架（入口 main ≤ 25 行、装配知识为零）。落盘前依次过三道门：Gate1 生成期 schema（必填字段、组件 kind 白名单、域声明与 proto 匹配、meta.name 与 bootstrap.app.name 只声明一处）；Gate2 生成期契约（生成物配置键由 proto 字段描述符派生并回读复检，模板不写任何裸配置键）；Gate3 运行期契约（生成物启用 StrictContract，未知契约键启动即报）。文件按归属三态管理：生成物可重写、生成一次的不再动（`kept:` 跳过）、用户物生成器永不读写。

**解决什么**：重生成不踩手写代码；「声明了却没人消费」这类死声明由机器守卫拦下；升级换代时生成器与用户代码的边界清晰。门拦下你时报错逐条指明字段路径与非法值，不会让你对着一个模糊的失败猜。

**一句代码印象**——先声明、再生成：

```bash
bald gen app --spec appspec.json
```

**深读**：[用 bald CLI 起步新服务](../用%20bald%20CLI%20起步新服务.md)。

### mech 机制层

**它是什么**：高级机制面——Effect 账本（登记逆操作、逆序回放、启动失败回滚）、Provides/Requires 能力声明与组件生命周期、OnKeyChange key 订阅与 Reconcile 期望态协调、Registry[T] 运行期可逆挂载——全部收在 `pkg/appkit/mech` 子包。它们不是新增的发明，而是原本平铺在装配 API 里的既有原语——下沉只是为了把业务默认可见面让给日常路径。

**解决什么**：机制层默认不进业务包面。业务默认不需要它，用不到可以整页跳过；需要热插拔、可逆停机回放、key 级热更新时，一行 import 启用。

**一句代码印象**——业务代码默认零接触；启用即 import mech。

**深读**：[机制层 mech - Effect 与期望态](../机制层%20mech%20-%20Effect%20与期望态.md)。
