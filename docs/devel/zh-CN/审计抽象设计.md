# bald 审计抽象：零后端耦合的旁路审计 + 全局注入点

## 摘要

`pkg/audit` 定义 bald 的审计日志抽象——**零后端耦合、传输中立**：核心只定义 `AuditEvent` 结构与 `Auditor` 接口，不 import 任何具体存储/消息总线（落库 / 发 Kafka / 写 ES 外置为桥接子模块）。默认后端为 nop（静默），由用户在装配期经 `audit.SetAuditor` 注入具体实现，或在拦截器/中间件构造时传入 `Auditor` 实例（双路径，见下）。

**最重要的承诺：审计是旁路（side-effect），永远不阻断业务请求。** 即便 `Auditor` 实现报错，也只记日志不向上游返回错误。

## 设计

### 1. `AuditEvent`：扁平结构化审计记录

```go
type AuditEvent struct {
    Time     time.Time         // 事件发生时刻（UTC），缺省时由 Auditor 填充
    Subject  string            // 主体标识（来自 AuthClaims.Subject）；匿名时为空
    TenantID string            // 租户标识（多租户隔离审计用）
    Object   string            // 被审计的资源（经 P9 归一化，如 "secret" "auth"）
    Action   string            // 被审计的动作（经 P9 归一化，如 "get" "delete"）
    Result   Result            // allow / deny / error
    Error    string            // Result=error 时填错误描述
    Meta     map[string]any    // request_id / trace_id / 客户端 IP 等附加上下文
}
```

字段均为扁平 key-value，便于直接落结构化日志或转存列式存储。三元组 `(subject, object, action)` 复用 P9 的归一化原语，使 REST/gRPC 在同一份审计语义下被记录。

### 2. `Auditor` 接口

```go
type Auditor interface {
    Record(ctx context.Context, event AuditEvent)
}
```

**实现契约：`Record` 必须非阻塞或快速失败，绝不向上游抛错（旁路语义）；若自身写入失败应内部降级（如记一条 error 日志），不得影响业务链路。**

内置实现与全局注入：

```go
func NopAuditor() Auditor       // 静默默认（未注入时零副作用）
func SetAuditor(a Auditor)      // 全局注入（进程级默认后端）
func GetAuditor() Auditor       // 读全局（未注入返回 Nop）
```

### 3. 双路径接入

- **全局路径**：`audit.SetAuditor(impl)` 装配期注入 → 中间件内部 `audit.GetAuditor().Record(...)`。适合"全进程一个审计后端"的简单场景。
- **构造器注入路径**：`AuditMiddleware(recorder, ...)` / `AuditInterceptor(recorder, ...)` 直接持有 `Auditor` 实例。适合"多审计后端共存/显式注入"的场景（与 `middleware/bundle` 的依赖注入纪律一致；bundle 未注入 auditor 时显式接 `NopAuditor`，不吃全局兜底）。

### 4. 审计事件来源

| 触发点 | Object | Action | 说明 |
|---|---|---|---|
| 请求中间件（gin/grpc） | P9 归一化资源 | P9 归一化动作 | 拦截器把 `(subject, object, action, result)` 组装为事件 |
| 协调器 `runReconcilers` | `"reconciler"` | `"reconcile"` | R1-2 每次协调发一条（成功/失败都可观测） |
| A1 运行期重组 | `"component"` | `"mount"/"unmount"` | 管理面热插拔自动发（§6.2 自修改审计），Subject 取 ctx AuthClaims |

## 理由与取舍

**决策①：为什么核心零后端耦合？** 与 `pkg/log` 同纪律——任何纯 HTTP/CLI/测试场景 import `pkg/audit` 都不该背上存储/消息总线依赖。后端（落库/Kafka/ES）由业务按需接入。

**决策②：为什么 `SetAuditor`/`GetAuditor` 全局点保留？** 兼容中间件与业务代码的"无显式注入"路径，且 nop 兜底保证零配置可跑。但框架纪律推荐构造器注入（见 `middleware/bundle`）——全局点是便利，不是唯一方式。

**决策③：为什么审计必须旁路？** 审计是观察系统的副产物，写失败（队列满/DB 挂）若阻断业务请求，会把"观察成本"放大为"可用性事故"。所有调用点（中间件、协调器、挂载）都套用 `recover` 兜底——Auditor panic 仅记日志。

## 兼容性

纯增量，无破坏：新增 `pkg/audit` 包与全局注入点；中间件新增 `Audit*` 构造器，既有中间件不受影响。
