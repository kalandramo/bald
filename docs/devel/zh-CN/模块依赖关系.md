# 模块依赖关系（2026-09-05）

> 本文记录 bald 各顶层模块（独立 Go module）之间的依赖关系、运行期数据流与设计原则。
> 依据为各 `go.mod` 的 `require`/`replace` 声明实证，非主观归纳。
> API 签名速查见《框架契约总览.md》，配置系统细节见《Bald 配置系统设计.md》。

---

## 1. 模块形态总览

| 模块 | module 路径 | 形态 | 内部依赖（go.mod 实证） |
|---|---|---|---|
| **berrors** | `github.com/kalandramo/bald/berrors` | 独立契约 | 无内部依赖（仅 grpc/genproto） |
| **bconf** | `github.com/kalandramo/bald/bconf` | 独立契约（proto 生成） | 无内部依赖（仅 pflag/protobuf） |
| **log** | `github.com/kalandramo/bald/log` | 契约 + 子包实现（`log/slog`） | 无内部依赖（仅 pflag/lumberjack） |
| **bconfig** | `github.com/kalandramo/bald/bconfig` | 源抽象 + provider 子包 | 无内部依赖、零契约依赖 |
| **transport** | `github.com/kalandramo/bald/transport` | 契约 + 4 子包实现（grpc/http/web/gateway） | `bconf`、`berrors` |
| **bootstrap** | `github.com/kalandramo/bald/bootstrap` | 装配层（含 `config/` Store 内核） | `bconf`、`bconfig`、`log`、`transport` |
| **主模块** | `github.com/kalandramo/bald` | 核心实现包（appkit/middleware/store/web/authn/…） | `bconf`、`berrors`、`bootstrap`、`log`、`transport`（bconfig 为间接传递依赖） |

说明：`pkg/appkit` 无独立 go.mod，归属主模块；appkit 直接 import `bootstrap/config`（Store 内核），即主模块经 bootstrap 间接获得 Store 能力——与「bootstrap 是装配+配置装载唯一 module」的定位一致。

## 2. 依赖方向图（自底向上）

```
第0层  berrors ──── 错误契约
       bconf   ──── 配置契约（bootstrapv1，proto 单一真相源）
       log     ──── 日志契约（Logger/全局表/nop；slog 后端在子包）
       bconfig ──── 配置源抽象（Reader/ValueWatcher/Decoder/FallbackReader
                    + file/env/etcd/consul/nacos/apollo/k8s/vault/http/fs）
              │
第1层  transport（→ bconf + berrors）
              │
第2层  bootstrap（→ bconf + bconfig + log + transport；不依赖 berrors）
              │
第3层  主模块 bald：pkg/appkit、middleware、store、web
      （→ bconf + berrors + bootstrap + log + transport）
```

要点：

- **底层四模块（berrors/bconf/log/bconfig）互不依赖**，是纯叶子契约层。
- **transport 只向上引用契约**（bconf 读 server 地址契约、berrors 做错误映射），不碰 bconfig/log。
- **bootstrap 是汇聚点**：唯一同时认识「契约（bconf）+ 源（bconfig）+ 组件契约（log/transport）」的模块，但不依赖 berrors（错误处理不在装配职责内）。
- **appkit 位于最顶层**，通过主模块消费 bootstrap 产出的 Logger/Server/Layer。

## 3. 运行期数据流（一次启动）

```
main()
  ├─ bconf.NewBootstrap()             # ① 契约默认值（bootstrapv1）
  ├─ bootstrap.NewRegistry()
  │    .MustRegister("file",...)      # ② 注册 Provider 工厂（注册序=层优先级）
  │    .Build(ctx, cfg)
  │      → bconfig/{file,etcd,...}    #    ③ 建各配置源（bconfig 抽象的实现者）
  │      → []config.Layer             #    ④ 产出层列表 → config.Store（深合并+热更新）
  ├─ bconf.UnmarshalMap(settings,cfg) # ⑤ settings 回填进契约（指针直通）
  ├─ bootstrap.BuildLogger(cfg)       # ⑥ 契约 → log.Logger → log.SetLogger
  ├─ bootstrap 建 http/grpc server    # ⑦ 契约 → transport.Server 实现
  └─ appkit.Run()                     # ⑧ 编排多 Server：errgroup 启停/级联停止/
                                      #    Settings()/Config() 供业务读配置
```

## 4. 设计原则印证

1. **契约/实现分离**：`log` vs `log/slog`、`transport` vs 4 子包、`bconf` 契约 vs `bootstrap` 装配——同一模式（顶层契约 + 子包/旁路实现）。
2. **依赖倒置**：`bconfig` provider 不认识契约；契约字段→options 的映射全部收在 `bootstrap` 的 Provider 层（`bconfig` 保持零契约依赖）。
3. **两条正交轴**：`berrors/transport` 是「请求处理轴」，`bconf/bconfig/bootstrap/log` 是「配置/可观察轴」，仅在 appkit 汇合。
