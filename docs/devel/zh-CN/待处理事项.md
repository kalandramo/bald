### #2 🔴 `noopContext` 与接口注释自相矛盾

**影响**：匿名/未授权上下文的 `IsPlatformContext()` 语义与接口定义不符——哨兵值语义重载**未真正消除，只是从 `0` 转移到了 `""`**。

**证据**：

| 位置 | 内容 |
|---|---|
| `bald-crud/viewer/context.go:37` | 接口注释定义：`IsPlatformContext` = 「无租户上下文，`TenantID == ""`」 |
| `bald-crud/viewer/noop.go:7` | `func (noopContext) TenantID() string { return "" }` |
| `bald-crud/viewer/noop.go:14` | `func (noopContext) IsPlatformContext() bool { return false }` ← 与上行矛盾 |

**为何重要**：`EnforceTenant`（`bald-crud/viewer/enforce.go:37`）用 `IsPlatformContext() || IsSystemContext()` 判定 pass-through。noop 上下文既不被认作平台视图也不被认作系统视图，故**落入「租户业务视图」分支**——但它没有任何租户身份。这与「匿名请求不应看到任何行」的 fail-closed 预期不符。

**状态**：🟡 待定。涉及 `noopContext` 的语义决策（匿名到底算平台视图还是第三种态），属代码设计变更，不在文档重整范围内。**需设计决策后修**。

### #3b ⚪ 缓存 key 用 `%d` 格式化 `TenantID()`（已修，2026-09-24）

**影响**：缓存 key 生成错误——`fmt.Sprintf("t:%d:...", vc.TenantID())` 对 string 输出 `%!d(string=t-1)`，导致 key 内容畸形。

**位置**（修复前，共 5 处）：

| 模块 | 位置 |
|---|---|
| gorm | `bald-crud/gorm/repository_cache.go:79`、`:94` |
| entgo | `bald-crud/entgo/repository_cache.go:102`、`:123`、`:195` |

**发现途径**：修复 #1 的测试桩后跑 `go test`，编译器（`go vet` 检查）报 `fmt.Sprintf format %d has arg vc.TenantID() of wrong type string`。

**根因**：与 #1 同源——`tenant_id` 类型统一时只改了类型声明，未扫完所有**消费点**。`%d` 是格式化字符串里的隐性类型断言，类型改了它不会立刻报错（`go build` 通过），只有 `go vet`（`go test` 会跑）才暴露。

**修复**：`%d` → `%s`（5 处）。

**教训**：类型统一必须扫「类型声明 + 所有格式化字符串 + 所有比较字面量」三类消费点。仅改声明会留下静默缺陷。

### #3c 🔴 `audit` 模块未发版，entgo 依赖旧版导致编译失败

**影响**：`bald-crud/entgo` 编译失败——`entgo/mixin/audit.go:71` 把 `vc.TenantID()`（string）赋给 `audit.Entry.TenantID`（uint64）：

```
mixin\audit.go:71:16: cannot use vc.TenantID() (value of type string) as uint64 value in struct literal
```

**根因（发版轨问题，非代码遗漏）**：

| 事实 | 证据 |
|---|---|
| 本地 `bald-crud/audit/entry.go:32` 已是 `TenantID string` | 随类型统一提交 `dc1c05e`（2026-09-24） |
| 但 `audit` 模块**只有 09-11 的旧 tag** | `git tag \| grep audit/` → 仅 `audit/v0.1.0`，指向 `403f007`（2026-09-11） |
| entgo 依赖 `bald-crud/audit v0.1.0` | `bald-crud/entgo/go.mod:9` |

故 entgo 编译时拿到的是 13 天前的 uint64 版 Entry，与本地 viewer（v0.2.0，string）不匹配。

**修复路径**（按发版轨顺序，不可倒置）：

1. 给 `audit` 打新 tag（`audit/v0.2.0`），含 `dc1c05e` 的类型统一；
2. 升级 `bald-crud/entgo/go.mod` 的 audit 依赖至新 tag；
3. 重跑 entgo 测试确认 GREEN。

**状态**：🔴 待发版（阻塞 entgo 验证）。需在 `bald-crud` 仓提交并发 tag 后完成。

**教训**：类型统一跨模块时，「本地源码已改」不等于「下游能看到」——模块化仓库必须发 tag 才能传播。这与 `viewer/v0.2.0` 必须先于各 ORM 模块升级是同一条纪律。

### #9 🔵 Token 是偏移游标，不是真游标

`bald/pkg/store/paging.go:7-9` 文件头自承：token 是 base64 编码的**十进制偏移量**（兼容裸十进制），非基于主键/排序键的真游标。深度翻页时后端 `OFFSET` 成本仍随页数增长。

升级为 last-key 游标的路径已在该注释中预留，业务调用方无感知。

**状态**：🔵 已知取舍。

---

### #10 🔵 字符串型数字列走字典序

`cmpNum`（`bald/pkg/store/inmemory/inmemory.go:359`）对无法 `ParseFloat` 的值按**字典序**比较，故 `"10" < "9"`。

仅影响 inmemory 后端对「字符串存数字」的排序/范围比较；gorm 后端由数据库类型系统决定。

**状态**：🔵 已知取舍（inmemory 定位是测试/原型，非生产）。

---

### #11 🔵 `rows == 0` 不能作为「记录不存在」的判据

`Update` / `Delete` 返回的是**受影响（被改变）行数**而非匹配行数，且**跨后端不一致**：MySQL 默认（未开 `CLIENT_FOUND_ROWS`）对「UPDATE 到与现有值相同」返回 0（行确实存在），SQLite 返回 1。

故上层写 `if rows == 0 { return ErrNotFound }` 在 MySQL 下会把「幂等更新到相同值」误判为不存在。需要精确存在性判断时应显式 `Get`。

**状态**：🔵 已知约束（`bald/pkg/store/store.go` 的 `Update` 注释已载明正误对照）。

---

### #12 🔵 `inmemory.Provider.Migrate` 与 `memQuery.Migrate` 重复定义

两处均为 `return nil` 空实现（`bald/pkg/store/inmemory/inmemory.go:52` 与 `:55`），Provider 层未委托给 query 层。

**判定**：**保留**。它与 gorm 侧 `Provider.Migrate`（`bald/contrib/store-gorm/gorm.go:61`，有真实消费者）构成 **Provider 层跨后端对称 API**——业务按 `provider.Migrate()` 写代码后可在内存/GORM 后端间无感切换。删除它会使下游切内存后端编译失败。

**状态**：⚪ 已判定保留（非缺陷）。

## 三、`pkg/crudbridge` 约束

### #13 🔵 `viewer.Context` 中 `UserID` / `OrgUnitID` 仍为 `uint64`

`tenant_id` 已统一为 `string`，但同接口的 `UserID()`（`bald-crud/viewer/context.go:9`）与 `OrgUnitID()`（`:20`）仍是 `uint64`。`bald/pkg/crudbridge/crudbridge.go` 中 `UserIDValue` / `OrgUnitIDValue` / `DataScope.TargetIDs` 亦然。

桥接层为此保留 `strconv.FormatUint` 转换（`bald/pkg/crudbridge/data_scope.go:39/53/59`）。

**状态**：🔵 约束。当前 `user_id` 来源（JWT claims）为数字字符串，转换无有损路径——**与 `tenant_id` 的情况不同**（后者存在非数字租户 ID，故必须统一）。若将来 `user_id` 也出现非数字形态，需同样处理。

---

### #14 🔵 桥接层与 `authn` 的依赖方向

`crudbridge.go` 零 `authn` import（避免循环依赖），故 `ViewerFromIdentity` 需 5 个平铺参数而非一个 claims 对象。但 `data_scope.go` **import 了 `pkg/authn`**（`RegisterDataScope` 回调签名带 `*authn.AuthClaims`）。

依赖方向单向（crudbridge → authn），不构成循环——循环只在 authn 反向 import crudbridge 时成立。

**状态**：🔵 约束（写入文档的「设计哲学」节）。
