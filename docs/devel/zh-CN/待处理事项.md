### #2 ⚪ 平台视图由空租户**隐式推断**（**已修，2026-09-25，方案 D**）

**影响**：`IsPlatformContext()` 的判据是 `TenantID == ""` 的**隐式推断**——空租户同时表示「匿名/未认证」与「平台视图」两种**相反**语义，靠推断会 fail-open。

**证据（2026-09-25 探针实测）**：同一 `TenantID == ""` 的两个身份，经 `EnforceTenant` 决策**相反**：

```
A 空 SimpleViewer : Enforce=false TenantID=""   ← 被推断为平台视图 → pass-through（跨租户可见，fail-open）
B noopContext     : Enforce=true  TenantID=""   ← 落入租户分支 → 注入 tenant_id=''
```

**⚠️ 纠正原记录的风险方向**：本条原写「noop 落入租户分支，与 fail-closed 预期不符」，暗示 noop 是越权方。实测恰好相反——

- `noopContext`（`IsPlatformContext()=false`）落租户分支 → 注入 `tenant_id = ''` → 查不到任何行，效果**近似 fail-closed**（安全）；
- `SimpleViewer{TenantID:""}`（`IsPlatformContext()=true`）→ pass-through → **看全部租户**，这才是真正的 **fail-open**。

真正的问题是**判据本身**（用空租户推断平台视图），不是 noop 返回 false。原记录的「或让 noop 返回 false」也是笔误——noop 本就是 false。

**为何重要**：`bald` 侧早已用**显式** `contextx.WithPlatform` / `PlatformFromContext`（「必须显式声明，绝不基于空租户推断」），而 `bald-crud/viewer` 侧仍在隐式推断。两套语义在同一 ctx 内共存，且认证中间件注入 `SimpleViewer` 时**不传** `claims.Platform`（平台标记被丢弃）。

**修复（方案 D，2026-09-25）**：

1. `viewer.Context.IsPlatformContext()` 语义收紧为「**必须显式声明**」——不再由 `TenantID` 推断；
2. `EnforceTenant` 增「身份不完整」分支：非平台、非系统、`TenantID == ""` → **fail-closed**（`ErrMissingViewer`），不再注入 `tenant_id = ''`；
3. `crudbridge.SimpleViewer` 增显式 `Platform` 字段；`ViewerFromIdentity` / `InjectViewerFromIdentity` 增 `platform` 参数，认证中间件（gin/grpc）透传 `claims.Platform`；
4. **同一不变量收敛**：`entgo/rule/tenant.go`（`TenantPrivacy.EvalQuery`/`EvalMutation`）与 `entgo/interceptor/tenant.go` 此前**内联** `IsPlatformContext()||IsSystemContext()`，现全部委托 `EnforceTenant`——单一闸门，结构上消除「修一处未扫全」。

**验证**：
- `bald-crud/viewer`：`go test ./...` 全绿；探针反证——把空租户守卫改回旧语义 → `TestEnforceTenant_NoopContextFailsClosed` / `TestEnforceTenant_EmptyTenantFailsClosed` **变红**，恢复后转绿；
- `bald-crud/gorm`：端到端（真实 sqlite + 真实 gorm callback）`TestTenantEnforce_EmptyTenantFailsClosed` 通过；
- `bald-crud/entgo`：9 包全 ok；
- `bald`（含 crudbridge + middleware）：主模块全量 exit 0，18 包 ok。

**发布轨（2026-09-25 已发）**：`viewer/v0.3.0` 已打并推送；5 个 ORM 模块（gorm/entgo/mongodb/doris/clickhouse）升依赖并各发 `v0.3.0`；`bald` 升 viewer 依赖并发 `v0.14.0`。均在零 replace 下验证（build exit 0 + 测试全绿）。本地联调用 `go mod edit -replace`，勿提交。

**状态**：⚪ 已修 + 已发版（`bald-crud` viewer/entgo/gorm + `bald` crudbridge/middleware；viewer/v0.3.0、5×ORM v0.3.0、bald v0.14.0）。

### #3b ⚪ 缓存 key 用 `%d` 格式化 `TenantID()`（已修，2026-09-24）

**影响**：缓存 key 生成错误——`fmt.Sprintf("t:%d:...", vc.TenantID())` 对 string 输出 `%!d(string=t-1)`，导致 key 内容畸形。

**位置**（修复前，共 5 处）：

| 模块 | 位置 |
|---|---|
| gorm | `bald-crud/gorm/repository_cache.go:79`、`:94` |
| entgo | `bald-crud/entgo/repository_cache.go:102`、`:123`、`:195` |

**发现途径**：修复 #1 的测试桩后跑 `go test`，编译器（`go vet` 检查）报 `fmt.Sprintf format %d has arg vc.TenantID() of wrong type string`。

**根因**：与 #1 同源——`tenant_id` 类型统一时只改了类型声明，未扫完所有**消费点**。`%d` 是格式化字符串里的隐性类型断言，类型改了它不会立刻报错（`go build` 通过），只有 `go vet`（`go test` 会跑）才暴露。

**修复**：`%d` → `%s`（5 处）。

**教训**：类型统一必须扫「类型声明 + 所有格式化字符串 + 所有比较字面量」三类消费点。仅改声明会留下静默缺陷。

func CheckColumn(table, column string) error { return checkColumn(table, column) }

**为何委托而非复制白名单**：白名单注册表只有一份真相源。若重新 import

**为何放 `validate.go` 而非 `ent.go`**：后者是 ent 生成物（DO NOT EDIT），

**返回值契约（调用方依赖）**：
- 表未注册 → 错误含 `"unknown table"` → 调用方 **fail-open**（保留字段）
- 表已注册但列不存在 → 错误含 `"unknown column"` → 调用方 **拒绝**该字段

产生，**不由本仓控制**——故测试显式钉住（上游若改文本，fail-open 会静默变成
fail-closed，未注册表的合法字段被全部丢弃）。

### #3g ⚪ `entgo` field/sorting 的列白名单拒绝路径无测试覆盖（**已修，2026-09-24**）

**发现方式**：探针打靶——把 `ent.CheckColumn` 改为恒 `return nil`（放行一切，
即完全关闭列白名单），跑三包既有测试：

| 包 | 结果 |
|---|---|
| `filter` | ✅ `TestStructuredFilter_FieldAllowlist` FAIL（抓到了） |
| `field` | ❌ ok（**未抓到**） |
| `sorting` | ❌ ok（**未抓到**） |

**盲区成因**：既有 hostile 用例的载荷都含 SQL 元字符（`id) OR (1=1 --`、
`(select version())` 等），被 `IsValidFieldPath` / `IsValidFieldName` **硬性
标识符校验**拦在列白名单**之前**。故它们测的是「元字符被拒」，**不是**
「合法标识符但不在白名单的列被拒」——后者才是 `CheckColumn` 的职责。
`columnAllowed` 的拒绝分支（`return false`）在这两包中**从未被执行过**。

### #11 🔵 `rows == 0` 不能作为「记录不存在」的判据

`Update` / `Delete` 返回的是**受影响（被改变）行数**而非匹配行数，且**跨后端不一致**：MySQL 默认（未开 `CLIENT_FOUND_ROWS`）对「UPDATE 到与现有值相同」返回 0（行确实存在），SQLite 返回 1。

故上层写 `if rows == 0 { return ErrNotFound }` 在 MySQL 下会把「幂等更新到相同值」误判为不存在。需要精确存在性判断时应显式 `Get`。

**状态**：🔵 已知约束（`bald/pkg/store/store.go` 的 `Update` 注释已载明正误对照）。

### #18 ⚪ `EnforceOnScopedInstanceAny` 对 typed-nil 指针 panic（**已修，2026-09-24**）

**影响**：批量写入路径遇到 nil 指针元素会**直接 panic**（不是返回 error），
使整个请求崩溃而非被 fail-closed 拒绝。

**根因**：`instance == nil` 只对**无类型** nil 成立。经 `any` 装箱的 typed-nil
（如 `(*T)(nil)`）其接口值非 nil，该判定拦不住，代码继续走到
`sm.SetTenantID(...)` 而空指针解引用。

**关键不对称**：同文件泛型版 `EnforceOnScopedInstance[T]`（`enforce.go:65`）
有 `if instance == nil { return nil }`，而 any 版（`:89`）虽写了同样一行，
却**对 typed-nil 无效**——两者注释却都称「语义完全一致」。同一不变量的两个
实现只对齐了一个，与 #3b/#3d 同族（「修一处未扫全」）。

**真实触发路径（非理论）**：`bald-crud/doris/tenant_enforce.go:105`
的批量插入对每个 struct 元素调 `viewer.EnforceOnScopedInstanceAny(ctx, item.Addr().Interface())`
——slice 中的 nil 指针元素经 `Addr().Interface()` 装箱后即 typed-nil。

**证据**（本轮实测）：

```
# 修复前（反射守卫改为 if false 复现）
--- FAIL: TestEnforceOnScopedInstanceAny_TypedNilPointer
    any 版对 typed-nil 指针 panic 了：runtime error: invalid memory address or nil pointer dereference
```

**修复**（`bald-crud@edcebbd`）：在 `instance == nil` 之后补反射判 nil——

```go
if rv := reflect.ValueOf(instance); rv.Kind() == reflect.Ptr && rv.IsNil() {
    return nil
}
```

与泛型版语义对齐（生产改动 8 行，纯守卫，不改既有行为）。
