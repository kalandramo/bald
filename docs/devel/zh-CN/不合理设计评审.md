## 一、高危（安全 / 正确性）

### D1 `MustTLSConfig` 失败降级为 `InsecureSkipVerify`
**[高] `pkg/conf/bindflags.go:348-356`**

```go
func MustTLSConfig(...) *tls.Config {
    if tlsConfig, err := buildTLSConfig(...); err != nil {
        // 注意：失败时降级为「跳过证书校验」而不是报错。
        return &tls.Config{InsecureSkipVerify: true}
    }
    return tlsConfig
}
```

`Must` 前缀按惯例是「出错即 panic」，但此处反而**静默关闭证书校验**。一旦证书路径配错/缺失，框架对外暴露的 TLS 端点等于明文中间人，且调用方完全无感知。

- 影响：安全反模式，运维误配即被降级为不安全链路。
- 建议：`Must` 失败应 `panic`（或返回 error 交由调用方 fail-fast）；绝不在 `_ = buildTLSConfig()` 出错时回退到 `InsecureSkipVerify`。如确需「开发期跳过校验」，用显式开关 `WithInsecureSkipVerify()` 而非默认行为。

### D2 日志脱敏 `FilterKey` 被 `With` / `WithAttrs` 绕过
**[高] `pkg/log/filter.go`（`WithAttrs` / `WithGroup` 未对传入 attrs 过滤）**

`filterHandler.WithAttrs(attrs)` 把属性直接转交 `h.next.WithAttrs(attrs)`，未过 `filter`：

```go
func (h *filterHandler) WithAttrs(attrs []slog.Attr) slog.Handler {
    return &filterHandler{next: h.next.WithAttrs(attrs), filter: h.filter} // attrs 不过滤
}
```

slog 中 `WithAttrs` 的属性在 `Handle` 阶段由内层 `withAttrs` 合并进 record，但本层 `filterHandler` 在 `WithAttrs` 时已把属性下沉到 `next`，导致这些属性**绕过了最外层 filter 的 `Handle` 过滤**（`FilterKey("password")` 对 `slog.With("password", x)` / `handler.WithAttrs(...)` 携带的字段无效）。

- 影响：脱敏是合规红线，旁路即等于明文落盘。与「脱敏是安全特性」的定位直接矛盾。
- 建议：在 `WithAttrs` 内对传入 attrs 先做 `a := h.filter(a)` 再 `h.next.WithAttrs(a)`（或统一在 `Handle` 阶段对 `r.Attrs` 全量过滤，包括来自 `WithAttrs` 的属性）。补充针对 `With("password",...)` 的单元测试。

### D3 认证失败（401/403）不产生审计事件
**[高] `pkg/middleware/gin/authn.go:29-34,46` + bundle 链序；`pkg/audit/audit.go:28-29`**

gin 认证中间件在失败时 `c.AbortWithStatusJSON(...)` 后 `return`，**不调用 `c.Next()`**：

```go
// gin/authn.go
token, err := bearerFromHeader(...)
if err != nil {
    c.AbortWithStatusJSON(...); return   // 直接返回，后续中间件（含 audit）被跳过
}
```

bundle 两条链中 `Audit` 都注册在 `Authn` 之后（gin：`Recovery→RequestID→Logging→CORS→Secure→Authn→Audit→Authz`；gRPC：`Error→RequestID→Observability→Authn→Audit→Authz`）。因此认证失败（缺 token / 校验失败 / 过期）时 `Audit` 根本不执行——gin 侧 `Audit` 中间件不被调用，依赖 `c.Writer.Status()==401/403` 派生 deny 的逻辑永远触不到；gRPC 侧 `AuthnInterceptor` 直接返回 Unauthenticated，内侧的 Audit 拦截器同样被跳过（**双传输同病**）。

而 `pkg/audit/audit.go` 文档明确写：`ResultError` = 「**含认证失败**/内部错误」——该语义在 authn abort 路径永远不会被触发。需精确化边界：示例中 `/v1/login` 这类**未挂 Authn 的路由**，其登录失败（业务层 401）仍会被全局链上的 Audit 记录；缺口是**受保护路由的 Authn abort 路径（401）与 gRPC Unauthenticated**——即 token 缺失/过期/无效的访问在两条传输上都无审计痕迹。

- 影响：合规审计缺口——登录爆破、越权试探、token 失效重试全部无痕迹；文档与实现矛盾。
- 建议：审计应下沉为**最外层**（在 Authn 之前注册，或 Authn 失败分支显式发一条 `ResultError` 审计事件），保证 401/403 必留痕。

### D4 审计后端多路径 → 分裂（split-brain sink）
**[高] `pkg/middleware/bundle/bundle.go`（`ginAudit`/`grpcAudit`）+ `pkg/appkit/mount.go:176` + `pkg/middleware/gin|grpc/audit.go`**

存在**三条**审计后端解析路径，优先级不统一：

1. `bundle` 的 gin/grpc audit：仅用 `b.auditor`，**为 nil 时落到 `NopAuditor`，不回退全局**。
2. `pkg/appkit/mount.go:176`：`audit.GetAuditor()`（全局）记录组件挂载/卸载审计。
3. 直接调用 `gin/grpc.AuditMiddleware`（不经 bundle）默认 `audit.GetAuditor()`（全局）。

后果：用 `bundle.Audit(a)` 注入审计器后，请求级审计走 `a`，但 `appkit.MountComponent` 的组件重组审计仍走全局（可能为 nop）；且 `appkit` 没有 `Auditor` Option，无法注入。`pkg/audit/global.go` 的 `SetAuditor/GetAuditor` 与 bundle 的注入互不连通。

- 影响：同一进程两条审计出口，部分事件静默丢弃或写错后端，排查时极难发现。
- 建议：统一**单一解析顺序**（注入优先 → 全局 → nop），三条路径复用同一个 `resolveAuditor()`；`appkit` 增加 `Auditor` Option 以消费注入实例。

### D5 gRPC 链缺显式 Recovery，且 `metrics.Record` 未被旁路 recover 覆盖
**[中/高] `pkg/middleware/bundle/bundle.go`（`GRPCInterceptors`/`GRPCChain`）+ `pkg/middleware/grpc/audit.go:116`**

- gin 链首道是 `ginmw.Recovery()`，gRPC 链**没有对应的 recovery 拦截器**（不对称）。
- `grpcAudit` 中 `rec.Record(...)`（metrics）写在 `recordSafely(...)` **之外**：

```go
// grpc/audit.go
recordSafely(ctx, func() { auditor.Record(ctx, event) }) // 仅此被 recover
if b.metrics != nil { b.metrics.Record(ctx, metrics...) } // 未被 recover，panic 逃逸
```

- 影响：与文档「旁路不阻断」承诺矛盾；metrics recorder panic 直接中断请求，且 gRPC 无兜底恢复。
- 建议：把 `metrics.Record` 也纳入 `recover` 保护（与 auditor 同级）；gRPC 链按需加 `otel/grpc` 或 `grpc.RecoveryInterceptor`（注意与「ErrorInterceptor 最外层」约定共存）。

## 二、中危（API / 一致性）

### D6 `AuditMiddleware` 首参 `audit.Auditor` 被丢弃（死参）
**[中] `pkg/middleware/gin/audit.go:46`、`pkg/middleware/grpc/audit.go:55`**

```go
func AuditMiddleware(_ audit.Auditor, opts ...Option) gin.HandlerFunc { ... }
```

首参 `_` 在签名里但**从未使用**，实际生效的只有 `AuditWithAuditor` option。文档示例与调用方按直觉传入位置审计器会**静默无效**，误导性强。

- 建议：删除首参，统一用 `AuditWithAuditor`；或真正消费首参（无 option 时回退首参）。

### D7 P9 归一化是 opt-in，默认仍是双命名空间 RBAC
**[中] `pkg/middleware/bundle/bundle.go:85`（`Normalized()` 默认 `false`）**

```go
func (b *Bundle) Normalized() bool { return b.normalized } // 默认 false
// grpcAuthz / grpcAudit 仅在 b.normalized 时做归一化
```

P9 的核心收益是「根治 REST/gRPC 双命名空间 RBAC」，但该行为必须显式 `bundle.Normalized()` 才生效，漏配即回到旧问题。这与「归一化是默认正确行为」的预期相悖。

- 建议：默认开启归一化（向后兼容可由 opt-out 控制），或启动期检测到未归一化时打印告警。

### D8 中间件构造期快照全局 Logger，运行期 `SetLogger` 无效
**[中] `pkg/middleware/gin/observability.go:139`、`pkg/middleware/grpc/observability.go:135`（audit 同）**

```go
config := &ObservabilityOptions{ ..., Logger: log.GetLogger() } // 构造期固化
```

中间件在构造时捕获 `log.GetLogger()`，之后全局 logger 被替换也不影响已构造的中间件。示例 `main.go` 的时间线直接暴露该问题：

- `:63` `setLogger(logOpts)`（带 `FilterKey("password")`）
- `:128` `ginBundle.Gin()` 构造 observability/audit 中间件 → 快照了 `:63` 的 logger
- `:262`（BeforeStart）`setLogger(baldconf.LogOptions(...))` 重建全局 logger

结果：**请求级日志**用 `:63` 的旧实例，**app 级日志**（`appkit`、组件审计）用 `:262` 的新实例，两者分裂；且脱敏 FilterKey 行为在两实例间可能不一致。

- 影响：运行期换 logger（不同 level/format/transport）只影响部分日志；脱敏可能在请求链路上失效。
- 建议：中间件每次请求惰性 `log.GetLogger()` 解析，或要求 `WithLogger` 在构造前显式注入同一实例（并在示例里先 `setLogger` 完再构建 bundle）。

### D9 HTTP 错误响应体形状不统一
**[中] `pkg/web/response.go:14-22` vs `pkg/middleware/gin/authn.go:29`**

- `pkg/web.WriteResponse`/`ErrorResponse` → `{ "error": { "code", "message" } }`
- gin `AuthnMiddleware` → `gin.H{ "reason", "message" }`

认证失败是最高频的错误响应，却用了与全站 `web` 包不同的 JSON 形状，客户端/网关按统一契约解析会漏字段。

- 建议：`AuthnMiddleware` 复用一个统一错误体构造器（如 `web.ErrorResponse` 等价的 helper），保证全链路形状一致。

---

### D10 `ResolveTLS` 提供 CA 即强制 mTLS（要求客户端证书）
**[中] `pkg/conf/bindflags.go:303-316`**

```go
if sc.CA != "" {
    c.ClientAuth = tls.RequireAndVerifyClientCert // 双向 mTLS
}
```

仅想校验证书签发链（服务端单向 TLS 校验对端链）却会被强制要求客户端证书——典型部署反模式（大多数对外服务不需要客户端证书）。

- 建议：用独立开关区分 `RootCA`（服务端验证对端链）与 `ClientCA`（mTLS 强制客户端证书），不要由 CA 非空隐式触发 mTLS。

> **方法**：四路并行源码走读 + 关键条目二次人工取证（本文所有行号经复核）。编号独立于首轮 D/E 系列：TR = transport/contrib，CR = 核心根包，CD = bald-crud，UT = bald-utils/go-bald-admin。
> **总结论**：呈现清晰的**双层质量断层**——核心契约层（bconf/bootstrap/appkit/中间件/错误模型）精工细作、文档纪律好；外围实现层（transport 后端、bald-crud driver、bald-utils）大量移植未消化，集中了注入面、竞态、fail-open、逐行复制与依赖倒挂。建议优先处理高危 10 条（下表 P0）。

### 8.1 transport / contrib（TR 系列）

#### TR1 [高] kafka 与 rocketmq 的 `logger.go` 100% 逐行复制且 `LogFatal` 误用 `Error` 实现
**[bald/transport/kafka/logger.go:1-60 vs rocketmq/logger.go:1-60]**

两份 60 行文件仅 `logKey` 常量值不同；且两边的 `LogFatal` 都用 `Error` 级实现：

```go
func LogFatal(args ...any) { LogError(args...) } // 调用方以为会 Fatal 退出，实际只打 Error
```

连带 `server.go` 约 200 行近似复制（Server struct、Start/Stop、订阅注册、泛型包装），且复制后已各自漂移：kafka 的 `RegisterSubscriber` 多一个 `disableAutoAck bool` 参数（kafka/server.go:118 vs rocketmq/server.go:116）。已有 `transport/subscribe` 共享包却未承载真正的公共逻辑。
- 影响：改一处必漏一处；LogFatal 语义误导。
- 建议：Server 生命周期/订阅注册/LogXxx 模板下沉 `transport/subscribe`（`NewMQServer(broker, kind)` 参数化），两包只留差异项。

#### TR2 [高] tcp 与 webrtc 的 SessionManager 跨模块复制 + `rangeSessions` 同名 API 语义相反
**[bald/transport/tcp/session_manager.go:80-91 vs webrtc/session_manager.go:73-80]**

```go
// tcp 版：注释说 "returns true, the iteration is stopped"，实现却忽略 fn 返回值
func (sm *SessionManager) rangeSessions(fn func(SessionID, *Session) bool) {
    ...
    fn(session.SessionID(), session) // 返回值被丢弃
}
// webrtc 版：尊重 fn 返回值提前 return
```

调用侧互相矛盾：tcp `BroadcastRawData` 回调 `return false` 期望"继续"，webrtc `Broadcast` 回调 `return true` 期望"继续"——两边回调互换即出错。约 90 行 `sync.Map`+observer+session 泵模式整体复制。
- 影响：复制后单边漂移的直接实证；维护陷阱。
- 建议：抽共享 session 基座，rangeSessions 语义与文档对齐后二选一。

#### TR3 [中] webrtc Session 三个死字段只写不读（跨 goroutine 无锁写）
**[bald/transport/webrtc/session.go:27-31,106,197]**

`lastReadMessageTime`/`lastWriteMessageTime`/`localTracks` 声明+赋值后全文件零读取（写点分布在 pion 回调与 writePump 两个 goroutine），系从 websocket 复制的残留（websocket 侧同名模式同样未接线）。将来一旦有人读这两个字段立即引入 data race。
- 建议：删除死字段，或补 IdleTimeout 消费逻辑并加锁。

#### TR4 [中] 同族 transport 日志设施四种形态并存 + tcp 死代码钉 import
**[bald/transport/tcp/server.go:141,467-468、cron/server.go:73,104]**

tcp 用标准库 `log.Printf("[tcp] ...")`、cron 用 `log.Println`+手工 prefix、kafka/rocketmq/webrtc 各自复制的 `LogXxx` 包装（见 TR1）、http/grpc 不打启动日志。tcp/server.go:467-468 还有：

```go
// 新增：供 session.go 使用
var _ = id.NewGUIDv4 // session.go 自己 import 了 id，此赋值纯多余
```

- 建议：随 TR1 下沉统一日志模板；删 `var _ =` 两行。

### 8.2 核心根包基础设施（CR 系列）

#### CR1 [中] berrors 每次 error 构造都捕获 32 帧调用栈，但 `StackTrace()` 全仓零消费
**[bald/berrors/errors.go:42,80,88,96,121-130]**

`Internal/BadRequest/...` 四个构造点全部调用 `captureStack()`（`runtime.Callers(3, pcs[:32])`），错误构造在请求热路径上高频发生；而 `StackTrace()`（注释自述"供日志收集器消费"）在全仓生产代码零调用（grep 仅命中定义与测试）。
- 影响：每次错误分配付出栈捕获成本，收益为零；高频错误场景是纯性能税。
- 建议：改为惰性捕获（`StackTrace()` 首次调用时才 capture），或接入日志中间件真正消费。

#### CR2 [低] bconfig 的 `Watcher`/`ReadWatcher`/`Decoder` 接口与组合器零真实消费
**[bald/bconfig/bconfig.go:42-54,78-81 + ~150 行组合器]**

三个导出接口全仓 grep 零匹配；`FallbackReader` 仅测试与注释引用，Store/Registry 生产路径（Layers 直连 + remoteLayer）均未使用；包文档自承 Watcher 不被组合层识别。
- 影响：公共抽象面里"看起来能用"的死接口，误导用户以为信号源/外部 Decoder 是受支持路径。
- 建议：按首轮 E9 同口径——删或补真实接线示例。

#### CR3 [低] 零散死代码：`berrors.Error.WithCode`、`encoding.Names()`、broker `SubscriberSyncMap` 四方法
**[bald/berrors/errors.go:101、encoding/encoding.go:60-69、broker/subscriber.go:135,143,169,202]**

`WithCode` 与 `Names()` 全仓零调用（health 包的 `Names` 是另一套独立实现）；`RemoveWithTimeout`/`ClearWithTimeout`/`ForceClear`/`Foreach` 仅测试引用，且 WithTimeout 系列内部"每个 Unsubscribe 起 goroutine + time.After"的模式无人验证过生产语义。
- 建议：与 E 系列卫生删除同批处理。

#### CR4 [低] argo 客户端三处小缺陷：假连接日志、无默认超时、logs 接口不查状态码
**[bald/workflow/argo/client.go:36,43,378-389]**

`NewClient` 打印 "connected to Argo Server" 但未发起任何连接；`http.Client{}` 无 Timeout（仅靠调用方 ctx）；`GetWorkflowLogs` 绕过 `doRequest` 的状态码检查直接 `io.ReadAll`——401/404/500 的错误体当日志返回 + nil error。
- 建议：logs 复用 doRequest；NewClient 做轻量探测再打日志；补默认 Timeout。

#### CR5 [低] `validation.RequestTypeName` 对非指针入参直接 panic
**[bald/pkg/validation/validation.go:116-118]**

```go
return reflect.TypeOf(request).Elem().Name() // 值类型入参 → zero Value.Name() panic
```

`Validate` 只挡了 untyped nil；业务误传值类型时 panic 发生在请求链路上，与中间件 fail-fast 哲学不符。
- 建议：判 `Kind() != Ptr` 返回空串并打 error 日志，或签名改 `(string, error)`。

### 8.3 bald-crud（CD 系列）

#### CD1 [高] influxdb `BuildQueryWithParams` 无转义字符串拼接——InfluxQL 注入面，且仓内就有带转义的安全平行实现
**[bald-crud/influxdb/utils.go:180-213 + client.go:89-109]**

```go
conditions = append(conditions, fmt.Sprintf("%s %s %v", key, operator, value)) // key/operator/value 全裸插值
```

`client.go` 走的是这份不安全版；而 `influxdb/query/utils.go:10-65` 存在带 `escapeString`（单引号/反斜杠转义）的安全实现未被使用。README:305-322 还把它宣传为"参数化查询"。
- 影响：过滤值携带 `' OR ...` 或 operators map 被污染时查询结构被改写。
- 建议：删 utils.go 版，client 改用 query 包转义实现，README 同步修正。

#### CD2 [高] gorm dbresolver 主库 Dialector 传参错误——读写分离主库路由必然损坏
**[bald-crud/gorm/client.go:269 vs 273]**

```go
masterDriver := createDriver(c.masterDSN, c.masterDSN) // 首参应为 c.driverName
replicaClient := createDriver(c.driverName, replicaDSN) // 副本侧是对的
```

`createDriver(driverName, dsn)` 按第一参 switch；传入 DSN 永远匹配不到 case，`default: fallthrough` 落到 `sqlite.Open(masterDSN)`（:323-326）。开启 `WithEnableDbResolver` 后主库查询全部用 sqlite 方言解析、必然失败。
- 建议：改 `createDriver(c.driverName, c.masterDSN)`，为 dbresolver 补打开期 ping 冒烟测试。

#### CD3 [高] 泛型分页器是共享可变状态且无锁——并发请求竞态 + 跨请求状态串读
**[bald-crud/gorm/pagination/page_paginator.go:22-34、opensearch/pagination/token_paginator.go:23-27、pagination/paginator/offset_paginator.go:8-12]**

每个 Client/Repository 构造时创建一份长期持有的分页器（gorm/repository.go:76-78 等 6 个 driver 同构），`BuildDB` 原地改共享字段、闭包执行时才读：

```go
p.impl.WithPage(page).WithSize(size) // 原地改共享字段，无锁
return func(db *gorm.DB) *gorm.DB { return db.Offset(p.impl.Offset()).Limit(p.impl.Limit()) }
```

- 影响：并发 List 请求互相覆盖 offset/token——请求 A 拿到请求 B 的分页参数（错页/串读）；`-race` 下多请求必报。
- 建议：`BuildClause/BuildDB` 改纯函数（参数进结果出），或每请求构造分页器。

#### CD4 [高] 过滤构建 fail-open 且 driver 间行为不一致：entgo 双重吞错返回全表、gorm 吞错返回未过滤集合
**[bald-crud/entgo/repository.go:332-340,574-582、gorm/repository.go:179-182,288-291]**

```go
filterExpr, err := paginationFilter.ConvertFilterByPagingRequest(req)
if err != nil { log.Error(...) } // 不 return → filterExpr 可能为 nil → 无过滤查询
whereSelectors, err = r.structuredFilter.BuildSelectors(filterExpr)
if err != nil { log.Error(...) } // 不 return
```

clickhouse/doris/influxdb 同位置是 `return nil, err`（正确），entgo/gorm 漂移。gorm/filter 自己的安全测试（filter_processor_security_test.go:161-186 "hostile field must fail the query"）宣称 fail-closed，仓储层却把错误吞掉——安全语义在最后一层被打穿。
- 建议：五个 SQL/文档 driver 统一为 `return nil, err`。

#### CD5 [中] gorm `enableMigrate` 双重 AutoMigrate
**[bald-crud/gorm/client.go:191-198 与 300-304,310-318]**

NewClient 内 `enableMigrate` 已 `AutoMigrate(models...)` 一次，启动函数又跑 `doAutoMigrate()` 再迁移一次；两次取模型的函数不同（`resolveMigrateModels` vs `getMigrateModels`），模型集可能不一致且迁移是昂贵操作。
- 建议：收敛为单一路径，启动函数只复用 NewClient 的结果。

### 8.4 bald-utils / go-bald-admin（UT 系列）

#### UT1 [高] AES-CBC 的 IV 回退为密钥前缀 + 硬编码默认密钥 + 空密钥静默降级
**[bald-utils/crypto/aes.go:11,19-21,76-79,115-118]**

```go
var DefaultAESKey = []byte("f51d66a73d8a0927")  // 硬编码密钥进库
if len(key) == 0 { key = DefaultAESKey }        // 空密钥静默用公开默认密钥
if iv == nil { iv = key[:blockSize] }           // IV==key 前缀，CBC 反模式
```

IV 取自密钥违反不可预测性要求，同明文密文相同；空密钥不报错而是静默切换为源码里公开的密钥。同文件 `AESGCMCipher.Encrypt`（:150-157）已是正确范本（随机 IV 随密文返回）。
- 建议：CBC 路径对齐 GCM 范本；空密钥返回错误。

#### UT2 [高] `NewSnowflakeID` 的 check-then-act 竞态——与刚修复的 idCounter 同类残留
**[bald-utils/id/snowflake.go:44-54]**

```go
find, ok := snowflakeNodeMap.Load(workerId)
if ok { node = find.(*SnowflakeNode) } else {
    node, err = NewSnowflakeNode(workerId) // 两 goroutine 同时 miss → 各建同 workerId 的 Node
    snowflakeNodeMap.Store(workerId, node) // 后写覆盖先写，败者节点仍被本地引用继续出号
}
```

snowflake 去重只在单 Node 内部；两个同 workerId 的 Node 并发 `Generate()` 可产出重复 int64，且败者节点泄漏。
- 建议：改 `LoadOrStore`，败者丢弃自建节点。

#### UT3 [高] id 子模块对根模块的倒挂依赖——实际只用到一行语法糖，拆分近乎零成本
**[bald-utils/id/order_id.go:10,32,45 + id/go.mod:8,26]**

id 全包对根模块的依赖仅 `trans.Time(time.Now())` 两处调用点，而该函数本体只是 `return &a`（bald-utils/trans/trans.go:163-165）。消费方被迫双 replace：`bald/transport/{tcp,webrtc}` 均同时 replace `bald-utils/id` 与 `bald-utils` 根模块两条。
- 建议：order_id.go 内联 `now := time.Now()` 删掉对 trans 的依赖，消费方回归单条 replace（拆分决策的关键输入：依赖面就这一行）。

#### UT4 [高] go-bald-admin gRPC `DeleteSecret` 是硬编码假删除，且恰落在测试盲区
**[bald/examples/go-bald-admin/internal/apiserver/grpc/secret.go:30,48-50]**

```go

    return &adminv1.DeleteSecretResponse{Deleted: req.GetId()}, nil // 什么都不删，直接报成功

```

gRPC 层还绕过 biz 层直连全局 `bootstrappkg.SecretStore`（:41,55，与 HTTP 侧经 biz 注入分层不一致），GetSecret 把所有错误折叠为 `berrors.NotFound`。gRPC e2e 只测了 viewer 的 deny 路径，admin 成功删除路径零覆盖——返回成功谎言未被测试发现。
- 建议：`NewServer` 注入 `*secretbiz.SecretBiz` 调真 Delete，与 HTTP 路径对齐；补 admin 成功路径 e2e。

#### UT5 [中] mapper 模块三种失败语义混杂：panic / 静默 nil / 无 error 通道
**[bald-utils/mapper/mapper.go:34,47、enum_converter.go:28-29]**

```go

    panic(err) // 注释自认 "Handle error appropriately in production code"

if !ok { return nil } // 未知枚举静默丢值
```

`Mapper` 接口签名不含 error，实现只能 panic 或静默丢数据；`AppendConverter`（:19-25）无锁突变 `copierOption.Converters`，并发 ToEntity 后追加会 data race。

#### UT6 [中] timeutil 时区全局变量 check-then-act 竞态 + LoadLocation 错误吞掉 → `In(nil)` panic 风险
**[bald-utils/timeutil/trans.go:12-26]**

```go

    defaultTimeLocation, _ = time.LoadLocation(name) // 失败置 nil 且每次重试
```

若首次 LoadLocation 失败（精简容器缺 tzdata），所有 `tm.In(GetDefaultTimeLocation())`（:36,108,133）触发 `time: missing Location` panic。

#### UT7 [中] `GenerateOrderIdWithIncreaseIndex` 索引不补零且 mod 1000 环绕——同秒第 1001 单必然碰撞
**[bald-utils/id/order_id.go:18,52]**

索引 1-3 位不定长（注释却宣称"生成20位订单号"）；同秒超过 1000 条时索引回绕，与完全同构的前段 ID 必然重复。现有并发测试恰好 10×100=1000 次未越过边界——边界被测试设计掩盖。

#### UT8 [中] go-bald-admin `InitBridges` 幂等护栏本身是 check-then-act
**[bald/examples/go-bald-admin/internal/bootstrap/bootstrap.go:95-98]**

`if Authenticator != nil { return nil }` 非原子检查——并发/重入调用会重复生成 RSA 密钥对并重建 Signer/Authenticator，恰好制造注释里要防的"签发方与验签方密钥不一致"；DB/UserStore 等包级全局被无同步覆盖写。

#### UT9 [低] machine_id 的 sync.Once 永久缓存失败 + 同一清洗逻辑三份拷贝
**[bald-utils/id/machine_id.go:62-68,24-51,88-105,110-147]**

#### UT10 [低] `GenerateOrderIdWithTenantId` 按字节截断商户 ID，多字节 UTF-8 被拦腰切断
**[bald-utils/id/order_id.go:64-70]**

**[bald-utils/trans/trans.go:167-172,547-550、timeutil/trans.go:288]**

`TimeValue(nil)` 返回 `time.Now()`（与同包其余 21 个 `XxxValue` 的零值语义不一致，把"缺省"悄悄变成"调用时刻"）；`ToUuid` 吞错返回零值 UUID；`StringToDurationpb` 吞错返回 0 时长。

### 8.5 横切观察

1. **双层质量断层**：核心契约层（bconf/bootstrap/appkit/中间件）有契约测试、race 回归、文档纪律；外围层（transport 后端、bald-crud driver、bald-utils）是移植品，未经同等强度收敛。**移植不是终点**——TR1/TR2/CD4 的"复制后单边漂移"是同一模式的三次显形。
2. **同构复制的系统性风险**：kafka↔rocketmq（500+ 行）、tcp↔webrtc（session 管理）、bald-crud 10 driver 的 errors.go/utils.go——每处复制都已产生语义分裂。下沉共享基座（transport/subscribe 已有雏形）应作为下一轮重构主线。
3. **check-then-act 是 bald-utils 的惯性模式**：idCounter（已修）、NewSnowflakeID（UT2）、timeutil 时区（UT6）、InitBridges（UT8）四处同源。建议以 `sync.OnceValue`/`LoadOrStore`/`atomic.Pointer` 为标准替代写法，可加 lint 或 code review checklist。
4. **fail-open 与"静默降级"偏好**：CD1（注入面）、CD4（吞错）、UT1（空密钥降级）、UT11（吞错零值）、CR1（栈白捕）——外围代码倾向"出错也继续"，与核心层 fail-fast 哲学相反。统一为 fail-fast + 显式 error 是最重要的风格收敛。
