# bald 指标抽象：可观测性第三支柱（与 trace/log 并列）

> 适用包：`pkg/metrics`
> 关联文档：`审计抽象设计.md`（指标与审计同源）、`Bald 日志平面接口设计.md`（可观测性闭环）、`服务端设计.md`、`框架契约总览.md`（§9 中间件表）
> 参考实现：otel 标准 `metric` API（默认 no-op，零配置可运行）
> Last updated: 2026-09-02
> Status: Accepted

## 摘要

`pkg/metrics` 定义 bald 的可观测性**指标**抽象（第三支柱）：默认使用 otel 全局 `MeterProvider`（未配置时为 no-op，零配置可运行），不 import 任何具体 exporter（prometheus/otlp 外置为桥接子模块，如 `bald-observability-otlp`）。

**与审计同源**：指标维度直接复用 `AuditEvent` 的 `(object, action, result)`，由拦截器在记录审计事件时同步 emit，避免重复解析——一次中间件记录，既进审计又出指标。

## 设计

### 1. 指标语义

覆盖生产可观测性的「量 / 延迟 / 错误率」三要素：

| instrument | 名称 | 维度 | 说明 |
|---|---|---|---|
| `Int64Counter` | `bald_requests_total` | transport / object / action / result | 请求计数（含 deny/error 分类） |
| `Float64Histogram` | `bald_request_duration_seconds` | transport / object / action | 请求延迟（秒） |

### 2. `Recorder` 接口

```go
type Transport string
const (
    TransportGRPC Transport = "grpc"
    TransportHTTP Transport = "http"
)

// Recorder 指标记录器；具体 instrument 由核心用 otel 构建，默认 noop。
type Recorder interface {
    Record(ctx context.Context, ev Event, transport Transport, durationSeconds float64)
}

// Event 是喂给指标的精简事件视图（避免 metrics 包反向依赖 audit 包）。
type Event struct {
    Object string
    Action string
    Result string // allow / deny / error
    Error  string
}
```

### 3. 构造

```go
func New(meterName string) Recorder  // 用全局 MeterProvider 构建真实 Recorder（no-op provider 时自动退化 no-op）
func NopRecorder() Recorder          // 静默默认
```

`meterName` 通常为 `"bald/<transport>"`。若调用方未配置全局 `MeterProvider`，otel 的 `MeterProvider()` 返回 no-op，instrument 退化为 no-op，`Record` 不产生副作用——零配置可跑。

### 4. 接入

- 中间件/拦截器构造期注入 `Recorder`（`bundle.Metrics(recorder)` 或 `ObservabilityMiddleware`）。
- 记录时机与审计同源：拦截器在请求结束时一次填充 `(object, action, result, duration)`，同步 emit 计数 + 延迟。
- 结果分类与 `audit.Result` 对齐（allow/deny/error），错误率即 `result="error"` 的计数占比。

## 理由与取舍

**决策①：为什么 `Event` 不直接复用 `audit.AuditEvent`？** 避免 `pkg/metrics` 反向依赖 `pkg/audit`——两个抽象应平行存在（都可独立用于不同拦截器组合）。拦截器负责从审计事件拷贝出精简字段，成本是一次小结构赋值。

**决策②：为什么基于 otel metric 而非自研 instrument？** 指标是 Go 生态最成熟的标准（otel 全局 API），bald 只做"语义维度固化"（命名/维度/单位），不做计量引擎。未配置 provider 自动 no-op 使核心保持零耦合可选——与 `log`/`audit` 的"零后端可跑"纪律一致。

**决策③：为什么指标维度与审计三元组同源？** 避免两套命名空间（M7 的教训）：同一请求在审计是 `(secret, get)`，在指标就应是 `(secret, get)`——否则按指标排查时无法对应审计详情。

## 兼容性

纯增量：新增 `pkg/metrics` 包与 `New`/`NopRecorder`，既有中间件新增可选项（注入 Recorder 才启指标），无破坏。
