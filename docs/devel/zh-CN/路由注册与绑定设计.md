# bald 路由注册与绑定设计：基于 gin 的路由、绑定与校验，业务 Handler 以 ApplyTo 挂载路由，服务器层零改动

> 适用包：`pkg/web`（新增，构建于 gin 之上）
> 关联文档：`服务端设计.md`（服务器生命周期抽象，本设计的接入点）、`应用框架设计.md`（AppKit 编排）、`错误模型设计.md`（§4 统一错误响应复用 `pkg/errors`）
> 参考实现：onexstack `pkg/core`（泛型流水线）、`pkg/binding`（多源绑定最后统一校验）；osbuilder 模板 `internal/apiserver/ginserver.go`、`grpcserver.go`、`jobserver.go`、`mqserver/kafkaserver.go`

## 修订说明

本设计于 2026-08-25 以 **Accepted** 定稿，当时坚持"标准库 `net/http` ServeMux、零 Web 框架依赖"的底座哲学（决策①），绑定/校验也只用手写最小实现（决策⑤，不引入第三方校验库）。

经评审，方向调整为**接受 go 生态成熟方案、引入外部依赖以保证稳定性**。本次修订推翻两项原决策：

- **决策①（推翻）**：从"标准库 ServeMux，不绑框架"改为**直接引入 gin** 作为 HTTP 路由/绑定/中间件底座。理由：gin 是 go 生态最成熟、最稳定的 Web 框架之一，路由组、方法级路由、中间件链、参数绑定开箱即用，能显著降低自研成本与长期维护风险。代价是放弃"标准库中立"承诺——这是一次深思后的取舍，不是倒退。
- **决策⑤（推翻）**：从"不内置第三方校验库"改为**引入 onexstack `pkg/validation`**（反射式类型化校验），复用 onexstack 成熟实现，不引入 `go-playground/validator/v10`。

**仍保留的承诺**：`web.Router` 包装的 gin engine 仍实现 `http.Handler`，`pkg/server` **零改动**；业务路由归属业务模块（`ApplyTo`）的多源绑定最后统一校验顺序不变。

## 摘要

bald 目前的路由是"裸的"：`NewHTTPServer` 只接收一个根 `http.Handler`，业务得自己手写 mux、手写参数解析、手写校验、手写错误响应。我们提议新增 `pkg/web` 包，**构建于 gin 之上**，提供四样东西：**Router**（gin engine 的薄封装，分组 + 中间件链）、**Handler 接口**（`Name() + ApplyTo(router, middlewares...)`，业务路由归属业务模块）、**多源绑定**（URI/Query/JSON 依次绑定，最后统一验证，复用 onexstack `pkg/binding` 思想）、**泛型处理流水线**（`HandleAllRequest` 等，绑定→默认值→校验→业务→统一响应，复用 onexstack `pkg/core` 思想）。

设计出处：onexstack 用泛型把"绑定 + 校验 + 业务 + 响应"焊成一条流水线（`pkg/core`），并用 `binding.Bind` 解决"部分填充结构体导致校验失败"的经典坑（`pkg/binding`）；osbuilder 生成的 apiserver 用 `InstallRESTAPI` 挂中间件与版本组、再 `c.Handler.ApplyTo(v1, authMiddlewares...)` 把业务路由绑定到路由组。这两套都是经过真实项目验证的模式，我们**直接采用 gin 之上的实现**。

**最重要的承诺：服务器层（`pkg/server`）零改动。** `web.Router` 包装的 gin engine 本身实现 `http.Handler`，直接作为根 handler 传给现有 `NewHTTPServer`；gRPC 侧延续现有 register 回调。全部改动是纯增量的新包 + 示例迁移。

## 背景与动机

**现在的 HTTP 路由没有任何组织。** `cmd/bald/main.go` 里业务入口是这么写的：

```go
httpSrv := server.NewHTTPServer(httpOpts, http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
    _, _ = w.Write([]byte("hello from bald http\n"))
}), ready)
```

它只证明了"HTTP 服务能跑起来"。一旦业务要加第二个接口，这段代码立刻撑不住：没有路由分组、没有方法级路由、没有中间件、没有参数绑定、没有统一错误响应。业务方只能自己 `http.NewServeMux`、自己 `json.NewDecoder`、自己手写校验、自己拼错误 JSON——每个接口重复一遍，出错的地方还各不相同。这是"框架底座"最不该留给用户的空白。

**参考实现把这条路走通了。** onexstack 的 `pkg/core` 用泛型定义了一条流水线：

```go
func HandleAllRequest[T any, R any](c *gin.Context, handler Handler[T, R], validators ...Validator[T]) {
    var request T
    if err := ShouldBindAll(c, &request, validators...); err != nil {
        WriteResponse(c, nil, err)
        return
    }
    response, err := handler(c.Request.Context(), &request)
    WriteResponse(c, response, err)
}
```

其中 `ShouldBindAll` 调用 `binding.Bind(c, rq, binding.URI, binding.JSON)`——URI、Query、JSON 依次绑定到同一个结构体，**最后统一校验**，而不是每绑一个字段就校验一次。这是 `pkg/binding` 的动机：如果 Query 绑定失败就立刻校验，部分填充的结构体（比如只绑上了 `page` 还没绑上 `keyword`）会触发假的必填校验错误。顺序（URI→Query→JSON）即优先级，后者覆盖同名前者。

osbuilder 模板 `internal/apiserver/ginserver.go` 展示了路由怎么"注册"到服务器上：

```go
func (c *ServerConfig) InstallRESTAPI(engine *gin.Engine) {
    InstallGenericAPI(engine)          // pprof / metrics / 404
    engine.GET("/healthz", c.Handler.Healthz)
    v1 := engine.Group("/v1")          // 版本路由组

    authMiddlewares := []gin.HandlerFunc{mw.AuthnMiddleware(c.Retriever), mw.AuthzMiddleware(c.Authz)}
    c.Handler.ApplyTo(v1, authMiddlewares...)   // 业务路由挂到版本组，认证作为路由级中间件
}
```

它回答了"路由注册"的一个关键问题：**路由不该集中在某张"全局路由表"里，而应该由业务模块自己通过 `ApplyTo` 挂载。** 每个 handler 结构体负责自己的路由，服务器装配层只负责创建版本组、把认证中间件传进去。同样，grpcserver.go 的 register 回调、jobserver/kafkaserver 的 worker 注册，都是同一个思想：**"注册/装配"与"具体路由"分离。**

一句话给问题定性：bald 缺一个"路由该在哪注册、请求该怎么绑、响应该怎么写"的约定，而这套约定**直接采用 gin 生态的成熟实现**，不再自研。

## 设计

从最小的一块讲起：Router。它足够回答"HTTP 路由在哪注册"；然后逐层加中间件、绑定、泛型流水线；最后展示它怎么接进现有服务器、以及 gRPC 侧怎么做。

### 1. Router：gin engine 的薄封装

Router 是对 `gin.Engine` 的极薄封装，只加一样 gin 没有的约定：**业务模块 `ApplyTo` 挂载点**。gin 本身已原生支持分组（`engine.Group`）、中间件（`Use`）、方法级路由（`GET/POST/...`）、路径参数（`/v1/users/:id`、`c.Param("id")`）。

```go
package web

// Middleware 采用 gin 原生中间件签名（与 onexstack/osbuilder 对齐）。
type Middleware = gin.HandlerFunc

type Router struct {
    engine *gin.Engine
}

// NewRouter 创建一个根路由器（gin engine）。
func NewRouter(middlewares ...Middleware) *Router

// Group 返回带路径前缀 + 中间件链的子路由器（中间件在调用方外->内执行）。
func (r *Router) Group(prefix string, middlewares ...Middleware) *Router

// Handle 注册方法级路由。method 支持 gin 的 GET/POST/PUT/DELETE 等。
func (r *Router) Handle(method, pattern string, handler gin.HandlerFunc, middlewares ...Middleware)

// HandleFunc 是 Handle 的便捷形式。
func (r *Router) HandleFunc(method, pattern string, h func(*gin.Context), middlewares ...Middleware)

// Engine 暴露底层 gin engine，供需要原生 gin 能力的高级场景使用。
func (r *Router) Engine() *gin.Engine

// ServeHTTP 让 *Router 成为合法 http.Handler——这是服务器层零改动的关键。
func (r *Router) ServeHTTP(w http.ResponseWriter, req *http.Request)
```

**边界：**
- `Handle` 的 `method` 支持 `GET` / `POST` / `PUT` / `DELETE` 等。
- 中间件在 `ServeHTTP` 时从外到内组装：先挂 Router 级中间件，再挂 Group 级，再挂路由级。同一层内按注册顺序。
- **不与探针冲突**：`NewHTTPServer` 内部把 `/healthz` `/readyz` 注册为精确路径（见 `服务端设计.md`）。gin engine 作为根 handler 传入后，探针路径需在 gin 内也注册（或由 `NewHTTPServer` 的 mux 优先匹配）。具体见 §5 接入约定——**探针注册权仍归 `pkg/server`**，Router 不碰这两个路径。
- **根路径基础设施**（对齐 ginserver.go 的 `InstallGenericAPI`）：`NewRouter` 在创建 engine 时默认挂 404 兜底（`c.JSON(404, ...)`）、`/metrics`、pprof 等通用端点，与 osbuilder 模板一致；但这些**不改变 `pkg/server` 探针的优先级**——探针（`/healthz`、`/readyz`）由 `pkg/server` 的外层 mux 优先匹配，之后其余流量才进 gin engine。业务不应在 `/v1` 之外的根路径注册会被探针占用的端点。

### 2. Handler 接口：路由归属业务模块

```go
// Handler 是业务 HTTP 模块的接口。
// 路由不集中注册，而由每个业务模块在自己的 ApplyTo 里挂载。
type Handler interface {
    Name() string                          // 模块名，用于日志/指标/OpenAPI 标签
    ApplyTo(r *Router, middlewares ...Middleware) error
}
```

**路由注册表（对齐 onexstack/osbuilder 的 `Registrar` + 全局 `registrars` 模式）：** 当业务模块较大、路由分散在多个文件时，用"全局注册表 + `init()` 自注册"解耦"路由定义"与"统一挂载"。这是 onexstack handler 包的真实写法，直接复用：

```go
// handler/handler.go
// Registrar 是单组路由的注册函数（模块内每个资源一个）。
type Registrar func(rg *gin.RouterGroup, h *Handler, mws ...Middleware)

var registrars []Registrar

// Register 把一组路由追加进全局注册表（由各资源的 init() 调用）。
func Register(r Registrar) { registrars = append(registrars, r) }

// ApplyTo 遍历注册表，把全部路由挂到给定组，并注入中间件。
func (h *Handler) ApplyTo(rg *Router, mws ...Middleware) error {
    for _, reg := range registrars {
        reg(rg.Engine().Group(""), h, mws...)   // 各 Registrar 内部自行 Group 版本/资源前缀
    }
    return nil
}

// handler/user.go
func init() {
    Register(func(rg *gin.RouterGroup, h *Handler, mws ...Middleware) {
        v1 := rg.Group("/v1")
        ug := v1.Group("/users")
        ug.POST("", h.CreateUser)
        ug.Use(mws...)                       // 认证中间件作用于该资源组（含子路由）
        ug.PUT(":userID/change-password", h.ChangePassword)
        ug.PUT(":userID", h.UpdateUser)
        ug.DELETE(":userID", h.DeleteUser)
        ug.GET(":userID", h.GetUser)
        ug.GET("", h.ListUser)
    })
}
```

**handler 薄层范式（对齐 onexstack `core.HandleX` 调用）：** handler 方法体只做"绑定 + 校验 + 转发 biz"，业务逻辑在 `biz` 层。标准写法是一行 `core.HandleJSONRequest(c, h.biz.UserV1().Login, h.val.ValidateLoginRequest)`：

```go
// handler/user.go
func (h *Handler) Login(c *gin.Context) {
    core.HandleJSONRequest(c, h.biz.UserV1().Login, h.val.ValidateLoginRequest)
}
func (h *Handler) CreateUser(c *gin.Context) {
    core.HandleJSONRequest(c, h.biz.UserV1().Create, h.val.ValidateCreateUserRequest)
}
func (h *Handler) UpdateUser(c *gin.Context) {
    core.HandleAllRequest(c, h.biz.UserV1().Update, h.val.ValidateUpdateUserRequest)
}
func (h *Handler) DeleteUser(c *gin.Context) {
    core.HandleUriRequest(c, h.biz.UserV1().Delete, h.val.ValidateDeleteUserRequest)
}
func (h *Handler) ListUser(c *gin.Context) {
    core.HandleQueryRequest(c, h.biz.UserV1().List, h.val.ValidateListUserRequest)
}
```

**装配层（对应 osbuilder 的 `InstallRESTAPI`，bald 侧就是 main.go 或一个 `NewRouter` 组装函数）：**

```go
router := web.NewRouter(web.Recovery(), web.RequestID(), mw.Cors(web.DefaultCorsConfig()), web.Secure())

// 无版本前缀、且认证中间件按需加载的真实模式（对齐 ginserver.go）：
// /login 公开，/refresh-token 仅需 Authn。
router.HandleFunc(http.MethodPost, "/login", core.HandleJSONRequest(c.Handler.Login, c.val.ValidateLoginRequest))
router.HandleFunc(http.MethodPut, "/refresh-token",
    mw.AuthnMiddleware(retriever), core.HandleJSONRequest(c.Handler.RefreshToken, c.val.ValidateRefreshTokenRequest))

authMiddlewares := []web.Middleware{mw.AuthnMiddleware(retriever), mw.AuthzMiddleware(authz)}
_ = c.Handler.ApplyTo(router, authMiddlewares...)   // 业务模块路由挂到版本组，认证从装配层注入
```

> 关键点：**部分路由（如 `/login`、`/refresh-token`）刻意不加 `/v1` 前缀**，且认证中间件是"选择性注入"而非一刀切——这与 osbuilder `ginserver.go` 的 `engine.POST("/login", ...)` / `engine.PUT("/refresh-token", AuthnMiddleware, ...)` 完全一致。`ApplyTo` 注入的 `mws` 作用于模块内需要鉴权的资源组（如 `/v1/users` 下的受保护子路由）。

**为什么路由不该集中注册**，见 Rationale 决策③。

### 3. 多源绑定 + 统一验证（基于 gin + validator）

绑定是请求到结构的映射。onexstack 的教训是：**URI/Query/JSON 依次绑定到同一个结构体，最后统一校验**，避免部分填充触发假校验错误。本次直接复用 onexstack `pkg/binding` 的成熟实现（gin 之上），不再手写 `fieldSetter`。

核心依赖（新增到 go.mod）：
- `github.com/gin-gonic/gin`：路由、绑定、中间件底座。
- `github.com/.../pkg/validation`（移植 onexstack `pkg/validation`，反射式类型化校验）：按 Request 类型名分发到 `Validate<ReqType>(ctx, *Req) error` 方法，业务代码即校验规则。仅依赖 `k8s.io/klog/v2`（若 bald 尚未引入需补）。

绑定语义细节：
- **多源顺序绑定**：`binding.Bind(c, &req, binding.URI, binding.JSON)`（URI → Query/Form → JSON 依次覆盖，后者优先）。`pkg/binding` 在 `init()` 时把 gin 的全局 validator 置 nil，使"绑定期不校验"，全部绑定完成后再统一跑校验。
- **默认值**：若 `obj` 实现 `interface{ Default() }`，绑定完成后调用 `Default()`（参考 `core.FinalizeRequest`）。
- **校验**：绑定完成后统一执行。优先用 `pkg/validation.Validator`——`NewValidator(customValidator)` 反射扫描 `customValidator` 上所有 `Validate<ReqType>` 方法并按请求类型名分发；request 结构体也可自带 `Validate<ReqType>` 方法自动命中。业务仍可额外传 `Validator[T]` 闭包做跨字段/业务校验（闭包内部可调用 `validation.Validator.Validate`）。
- **JSON 绑定**：gin 的 `ShouldBindJSON` 要求 `Content-Type: application/json`；非 JSON 类型且携带 body 按"非法即拒绝"返回 400（沿用 `错误模型设计.md` 的 `BIND_ERROR` 约定，不静默容错）。

> 注：`pkg/binding` 的 `init()` 改的是 gin 的全局 `binding.Validator`。在 bald 中若直接移植该包，需确认其副作用范围（仅影响 gin 绑定，不污染其他）。建议将 `pkg/binding` 作为内部子包（如 `pkg/web/binding`）纳入，避免与 onexstack 版本漂移。

### 4. 泛型处理流水线 + 统一响应

绑定、校验、业务、响应这条链路，每个接口都手写一遍会重复到令人发指。直接复用 onexstack `pkg/core` 的泛型方案（gin 之上）：

```go
// Handler 是业务处理函数。
type Handler[T any, R any] func(ctx context.Context, req *T) (R, error)

// Validator 是校验函数。
type Validator[T any] func(ctx context.Context, obj *T) error

// HandleAllRequest：URI + Query + JSON 全绑，统一校验，业务，统一响应。
func HandleAllRequest[T any, R any](c *gin.Context, handler Handler[T, R], validators ...Validator[T])

// HandleJSONRequest / HandleQueryRequest / HandleUriRequest：单源快捷函数。
func HandleJSONRequest[T any, R any](c *gin.Context, handler Handler[T, R], validators ...Validator[T])

// WriteResponse：成功直接写 data；失败写统一 ErrorResponse 并映射 HTTP 状态码。
func WriteResponse(c *gin.Context, data any, err error)
```

`pkg/core` 的 `HandleAllRequest` / `ShouldBindAll` / `FinalizeRequest` / `WriteResponse` 可直接照搬（仅需把 `errorsx.FromError` 替换为 bald 自有的 `pkg/errors.FromError`，见下方"错误响应"说明）。

错误响应沿用 onexstack 的约定：

```go
type ErrorResponse struct {
    Reason   string            `json:"reason,omitempty"`
    Message  string            `json:"message,omitempty"`
    Metadata map[string]string `json:"metadata,omitempty"`
}
```

**状态码怎么来？** 结构化错误独立在 `pkg/errors`（见 `错误模型设计.md`），web 层不重复定义 `Error`。`WriteResponse` 调用 `berrors.FromError(err)` 提取 `Reason/Message/Details`，并用 `StatusCoder`（或 `berrors.Error.StatusCode()`）决定 HTTP 状态码：

```go
// StatusCoder 是 web 层与错误模型的唯一契约：
// 实现了 StatusCode() 的错误自己决定 HTTP 状态码，未实现的统一 500。
type StatusCoder interface { StatusCode() int }
```

- 复用了 bald 自有的 `pkg/errors`（WindError），**不引入 onexstack 的 `errorsx`**——错误模型是 bald 已定稿的独立设计，gin 只负责路由/绑定，错误响应仍由 `pkg/errors` 统一产出。
- 与 gRPC/Kratos 桥接走 `pkg/errors/grpcerr`（`ToStatus`/`FromStatus`），保证多协议错误语义透传。

### 5. 服务器侧接入：gin engine 即 http.Handler，服务器零改动

gin 的 `*gin.Engine` 实现了 `http.Handler`，所以直接塞进现有的 `NewHTTPServer`：

```go
router := web.NewRouter(web.Recovery(), web.RequestID())
_ = handler.ApplyTo(router)                       // 业务挂载
httpSrv := server.NewHTTPServer(httpOpts, router, ready)   // 与今天完全相同的构造签名
```

`pkg/server` 一行不改：探针、TLS、动态端口、优雅停机全部照旧。这是本设计最重要的兼容性承诺，见 Compatibility。

> **探针共存约定**：`NewHTTPServer` 当前用 `http.ServeMux` 注册 `/healthz` `/readyz`。将 gin engine 作为根 handler 传入后，需确保探针路径优先匹配——有两种做法：(a) 由 `NewHTTPServer` 在 gin 外层再包一层 mux，精确路径优先；(b) 在 `pkg/web` 初始化时由 `pkg/server` 注入探针路由到 gin。本设计选 (a)，不改 `pkg/server` 即可达成零改动。

### 6. gRPC 路由注册：延续 register 回调

gRPC 的路由"注册"本质是 `pb.RegisterXXXServer(s, impl)`，现有 `NewGRPCServerWithRegister` 的 register 回调已经够用：

```go
grpcSrv := server.NewGRPCServerWithRegister(grpcOpts, nil, func(s *grpc.Server) {
    pb.RegisterUserServiceServer(s, grpcHandler)   // 业务 service 在此注册
}, ready)
```

本设计只补两样，都不改 server 包签名：
- **拦截器链 helper**：提供 `pkg/grpcmw`，组装一条与 osbuilder `grpcserver.go` **完全一致**的拦截器链。顺序即契约（注意 RequestID 在最外、Validator 在 Defaulter 之后）：

```go
serverOptions := []grpc.ServerOption{
    grpc.ChainUnaryInterceptor(
        mw.RequestIDInterceptor(),                              // 1. 请求 ID（最外）
        selector.UnaryServerInterceptor(mw.AuthnInterceptor(retriever), NewAuthnWhiteListMatcher()), // 2. 认证（白名单跳过公开方法）
        selector.UnaryServerInterceptor(mw.AuthzInterceptor(authz), NewAuthzWhiteListMatcher()),     // 3. 授权
        mw.DefaulterInterceptor(),                              // 4. 默认值填充
        mw.ValidatorInterceptor(genericvalidation.NewValidator(c.val)), // 5. 校验（自动按类型名分发 Validate<Req>）
        // ... Observability() / Context()（可选，OTel 场景）
    ),
}
```

  其中 `ValidatorInterceptor(genericvalidation.NewValidator(c.val))` 是 onexstack 的校验注入点——把全局 `Validator` 注入拦截器，每个 gRPC 方法进入时自动按请求类型名找到 `Validate<Req>` 执行。HTTP 侧的等价物是 handler 方法里显式传 `h.val.ValidateXxx`（见 §2 薄层范式），两条路径共用同一套 `validation.Validator`。server 包本身**不强制**挂拦截器，保持透明。
- **多协议复用（可选实践）**：HTTP handler 与 gRPC handler 共享 `biz` 层（onexstack 的分层：handler 薄、biz 厚），两份 handler 只做协议翻译。

> 设计边界：gateway（grpc-gateway 反代）维持 `服务端设计.md` 现状——gateway 的 handler 注册仍走 register 回调，本设计不介入。

### 7. 改造前 vs 改造后对照

| | 今天（main.go） | 引入 gin + pkg/web 后 |
|---|---|---|
| 路由组织 | 一个写死的 `http.HandlerFunc` | gin engine + 版本组 + 各模块 `ApplyTo` |
| 新增接口 | 手写 mux / 手写解析 / 手写响应 | 模块内一行 `HandleFunc` + 泛型流水线 |
| 认证 | 无 | 路由级中间件注入（`ApplyTo(v1, authn, authz)`） |
| 参数绑定 | 无 | gin + `binding.Bind` 自动 URI/Query/JSON 绑定 |
| 校验 | 无 | `pkg/validation`（类型化 `Validate<Req>` 分发）+ `Validator[T]` |
| 错误响应 | 各写各的 | `WriteResponse` 统一 `ErrorResponse`（复用 `pkg/errors`） |
| 服务器层 | `NewHTTPServer(opts, handler, ready)` | 签名不变，handler 换成 `*web.Router` |

## 理由与取舍

**决策①（已推翻，原：标准库 ServeMux 不绑框架 → 现：引入 gin）：为什么是 gin，而不是标准库 ServeMux / httprouter / gorilla-mux / 自研 trie？**

原决策①曾否决 gin，理由是"引入 gin 等于把整个框架拴在 gin 的 Context 上，违反底座中立"。经评审推翻：bald 当前阶段更看重**稳定性与生态成熟度**而非框架中立。gin 是 go 生态最广泛采用的 Web 框架，路由、绑定、中间件、校验集成度极高，社区活跃、长期维护有保障。相较之下：
- **标准库 ServeMux**：虽零依赖，但分组、中间件、参数绑定都需自研，长期维护成本高、易出错（本次已自研一版 `fieldSetter`/`Binder`，验证可行但非生态标准）。
- **httprouter / gorilla-mux**：仍是第三方依赖，且能力不如 gin 全家桶（缺绑定/校验集成）。
- **自研 trie**：过早优化，ServeMux/gin 已覆盖需求。
- **go-lulu 式 Driver 抽象**：早期评审已否决（YAGNI）。

**接受 gin = 接受"框架绑定"这一事实**，换取生态成熟度的确定性收益。gin engine 仍实现 `http.Handler`，故服务器层零改动承诺依然成立。

**决策②：为什么要有 Router 封装，而不直接用 gin.Engine？**
gin 没有"业务模块 ApplyTo 挂载"的约定，且 `NewHTTPServer` 接收的是 `http.Handler`。Router 是薄封装：`Group` 管前缀 + 中间件，`Handle` 管方法路由，`ServeHTTP` 暴露为 `http.Handler`，并预留 `Engine()` 供高级场景。它不替换 gin 的匹配算法，只是"组合层 + 接入适配层"。

**决策③：为什么路由归属业务模块（ApplyTo），而不是集中路由表？**
osbuilder 模板的答案是 ApplyTo，我们沿用。集中路由表在小项目没问题，模块一多就变成"谁都能改所有人的路由"。`ApplyTo` 把"路由属于谁"画清楚：user handler 的路由在 user handler 里，auth 中间件由装配层注入（权限边界不落在业务模块手里）。代价是"路由在哪"不再是单一文件可见——用 `Name()` 打日志/指标缓解。

**决策④：为什么多源绑定 + 统一验证，而不是逐字段手动解析，也不是一绑一验？**
逐字段手动解析是最朴素做法，被否决；一绑一验（绑 Query 就立刻验）被 `pkg/binding` 明确否决：部分填充的结构体会让"必填"校验误报。统一验证（绑定全部完成后跑 validators）才是正确顺序——直接复用 onexstack `pkg/binding` 的实现。

**决策⑤（已推翻，原：不内置第三方校验库 → 现：引入 onexstack `pkg/validation`）：为什么用 `pkg/validation` 而非手写或 `go-playground/validator`？**
原决策⑤为避免重依赖只用手写最小校验。本次推翻：用户明确"接受外部依赖以保证稳定"，且指定采用 onexstack 已有的 `pkg/validation` 包，而非 `go-playground/validator/v10`。
- `pkg/validation` 是 onexstack 经过真实项目验证的反射式类型化校验：每个 Request 类型写 `Validate<ReqType>(ctx, *Req) error` 方法，`Validator.Validate(ctx, req)` 按 `reflect.TypeOf(req).Elem().Name()` 自动分发——**校验规则就是业务代码，无需学一套 tag DSL**，可读性与可调试性优于 `validate:"required,email"` 字符串。
- 依赖极轻：仅 `k8s.io/klog/v2`（日志），不引入 gin 之外的重框架，也不与 `validator/v10` 的全局 `binding.Validator` 机制耦合。
- 仍保留泛型流水线的 `Validator[T]` 闭包作为统一入口，闭包内可调用 `validation.Validator.Validate`，兼容需要跨字段/动态规则的场景。

**决策⑥：为什么服务器层零改动是硬约束？**
`pkg/server` 是 bald 的心脏（探针、TLS、动态端口、优雅停机）。而 gin engine 实现 `http.Handler` 让接入成本为零：不用改 `NewHTTPServer`、不用改 AppKit、不用改服务注册。这条约束不是"方便"，是**风险管理**——把路由能力独立成新包，坏了只影响 `pkg/web`。

**决策⑦：gRPC 侧为什么只加 helper、不改 register 回调？**
`NewGRPCServerWithRegister` 的 register 回调已能注册任意 service。我们不动它，只补拦截器链 helper 与"biz 共享"约定。给 gRPC 也造 `ApplyTo` 式抽象是过度设计（gRPC 路由是编译期 `pb.RegisterXXX` 生成）。
- **拦截器链顺序已固化（对齐 osbuilder `grpcserver.go`）**：`RequestID → Authn(selector+白名单) → Authz(selector+白名单) → Defaulter → Validator → [Observability/Context]`。该顺序是 onexstack 验证过的成熟范式，直接作为 `pkg/grpcmw` 的默认链；白名单用 `NewAuthnWhiteListMatcher`/`NewAuthzWhiteListMatcher` 放行 `/login`、`/healthz` 等公开方法。Validator 拦截器内部用 `genericvalidation.NewValidator(c.val)` 自动分发——与 HTTP 侧 `h.val.ValidateXxx` 共用同一套 `validation.Validator`。

## 兼容性

**这是纯增量变更，无破坏。** 具体承诺：

1. `pkg/server` API 一字不改，`NewHTTPServer(opts, handler, readiness)` 的 `handler` 参数本来就是 `http.Handler`，gin engine 包装的 `*web.Router` 直接替换。
2. 现有 `cmd/bald/main.go` 用 `http.HandlerFunc` 的方式**继续可用**，迁移是自愿的。
3. gRPC register 回调、gateway、AppKit、服务注册全部不受影响。
4. 依赖：新增 `github.com/gin-gonic/gin`、`github.com/.../pkg/validation`（移植 onexstack `pkg/validation`，仅依赖 `k8s.io/klog/v2`）；结构化错误复用既有 `pkg/errors`（不引入 onexstack `errorsx`）。

**迁移路径**：分两步走。
- 第一步（示例先行）：在 `cmd/bald` 增加一个基于 `pkg/web`（gin）的示例接口（如 `GET /v1/version`），与现有写死 handler 并存——HTTP 服务器只能有一个根 handler，让 `pkg/server` 的外层 mux 优先匹配探针、其余转发给 gin Router。
- 第二步（业务自选）：真实业务把各模块改造成 `Handler.ApplyTo` 模式，按模块逐个迁移，每迁一个模块验证一个模块。gin 与裸 `http.Handler` 混用不受限。

**已知代价（诚实列出）：**
- 引入 gin 意味着 bald 的 HTTP 层与 gin 强绑定——这是本次主动接受的取舍（换取生态成熟度）。
- `pkg/binding` 的 `init()` 修改 gin 全局 validator，需纳入 bald 内部管理（建议作为 `pkg/web/binding` 子包），避免与 onexstack 版本漂移或全局副作用外泄。
- gin 的 JSON 绑定要求显式 `Content-Type: application/json`，非 JSON 且带 body 按"非法即拒绝"返回 400（见 `错误模型设计.md`），调用方需遵守。

### B. onexstack 可移植性评估

| onexstack 源码 | 依赖 | 在 bald（gin）下可否直接复用 |
|---|---|---|
| `pkg/core` 泛型流水线（`HandleAllRequest`/`ShouldBindAll`/`FinalizeRequest`/`WriteResponse`） | gin + `errorsx` | ✅ 逻辑可直接照搬；仅 `WriteResponse` 内 `errorsx.FromError` 改为 `pkg/errors.FromError` |
| `pkg/binding`（`Bind`/`URI`/`JSON` + `init()` 关校验） | gin | ✅ 可直接移植为 `pkg/web/binding` 子包；`init()` 副作用需纳入 bald 内部管理 |
| `pkg/validation`（`Validator` 类型化分发 + `Rules` 规则式校验） | `k8s.io/klog/v2` | ✅ 可直接移植为 `pkg/web/validation`（或 `pkg/validation`）；仅依赖 klog，无 gin/validator 耦合，作为校验底层 |
| `pkg/errorsx`（错误模型） | kratos + grpc | ❌ 不引入；bald 已有独立 `pkg/errors`（WindError），沿用即可 |

结论：**引入 gin 后，onexstack 的 `pkg/core` + `pkg/binding` 模式可直接照搬**，校验改用 `pkg/validation` 的 `Validator`（无需 `go-playground/validator/v10`）。代码实现阶段无需重新设计绑定/校验逻辑，只需把错误提取从 `errorsx` 换成 `pkg/errors`。

### C. FAQ

**为什么叫 `Handler` 接口而不是 `Controller` / `Service`？** 与 onexstack/osbuilder 模板的既有命名对齐；`Handler` 强调"处理 HTTP 请求"这一层职责，`biz` 层才是业务逻辑。

**和 Kratos 的 `transport.Server` 是什么关系？** 无关。Kratos 管服务生命周期，`pkg/web` 管单协议的请求路由与绑定。bald 的 server 层已兼容 Kratos（见 `服务端设计.md`），`pkg/web` 在其之上。

**引入 gin 后，之前的 `pkg/web`（标准库版）代码怎么办？** 本次仅修订设计文档（Status 回到 Draft），代码实现后续再做。实现阶段将用 gin 版重写 `pkg/web`，标准库版的手写 `fieldSetter`/`Binder` 会被 `pkg/binding`（gin 之上）取代。
