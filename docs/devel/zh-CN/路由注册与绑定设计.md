# 路由注册与绑定设计

> 状态说明：早期 `web.Error` 提案章节已移除（其功能由 `pkg/berrors` 承载），错误语义以 [错误模型设计](./错误模型设计.md) 为准；其余章节（路由注册、绑定/校验/响应、gin 复用）仍有效。

本文描述 bald 的「路由注册」与「请求绑定 / 校验 / 响应」设计。核心结论先行：

- **路由注册完全由业务侧（用户）用 gin 编写**，框架不提供统一的路由注册中心。
- **绑定 / 校验 / 响应收敛到强绑定 gin 的 `pkg/web` 流水线**，同一套 `web.Handle*` 既能被 gin 路由调用，也能被 grpc-gateway 生成的 HTTP 接口复用（grpc-gateway 走标准库 `net/http`，业务逻辑 biz 层共享）。
- **路径变量由 gin 原生 `ShouldBindUri`（结构体 `uri` tag）处理，无需任何桥接层**。
- **错误语义复用 bald 自有的 `pkg/berrors`**（传输中立的 `Code`/`Reason`），不引入 onexstack 外部依赖。

---

## 1. 设计动机

早期版本用一个引擎无关的 `pkg/core` 包（只依赖标准库 `net/http`），通过 `WithPathVars` 把 gin/chi 的路径参数桥接进请求上下文，以支持多种 HTTP 引擎。但它带来两个问题：

1. 自研的反射 binder（`binder.go`/`pathvar.go`/`bind.go`）与 gin 原生绑定重复，维护成本高。
2. 为了"引擎无关"付出的桥接成本，实际只用到了 gin 与 grpc-gateway 两种传输。

因此改为**参考 onexstack 的 `pkg/core` 思路**：`web` 包直接消费 `*gin.Context`，强绑定 gin，删掉所有引擎无关的反射 binder 与路径变量桥接。框架只支持 **gin（HTTP）与 grpc（grpc-gateway 复用同一 biz 层）**。

---

## 2. 分层结构

```
业务 main.go / handler（路由注册，直接用 gin）
        │  c *gin.Context
        ▼
pkg/web（强绑定 gin：绑定 → 校验 → 响应）   ← 拆出的核心
        │  gin.ShouldBind* + pkg/berrors
        ▼
pkg/berrors（统一错误语义 / HTTP 状态码）
```

- **路由注册层**：由用户在 `main.go`（或按 miniblog 风格的 `internal/handler/http`）中用 gin 直接编写，例如 `engine.POST(...)`、`engine.GET("/v1/users/:id", ...)`。
- **核心流水线层**：`pkg/web` 提供 `Handle*` 与底层 `ShouldBindAll` / `WriteResponse` / `ErrorResponse`，直接依赖 gin 与 `pkg/berrors`。
- **错误语义层**：`pkg/berrors` 提供统一的错误语义（`*Error`，核心零依赖，HTTP 状态码经 `httperr.StatusCode` 还原），被 `web.ErrorResponse` 直接取 HTTP 状态码与 `Reason`/`Message`。

> 示例位于 `_example/`（对标 miniblog 的 `examples/`）：`_example/bald`（appkit 编排 + HTTP/gRPC 双协议）、`_example/bald-gin`（纯 gin 引擎）。已删除仅用于演示 chi 的 `_example/bald-chi`，因为 bald 不再支持 gin 之外的 HTTP 引擎。

## 3. 核心流水线 `pkg/web`

### 3.1 Handler 与 Validator 签名

```go
// 业务处理函数：接收已绑定并校验的请求指针 *T，返回响应 R 或 error。
type Handler[T any, R any] func(ctx context.Context, req *T) (R, error)

// 请求校验器；校验错误应返回 pkg/berrors 中标识为校验错误的错误（如 errors.BadRequest）。
type Validator[T any] func(ctx context.Context, req *T) error
```

业务只需实现 `Handler`：接收 `*T`（指针，与 onexstack 一致），返回 `R` 或 `error`。业务逻辑不依赖 gin 类型，从而与传输层解耦（参考 miniblog handler 分层，可被 gin 与 grpc 共用）。

### 3.2 四个入口函数

| 函数 | 绑定来源 | 适用场景 |
|------|----------|----------|
| `HandleJSONRequest[T,R]` | 仅 JSON body（`c.ShouldBindJSON`） | 纯 JSON 接口（POST/PUT 等） |
| `HandleQueryRequest[T,R]` | 仅 URL 查询参数（`c.ShouldBindQuery`） | 过滤 / 分页 / GET 列表 |
| `HandleUriRequest[T,R]` | 仅路径变量（`c.ShouldBindUri`，需 `uri` tag） | 路径即参数（如 `/users/:id`） |
| `HandleAllRequest[T,R]` | URI → Query → JSON 依次覆盖 | 多源组合，优先级 JSON 最高 |

调用示例：

```go
engine.POST("/v1/greet", func(c *gin.Context) {
    web.HandleJSONRequest[greetReq, greetResp](c,
        func(_ context.Context, g *greetReq) (greetResp, error) {
            return greetResp{Greet: "hello, " + g.Name}, nil
        })
})
```

### 3.3 多源绑定 `ShouldBindAll`

`ShouldBindAll` 对应 onexstack `binding.Bind` 的动机，但保留 bald 的"先合并、后校验"顺序：

1. 依次 `c.ShouldBindUri` → `c.ShouldBindQuery` → `c.ShouldBindJSON`（仅当请求体非空），**后者覆盖前者——URI 优先级最低，JSON 最高**。
2. 若对象实现了 `Defaulter` 接口（`Default()` 方法），调用它填充默认值。
3. 全部绑定完成后再由业务 `Validator` 执行校验，避免部分填充的结构体触发假的必填错误。

```go
type Defaulter interface { Default() }
```

### 3.4 统一响应与错误

- `WriteResponse[T](c, data, err)`：成功时写 JSON；`data` 为 nil / 零值引用时仅置 200。
- `ErrorResponse(c, err)`：
  - 经 `errors.FromError` 还原为 `*errors.Error`，取 `httperr.StatusCode` 与 `Reason`/`Message`；无法还原则兜底 `errors.Internal`（HTTP 500）。
  - 响应体 `ErrorBody{Error:{Code, Message}}`：`Code` 填 `Reason`，`Message` 填业务消息。
  - 校验错误（如 `errors.BadRequest`）自然映射为 HTTP 400。

`pkg/berrors` 支持 `WithCause` 包装，被 `%w` 包裹的业务 `*Error` 仍能被 `FromError` 拆链映射，不会误落 500。

## 4. 路径变量（gin 原生）

`web` 强绑定 gin，路径参数由 gin 原生 `ShouldBindUri` 处理，结构体字段用 `uri` tag 标注，与路径变量名一致：

```go
type userReq struct {
    ID string `json:"id" uri:"id"`
}

engine.GET("/v1/users/:id", func(c *gin.Context) {
    web.HandleUriRequest[userReq, map[string]string](c,
        func(_ context.Context, u *userReq) (map[string]string, error) {
            return map[string]string{"id": u.ID}, nil
        })
})
```

**无需任何桥接层**：相比旧版 `pkg/core` 的 `WithPathVars` / `mid.PathVars()`，强绑 gin 后路径变量直接由 gin 解析，代码更简洁。

### grpc-gateway 复用

grpc-gateway 生成的 HTTP 接口会落到标准库 `net/http`，但其 handler 内部仍调用同一套 biz 层 `Handler[T,R]`（指针签名），业务校验 / 逻辑与 gin 完全一致，只有传输边界不同。

## 5. 完整示例（gin）

```go
import (
    "github.com/gin-gonic/gin"

    "github.com/kalandramo/bald/pkg/web"
)

engine := gin.New()
engine.Use(gin.Recovery())

engine.POST("/v1/greet", func(c *gin.Context) {
    web.HandleJSONRequest[greetReq, greetResp](c,
        func(_ context.Context, g *greetReq) (greetResp, error) {
            return greetResp{Greet: "hello, " + g.Name}, nil
        })
})

type userReq struct {
    ID string `json:"id" uri:"id"`
}
engine.GET("/v1/users/:id", func(c *gin.Context) {
    web.HandleUriRequest[userReq, map[string]string](c,
        func(_ context.Context, u *userReq) (map[string]string, error) {
            return map[string]string{"id": u.ID}, nil
        })
})

// 原生 gin.Engine 直接作为 http.Handler 交给服务器层。
httpSrv := server.NewHTTPServer(httpOpts, engine, ready)
```

`_example/bald` 与 `_example/bald-gin` 结构完全一致，仅装配方式不同（前者用 appkit 编排 HTTP/gRPC 双协议）。

## 6. 约定与建议

1. **路由注册在用户侧**：不要在框架层集中登记路由；业务直接写 gin 路由。
2. **Handler 保持引擎无关**：不要在 handler 里引用 `*gin.Context` 等具体类型（参数用 `*T` 指针，返回 `R`/`error`）。
3. **路径参数用 `uri` tag**：`HandleUriRequest` 依赖 gin 原生 `ShouldBindUri`，字段需标注 `uri:"xxx"`。
4. **多源参数用 `HandleAllRequest`**：URI → Query → JSON 后者覆盖前者，`Defaulter.Default()` 在所有绑定后执行，校验器放最后。
5. **错误使用 `pkg/berrors`**：返回带 `Reason` 的业务错误即可被 `ErrorResponse` 还原为统一的 `{code, message}` 与正确状态码。

---

## 7. HTTP 层选型决策声明（P4）

**决策：HTTP 入口层（`pkg/web` + 路由注册）选用 gin 为默认实现，是 bald 的有意为之的选型，非暂时妥协。**

- `pkg/server` 的 `HTTPServer` 仍封装标准库 `net/http`（底座零框架耦合，见《服务端设计》决策 ③）；
  而**业务处理流水线**（`pkg/web` 的「绑定 / 校验 / 响应」）直接消费 `*gin.Context`。
- 取舍理由：gin 是成熟主流、性能优异、生态完备的 Go Web 框架；`pkg/web` 只负责参数绑定与统一响应，
  路由注册仍交给业务直接用 gin 编写（约定 1），框架不侵入路由组织。
- **不**为支持多 Web 框架（echo/fiber 等）抽象出 `web.Context` 接口层——这会引入过度设计，
  且当前无第二框架需求。若未来确有诉求，再以适配器模式接入，不影响现有契约。
- gRPC / grpc-gateway 侧通过 `pkg/server.GatewayServer` 复用同一 biz 层，REST 与 gRPC 共享校验与错误模型，
  故"HTTP 层绑定 gin"不限制 gRPC 生态的接入。
