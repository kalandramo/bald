# bald 路由注册与绑定设计：标准库 ServeMux 之上的 Router 与泛型绑定流水线，业务 Handler 以 ApplyTo 挂载路由，服务器层零改动

> 适用包：`pkg/web`（新增）
> 关联文档：`服务端设计.md`（服务器生命周期抽象，本设计的接入点）、`应用框架设计.md`（AppKit 编排）、`错误模型设计.md`（§4 统一错误响应复用 `pkg/errors`）
> 参考实现：onexstack `pkg/core`、`pkg/binding`；osbuilder 模板 `internal/apiserver/ginserver.go`、`grpcserver.go`、`jobserver.go`、`mqserver/kafkaserver.go`
> Last updated: 2026-08-25
> Status: Accepted

## 摘要

bald 目前的路由是"裸的"：`NewHTTPServer` 只接收一个根 `http.Handler`，业务得自己手写 mux、手写参数解析、手写校验、手写错误响应。我们提议新增 `pkg/web` 包，在标准库 `net/http`（Go 1.22+ 的 `http.ServeMux`）之上提供四样东西：**Router**（分组 + 中间件链）、**Handler 接口**（`Name() + ApplyTo(router, middlewares...)`，业务路由归属业务模块）、**多源绑定**（URI/Query/JSON 依次绑定，最后统一验证）、**泛型处理流水线**（`HandleAllRequest` 等，绑定→默认值→校验→业务→统一响应）。

设计出处是 two places：onexstack 用泛型把"绑定 + 校验 + 业务 + 响应"焊成一条流水线（`pkg/core`），并用 `binding.Bind` 解决"部分填充结构体导致校验失败"的经典坑（`pkg/binding`）；osbuilder 生成的 apiserver 用 `InstallRESTAPI` 挂中间件与版本组、再 `c.Handler.ApplyTo(v1, authMiddlewares...)` 把业务路由绑定到路由组。这两套都是经过真实项目验证的模式，我们照搬到标准库生态上。

**最重要的承诺：服务器层（`pkg/server`）零改动。** `web.Router` 本身实现 `http.Handler`，直接作为根 handler 传给现有 `NewHTTPServer`；gRPC 侧延续现有 register 回调。全部改动是纯增量的新包 + 示例迁移。

## 背景与动机

**现在的 HTTP 路由没有任何组织。** `cmd/bald/main.go` 里业务入口是这么写的：

```go
httpSrv := server.NewHTTPServer(httpOpts, http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
    _, _ = w.Write([]byte("hello from bald http\n"))
}), ready)
```

它只证明了"HTTP 服务能跑起来"。一旦业务要加第二个接口，这段代码立刻撑不住：没有路由分组、没有方法级路由、没有中间件、没有参数绑定、没有统一错误响应。业务方只能自己 `http.NewServeMux`、自己 `json.NewDecoder`、自己手写校验、自己拼错误 JSON——每个接口重复一遍，出错的地方还各不相同。这是"框架底座"最不该留给用户的空白。

**参考实现把这条路走通了。** onexstack 的 `pkg/core` 用泛型定义了一条流水线：

```go
func HandleAllRequest[T any, R any](c *gin.Context, handler Handler[T, R], validators ...Validator[T]) {
    var request T
    if err := ShouldBindAll(c, &request, validators...); err != nil {
        WriteResponse(c, nil, err)
        return
    }
    response, err := handler(c.Request.Context(), &request)
    WriteResponse(c, response, err)
}
```

其中 `ShouldBindAll` 调用 `binding.Bind(c, rq, binding.URI, binding.JSON)`——URI、Query、JSON 依次绑定到同一个结构体，**最后统一校验**，而不是每绑一个字段就校验一次。这是 `pkg/binding` 的动机：如果 Query 绑定失败就立刻校验，部分填充的结构体（比如只绑上了 `page` 还没绑上 `keyword`）会触发假的必填校验错误。顺序（URI→Query→JSON）即优先级，后者覆盖同名前者。

osbuilder 模板 `internal/apiserver/ginserver.go` 展示了路由怎么"注册"到服务器上：

```go
func (c *ServerConfig) InstallRESTAPI(engine *gin.Engine) {
    InstallGenericAPI(engine)          // pprof / metrics / 404
    engine.GET("/healthz", c.Handler.Healthz)
    v1 := engine.Group("/v1")          // 版本路由组

    authMiddlewares := []gin.HandlerFunc{mw.AuthnMiddleware(c.Retriever), mw.AuthzMiddleware(c.Authz)}
    c.Handler.ApplyTo(v1, authMiddlewares...)   // 业务路由挂到版本组，认证作为路由级中间件
}
```

它回答了"路由注册"的一个关键问题：**路由不该集中在某张"全局路由表"里，而应该由业务模块自己通过 `ApplyTo` 挂载。** 每个 handler 结构体负责自己的路由，服务器装配层只负责创建版本组、把认证中间件传进去。同样，grpcserver.go 的 register 回调、jobserver/kafkaserver 的 worker 注册，都是同一个思想：**"注册/装配"与"具体路由"分离。**

一句话给问题定性：bald 缺一个"路由该在哪注册、请求该怎么绑、响应该怎么写"的约定，而这套约定必须长在标准库生态上，不能逼用户换 Web 框架。

## 设计

从最小的一块讲起：Router。它足够回答"HTTP 路由在哪注册"；然后逐层加中间件、绑定、泛型流水线；最后展示它怎么接进现有服务器、以及 gRPC 侧怎么做。

### 1. Router：标准库 ServeMux 之上的分组路由器

Router 是对 `http.ServeMux` 的极薄封装，只加两样 ServeMux 没有的东西：**分组**和**中间件链**。

```go
package web

type Middleware func(next http.Handler) http.Handler

type Router struct {
    mux         *http.ServeMux
    middlewares []Middleware
}

// NewRouter 创建一个根路由器。
func NewRouter(middlewares ...Middleware) *Router

// Group 返回带路径前缀 + 中间件链的子路由器（中间件在调用方外->内执行）。
func (r *Router) Group(prefix string, middlewares ...Middleware) *Router

// Handle 注册方法级路由。pattern 遵循 http.ServeMux 的 Go 1.22+ 语法，
// 如 "/v1/users" 或 "/v1/users/{id}"。通配符段可通过 r.PathValue("id") 读取。
func (r *Router) Handle(method, pattern string, handler http.Handler, middlewares ...Middleware)

// HandleFunc 是 Handle 的便捷形式。
func (r *Router) HandleFunc(method, pattern string, h func(http.ResponseWriter, *http.Request), middlewares ...Middleware)

// ServeHTTP 让 *Router 成为合法 http.Handler——这是服务器层零改动的关键。
func (r *Router) ServeHTTP(w http.ResponseWriter, req *http.Request)
```

**边界：**
- `Handle` 的 `method` 支持 `GET` / `POST` / `PUT` / `DELETE` 等，传 `""` 表示匹配所有方法（对应裸 pattern）。
- 中间件在 `ServeHTTP` 时从外到内组装：先挂 Router 级中间件，再挂 Group 级，再挂路由级。同一层内按注册顺序。
- **不与探针冲突**：`NewHTTPServer` 内部把 `/healthz` `/readyz` 注册为精确路径（见 `服务端设计.md`），Router 挂载到 `/` 根路径，精确路径优先匹配，探针永远赢。Router 内若业务自己注册 `/healthz`，标准库会因重复注册 panic——这同样是既有约定，业务不碰这两个路径。

### 2. Handler 接口：路由归属业务模块

```go
// Handler 是业务 HTTP 模块的接口。
// 路由不集中注册，而由每个业务模块在自己的 ApplyTo 里挂载。
type Handler interface {
    Name() string                          // 模块名，用于日志/指标/OpenAPI 标签
    ApplyTo(r *Router, middlewares ...Middleware) error
}
```

用法与 osbuilder 模板对齐——业务模块自己持有路由：

```go
type userHandler struct{ biz *biz.UserBiz }

func (h *userHandler) Name() string { return "user" }

func (h *userHandler) ApplyTo(r *web.Router, authn ...web.Middleware) error {
    v1 := r.Group("/v1/users", authn...)     // 认证中间件从装配层注入
    v1.HandleFunc(http.MethodGet, "/{id}", core.HandleJSONRequest(h.Get, ...))
    // 或更常见：v1.HandleFunc(http.MethodPost, "", core.HandleJSONRequest(h.Create, ...))
    return nil
}
```

装配层（对应 osbuilder 的 `InstallRESTAPI`，bald 侧就是 main.go 或一个 `NewRouter` 组装函数）：

```go
router := web.NewRouter(web.Recovery(), web.RequestID(), mw.Cors(web.DefaultCorsConfig()), web.Secure())
router.HandleFunc(http.MethodPost, "/login", core.HandleJSONRequest(c.Handler.Login, ...))

authMiddlewares := []web.Middleware{mw.AuthnMiddleware(retriever), mw.AuthzMiddleware(authz)}
_ = c.Handler.ApplyTo(router, authMiddlewares...)   // 业务模块挂载自己的路由
```

**为什么路由不该集中注册**，见 Rationale 决策③。

### 3. 多源绑定 + 统一验证

绑定是请求到结构的映射。onexstack 的教训是：**URI/Query/JSON 依次绑定到同一个结构体，最后统一校验**，避免部分填充触发假校验错误。

```go
// Binder 把请求的一部分绑定到 obj。
type Binder func(r *http.Request, obj any) error

// 内置 Binder：按顺序调用，后者覆盖同名前者（URI > Query > JSON）。
var (
    URI   Binder // 从 r.PathValue 读取，绑定 {id} 等通配符段
    Query Binder // 从 r.URL.Query() 读取
    JSON  Binder // 从 r.Body 读取（Content-Type: application/json）
)

// Bind 执行多源绑定 + 可选校验。
// validators 在绑定完成后统一执行，绝不中途校验。
func Bind[T any](r *http.Request, obj *T, binders []Binder, validators ...Validator[T]) error
```

绑定语义细节：
- JSON 绑定用标准库 `encoding/json` + `DisallowUnknownFields`？**不**。onexstack 选择宽容（允许未知字段，方便前后端演进）。bald 默认宽容，需要严格时可另传 strict binder。
- Query/URI 绑定支持结构体 tag：`json:"page"` 优先，否则用字段名（小写首字母）。Query 值可空，空的直接忽略（不覆盖已绑定的值）。
- **默认值**：若 `obj` 实现 `interface{ Default() }`，绑定完成后调用 `Default()`（参考 `core.FinalizeRequest`）。
- 校验函数 `Validator[T]`：`func(ctx context.Context, obj *T) error`，顺序执行，首个错误即返回。内置最小校验器用 `net/mail`、`net/url` 等标准库判断；需要 `go-playground/validator` 这类重武器的项目可自写一个适配 validator 的闭包——**bald 不内置第三方校验库**（见 Rationale 决策⑤）。

### 4. 泛型处理流水线 + 统一响应

绑定、校验、业务、响应这条链路，每个接口都手写一遍会重复到令人发指。我们照抄 onexstack 的泛型方案，只把 `*gin.Context` 换成标准库签名：

```go
// Handler 是业务处理函数。
type Handler[T any, R any] func(ctx context.Context, req *T) (R, error)

// Validator 是校验函数。
type Validator[T any] func(ctx context.Context, obj *T) error

// HandleAllRequest：URI + Query + JSON 全绑，统一校验，业务，统一响应。
func HandleAllRequest[T any, R any](w http.ResponseWriter, r *http.Request, handler Handler[T, R], validators ...Validator[T])

// HandleJSONRequest / HandleQueryRequest / HandleUriRequest：单源快捷函数。
func HandleJSONRequest[T any, R any](w http.ResponseWriter, r *http.Request, handler Handler[T, R], validators ...Validator[T])

// WriteResponse：成功直接写 data；失败写统一 ErrorResponse 并映射 HTTP 状态码。
func WriteResponse(w http.ResponseWriter, data any, err error)
```

错误响应沿用 onexstack 的约定：

```go
type ErrorResponse struct {
    Reason   string            `json:"reason,omitempty"`
    Message  string            `json:"message,omitempty"`
    Metadata map[string]string `json:"metadata,omitempty"`
}
```

**状态码怎么来？** 结构化错误独立在 `pkg/errors`（见 `错误模型设计.md`），web 层不重复定义 `Error`，只保留一个判定约定：

```go
// StatusCoder 是 web 层与错误模型的唯一契约：
// 实现了 StatusCode() 的错误自己决定 HTTP 状态码，未实现的统一 500。
type StatusCoder interface { StatusCode() int }
```

- 业务返回 `pkg/errors` 的工厂函数或 `New` 构造的 `*errors.Error`（其 `StatusCode()` = `CodeToHTTP(code)`），`WriteResponse` 直接写出对应状态码 + `ErrorResponse`。
- 与 gRPC/Kratos 桥接走 `pkg/errors/grpcerr`（`ToStatus`/`FromStatus`，含 `errdetails.ErrorInfo`），保证 Kratos 服务间错误语义透传（bald 的 gRPC 侧本就是 Kratos 风格）。
- **边界**：`WriteResponse` 不负责业务错误分类——`StatusCoder` 接口（`StatusCode() int`）就是全部约定，谁实现了谁决定状态码。默认 500。

### 5. 服务器侧接入：Router 即 http.Handler，服务器零改动

`web.Router` 实现了 `http.Handler`，所以直接塞进现有的 `NewHTTPServer`：

```go
router := web.NewRouter(web.Recovery(), web.RequestID())
_ = handler.ApplyTo(router)                       // 业务挂载
httpSrv := server.NewHTTPServer(httpOpts, router, ready)   // 与今天完全相同的构造签名
```

`pkg/server` 一行不改：探针、TLS、动态端口、优雅停机全部照旧。这是本设计最重要的兼容性承诺，见 Compatibility。

### 6. gRPC 路由注册：延续 register 回调

gRPC 的路由"注册"本质是 `pb.RegisterXXXServer(s, impl)`，现有 `NewGRPCServerWithRegister` 的 register 回调已经够用：

```go
grpcSrv := server.NewGRPCServerWithRegister(grpcOpts, nil, func(s *grpc.Server) {
    pb.RegisterUserServiceServer(s, grpcHandler)   // 业务 service 在此注册
}, ready)
```

本设计只补两样，都不改 server 包签名：
- **拦截器链 helper**：提供 `web` 之外的 `pkg/grpcmw`（或直接建议业务用 kratos/grpc 生态的拦截器），组装 RequestID、日志、recovery、OTel——与 osbuilder grpcserver.go 的链式拦截器对齐。server 包本身**不强制**挂拦截器，保持透明。
- **多协议复用（可选实践）**：HTTP handler 与 gRPC handler 共享 `biz` 层（onexstack 的分层：handler 薄、biz 厚），两份 handler 只做协议翻译。这不是新代码，是一条**参考约定**——先有 biz 再有双端 handler。

> 设计边界：gateway（grpc-gateway 反代）维持 `服务端设计.md` 现状——gateway 的 handler 注册仍走 register 回调，本设计不介入。

### 7. 改造前 vs 改造后对照

| | 今天（main.go） | 引入 pkg/web 后 |
|---|---|---|
| 路由组织 | 一个写死的 `http.HandlerFunc` | `Router` + 版本组 + 各模块 `ApplyTo` |
| 新增接口 | 手写 mux / 手写解析 / 手写响应 | 模块内一行 `HandleFunc` + 泛型流水线 |
| 认证 | 无 | 路由级中间件注入（`ApplyTo(v1, authn, authz)`） |
| 参数绑定 | 无 | `HandleAllRequest` 自动 URI/Query/JSON 绑定 |
| 校验 | 无 | `Validator[T]` + `Default()` |
| 错误响应 | 各写各的 | `WriteResponse` 统一 `ErrorResponse` |
| 服务器层 | `NewHTTPServer(opts, handler, ready)` | 签名不变，handler 换成 `*web.Router` |

## 理由与取舍

**决策①：为什么是标准库 ServeMux，而不是 gin / httprouter / gorilla-mux / 自研 trie / go-lulu 式 Driver 抽象？**
`服务端设计.md` 决策③已经确立 bald 的底座哲学：不绑定任何 Web 框架，业务可以传任意 `http.Handler`。`pkg/web` 延续同一承诺——我们用 `http.ServeMux`（Go 1.22+ 的 method+pattern 语法），它原生支持 `GET /v1/users/{id}` 与 `r.PathValue("id")`，REST 路由所需的能力都有了。**我们没选 gin**，因为引入 gin 等于把整个框架拴在 gin 的 `Context` 上，违反底座中立；**没选 httprouter/gorilla-mux**，因为它们是第三方依赖、维护状态不一，而 ServeMux 是标准库（bald go.mod 已是 Go 1.26.5，语法全部可用）；**没选自研 trie**，因为 ServeMux 已覆盖 95% 需求，自研只带来性能和代码量负担，属于过早优化；**也没选 go-lulu 式的 Driver 抽象**（`Driver` 接口 = `Handle/HandlePrefix/Start/Stop`，可插拔 chi/gin/fiber 驱动）——该方案在早期评审中被否决：可换引擎的能力对 bald 当前"标准库定位"阶段是 YAGNI，约 150 行抽象 + 一层间接换不来实际收益。等真出现"必须换引擎"的诉求时，再造 `Driver` 不迟，届时 `Router` 的 `Handle(method, pattern, ...)` 签名正是天然适配点。

**决策②：为什么要有 Router，而不直接用 ServeMux？**
ServeMux 没有中间件、没有分组，只有"一个 pattern 一个 handler"。Router 是极薄封装：`Group` 管前缀 + 中间件，`Handle` 管方法路由，`ServeHTTP` 组装链。不引入新的路由匹配算法、不改变 ServeMux 的匹配语义——它只是"组合层"。

**决策③：为什么路由归属业务模块（ApplyTo），而不是集中路由表？**
osbuilder 模板的答案是 ApplyTo，我们沿用。集中路由表（main.go 里一把 `mux.Handle` 全登记）在小项目没问题，模块一多就变成"谁都能改所有人的路由"，模块间的路由在同一个文件里互相纠缠。`ApplyTo` 把"路由属于谁"画清楚：user handler 的路由在 user handler 里，auth 中间件由装配层注入（权限边界不落在业务模块手里）。代价是"路由在哪"不再是单一文件可见——用 `Name()` 打日志/指标缓解，且这符合"模块自包含"的 Go 惯例。

**决策④：为什么多源绑定 + 统一验证，而不是逐字段手动解析，也不是一绑一验？**
逐字段手动解析是最朴素的做法，被否决：每接口 20 行样板，且极易漏绑、漏校验。一绑一验（绑 Query 就立刻验）被 onexstack `pkg/binding` 明确否决：部分填充的结构体（只绑了 `page`、还没绑 `keyword`）会让"必填"校验误报。统一验证（绑定全部完成后跑 validators）才是正确顺序——我们照搬这个结论。

**决策⑤：为什么内置最小校验，而不是内置 go-playground/validator？**
onexstack 靠 gin 的 validator，我们不想为"校验"引入重依赖。标准库的 `net/mail`（邮箱）、`net/url`、`strconv`（数值）已覆盖常见校验；业务要 tag 驱动校验（`validate:"required"`）时，写一个闭包把 `go-playground/validator` 适配成 `Validator[T]` 即可——这是业务的自选，不是底座的责任。

**决策⑥：为什么服务器层零改动是硬约束？**
`pkg/server` 是 bald 的心脏（探针、TLS、动态端口、优雅停机，见 `服务端设计.md`），任何改动都牵一发动全身。而 Router 实现 `http.Handler` 让接入成本为零：不用改 `NewHTTPServer`、不用改 AppKit、不用改服务注册。这条约束不是"方便"，是**风险管理**——把路由能力独立成新包，坏了只影响 `pkg/web`，绝不动生命周期逻辑。

**决策⑦：gRPC 侧为什么只加 helper、不改 register 回调？**
`NewGRPCServerWithRegister` 的 register 回调已经能注册任意 service，接口足够。我们不动它，只补拦截器链 helper 与"biz 共享"的参考约定。被放弃的：给 gRPC 也造一个 `ApplyTo` 式的抽象——gRPC 的路由是编译期生成的 `pb.RegisterXXX`，没有"运行期路由"问题，强行抽象是过度设计。

## 兼容性

**这是纯增量变更，无破坏。** 具体承诺：

1. `pkg/server` API 一字不改，`NewHTTPServer(opts, handler, readiness)` 的 `handler` 参数本来就是 `http.Handler`，`*web.Router` 直接替换。
2. 现有 `cmd/bald/main.go` 用 `http.HandlerFunc` 的方式**继续可用**，迁移是自愿的（见下）。
3. gRPC register 回调、gateway、AppKit、服务注册全部不受影响。
4. 依赖：仅新增 `pkg/web` 内部代码，使用标准库 + 现有依赖；结构化错误复用 `pkg/errors`（见 `错误模型设计.md`），不新增第三方依赖。

**迁移路径**：分两步走。
- 第一步（示例先行）：在 `cmd/bald` 增加一个基于 `pkg/web` 的示例接口（如 `GET /v1/version`），与现有写死 handler 并存——HTTP 服务器只能有一个根 handler，因此让 Router 包住旧的 `http.HandlerFunc` 即可（`router.HandleFunc("", "/", oldHandler)`），一行都不破坏。
- 第二步（业务自选）：真实业务把各模块改造成 `Handler.ApplyTo` 模式，按模块逐个迁移，每迁一个模块验证一个模块。Router 与裸 ServeMux 混用不受限——它们都只是 `http.Handler`。

**已知代价（诚实列出）：**
- ServeMux 的路由性能不如专用 trie，但对 bald 面向的服务规模（微服务内部 API）可忽略。
- `pkg/web` 提供的是"约定 + 最小工具"，不包含 gin 级全家桶（自动 `X-Forwarded-*`、multipart 表单处理、模板渲染）。需要时业务自选库，Router 不挡路。

### B. FAQ

**为什么叫 `Handler` 接口而不是 `Controller` / `Service`？** 与 onexstack/osbuilder 模板的既有命名对齐；`Handler` 强调"处理 HTTP 请求"这一层职责，`biz` 层才是业务逻辑。

**和 Kratos 的 `transport.Server` 是什么关系？** 无关。Kratos 管服务生命周期，`pkg/web` 管单协议的请求路由与绑定。bald 的 server 层已兼容 Kratos（见 `服务端设计.md`），`pkg/web` 在其之上。

**业务已经是 gin/fiber 怎么办？** Router 是 `http.Handler`，gin 的 `engine` 也是 `http.Handler`——两者可在同一服务器内以不同前缀共存（Router 挂 `/v1`，gin 挂 `/legacy`），不需要一次性迁移。
