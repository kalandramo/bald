## §1 第二轮的问题清单

第一轮（P0–P9，见《[架构演进路线](./架构演进路线.md)》）解决了「进程级」的编排正确性：并发启停、
优雅停机、崩溃级联、防重入、动态端点注册。但**组件级（进程内）的可组合性**仍是空白：

| 缺口 | 现象 | 根因 |
|---|---|---|
| **全局写入不可逆** | `store.RegisterTenant` / `audit.SetAuditor` / `log.SetLogger` 等对共享环境的写入没有逆操作记录，覆盖即丢弃旧值 | 注册是无返回值的单向操作 |
| **依赖缺失到运行时才炸** | `go-bald-admin` M8：`issueToken` 在 `InitBridges` 之前调用 → Signer nil panic | 组件互相依赖时不声明、不解析 |
| **进程内基础设施散装** | trace provider / metrics exporter / 审计后端连接靠「Setup + 手工 BeforeStop flush」，忘挂就丢数据 | 无统一生命周期抽象 |
| **运行期无法变更** | 组件一旦装配即固定，管理面热插拔、agent 工具挂载无原语 | 装配期与运行期语义混同 |
| **配置变更全量重载** | `OnConfigChange` 是单一全量回调，「哪些 key 变了」的 diff 责任推给每个业务 | 无细粒度订阅 |
| **期望态无法收敛** | 部分失败 / 乱序变更留下中间态，业务回调要自己兜底 | 事件驱动模型缺收敛性 |

**第二节（P10–A1）的目标**：把 dsh/Cordis 的「时空可组合性」在 Go 中落地为**五组原语**——
T1（效应账本）、S1（能力声明）、C1（组件生命周期）、A1（运行期挂载）、R1（配置增量协调）。

> **参照系**：Cordis 论文的「时间可组合性」（注册/卸载的逆序对称）与「空间可组合性」（服务作用域树）。
> bald 的翻译是**有取舍的子集**：不做运行时 dlopen（Go `plugin` 包不可卸载、不支持 Windows），
> 只做进程内可逆注册。取舍论证见《[架构演进路线](./架构演进路线.md)》§0 与 01-需求文档 1.3。

## §2 分层可逆性：装配期 vs 运行期

第二轮所有原语共享一条纪律——**可逆性分层**（对齐 dsh 的核心不可逆 / 扩展可逆）：

| 层次 | 时机 | 语义 | 犯错后果 | API |
|---|---|---|---|---|
| **装配层** | `New` / `FromBootstrap` 构造期 | 不可逆；重名**报错不覆盖** | 装配笔误应 fail-fast（panic 合理） | `Registry.Register` / `MustRegister` |
| **运行层** | `Run` 存活期 | 可逆；返回 `undo` 闭包（幂等） | 运行期变更必须可回滚 | `Registry.Mount` / `AppKit.MountComponent` |

依据落点：`pkg/appkit/mount.go:1-20` 文件头（「装配期 Register（不可逆、冲突报错）的
**运行期对偶**——可逆挂载、undo 幂等。两个语义必须分开：装配期错误应 fail-fast，运行期变更必须可回滚」）。

## §3 四组原语：T1 / S1 / C1 / A1 + P10 / R1-2 / P12

### 3.1 T1 · 效应账本（Effect Ledger）

**问题**：全局注册点（`store.RegisterTenant` / `audit.SetAuditor` / `log.SetLogger`）是不可逆效应——
对共享环境的写入没有逆操作记录，覆盖即丢弃旧值。后果：e2e 测试全局污染、重复注册语义靠约定。

**设计**（`pkg/appkit/effect.go`）：

```go
// 装配期登记逆操作
func Effect(name string, undo func(ctx context.Context) error) Option

// 运行期登记（构造产物与注册同时刻入账，避免「构造成功但注册失败」的窗口泄漏）
func (a *AppKit) addEffect(name string, undo func(ctx context.Context) error)

// 逆序回放（LIFO），幂等（回放后清空账本）
func (a *AppKit) UndoEffects(parent context.Context)
```

**契约**（由 `effect_test.go` 固化）：
- 逆序执行——后注册的先撤销，与依赖建立顺序对称；
- 每条 undo **独立超时**（`EffectTimeout`，默认 `defaultHookTimeout` = 5s，见 `types.go:7`）；
- undo **panic 被隔离**（经 `runHook` 的 recover），不拖垮其余撤销与整机停机；
- 回放**幂等**：执行后账本清空，重复调用无副作用。

**时序**：`stopAll` 阶段 0 最先回放（`appkit.go:572`），先于一切停机钩子；
启动失败路径（loadConfig / Resolve / beforeStart / startComponents / waitForEndpoints / register / afterStart）
也各自回滚账本。

### 3.2 S1 · 能力声明（Capability Declaration）

**问题**：`go-bald-admin` M8——`issueToken` 在 `InitBridges` 之前调用 → Signer nil panic。
依赖缺失要到运行时第 N 个请求才炸。

**设计**（`pkg/appkit/capability.go`）：

```go
func Provides(caps ...string) Option                          // 声明本进程将提供的能力
func Requires(component string, caps ...string) Option        // 声明组件依赖的能力
func (a *AppKit) Resolve() error                              // 启动早期校验，缺依赖 fail-fast
```

**校验规则**（`capability.go:52`）：① 所有 Requires 被 Provides 覆盖（缺失**聚合报错**，一次列全，`sort.Strings` 稳定输出）；
② Provides 无重复声明；③ 能力名/组件名非空。

**边界**：能力是**纯声明符号**，不做实例管理（那是 C1 的职责）——Resolve 只校验装配一致性，为 C1/R1 的组件图打底。

**调用时机**：`Run` 启动早期自动调用（配置加载后、beforeStart 前，`appkit.go:450`）。

### 3.3 C1 · 组件生命周期（Component）

**问题**：trace provider / metrics exporter / 审计后端 / 缓存连接池等进程内基础设施此前是**散装全局**
（Setup + 手工 BeforeStop flush），忘挂 BeforeStop 就丢数据（M9：trace 退出前必须 shutdown 否则丢尾批 span）。

**设计**（`pkg/appkit/component.go`）：

```go
type Component interface {
    Name() string
    Start(ctx context.Context) error    // 顺序 Start（注册序 = 依赖建立序）
    Dispose(ctx context.Context) error  // 逆序 Dispose（停机对称），幂等
}
func ComponentFunc(name string, dispose func(context.Context) error) Component  // 纯清理函数适配
func Components(comps ...Component) Option
func ComponentTimeout(d time.Duration) Option
```

**语义**：
- `Component` 是 `transport.Server` 的广义化——**Server = Component + Endpoint**；
- 与 servers 一起纳入 appkit 编排：`startComponents`（`component.go:80`）在 beforeStart 之后、servers 之前顺序启动；
- `disposeComponents`（`component.go:99`）在 stopAll 阶段 4、AfterStop 之后逆序 Dispose；
- **panic 隔离 + 独立超时**——单个组件失败仅记日志，不中断其余销毁（旁路语义，与审计/效应撤销一致）；
- **幂等**：`disposed` 置位后直接返回。

**与 T1 的分工**：账本管**全局注册表的逆操作**（低级、细粒度），组件管**实例生命周期**（高级、结构化）。

### 3.4 A1 · 运行期可逆挂载（Runtime Mount）

**设计**（`pkg/appkit/mount.go`）：

```go
// Registry[T]：装配期 Register 的运行期对偶
func (r *Registry[T]) Mount(name string, impl T) (undo func(), err error)  // undo 幂等
func (r *Registry[T]) Unmount(name string) (T, bool)

// AppKit：运行期组件热插拔
func (a *AppKit) MountComponent(ctx context.Context, c Component) error    // Start + 纳入停机序列
func (a *AppKit) UnmountComponent(ctx context.Context, name string) error  // 移除 + 立即 Dispose（LIFO）
func (a *AppKit) ListComponents() []string
```

**竞态闭环**（`mount.go:94`）：组件系统停机销毁（阶段 4）开始后**拒绝**新挂载；若销毁与挂载并发竞争，
挂载方的 `Start` 会随之**回滚 Dispose**——保证「挂载失败 = 无副作用」。

**审计**：每次 mount/unmount 发一条审计事件（`Object: "component"`，`Subject` 取 ctx 中 `AuthClaims`），
**旁路不阻断**（§6.2 自修改审计原语）。

**详见** §6。

### 3.5 P10 · Bundle 门面（横切关注点链序固化）

**问题**：`pkg/middleware/gin` 的中间件与 grpc 拦截器此前**全部散装手挂**，正确链序只写在文档与坑清单里
（原话：「正确链序只活在文档里……是当前最大的『隐性知识税』」）。

**设计**：`pkg/middleware/bundle` 一次构造、双传输产出，链序由框架固化。

| 面 | 链序（由 `bundle_test.go` 固化） |
|---|---|
| gin | Recovery → RequestID → Logging → CORS → Secure → Authn → Audit → Authz（未注入层省略） |
| gRPC | Error → Recovery → RequestID → Observability → Authn → Audit → Authz（Error 最外层收口，Recovery 第二外层） |

**关键约束**：Audit 夹在 Authn/Authz 之间——Authn 内侧读 subject/tenant，Authz 外侧捕 deny/error；
Authn 失败由 Authn 层显式发审计留痕（D3 盲区补偿）。

**详见**《[Bald 中间件设计](./Bald%20中间件设计.md)》。

### 3.6 R1-2 · 期望态 diff-apply 协调

**问题**：R1-1（`OnKeyChange`）是**事件驱动**——框架告诉你「key 从 A 变 B」，业务自己决定怎么响应。
连续变更/部分失败/乱序会留下中间态，业务回调要自己兜底。

**设计**（`pkg/appkit/reconcile.go`）：R1-2 是**状态驱动**——业务只声明「期望是什么样」，
框架拿期望态与实际态做差集，只增/删/改差异部分，反复执行直到收敛（对齐 Kubernetes declarative reconcile）。

```go
func Reconcile(name string, fn ReconcileFunc) Option
func DiffStrings(want, have []string) (add, remove []string)   // 期望/实际集合 diff 工具

type ReconcileCtx struct {
    Settings map[string]any   // 期望态快照（只读）
    Name     string
    // 实际态查询/操作：
    // Mounted() []string / Has(name) bool / Mount(ctx, name, c) error / Unmount(ctx, name) error
}
```

**核心差异是收敛性**：状态模型下每次协调都重读两边再 diff，**失败不回滚、下次重试自然补齐**
（K8s controller 挂了重启也能继续收敛）。

**触发**：启动收敛期（`loadConfig` 基线后、AfterStart 前）+ 每次配置变更（keywatch 分发后）。
单协调器失败仅记日志（隔离），错误留审计痕迹。

### 3.7 P12 · 代码生成（`gen app` + AppSpec 方言）

**第一步**（`internal/codegen/app.go`）：`gen app <name>` 模板生成器——产出的装配骨架集成
T1 效应账本、S1 能力声明、C1 组件、R1 key 订阅、P10 bundle 接线。

**第二步**（`internal/codegen/appspec_gen.go`）：`gen app --spec appspec.json` 以 **AppSpec proto 方言**
（`bconf/proto/bald/appspec/v1`）驱动生成——servers / 组件 / 能力声明 / 审计协调按 AppSpec 真实接线，
而非模板占位。AppSpec 是应用装配的**单一真相源**。

**装配纪律**（`appspec_gen.go:19`）：对照 `kalandramo/bald-admin` M10 形状修正。

**工具归属**：`cmd/bald` 是官方 CLI（`P4/P12 工具链归属落地`，见 `cmd/bald/main.go:1`）。

## §5 R1-1 · key 级配置订阅

**问题**：`OnConfigChange` 是全量回调——配置任何变更都触发，业务在其中重新 Unmarshal；
「哪些变了」的 diff 责任推给每个业务。

**设计**（`pkg/appkit/keywatch.go`）：`OnKeyChange(key, fn)`——只有订阅的 key 新旧值确实不同才触发。

**语义**（由 `keywatch_test.go` 固化）：
- 启动时以**首次加载值为基线**（首次变更前不触发，`armed` 置位前只建快照）；
- 仅当新值 `!=` 旧值才触发（同值刷新不触发）；
- 与 `OnConfigChange` **共存**：先跑全量回调，再分发 key 订阅，最后跑 R1-2 协调（`wrapKeyWatch`）；
- 未开启 watch 时永不触发；
- 锁内串行分发（同一 watcher 的 fn 不并发）。

## §6 A1 深化：运行期挂载与自修改审计

### 6.1 挂载原语

见 §3.4。要点：`MountComponent` 立即 `Start` 并纳入停机序列（stopAll 阶段 4 逆序 Dispose，顺序 = 挂载序）。

### 6.2 自修改审计

运行期重组（mount / unmount / reconcile）**天然一条审计事件**——这是「自修改审计原语」：

```go
AuditEvent{
    Object: "component",   // 或 "reconciler"
    Action: "mount" / "unmount" / "reconcile",
    Subject: <ctx 中的 AuthClaims.Subject>,
    TenantID: <ctx 中的 AuthClaims.TenantID>,
}
```

**旁路不阻断**：`auditComponent` / `auditReconcile` 均 `defer recover()`，
Auditor panic/错误仅记日志，**绝不阻断挂载/卸载本身**（与审计中间件 `recordSafely` 同一纪律）。

**Sink 单一解析**（D4）：`resolveAuditor` 顺序为「显式注入（`Auditor` Option）→ 全局 `audit.GetAuditor()`（默认 nop）」
——消除「bundle 注入 a、appkit 走全局」的 split-brain sink。

**管理面用法**：handler 传入带认证的 request ctx 即自动携带 subject，无需额外传参。
