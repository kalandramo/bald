# bald 架构优化路线（第二轮）

> 前情：《[架构演进路线](./架构演进路线.md)》P0–P9 已落地（P9 = 授权归一化 `pkg/authz/normalize.go` + `AuthzOption` resolver 模式，由 go-bald-admin M6.8 CR Issue4 反哺）。
> 本文是第二轮优化的完整结论，外部输入有二：
> 1. **GoWind 框架设计哲学对比**（gowind.cloud，`tx7do/go-wind` 生态：积木式架构 / 分层职责 / 零外部依赖）；
> 2. **论文《A Programming Paradigm for Spatiotemporal Composability》**（arXiv:2608.25512，北京大学 + DeepSeek-AI，Cordis 元框架与 DeepSeek Harness 的形式化基础，经 Koishi 4000+ 插件四年生产验证）。
>
> 核心判断：**bald 的坑几乎全是「装配期错误」（链序、注入顺序、命名空间归一化），而不是「运行时错误」**。第二轮优化的方向因此不是学 GoWind 做成可替换积木，而是——**把「正确的装配」从文档知识和纪律约定，变成框架的结构保证**；并在组件级补齐进程级已经具备的可组合性。

## 1. 两份外部输入的要点

### 1.1 GoWind 对比：同一问题的正交解

| 维度 | GoWind | bald |
|------|--------|------|
| 定位 | 一盒积木（生态型） | 固执己见（融合型，AGENT.md） |
| 核心体量 | < 500 行，仅依赖 `golang.org/x/sync` | `pkg/` 十余包，13 个直接依赖 |
| 接口策略 | 全领域最小接口 + 插件（100+ 适配器） | 领域边界接口化（`Auditor`/`Authorizer`/`Recorder`/`Registrar`），技术栈焊死（gin/viper/slog） |
| 装配 | YAML 声明式 + SPI `init()` 自注册（「零代码组装」） | Go Options + appkit 显式拼装 |
| 配置真相源 | YAML | proto（单一真相源） |
| 传输 | 22+ 协议广度抽象 | HTTP/gRPC/gateway 三件套语义深度对齐（berrors 双栈、P9 归一化、审计链序） |

逐条哲学兑现度：**组合优于继承**两者一致；**接口优于实现** bald 在领域边界兑现、技术栈层面有意背离（opinionated 的价值）；**零外部依赖** bald 刻意反着做（`berrors` 仅标准库、otel 仅 API、grpc-gateway 不进核心——依赖面靠纪律控制而非清零）；**零隐藏魔法** 各有张力（GoWind 的 SPI blank-import 注册是隐式副作用，bald 的 `SetLogger`/`SetAuditor` 是显式全局但违例诚实）。

**结论**：GoWind 把选择权留给业务，bald 替业务做好选择并验证到底。两者是同一问题（微服务框架可维护性）的正交解，非竞品。bald 可借鉴的是三点：contrib 生态的可持续供给（→ P11）、声明式装配的开发体验（→ P12/R1，但用 proto+codegen 而非运行时 YAML 保编译期检查）、插件独立 module 按需引入（已采用）。

### 1.2 Cordis 论文：时空可组合性

论文把「动态组合」拆为两个正交维度，并将静态分析工具（效应系统 / 共效应系统）**提升为运行时机制**：

- **时间可组合性（temporal）**：组件卸载时对共享环境的每一处修改必须被完整撤销，系统回到干净状态——「卸载零残骸」。传统插件系统恰恰栽在这里（注册处理器、补丁全局、写入状态，卸载后一地残骸）。
- **空间可组合性（spatial）**：组件必须能声明、发现、解析彼此依赖；替换一段代码要能安全传播到依赖图上相连的一切，而不是悄悄弄坏依赖方（论文的 VSCode 案例：Top100 扩展仅 7 个声明依赖；禁用扩展须重启宿主进程）。

对应机制：**可逆效应**（经框架上下文的每次写入自动生成逆操作 `dispose`，卸载时逆序回放）+ **响应式共效应**（`ctx.set`/`ctx.get` 声明提供/需要的能力，依赖变化触发激活/停用而非报错）。Cordis 三层：核心库（效应追踪 + 生命周期状态机）→ 组件加载器（声明式配置 + 增量协调 + HMR）→ 领域层。DeepSeek Harness 在其上实现「万物皆插件」（连 agent-loop 都是插件）与 self-modification（agent 运行中挂载/卸载自己的能力）。

## 2. 诊断：用论文语言重新审视 bald 的坑清单

把既有坑（见 `docs/devel/zh-CN/` 各设计与 CR 记录）放到论文框架下，**全部命中两类失效**：

| bald 现状 | 论文语言 | 证据 |
|-----------|----------|------|
| `SetLogger` / `SetAuditor` / `RegisterTenant` / `RegisterStoreProvider` 是纯全局写入，覆盖即丢弃旧值 | **不可逆效应**：对共享环境的写入无逆操作记录 | `pkg/store/tenant.go:40` 仅 map 写入，无 `Unregister`；`pkg/log/global.go:12`、`pkg/audit/global.go:11` 同构 |
| InitBridges 装配顺序坑：`issueToken` 依赖 `bootstrappkg.Signer`，须在 `InitBridges` 之后调用，初版顺序反致 nil panic | **共效应失效**：依赖未声明、未解析，运行时第 N 个请求才炸 | go-bald-admin M8 踩坑记录 |
| 中间件/拦截器链序（Error 最外、Authn→Audit→Authz）靠文档与纪律手挂 | **空间组合靠纪律不靠结构** | gRPC 审计链序坑：Audit 放最外层读到空 subject |
| `traceShutdownFn` 手动塞 `BeforeStop` flush 尾批 span，忘了挂就丢批 | **手工 dispose**：有 Dispose 语义但无统一契约 | go-bald-admin M9 trace 段 |
| P0 三阶段停机、`Deregister` 先于 `Server.Stop` | **进程级 temporal 已解决**；组件级（进程内）完全缺失 | `pkg/appkit/appkit.go:432-438`（`stopAll` 三阶段，仅覆盖 servers + 钩子） |

**判断**：Go 长驻服务退出频率低，所以组件级可组合性缺口平时不痛，但它在三处持续放血——**e2e 测试全局污染**（全局注册项跨用例泄漏）、**配置热更新无法传播**（`WatchConfigFile` 只回调不重组）、**管理面变更不可回滚**。这正是 T1/S1/C1/R1 的靶子。

## 3. 优化项详述

### P10 — 横切关注点 Bundle（S1 的第一子集）

**现状**：`pkg/middleware/gin` 13 个中间件与 grpc 对应拦截器全部散装手挂，正确链序只活在文档里——坑清单中 2 条即链序，是当前最大的「隐性知识税」。

**目标**：一个门面一次构造、双传输产出、链序固化：

```go
b := bundle.New(
    bundle.Authn(authenticator),                       // 依赖实例经构造器注入（顺带减少全局依赖）
    bundle.Authz(authorizer, bundle.WithGRPCDefaults()), // 内置 P9 归一化默认 resolver
    bundle.Audit(auditor, bundle.WithMetrics(rec)),
)
router.Use(b.Gin()...)                    // gin 链序由框架保证
grpcSrv := server.NewGRPCServerWithRegister(opts, b.GRPCChain(), reg, ready)
```

**要点**：
- 固化链序契约：gin 侧 `Recovery → RequestID → Logging → Authn → Audit → Authz → ...`；gRPC 侧 `Error（最外）→ Authn → Audit → Authz`（Error 必须最外层调 `grpcerr.ToStatus`，否则 `*berrors.Error` 兜底成空 Unknown；Audit 在 Authn 内侧才能读到 subject/tenant、在 Authz 外侧才能捕获 deny/error 最终 result）。
- P9 归一化默认就配好（`WithGRPCDefaults` 内接 `authz.DefaultGRPCObject/Action`），Issue4 类双命名空间回归从结构上杜绝。
- 依赖（Authenticator/Authorizer/Auditor/Recorder）走构造器注入，`SetAuditor` 等全局退化为兜底路径（`pkg/audit/audit.go:11` 本就设计了双路径）。
- **零破坏**：散装手挂路径保留，bundle 只是预组装。

**产出**：`pkg/middleware/bundle` + 装配层测试 + go-bald-admin 改接 bundle 验证。

**代价/风险**：一个新包 + 测试；低，纯增量。

### P11 — contrib 晋升管道（制度化「反哺」）

**现状**：`contrib/` 仅 `authn-jwt`、`store-gorm`（后者已是独立 go.mod，模式已验证）。而 go-bald-admin 的 `internal/cache/redis`、`internal/security/casbin`、`internal/observability/{metrics,trace}` 都是**事实上的 contrib**——下个项目要么重写要么复制。

**目标**：收编三件套为独立 module：

| 范例 internal | 晋升为 | 内容 |
|---------------|--------|------|
| `internal/cache/redis` | `contrib/cache-redis` | Cache-Aside（键含租户），`Client()` 暴露底层连接 |
| `internal/security/casbin` | `contrib/authz-casbin` | 纯 Enforce 桥接（归一化在核心，勿重复） |
| `internal/observability/{metrics,trace}` | `contrib/observability-otlp` | Prometheus + OTLP 双通道 Setup，单一 `OTLP_ADDR` 开关 |

范例改 import 验证零改动可用。此后规则固化：**internal 桥接存活过两个里程碑 → 晋升 contrib**（照 `bald-store-gorm` 模式：实现核心抽象、独立 go.mod、单向依赖核心、传输中立不泄漏引擎类型，见《架构演进路线》§0.5.2 桥接契约）。

**价值**：bald 相对 GoWind 插件生态的追赶方式——不拼数量，拼「被验证过」。

**代价/风险**：抽包 + import 改动 + 各 module 版本管理；低。

### T1 — 效应账本（appkit 从「钩子集合」升级为「可逆操作台账」）

论文的效应追踪 = 所有经框架上下文的写入自动生成逆操作。bald 的最小可行版本，**不动现有 API**：

```go
// 登记逆操作：Stop 时在 BeforeStop 之前逆序执行全部 undo
appkit.Effect("tenant-registration", func(ctx context.Context) error {
    store.UnregisterTenant("tenant_id")
    return nil
})
```

**进阶**：`RegisterTenant` / `SetAuditor` / `RegisterStoreProvider` 的重复注册不再覆盖而是登记 `(旧值, 新值, undo)` 三元组，账本逆序回放即恢复启动前状态。

**收益**：
1. **e2e 测试隔离**：`t.Cleanup` 挂一次账本回放，全局状态归零——直接解决大量 e2e 并行/顺序执行的污染问题（对 bald 自身开发节奏立即变现）。
2. `InitBridges` 幂等性这类约定不再需要——重复注册被账本语义自然处理。

**代价/风险**：`pkg/appkit` 增量 + 各全局注册点补 `Unregister` 对偶；低，纯增量。

### S1 — 能力声明与解析（共效应，fail-fast）

论文的 `ctx.set`/`ctx.get` 对偶到 bald：bundle/contrib 组件声明 `Provides`/`Requires`，appkit 启动期做**拓扑排序 + 缺依赖 fail-fast**：

```go
bundle.Audit(auditor).Requires("db")   // 审计落库需要 DB 就绪
appkit.Resolve()                        // 启动期报 "component audit requires capability 'db', not provided"
```

**价值**：把「Signer 必须在 InitBridges 之后调用」这类**运行时炸弹变成启动期一行清晰错误**——论文「替换能安全传播」的反面保障：缺失能被结构化发现而非静默 nil。

**与 P10 关系**：P10（bundle）是 S1 的第一子集（bundle 是横切关注点的空间组合单元）；S1 是 P10 的泛化（任意 contrib 组件均可声明）。

**代价/风险**：能力键命名约定 + 解析器；中低。

### C1 — Server ⊂ Component：组件统一生命周期

论文「万物皆插件」在 bald 的可翻译子集：**`server.Server` 只是带 `Endpoint()` 的广义组件**。当前 M9 的 trace provider、metrics exporter、StreamAuditor（有 goroutine 要收）、审计 DB、cache pool——全是散装全局 + 手工 `BeforeStop`。统一为：

```go
type Component interface {
    Start(ctx context.Context) error
    Dispose(ctx context.Context) error   // 论文语言的「逆操作」
}
appkit.Components(traceProvider, metricsExporter, streamAuditor)
// 停机顺序按依赖图（logger 最后死）；三阶段停机泛化为组件通用
```

**价值**：「trace 退出前必须 shutdown 否则丢批」从文档知识变成结构保证；与 P0 天然融合（`stopAll` 泛化，而不仅 servers 专用）。

**代价/风险**：与现有 `Server` 契约的兼容层（`Server` 可视为 `Component` + `Endpoint`）；中低。

### P12 — AppSpec + 装配 codegen（拓扑真相源：静态半边）

**现状**：proto-first 只覆盖**配置**（Bootstrap proto），应用**拓扑**（起哪些 server、挂哪些 bundle、注册什么 provider）仍是手写 main.go 的复制粘贴。

**目标**：扩展 proto 定义 `AppSpec`（servers 列表 + 中间件开关 + contrib 绑定），P4 codegen CLI 生成装配骨架：

```
app.proto → bald codegen → main.go（appkit.New(Servers(...), Registrar(...)) + bundle 装配 + config 绑定）
```

**定位**：对 GoWind「YAML 即拓扑」的**同目标反解**——GoWind 用运行时 YAML+SPI 换灵活性（代价：组装逻辑逃出编译期检查）；bald 用 proto+codegen 换编译期类型安全（代价：改拓扑要重新生成）。后者更贴 proto 单一真相源哲学。

**分两步**：先生成 config 绑定代码（低风险），再生成 server/bundle 装配。生成物应短小、只做装配不含逻辑。

**代价/风险**：高（codegen 维护负担）；放后。

**设计细化（2026-08-31 固化，待模板实践沉淀后落地）**：
- **第一步修正**：P4 CLI（`_example/bald/codegen`）已有 `gen proto`/`gen store`，第一步扩展为 `gen app <name>`——生成 `cmd/<name>/main.go` **装配模板**（appkit.New 标准选项块：Name/Version/ConfigFile/Servers 占位 + `Provides/Requires` 能力声明 + `ComponentFunc` 组件占位 + `OnKeyChange` 示例 + bundle 接线注释）。这比「AppSpec proto 方言」轻一个量级：模板生成先覆盖 80% 脚手架价值，proto 方言（完整拓扑声明 + 编译期校验）作为第二步。
- **暂不落地的理由**（照 P11「存活两个里程碑再晋升」规则）：① 生成模板的「最佳实践内容」刚在 go-bald-admin 沉淀（S1/C1/R1 本日才落地），应先让模板内容在真实项目中验证一个里程碑，再固化进生成器——否则生成器固化的是未经验证的形状；② P4 CLI 位于 `_example` module（example module 验证路径），`gen app` 提升为核心子命令还是独立工具涉及工具链归属决策，需独立评估；③ P12 生成物的热绑定语义依赖 R1（本日落地），先让 R1 稳定。

### R1 — 配置增量协调（运行时半边）

论文组件加载器的杀手锏不是 HMR 本身，是**增量协调**：配置变化只更新有变动的部分。bald 已有 `WatchConfigFile`/`OnConfigChange`，缺的是期望态 vs 实际态 diff-apply：

- 热切换 auditor 后端（日志 → DB+Stream，走 `MultiAuditor` 重组）；
- 热更新日志级别、casbin 策略、OTLP endpoint；
- **细粒度订阅**：只有订阅了变化 key 的组件收到回调，而非全量 reload。

**Go 的边界**：编译语言做不了代码级 HMR（`plugin` 包 cgo 限定、不支持 Windows、生产不可靠），**但配置态重组是完整可行的子集**。P12（静态）+ R1（运行时）合起来才是论文「声明式配置→组件树→增量协调」的完整翻译。

**前置**：C1（组件化是可协调的前提）。

**落地记录（2026-08-31，第一子集：key 级细粒度订阅）**：`pkg/appkit/keywatch.go` 提供 `OnKeyChange(key, fn(old, new))` Option——配置变更时仅当订阅 key 的新旧值确实不同才触发（同值刷新不触发、未订阅 key 变更不波及），与 `OnConfigChange` 全量回调共存（先全量后分发）。基线在 `loadConfig` 完成时以首次加载值建立；分发串行于锁内（同一 watcher 不并发、顺序与变更一致）。并发语义与 `OnConfigChange` 同级：fn 应轻量（改状态/切引用/记日志），不得调用 config 重载/注入类操作。契约测试 6 个：diff 触发、同值不触发、多 key 独立、与全量回调共存、连续变更按序（old=上次 new）、基线不触发。go-bald-admin 演示接入：`OnKeyChange("http.addr", ...)` 定点观测与全量 reload 互补。

**落地记录（2026-09-02，第二子集：期望态 diff-apply 协调）**：`pkg/appkit/reconcile.go` 提供 Kubernetes controller 语义的协调循环：
- `AppKit.Reconcile(name string, fn func(ctx, *ReconcileCtx) error) Option`：声明一个以 `name`（配置键）为标识的协调器；框架在**启动收敛期**（`loadConfig` 基线后、AfterStart 前，`runReconcilers(gctx, cfg.v)`）与**每次配置变更**（keywatch 分发后 `runReconcilers(Background, v)`）两个阶段自动调用。
- `ReconcileCtx`：携带 `Viper *viper.Viper`（当前配置快照）、`Name string`（协调器名）、`app *AppKit`，并暴露组件实际态查询/操作原语 `Mounted() []string` / `Has(name)` / `Mount(ctx, name, c)` / `Unmount(ctx, name)`（基于 A1 的 `Registry.Mount/Unmount` 与 `AppKit.MountComponent/UnmountComponent`）。
- `runReconcilers` 遍历协调器，构建 `ReconcileCtx` 调 `fn`，发重组审计 `AuditEvent{Object:"reconciler", Action:收敛/错误}`；并发由 `reconMu` 保护 `reconItems`（协调器名→组件列表），`ReconcileCtx` 的方法是并发安全的。
- `DiffStrings(want, have)` 工具函数（导出）做期望/实际集合 diff，返回 `add`/`remove`，供协调函数做**幂等 diff-apply**（期望==实际直接早退，不抖动）。
- 语义对齐论文「增量协调」：期望态写在配置，框架只更新有变动的部分；部分失败留中间态，下一次协调补全（controller 自愈）。
- 契约测试 8 个（reconcile_test.go，race-clean）：收敛到期望态、幂等、移除多余、部分失败后收敛、启动期应用初始配置、审计事件、DiffStrings、ParseStringList。

**go-bald-admin 集成范例（R1-2 端到端）**：`cmd/.../main.go` 中 `reconcileAudit` 协调器以配置键 `audit.backends`（逗号/空格分隔 `log|store|stream`）为期望态：
- 旧静态装配（`BeforeStart` 里直接 `audit.SetAuditor(MultiAuditor)`）已移除——单一事实来源收敛到配置键，避免「配置与代码两处声明」。
- **逐后端粒度 diff-apply（非整体重建）**：协调器以 `rctx.Mounted()`（本协调器经 `ReconcileCtx.Mount/Unmount` 维护的实际态）为「实际态」、以 `audit.backends` 为「期望态」做 `DiffStrings`；`add` 的逐后端 `rctx.Mount(ctx, name, &auditBackendComponent{name, build})`、`remove` 的逐后端 `rctx.Unmount(ctx, name)`。每个 `auditBackendComponent` 在 `Start` 时把自身 `audit.Auditor` 注册进共享 `reconAuditors` 表并刷新全局 `MultiAuditor`、`Dispose` 时注销——**只变动差异部分**，完整兑现论文增量协调语义。`build` 延迟构造依赖 `InitBridges` 后的 DB/Redis（未就绪返回 nil → 该后端跳过，旁路语义绝不阻断）。
- `configs/go-bald-admin.yaml` 新增 `audit.backends: "store,stream"`；运行期改此键经 `WatchConfigFile`→`OnConfigChange`→keywatch→`runReconcilers` 自动热切审计后端组合，无需重启。
- 范例测试（reconcile_audit_test.go）：后端列表解析（去重/过滤）、log 挂载收敛、幂等二次收敛（不重复挂载）、期望置空卸载退回 nop。

## 4. 明确不做的（防漂移清单）

比学什么更重要的是不学什么。任何后续 P/T/S/C/R 项若触碰下表，视为破坏定位：

| 诱惑 | 不做的理由 |
|------|-----------|
| 抽象可换 HTTP 栈（GoWind 式 transport 插件） | 会毁掉 `pkg/web` 强绑定 gin 的泛型流水线深度——opinionated 的价值就在选好了 |
| 运行时 YAML 拓扑解析 | 丢编译期检查；P12 codegen 已达成同目标且更贴 proto-first |
| 追 22+ 协议广度 | 无场景；HTTP/gRPC/gateway 三件套的语义对齐深度是护城河 |
| Go 动态加载 / HMR | 编译语言认命（`plugin` 包不可靠），只做配置态重组（R1） |
| 形式化元定理 | Go 表达不了效应类型演算；bald 的「元定理」就是既有文化——BUG-1/3/4 式**契约回归测试**。实现操作规则 + 测试固化即可 |
| 彻底消灭全局状态 | otel 全局是 Go 生态惯例，显式注入点可控（audit 已双路径）；追求的是「可逆」而非「无全局」 |
| 通用元框架化 | Cordis 是 meta-framework 不碰领域，bald 的护城河是 opinionated 深度。**吸收机制，不改定位** |
| 万物皆插件教条 | bald 的 blessed stack（gin/gRPC 语义对齐）恰恰依赖「不可换」；论文的完整一般性（88 页证明 + 四年生产验证）非 bald 场景所需 |

## 6. agent-native 能力扩展（论文最前沿方向的 Go 对偶）

论文终局是 **self-modification**：agent 运行中检查、挂载、修改自己的插件（DeepSeek Harness 的 `self-modification` 包）。bald 的对偶不是让服务自己改自己，而是把 bald 升级为 **Go 侧 agent harness 底座**：

1. **可逆工具注册表**：P1 泛型 `Registry[T]` 升级——agent 运行时挂载/卸载工具，每次变更经 T1 效应账本，卸载自动撤销全部注册（时间可组合性直接复用）。
2. **自修改审计**：agent 给自己加工具 = 一次运行时重组 = 天然一条 `AuditEvent{Object:"tool", Action:"mount", Subject:agent-id}`——五支柱中的审计直接覆盖 self-modification 追踪，这是 DeepSeek Harness 没有的现成能力。
3. **管理面 API**：admin endpoint 做能力开关/策略热切换，所有变更走账本可回滚，失败一键恢复到重组前。

**落地记录（2026-08-31，A1 最小前置原语）**：`pkg/appkit/mount.go` 提供三层原语——
- `Registry[T].Mount/Unmount`：装配期 `Register`（不可逆，`init()` 自注册语义，错误应 panic）的**运行期对偶**——可逆挂载、undo 幂等（`sync.Once`）、同名冲突报错不覆盖。两个语义分开的原因：装配期错误要 fail-fast，运行期变更要可回滚。
- `AppKit.MountComponent/UnmountComponent`：C1 组件生命周期扩展到运行期——挂载即 Start 并纳入 stopAll 阶段 4 停机序列（此后正常逆序 Dispose），卸载即移除并立即 Dispose（LIFO）；`ListComponents()` 供观测。竞态闭环：`disposed` 标志（startedMu 锁内）保证组件系统销毁后拒绝新挂载，且与销毁并发竞争时自动回滚挂载方的 Start（挂载失败=无副作用）；`ErrNotRunning` 守卫 Run 存活期。
- **重组审计**：mount/unmount 自动发 `AuditEvent{Object:"component", Action:"mount"/"unmount", Subject:ctx.AuthClaims, Meta:{component}}`——Subject 经 `AuthClaimsFromContext` 自动携带管理面身份；panic/错误隔离（recordSafely 同纪律）。

契约测试 8 个：undo 幂等、Register/Mount 互斥冲突、卸载缺失安全、ErrNotRunning 守卫、运行期挂载/卸载生命周期顺序（`AfterStart` 内 mount→unmount→停机仅销毁存量）、挂载失败不入列、审计事件形状（三元组+Meta+Subject）、Auditor panic 隔离。

**剩余**（复绪条件已由 M10 达成，2026-09-01）：admin HTTP 端点与 R1 期望态 diff-apply 均已随 M10 落地（见下；R1-2 逐组件 diff-apply 见 §3 R1）。远期 agent-native 编排（可逆工具注册表 + 自修改审计）待独立实践里程碑再推进。

> **M10 落地（2026-09-01）**：go-bald-admin 已接入——bundle 等价替换（gin 全局层 + gRPC 全链）、管理面端点（`/admin/components` GET/POST/DELETE，authn+authz 保护，`demo.heartbeat` 组件演示 goroutine 生命周期）、并修复真实装配时序 bug（`RegisterRoutes` 传构造期 nil Authenticator → gin 认证空操作，`LazyAuthenticator` 请求期解析根治）。e2e 4 用例验证挂载/卸载全链与权限边界。管理面实践里程碑达成，R1 期望态 diff-apply 复绪条件满足。

**定位**：「被验证的运行时可重组服务框架」——这是 bald 相对 GoWind、乃至相对多数 Go 框架的差异化赛道。
