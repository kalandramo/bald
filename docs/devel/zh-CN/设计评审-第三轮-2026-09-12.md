### C2 [高] FromBootstrap 文档停机链序表述错误（行为-文档矛盾）
**`docs/devel/zh-CN/AppKit FromBootstrap 约定装配.md:165`**：「servers→registrar→database→cache→storage→ai→workflow→broker——逆序回放时服务器先 drain，**broker 最后关**……数据库仍保持最后关闭之外的最晚次序」。

实际（bootstrap.go Effect 注册行号 421-519 + effect.go:71 逆序回放 `for i := len-1; i >= 0; i--`）：

```
注册序：tracer(421)→metrics(427)→logger(441)→registrar(448)→database(454)
        →cache(460)→storage(466)→ai(472)→workflow(478)→broker(484)
        →config-layers(513)→servers(519)
回放序：servers→config→broker→workflow→ai→storage→cache→database
        →registrar→logger→metrics→tracer
```

- 「broker 最后关」**错误**：broker 是第 3 个关（servers、config 之后）。
- 「数据库最晚次序」**错误**：database 第 8 个关，registrar/logger/metrics/tracer 都比它晚。
- **代码行为是正确的**（依赖对称拆除：broker 依赖 database，先拆依赖方再拆被依赖方；tracer/metrics flush 最后保证尾批数据不丢）——文档表述把「注册序最后」误写成「关闭最后」，且与「逆序回放」自相矛盾。
**修法**：按实际回放序重写该段。

## 三、R 系：三原则发现

### R1 [中，DRY] gin/grpc 可观测性平行实现（E5 遗留，第二轮未动）
两份 observability.go 的常量块/TraceInjectionMode/Option/matchWildcard/injectTrace 仍逐行重复（今晚 SpanKind 修复又改了两份，重复税已实缴）。**修法**：抽 `pkg/middleware/shared`（传输无关 `InjectTrace(mode, traceID, spanID, spanCtx, set)`）。规模中，收益「改一处两处生效」。
**本轮决策**：进遗留清单（合并属结构性重构，独立 PR 执行）。
**已完成（批 I，2026-09-12）**：`pkg/middleware/shared` 落地——header 常量、`TraceInjectionMode`、`InjectTrace(mode, customHeader, spanCtx, set)`（回调落点：gin 直传 `c.Header`，gRPC 传 `md.Set` 单值闭包）、`MatchWildcard` 收敛一处；gin/grpc 两侧以**类型别名 + 常量别名**维持既有导出 API 稳定（零 breaking）。传输特有部分（span 起法/日志结构/跳过语义——gin 的 method 前缀 pattern 与路径前缀匹配、grpc 的 matchMethod）留在各侧。契约测试钉住：`InjectTrace` 四模式 × 采样位 × 自定义 header × 无效 spanCtx 不注入、`MatchWildcard` 通配矩阵。`Option`/`WithLogger`/`resolveLogger` 因选项结构体字段差异（SkipPaths vs SkipMethods）保持各侧——共享需引入泛型体操，收益不抵复杂度。

### R2 [低，DRY] appkit 错误包裹串两处重复（E11 收尾）
`component.go:77` 与 `mount.go:102` 完全相同的 `fmt.Errorf("appkit: component %q start: %w", ...)`。**本轮修**：抽 `wrapComponentStartErr`。

### R3 [中，DRY/三次原则] Registry 家族 9 处同构样板
database/cache/storage/ai/workflow/broker/registrar/tracer/metrics 九个 Registry：`mu + providers map + Register + MustRegister + Build` 同构（subagent 任务 1 输出缺失，以人工走读补录）。重复次数已远超三次原则阈值，**但**：①key 语义有差异（单选 type vs 多段并存 vs 带默认值缺省）；②样板各自 ~80 行、独立可测；③泛型基座会引入 `Registry[K, V]` + provider 接口适配层，复杂度转移而非消除。
**按本轮核心准则裁定**：用户侧只见 `New + MustRegister + Build` 三行，样板复杂度被封装在用户视野之外——**内部复杂度可接受，不抽**。三次原则的适用对象是「用户可见的重复概念」而非「内部样板行数」。维持现状，进遗留观察。
