# Bald 设计判据

> 本文收编**跨模块复用的裁决原则**。各设计文档在做出「保留 / 删除 / 收敛 / fail-closed」类决定时引用本文条目（格式 `见《设计判据》#N`），不再各自复述理由。
>
> 判据不是历史记录：它们是**当前有效的决策工具**，新代码应按此判断，已落地的实现可在源码注释与测试中找到对应形态。

## 判据总表

| # | 判据 | 一句话 | 典型落点 |
|---|---|---|---|
| J1 | 零调用不是删除依据 | 导出能力零调用 ≠ 死代码；**缺测试才是问题** | `cache/*`、`encoding.Names()`、`circuitbreaker/*` |
| J2 | 重复税 | 同一不变量两处各自实现 → 抽单一真相源 | `pkg/middleware/shared`、`store.shouldIsolate`、`viewer.EnforceTenant` |
| J3 | 出站客户端必须设默认超时 | 「随调用方 ctx」不等于安全 | `workflow/argo`、`ai/eino` |
| J4 | 身份不完整即 fail-closed | 非平台、非系统且租户为空 → 拒绝，不猜测 | `viewer.EnforceTenant`、`crudbridge` 数据范围 |
| J5 | 显式声明，不基于空值推断 | 平台身份必须显式标记，不从 `TenantID == ""` 推断 | `contextx.WithPlatform`、`SimpleViewer.Platform` |
| J6 | 协议实现只承诺协议形状 | 传输层不认识健康检查等业务语义 | `transport/http`·`grpc`·`gateway` |
| J7 | 未实现配置段 fail-fast | 声明了契约却无实现的段，静默丢弃是缺陷 | `segment_coverage.go` 的 `checkSegmentCoverage` |
| J8 | 契约只为已实现的东西承诺形状 | 不预留「将来也许」的字段 | `bootstrapv1` 契约段 |

---

## J1 · 框架能力零调用不是删除依据

多个独立 module（缓存四后端、熔断四实现、`encoding.Names()`）在仓内**没有生产调用点**。这不构成删除理由：框架提供的是**能力面**，消费者可以在下游出现。

| 状态 | 裁决 |
|---|---|
| 零调用 **且** 有测试钉住行为 | **保留**——合法的诊断/文档能力面 |
| 零调用 **且** 无测试 | **补契约测试**（不是删除） |

「能力已备、消费者未至」是框架常态；真实风险是无测试覆盖导致静默腐烂。

**注意与死代码的区别**：未导出符号、无调用且无测试的**内部**代码仍应删除；J1 只保护**导出 API 面**。

## J2 · 重复税

同一不变量在两处各自实现，迟早只修一处。**修法不是「记得修两处」，而是抽成单一闸门**，让第二处没有独立实现可改。

已落地的收敛：

| 收敛点 | 消除的重复 |
|---|---|
| `pkg/middleware/shared` | gin / grpc 两份 `observability.go`（trace header、`TraceInjectionMode`、`injectTrace`） |
| `store.shouldIsolate` | `applyIsolation` 与 `translate` 各自判断平台豁免 |
| `viewer.EnforceTenant` | tenant rule 与 interceptor 各自内联「平台/系统则跳过」判断 |

新代码出现第二份同形判断时，先找闸门，再写逻辑。

## J3 · 出站客户端必须设默认超时

无默认超时的 `http.Client` 会随调用方 ctx 永久挂起：**服务端无响应即挂死，除非调用方恰好取消 ctx**。漏传 ctx 的调用点、未设 deadline 的 goroutine 都是真实挂起路径。

所有出站 HTTP 客户端（`workflow/argo`、`ai/eino`、各 registry/配置源后端）都应显式设置默认超时；调用方 ctx 是**附加约束**，不是超时来源。

## J4 · 身份不完整即 fail-closed

空租户同时可能表示「匿名/未认证」与「平台视图」两种相反语义。**不得靠推断区分**：非平台、非系统上下文且 `TenantID == ""` 一律拒绝（`ErrMissingViewer`），不注入 `tenant_id = ''`。

数据范围翻译同理：身份缺失时返回恒假布尔树，而不是空条件（空条件等于放行全部）。

## J5 · 显式声明，不基于空值推断

需要「跨租户 / 平台级」能力时，由调用方**显式**标记（`contextx.WithPlatform`、`crudbridge.SimpleViewer.Platform`、`WithPlatformLevel`），框架不把任何空值或默认值解释成特权语义。

判据的验证方式：在认证中间件注入身份时，平台标记必须从令牌 claims **透传**；丢弃标记会让平台用户退化为普通租户（安全方向正确），而推断空值会让普通用户变成平台用户（fail-open）。

## J6 · 协议实现只承诺协议形状

传输层负责监听、TLS、`Start`/`Stop`/`Endpoint`、服务注册；健康检查、就绪、业务路由装配归 `health` 与装配层。唯一例外是 gRPC 的 `grpc.health.v1` 标准服务——它是生态系统标配，注册它属于「实现 gRPC 协议」，但仍只注册、不判断。

配套实现见《[Bald 健康检查设计](./Bald%20健康检查设计.md)》§装配。

## J7 · 未实现配置段 fail-fast

契约声明了若干子段，实现只覆盖其中一部分时，**未实现段被静默忽略**是最常见的配置失效方式（用户以为配了，实际没生效）。

装配层对「配置里出现顶层段但无消费者」的情况直接报错（`pkg/appkit/segment_coverage.go` 的 `checkSegmentCoverage`），逃生舱是显式白名单（`WithUnimplementedSegments`）。子段级枚举目前只覆盖 `server` 的非内置子段（同一函数的 `cfg.GetServer()` 分支，`--plan` 的 `SegmentUse` 清单同此范围）；`broker`/`database`/`workflow`/`cache` 的未实现子段在「同域 Provider 顶住顶层段」时会静默——这一格是登记册 §7.28 方向① 尚未收口的缺口，不是本判据已经兑现的面。

## J8 · 契约只为已实现的东西承诺形状

proto 契约里的字段必须有真实消费者；「先占位、将来可能用」的字段会长期误导配置作者。新增字段时应同时落地读取点，或明确标注保留原因。

## J9 · 配置取值只有契约一条通道

一个值如果能从契约之外进来，它就同时躲开了三层合并链、`--plan` 与热更新重算——配置作者看不到它，运维改它也不会有任何回执。**最危险的形态不是「有旁路」而是「旁路比正路更显眼」**：读代码的人按契约找取值来源，找不到，于是把缺陷归给契约。

裁决按「是否在取值链上」分三档，而不是按「是否用了环境变量」：

| 形态 | 裁决 |
|---|---|
| 契约 env 层本体（按键名/前缀读环境，键名由 `BootstrapConfig` 描述符派生） | **正路**，保留；两层各判一种读取形状：按名查与全量枚举 |
| 读环境变量但**不参与取值**（拼 IDE 配置文件路径、集成测试夹具注入后端地址） | **保留并登记理由** |
| 在役的链外输入（能覆盖契约字段，或契约里根本没有对应字段） | **不许静默保留**：接进契约（字段＋映射行＋运行期闸门）或由 owner 裁决其去留；删除属能力删除，需先问 |

同一条判据也管 flag 层，那里量出过一条**在役缺陷（已修）**：全仓唯一的手写 flag 注册器 `bslog.Options.AddFlags` 注册 8 个 `--log.*`，键落在顶层 `log`，而契约段叫 `logger`（其旋钮还在 `repeated logger.backends[i].slog` 下，没有任何等价的标量 flag 路径）⇒ 修复前传入任意 `--log.*` 会被严格契约校验判成未知键并终止启动。它躲不开闸门、也躲不开契约校验，唯一躲开的是「有人试过」。修法取的是第四种，不在上面三档里：flag 值不进合并树，`Bind` 按 `pkg/appkit.LogFlagNames()`（派生自注册器本身，不是手抄清单）把它摘出，再在 `bconf.Validate` 之后、计划编译之前由 `pkg/appkit.ApplyLogFlagOverrides` 写进契约 logger 段，冷启动与热更新同一动作。判据的主句没有因此被削弱——CLI 值是**进入**契约而不是绕过它，运行期取值仍只有契约一个载体：紧随覆盖之后的 `compilePlan` 得到含终值的期望态摘要（reconcile/drift 的基线），Logger 重建与热更新协调读的都是它。两句边界必须一起给：① `--plan` 在任何副作用之前打印、且只投影段名与消费者（实测带不带 `--log.level` 输出逐行相同），所以 CLI 覆盖不出现在 `--plan` 里——那是 `--plan` 的既有语义，不是这条覆盖链的缺口；② proto3 标量无 presence，`--log.rotate.enabled=false` 压不过契约里已置真的值。口径与证据见 §7.39。

这条判据不是纪律口号：环境变量侧 `internal/docscheck.TestEnvironmentVariableRoutesAreRegistered` 用 AST 派生全仓读取点并与登记表双向对账；flag 侧 `bootstrap.TestHandwrittenFlagRoutesLandInContract` 真调注册器取 flag 名、交给运行期同一个谓词 `bconf.FindUnknownKeys` 判落点。两侧同规则——新增未登记的路由判红，登记了却不再被派生的死条目同样判红（后者保证「修好了」也会逼着改登记）。flag 侧另有两条同源判据：`pkg/appkit.TestLogFlagNamesMatchAppliedKeys` 把「摘出合并树的清单」与「覆盖时实际读取的清单」两向对账——两份清单一旦分叉，症状是「flag 解析了却永不生效」，只有对账能拦住；`pkg/appkit/log_flag_overlay_test.go` 判三层（带 flag 时契约与重建入参都是终值／不带 flag 时文件值不动／热更新后 CLI 值仍压过远端快照）。登记册的现值、各条理由与待裁决项见 §7.38、§7.39。
