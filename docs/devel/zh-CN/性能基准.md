# 性能基准

> 批 5 W3 落地。全套 15 项基准（17 个基准函数，含子跑）覆盖 bconf / bootstrap/config / pkg/appkit / contrib/authz-casbin 四个 module，其中 4 项与 v0.24.0 做了同机同口径对照实测，其余为仅基线项（v0.25.0 新模型，无历史版本可比）。所有数字为 go 1.27.1 / windows / amd64 / i5-1345U（12 线程，`-12` 后缀）实测。

## 目的

批 1-4 的重构主要触及装配期（Option/Decl/资源面），运行期路径基本未动——但「基本未动」此前只是代码审查结论，没有数字。本套件给出两个东西：

1. 可长期回归的基准基线：后续任何改动跑一遍 `-bench` 即可与本文档的数字对照；
2. v0.24.0 → v0.25.0 的实测对照：对 API 未断裂的路径给出两版同机数据，证明重构没有引入性能回归（也如实暴露引入了的）。

## 运行命令

```bash
# bconf（对照项所在 module）
cd bconf && go test -run '^$' -bench . -benchmem -count=5 .

# bootstrap/config（remerge / MountEnv）
cd bootstrap && go test -run '^$' -bench . -benchmem -count=5 ./config

# pkg/appkit（根 module，仅触及包）
go test -run '^$' -bench . -benchmem -count=5 ./pkg/appkit

# contrib/authz-casbin
cd contrib/authz-casbin && go test -run '^$' -bench . -benchmem -count=5 .
```

对照方法（v0.24.0 vs HEAD）：

```bash
git worktree add <临时目录> v0.24.0
# 对照基准文件复制进 worktree（bconf/bench_test.go 原样；bootstrap/config 的
# bench_test.go 须去掉 BenchmarkStoreMountEnv——v0.24.0 无此 API）
cd <临时目录>/bconf && go test -run '^$' -bench . -benchmem -count=5 .
git worktree remove <临时目录>
```

两版同一 module 路径，分别进目录跑即可，不改 go.mod。

## 口径

- `b.Loop` 惯用法（go 1.27）；fixture 全部在计时外构造；热路径无 fmt/日志。
- bconf 契约树以 JSON name 规范形书写。`UnmarshalMap` 会把输入树写回规范形（coerceMessage/foldPath），首轮迭代后为稳态——两版同口径，不影响对照。
- 契约树**刻意不含 map<string,string> 字段**：`clearPresentLists` 的 map 字段修复仅落在 HEAD（v0.24.0 同位置仍 panic，见「本波变更」），对照要求两版跑完全相同的树。map 路径由 `TestUnmarshalMap_MapFieldReplace` 单独覆盖。
- 内层授权器一律用真实 casbin 引擎（不用桩）——落证的是「装饰器 + Enforce」全路径。
- 本机为笔记本，连续压测存在明显热漂移（同一基准 5 连跑呈现「先快后慢」的单调漂移，UnmarshalMap 可达 ±35%）。**结论不取单点 ns/op，而以 B/op + allocs/op 的一致性为主证据**（分配剖面不受 CPU 频率影响），ns/op 辅以交替复跑交叉验证。

## 对照实测：v0.24.0 vs v0.25.0

方法：`git worktree add` v0.24.0 → 铺入对照基准（v0.24.0 侧 bench_test.go 去掉 MountEnv 项）→ 两侧 `-count=5 -benchmem` → 交替复跑 3 轮对冲跑序偏置 → `git worktree remove`。

|------|---------------|---------------|--------------|--------------|----------------|------|
| UnmarshalMap_FullContract | 280,700 ± 89,700 | 261,100 ± 98,400 | 28,385 | 28,385 | 808 | 无系统性差异 |

| StoreRemerge_Layers | 14,940 ± 5,700 | 12,260 ± 4,000 | 13,072 | 13,072 | 78 | 无系统性差异 |

### 交替复跑交叉验证（对冲热漂移的跑序偏置，count=1 × 3 轮交替）

| 基准 | v0.24.0（3 轮） | v0.25.0（3 轮） |
|------|------------------|------------------|
| UnmarshalMap_FullContract | 150,454 / 169,200 / 153,827（均值 157,800） | 148,264 / 192,192 / 156,302（均值 165,600） |
| StoreRemerge_Layers | 9,825 / 12,377 / 12,625（均值 11,600） | 10,027 / 10,447 / 17,465（均值 12,600） |

交替轮里两版互有胜负、分布完全重叠；count=5 序列表里 v0.25.0 略「快」纯粹是 v0.25.0 后跑、吃到了各自会话内同款的热漂移相位差，不构成结论。

### 归因分析

- **四项对照全部无系统性回归，铁证是分配剖面逐字节一致**：B/op 与 allocs/op 两版完全相同（UnmarshalMap 28,385 B / 808 allocs；remerge 13,072 B / 78 allocs）。批 1-4 没有触碰这四条运行期路径的任何分配行为——与「重构只动装配期」的代码审查结论互相印证。
- ns/op 的差异全部落在热噪声带内（交替轮互有胜负即可证）。若强行把 count=5 序列表的 ±15% 当回归/优化结论，复跑一次就会反转——不硬凑。
- FindUnknownKeys 每层递归重建 byName 查找表（37 KB / 458 allocs / 全树扫描一次）是当前最大的单点分配来源，两版同构。StrictContract 全量开启时的成本主体即此项；如需优化（缓存字段描述符查找表），属后续独立课题，两版对比不改变其优先级。

### casbin 落证：「Enforce 路径无逐请求分配」的如实结论

该论断**在装饰器层成立、在 casbin 引擎层不成立**：

- 装饰器自身零逐请求分配：Direct 路径（内层放行/出错）在进入任何分配前透传返回（alias.go:86，候选切片仅在明确拒绝后构造）——Direct 的 206 allocs/op 全部来自内层 casbin Enforce。
- casbin 引擎每次 Enforce 有可观分配（本口径下 ≈206 allocs / 8.6 KB，源于表达式求值器逐请求重建匹配闭包）；拒绝路径需扫全部 101 策略行，故 Hit/Miss（两次 Enforce）≈ 1,270 allocs / 41 KB，且 Hit ≈ Miss（重试不放大）。
- 若「请求路径零分配」是设计目标，改进点在引擎层（表达式编译/匹配缓存）而非装饰器；属后续独立课题。

## 复跑指引

1. 命令见上；常规回归用 `-count=5`，快速冒烟用 `-benchtime=1x`（只验证可执行，数字不入档）。
2. 笔记本/共享机上跑数前先空转预热一轮（`-count=1` 丢弃），或用交替复跑对冲热漂移；跨机器数字不可比，只与同机基线比。
3. 新增/修改基准遵守口径段：fixture 计时外、b.Loop、热路径无 fmt/日志、修改运行期路径后同步更新本文档对应行。
4. 对照历史版本时，先确认目标版本的 API 形状（本波 bootstrap/config 对照副本须剔除 MountEnv 项即是先例）。

## 本波变更与遗留

- **新增**：四个 *_bench_test.go（上表 15 项 + 1 个回归测试）；本文档。
- **顺手修 1（任务书内）**：internal/codegen/appspec_gen.go:5 头注「12 个落盘项」→ 13（configs/<app>.yaml 为 Gate2 派生追加项；appspec_budget_test.go 13 行清单为实证），仅注释。
- **顺手修 2（任务书外，基准套件首跑实证）**：bconf/unmarshal.go `clearPresentLists` 对 map 字段 panic——map 字段的 Kind 是合成 entry 消息，此前落入 MessageKind 分支后 `Mutable(fd).Message()` 直接崩；契约里任何非空 `map<string,string>`（tracer.otlp.headers、logger.loki.labels）都会让 UnmarshalMap 崩溃。**v0.24.0 起即存在，无既有测试覆盖**。修复为 map 与 repeated 同取「替换」语义（src 显式给出时 `dst.Clear(fd)`，一行分支），并补 `TestUnmarshalMap_MapFieldReplace` 回归测试。修复使 HEAD 的 UnmarshalMap 比 v0.24.0 多一个 switch 分支——分配剖面零变化（对照表可证），不影响对照有效性。
- **遗留**：FindUnknownKeys 的逐层查找表重建（37 KB/458 allocs 每次）与 casbin 引擎逐请求分配是两个可选的后续优化课题，均已量化，不阻塞本批。
