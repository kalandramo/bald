# 性能基准

> 批 5 W3 落地。全套 15 项基准（17 个基准函数，含子跑）覆盖 bconf / bootstrap/config / pkg/appkit / contrib/authz-casbin 四个 module，其中 4 项与 v0.24.0 做了同机同口径对照实测，其余为仅基线项（v0.25.0 新模型，无历史版本可比）。所有数字为 go 1.27.1 / windows / amd64 / i5-1345U（12 线程，`-12` 后缀）实测。

## 目的

批 1-4 的重构主要触及装配期（Option/Decl/资源面），运行期路径基本未动——但「基本未动」此前只是代码审查结论，没有数字。本套件给出两个东西：

1. 可长期回归的基准基线：后续任何改动跑一遍 `-bench` 即可与本文档的数字对照；
2. v0.24.0 → v0.25.0 的实测对照：对 API 未断裂的路径给出两版同机数据，证明重构没有引入性能回归（也如实暴露引入了的）。

## 口径

- `b.Loop` 惯用法（go 1.27）；fixture 全部在计时外构造；热路径无 fmt/日志。
- bconf 契约树以 JSON name 规范形书写。`UnmarshalMap` 会把输入树写回规范形（coerceMessage/foldPath），首轮迭代后为稳态——两版同口径，不影响对照。
- 契约树**刻意不含 map<string,string> 字段**：`clearPresentLists` 的 map 字段修复仅落在 HEAD（v0.24.0 同位置仍 panic，见「本波变更」），对照要求两版跑完全相同的树。map 路径由 `TestUnmarshalMap_MapFieldReplace` 单独覆盖。
- 内层授权器一律用真实 casbin 引擎（不用桩）——落证的是「装饰器 + Enforce」全路径。
- 本机为笔记本，连续压测存在明显热漂移（同一基准 5 连跑呈现「先快后慢」的单调漂移，UnmarshalMap 可达 ±35%）。**结论不取单点 ns/op，而以 B/op + allocs/op 的一致性为主证据**（分配剖面不受 CPU 频率影响），ns/op 辅以交替复跑交叉验证。

### 归因分析

- **四项对照全部无系统性回归，铁证是分配剖面逐字节一致**：B/op 与 allocs/op 两版完全相同（UnmarshalMap 28,385 B / 808 allocs；remerge 13,072 B / 78 allocs）。批 1-4 没有触碰这四条运行期路径的任何分配行为——与「重构只动装配期」的代码审查结论互相印证。
- ns/op 的差异全部落在热噪声带内（交替轮互有胜负即可证）。若强行把 count=5 序列表的 ±15% 当回归/优化结论，复跑一次就会反转——不硬凑。
- FindUnknownKeys 每层递归重建 byName 查找表（37 KB / 458 allocs / 全树扫描一次）是当前最大的单点分配来源，两版同构。StrictContract 全量开启时的成本主体即此项；如需优化（缓存字段描述符查找表），属后续独立课题，两版对比不改变其优先级。

### casbin 落证：「Enforce 路径无逐请求分配」的如实结论

该论断**在装饰器层成立、在 casbin 引擎层不成立**：

- 装饰器自身零逐请求分配：Direct 路径（内层放行/出错）在进入任何分配前透传返回（alias.go:86，候选切片仅在明确拒绝后构造）——Direct 的 206 allocs/op 全部来自内层 casbin Enforce。
- casbin 引擎每次 Enforce 有可观分配（本口径下 ≈206 allocs / 8.6 KB，源于表达式求值器逐请求重建匹配闭包）；拒绝路径需扫全部 101 策略行，故 Hit/Miss（两次 Enforce）≈ 1,270 allocs / 41 KB，且 Hit ≈ Miss（重试不放大）。
- 若「请求路径零分配」是设计目标，改进点在引擎层（表达式编译/匹配缓存）而非装饰器；属后续独立课题。

## 批 6 第 1 项：casbin 引擎逐请求分配优化（判定缓存）

> 上节「casbin 落证」遗留课题的落地：contrib/authz-casbin 桥层判定结果缓存（enforceCache，cache.go）。API 零变更（NewRows/NewAlias 签名不动），语义零变更（既有白名单测试全过）。

### 调研结论（先查后写）

- **版本升级无收益，不采用**：v2.128.0 → v2.135.0（当时最新）的 enforcer.go 仅 4 行差异（matcherMap 失效钩子 + 自定义 matcher 字面量转义修复），govaluate 同为 v1.3.0，逐请求分配热路径原样未动——升级只承担语义风险、无性能收益。
- **官方 CachedEnforcer 不满足红线，不采用**：其默认缓存 `persist/cache.DefaultCache` 是**无上界 map**（TTL 缺省 -1 即永不过期），不满足「容量有界防膨胀」；键构造走可变参数装箱 + strings.Builder（每次查询先造数笔分配，正是「省了引擎分配、键又造出来」）；且每次缓存读取取**独占写锁**（`locker.Lock()` 而非 RLock），并发 Authorize 全串行化。仅「LoadPolicy 清缓存」一点可取。→ 判定：上游现成能力不足，自研桥层缓存。
- 修正批 5 落证的一处措辞：matcher AST 上游已缓存（enforcer.go matcherMap sync.Map），逐请求重建的是**匹配闭包的参数装载**（GetFunctions 函数表、rTokens/pTokens 令牌表、逐行 Eval 参数装箱），非 AST 本身。

### 实现形态

enforceCache（cache.go）：按 (subject, object, action) 三元组的有界 LRU 判定结果缓存。键即三字段结构体（string 不可变，作 map 键**零分配**；action 取 ToLower 后的值，大小写变体共享判定）。集成点（casbin.go）：

- `Authorize`：先查缓存，命中零引擎调用、零分配（~50-200ns）；未命中照常 RLock + Enforce，**仅缓存 (bool, nil) 结果**——引擎错误永不入缓存，miss 照常评估，fail-closed 不变；
- `Reload`：LoadPolicy 后**无论成败整体失效**（失败时 casbin fail-safe 保留旧策略，失效只是多一次冷启动）——「Reload 后缓存必空」无例外；空策略初始态（无 adapter）Reload 为无操作，不触碰缓存；
- 容量 1,024（`defaultEnforceCacheCapacity`），LRU 逐出，map 尺寸有上界；map 不按容量预分配——LoadPolicy 仅 +3 allocs（cache 结构 + hmap + 链表头，+67B）；
- 并发：单互斥锁、临界区无分配；锁序 a.mu → cache.mu，从不反序嵌套；-race 全绿（含 8 goroutine 判定 × 20 次 Reload 交叉测试）。

### 语义边界与命中率假设

- **命中场景**：同一 (subject, object, action) 重复判定。真实流量形态——同一主体反复访问同一资源是 Web 服务常态（页面刷新、列表轮询、批量操作同资源、别名重试路径的内层重判），这正是缓存生效面；键空间大于容量时 LRU 保住最近活跃工作集。
- **安全边界**：命中返回的是**曾依据当时策略算出的结果**，不是无策略依据的放行；本桥不暴露 AddPolicy 等就地策略变更，策略变更唯一入口是 Reload → 整体失效；失败 Reload 亦失效（fail-safe 下旧策略仍在，判定重新评估结果不变，已测）。
- **失配场景**：策略源在进程外变更且业务不调 Reload（本桥无法感知）——与无缓存时相同：判定不变直到 Reload；缓存不扩大也不缩小这一边界。
- **有界性**：subject 基数爆炸（爬虫/扫描）时 LRU 逐出，内存上界 ≈ 容量 × 条目尺寸（约 1,024 × ~100B ≈ 100KB 量级），不随键空间增长。
