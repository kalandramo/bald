# 性能基准

> 15 项基准（17 个基准函数，含子跑）覆盖 `bconf` / `bootstrap/config` / `pkg/appkit` / `contrib/authz-casbin` 四个 module。本文给出可长期回归的基线数字与测量口径。数字采集环境：go 1.27.1 / windows / amd64 / i5-1345U（12 线程，`-12` 后缀）。

## 目的

装配层改动主要触及装配期（Option/Decl/资源面），运行期路径不应被波及——「不应」需要数字证明。基准套件回答两件事：

1. **回归基线**：任何改动跑一遍 `-bench` 即可与本文档的数字对照；
2. **分配剖面**：B/op 与 allocs/op 不受 CPU 频率影响，是判断「代码行为是否变化」的主证据。

## 运行命令

```bash
cd bconf               && go test -run '^$' -bench . -benchmem -count=5 .
cd bootstrap           && go test -run '^$' -bench . -benchmem -count=5 ./config
                       go test -run '^$' -bench . -benchmem -count=5 ./pkg/appkit
cd contrib/authz-casbin && go test -run '^$' -bench . -benchmem -count=5 .
```

## 测量口径

- `b.Loop` 惯用法；fixture 全部在计时外构造；热路径无 fmt/日志。
- bconf 契约树以 JSON name 规范形书写。`UnmarshalMap` 会把输入树写回规范形，首轮迭代后为稳态。
- 内层授权器一律用真实 casbin 引擎（不用桩）——落证的是「装饰器 + Enforce」全路径。
- 笔记本上连续压测有明显热漂移（同一基准 5 连跑可呈 ±35%，双向交替可达 ±80%）。**结论不取单点 ns/op，而以 B/op + allocs/op 的一致性为主证据**，ns/op 只作量级参考；跨机器数字不可比。
- 修改运行期路径后，同步更新下表的对应行。

### 端到端计时

`TestTree_EndToEndTimed`（`-count=1`）：gen app+domain 0.28s → `go mod tidy` 4.0s → `go build` 30.4s → 起服务到 readyz 200 11.5s → 请求 0.5ms → 优雅退出 0.02s，**T1−T0 ≈ 46s**（热构建缓存口径）。判据 ≤1800s，余量约 39 倍；冷缓存下主要增量在 `go build`，量级仍远低于判据。

## 关键结论

### casbin 的分配在哪一层

「Enforce 路径无逐请求分配」在装饰器层成立、在引擎层不成立：

- 装饰器自身零逐请求分配：Direct 路径（内层放行/出错）在进入任何分配前透传返回，候选切片只在明确拒绝后构造。
- casbin 引擎每次 Enforce 有可观分配（≈206 allocs / 8.6 KB，源于表达式求值器逐请求装载匹配闭包——matcher AST 本身在上游 `matcherMap` 已缓存）。拒绝路径扫全部 101 策略行，故 Hit/Miss（两次 Enforce）≈ 1,270 allocs / 41 KB。
- 桥层 `enforceCache`（`contrib/authz-casbin/cache.go`）按 `(subject, object, action)` 缓存**确定的**判定结果，命中后逐请求分配归零。引擎层若要「零分配」，改进点在表达式编译/匹配缓存，属独立课题。

缓存的安全边界：

- 只缓存 `(bool, nil)`——引擎错误永不入缓存，miss 照常评估，fail-closed 不变；`Reload` 后无论成败整体失效（失败时 casbin fail-safe 保留旧策略，失效只是多一次冷启动）。
- 命中返回的是「曾依据当时策略算出的结果」，策略变更唯一入口是 `Reload`；进程外策略变更且业务不调 Reload 的边界与无缓存时相同。
- 有界 LRU（容量 1,024），内存上界 ≈ 100KB 量级，不随键空间增长；`LoadPolicy` 仅多 3 allocs。

### FindUnknownKeys 的成本构成

原始实现每次扫描逐层重建字段查找表，并给每个键先拼路径串、为取描述符构造 `dynamicpb` 消息。拆解（458 allocs/op）：`dynamicpb` ≈31%、路径串 ≈29%、查找表 ≈27%、`ToLower(输入键)` ≈8%。

现行实现：`fieldLookupCache`（`sync.Map`，描述符 → 小写键名 → 字段描述符）常驻，递归参数直传 `MessageDescriptor`，路径串惰性拼接——稳态降到 95 allocs / 1.6 KiB，剩余都是语义必需（下钻路径串、输入键大小写归一、未知键收集）。缓存值完全由进程内不可变的 proto 描述符派生，无需失效机制；冷启动首建约 400 KB / 1.5k allocs，按「启动 1 次 + 热更 N 次」在 N≈12 后反超旧实现，生产形态（单棵契约树）无膨胀面。

语义由 `TestFindUnknownKeys_Semantics` 钉住：未知键集合与路径逐字节一致（含列表下标与原始大小写）、白名单整树跳过、输入只读、20 次重复与 8 goroutine 并发结果一致（map 迭代序随机下顺序仍确定）。

## 复跑指引

1. 常规回归用 `-count=5`；快速冒烟用 `-benchtime=1x`（只验证可执行，数字不入档）。
2. 笔记本/共享机跑数前先空转预热一轮（`-count=1` 丢弃），或用交替复跑对冲热漂移；只与同机基线比。
3. 对照历史版本时用 `git worktree`：同 module 路径分别进目录跑，不改 `go.mod`；先确认目标版本的基准文件 API 形状（例如旧版本可能缺少新基准调用的 API）。
4. 判定回归以 B/op、allocs/op 为准；ns/op 差异需在交替复跑中方向一致才可采信。

## 局限

1. **笔记本口径**：ns/op 会话内相位漂移实测可达 ±80%，仅量级可用；跨日/跨机一律不可比。
2. **共享机负载**：基准与其他进程同机共存时只对冲了跑序相位，未对冲外来负载；理想口径是静置机器。
3. Defender/搜索索引等不可控变量未关闭。
4. 计时项为热构建缓存口径（冷缓存主要影响 `go build` 段）。
5. 换机后应以新口径重存基线，数字不与本表直接互比。

## CI 现状

`.github/workflows/ci.yml`（push main + PR）：ubuntu-latest，按 `find go.mod` 自动发现模块，循环 build + vet + `go test -short -timeout 5m`。`publish-bconf.yml`：`bconf/v*` tag → buf lint/build/push BSR。**基准目前不在 CI 中**：B/op、allocs/op 在 runner 上是确定性的，可做 `-benchtime=1x` 冒烟或分配剖面报警；ns/op 在共享 runner 上无意义，不建议入档比对。`TestTree_EndToEndTimed` 未加 `testing.Short` 守卫，事实上随 `-short` 在跑，包级 5m 超时对冷缓存 E2E 的余量需要按最近一次 CI 耗时核查。
