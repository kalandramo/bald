# bald 代码生成工具设计（cmd/bald gen：proto/store/app）

> 适用：`cmd/bald`、`internal/codegen`、`api/proto/bald/appspec/v1`
> 关联文档：`架构优化路线.md`（§P12 进度与验收记录）、`架构演进路线.md`（§P4 脚手架最小集由来）、`路由注册与绑定设计.md`（生成物中 `pkg/web` 流水线）、`框架契约总览.md`
> Last updated: 2026-09-02

## 摘要

bald 作为框架库（核心零后端耦合）同时提供**官方开发工具 CLI `cmd/bald`**：`go install github.com/kalandramo/bald/cmd/bald@latest` 即可获得 `gen proto` / `gen store` / `gen app` 三个代码生成子命令，为使用 bald 的新服务生成可编译的 starter 骨架（proto 服务 / 实体 / 应用装配 main.go）。

**最重要的定位：生成器只做装配、不做业务。** 生成物覆盖框架装配形状（servers / capability / 组件生命周期 / 审计协调 / 配置 flag 覆盖），业务路由、handler、gRPC service 注册、wire 注入、管理面一律留 TODO 填充点——业务无法也不应由模板表达（反向生成 go-bald-admin 验证了这一边界）。

代码生成不替代手写业务：生成物是可编译骨架，业务路由/handler/grpc service 注册留 TODO 填充点（见各模板头部注释）。

## 背景与动机

P4 工程化脚手架落地时，bald 需要一个「框架可生成 starter 骨架」的最小验证，CLI 放在 `_example/bald`（示例模块）作为孵化场。P12 把「应用装配」升格为单一 proto 真相源（AppSpec 方言），解决了「模板 + 手填配置键 = 双真相源」问题。此后工具链归属（示例 vs 核心）成为待评估架构债——直到 2026-09-02 落地为 `cmd/bald`。

参考：osbuilder 的嵌入模板脚手架范式（`kubectl` 风格 CLI + PATH 插件发现 `bald-<name>`）。

## 设计

### 1. 工具链归属与分发

```
bald/
├── cmd/bald/main.go        # cobra root（Use: "bald"）+ codegen.NewCommand()
├── internal/codegen/       # 生成器实现（gen.go / app.go / appspec_gen.go + 测试）
├── api/proto/bald/appspec/v1/appspec.proto   # AppSpec 方言（P12）
```

- **放核心 module（而非示例/独立 tools module）**：AppSpec 的 Go 生成代码在核心 `pkg/conf/gen/go/bald/appspec/v1`（同 module），模板直接引用；与框架同版本发布、proto 契约天然对齐。核心 go.mod 仅新增 **cobra**（轻依赖，非后端，不违背零后端耦合纪律）。
- **`internal/codegen` 而非 `pkg/codegen`**：生成器是工具内部实现，不是库公共 API；未来需对外暴露（嵌入业务 CLI）再提升。
- **核心 go.mod 不引入 gin/grpc**：生成物 import gin/grpc/cobra，其编译/运行验证以 `_example/bald` 消费者 module（go.mod 含这些依赖、`replace` 指向核心工作树）为上下文——见 §6 测试策略。

### 2. 三个子命令

| 命令 | 输入 | 输出 | 说明 |
|---|---|---|---|
| `bald gen proto <name>` | 名称 + `--out` + `--go-package` | `api/proto/bald/<name>/v1/<name>.proto` | protobuf 服务骨架文本（含 `PagingRequest`/`FilterExpr` 引用）；`go_package` 默认不写（bald 生态经 buf managed mode 补充） |
| `bald gen store <name>` | 名称 + `--out` + `--out-pkg` | `<name>.go` | 实体骨架（gorm tag + `KeyOf` 提取函数），gofmt 保证可编译 |
| `bald gen app <name>` | 名称 + `--out`（默认 `cmd/<name>/main.go`） | 装配骨架 main.go | 模式一：硬编码模板（含 `[FILL]` 填充点） |
| `bald gen app <name> --spec <AppSpec.json>` | AppSpec（protojson）+ `--out` | AppSpec 方言驱动装配 | 模式二：AppSpec 单一真相源（P12） |

### 3. AppSpec 方言（应用装配的 proto 单一真相源）

```proto
message AppSpec {
  AppMeta meta = 1;                  // name/module/desc（生成标识）
  ServerSpec server = 2;             // http/grpc/gateway + http_addr/grpc_addr
  repeated ComponentSpec components = 3; // kind/name/config_prefix（C1 组件）
  CapabilitySpec capability = 4;     // provides + requires（S1）
  repeated string audit_backends = 5;    // R1-2 审计后端默认期望态
  bool bundle_normalized = 6;        // P9 归一化开关
}
message Requirement { string component = 1; repeated string caps = 2; }
```

**`Requirement` 结构化是关键设计修正**（反向生成 go-bald-admin 时暴露）：S1 的 `appkit.Requires(component, caps...)` 是「组件声明对能力的依赖」对，不是扁平能力名。早期 `requires []string` 生成的 `Requires("db")` 无归属语义（组件名被当成了能力名），既无法表达 `audit.store → db` 的定位关系，也让 S1 fail-fast 失去"缺哪个组件需要的能力"的报错价值。结构化后模板输出 `appkit.Requires("audit.store", "db")`，与手写装配一致。

### 4. 模板装配纪律（审查修复固化的两条 P0）

代码审查曾发现生成物「编译通过但运行即坏」的装配顺序错误，模板现固化为两条纪律（并由防回归测试断言）：

1. **servers 与组件一律经 `appkit.Servers` / `appkit.Components` Option 传给 `New`**——Option 只有 `New` 消费，`New` 之后再 append 无效（servers 永不注册的静默 bug 根源）。
2. **不生成 Run 前调 `MountComponent`**——它要求运行态（`running` 在 `Run` 内才置位），装配期挂载必须走 `Components` Option。

正确形态对照 `examples/go-bald-admin` M10 装配：`appkit.New(capOpts...)` 之前完成全部 Option 组装。

### 5. 生成物骨架边界（业务填充点，非模板缺陷）

模板对以下元素留 TODO（生成器只做装配不做业务）：

| 元素 | 模板形态 | 归属 |
|---|---|---|
| 业务组件工厂（trace/db/redis 等 kind，依赖 contrib/引擎） | `buildComponent` 的 TODO | 业务/contrib 注入 |
| store/stream 审计后端（依赖 DB/Redis 桥接） | `buildAuditBackend` 的 TODO（log 开箱即用） | 业务桥接 |
| bundle 的 Authn/Authz/Metrics 注入 | 注释 TODO（未注入自动省略） | 业务实例 |
| gateway 装配 | 注释 TODO | go-bald-admin 用 gatewayFactory init 注入 |
| Registrar 注册中心、`internal/` 分层、wire、管理面端点 | 不生成 | 业务层 |

### 6. 测试策略

三层防线固化模板质量（防止「编译过但运行即崩」的盲区复发）：

1. **模板渲染锚点断言**：gofmt 必须成功 + 关键原语存在 + **装配顺序断言**（`appkit.New` 在最后一次 `capOpts = append` 之后；生成物不得含 `.MountComponent(` 调用）。
2. **消费者 module 端到端编译**：生成物在 `_example/bald`（独立 module：含 cobra/gin/grpc 依赖 + `replace ../..` 指向核心工作树）内 `go build`——核心 go.mod 保持不引入 gin/grpc。
3. **运行时冒烟**：无传输 server 的生成物真实运行 3s 存活断言（捕获 `ErrNotRunning` 等装配期崩溃）。

`internal/codegen/app_test.go` 的 `exampleModule(t)` helper 负责定位消费者 module 路径（`go test` 的 cwd 恒为包目录，上溯两级到仓库根）。

### 7. 反向生成验证（真实项目里程碑）

为官方范例 `go-bald-admin` 撰写 AppSpec（`_example/bald/_scratch/go-bald-admin.appspec.json`：http+grpc+gateway 声明、heartbeat 组件、`provides: db` + `requires: audit.store→db`、audit log、bundle normalized），`bald gen app --spec` 反向生成骨架，在 go-bald-admin 真实 module（gin/grpc/wire 依赖面）内 `go build` 编译通过——证明 AppSpec 方言能表达真实项目的框架装配形状。模板覆盖度以「真实项目编译通过 + 差距边界文档化」作为 P12 骨架里程碑验收。

## 理由与取舍

**决策①：为什么工具进核心 module 而不是独立 tools module？** AppSpec 生成代码在核心同 module（引用零成本）、与框架同版本（buf 版本与 proto 契约天然对齐）；独立 tools module 要跨 module import + replace + 版本协调。代价是核心 go.mod 引入 cobra——工具性质允许。

**决策②：为什么 `requires` 结构化而不是保持扁平？** 见 §3。扁平 `requires` 把 `appkit.Requires` 的 (component, caps) 语义压成单个字符串，S1 fail-fast 的"哪个组件缺什么能力"报错价值丢失。

**决策③：为什么生成物测试用消费者 module 而非核心 module？** 生成物 import gin/grpc/cobra（生成给用 bald 的服务），核心 go.mod 若为其加这些依赖会污染框架依赖图（P5 纪律）。`_example/bald` 已是现成的消费者依赖面（replace 指向工作树，闭环测试）。

**决策④：为什么 `gen proto` 默认不写 `go_package`？** bald 生态的 proto 生成统一走 buf managed mode（`api/proto/buf.gen.yaml` 的 `go_package_prefix`），模板写死 `go_package` 会与 managed mode 冲突或残留错误的 example 路径。需要独立 protoc 的调用方用 `--go-package` 显式指定。

**决策⑤：为什么模板留业务 TODO 而不是全自动？** 生成器的价值在"装配骨架 + 最佳实践示范"（每个原语带注释），业务（handler/wire/组件工厂/管理面）无法 proto 化也不应由框架替业务决定。全自动会让模板与业务耦合，违背框架"只做装配"的定位。

## 兼容性

纯增量：新增 `cmd/bald`、`internal/codegen` 与 AppSpec proto（`Requirement` 为同字段号新增消息，`requires` 字段语义从扁平变结构化——protojson 旧样本需同步，无运行时消费者存量）；`_example/bald` 移除 codegen 挂载（`user` demo 与 PATH 插件发现保留）。
