# bald 代码生成工具设计（cli/cmd/bald gen：proto/store/app）

> 适用：`cli/cmd/bald`、`cli/internal/codegen`、`api/proto/bald/appspec/v1`
> 关联文档：`路由注册与绑定设计.md`（生成物中 `transport/web` 流水线）、`框架契约总览.md`
> Status: Accepted（已落地；AppSpec 反向生成验证完成）

## 摘要

bald 作为框架库（核心零后端耦合）同时提供**官方开发工具 CLI `cli/cmd/bald`**：`gen proto` / `gen store` / `gen app` 三个代码生成子命令，为使用 bald 的新服务生成可编译的 starter 骨架（proto 服务 / 实体 / 应用装配 main.go）。

CLI 住在独立 module `github.com/kalandramo/bald/cli`，它的 `go.mod` **零 `replace`**——这是 [风险评审 §3.4](../../architecture/risk-review.md) 选定的结构性解法：Go 为命名包按版本安装时读取目标 module 的**已发布** `go.mod`，只要含任何 `replace` 就直接拒绝，而仓库根带着 19 条同仓 `replace`。因此：

- 从源码检出装：`git clone` → `cd bald/cli` → `go install ./cmd/bald`。
- 按 tag 装：`go install github.com/kalandramo/bald/cli/cmd/bald@vX.Y.Z`，前提是 `cli/vX.Y.Z` 这个 tag 已发出且在你用的代理上解析得到。

业务代码只依赖 bald 库（`github.com/kalandramo/bald/pkg` 及各适配器），不受这条限制影响。

**最重要的定位：生成器只做装配、不做业务。** 生成物覆盖框架装配形状（servers / capability / 组件生命周期 / 审计协调 / 配置 flag 覆盖），业务路由、handler、gRPC service 注册、wire 注入、管理面一律留 TODO 填充点——业务无法也不应由模板表达（反向生成 go-bald-admin 验证了这一边界）。

代码生成不替代手写业务：生成物是可编译骨架，业务路由/handler/grpc service 注册留 TODO 填充点（见各模板头部注释）。

## 背景与动机

P4 工程化脚手架落地时，bald 需要一个「框架可生成 starter 骨架」的最小验证，CLI 放在 `_example/bald`（示例模块）作为孵化场。P12 把「应用装配」升格为单一 proto 真相源（AppSpec 方言），解决了「模板 + 手填配置键 = 双真相源」问题。此后工具链归属（示例 vs 核心）成为待评估架构债——直到落地为核心 `cmd/bald`，又因 §3.4 的安装路径缺陷迁为独立 module `cli/`。

范式：嵌入模板脚手架 + `kubectl` 风格 CLI + PATH 插件发现 `bald-<name>`。

## 设计

### 1. 工具链归属与分发

```
bald/
├── cli/cmd/bald/main.go          # cobra root（Use: "bald"）+ codegen.NewCommand()
├── cli/internal/codegen/         # 生成器实现（gen.go / app.go / appspec_gen.go + 测试）
├── cli/go.mod                    # module github.com/kalandramo/bald/cli，零 replace
├── api/proto/bald/appspec/v1/appspec.proto   # AppSpec 方言
```

- **独立 `cli` module（而非塞在仓库根）**：按 tag 安装命名包要求目标 module 的已发布 `go.mod` 零 `replace`，而仓库根必须有 19 条同仓 `replace` 才能让本仓工具在检出里跑起来。把 CLI 拆出来是同时满足两者的唯一姿势（§3.4 方案 B）。代价：`cli` 只能按 tag 消费同仓兄弟模块，目前依赖 `github.com/kalandramo/bald/bconf`，于是「bconf 的新 tag 得先在代理上解析得到」成了发布顺序的前置条件。
- **AppSpec 的 Go 生成代码在 `bconf` module**（`bconf/gen/go/bald/appspec/v1`）：模板直接引用它，契约与生成器分别演进、按 tag 对齐。`cli` 因此是 bconf 的下游消费者，不再共享其工作树——`cli/go.mod` 只 require `bconf`，零 `replace`。仓库根的 `go.mod` 只剩本仓文档闸门 `internal/docscheck`，不再依赖 cobra。
- **`cli/internal/codegen` 而非 `cli/pkg/codegen`**：生成器是工具内部实现，不是库公共 API；未来需对外暴露（嵌入业务 CLI）再提升。
- **`cli` 不引入 gin/grpc**：生成物 import gin/grpc/cobra，其编译/运行验证以 `_example/bald` 消费者 module（go.mod 含这些依赖、`replace` 指向核心工作树）为上下文——见 §6 测试策略。

### 2. 三个子命令

| 命令 | 输入 | 输出 | 说明 |
|---|---|---|---|
| `bald gen proto <name>` | 名称 + `--out` + `--go-package` + `--force` | `api/proto/bald/<name>/v1/<name>.proto` | protobuf 服务骨架文本（含 `PagingRequest`/`FilterExpr` 引用）；`go_package` 默认不写（bald 生态经 buf managed mode 补充） |
| `bald gen store <name>` | 名称 + `--out` + `--out-pkg` + `--force` | `<name>.go` | 实体骨架（gorm tag + `KeyOf` 提取函数），gofmt 保证可编译 |
| `bald gen app --spec <AppSpec.json>` | AppSpec（protojson）+ `--out` + `--adopt` + `--check` | 应用装配**目录树** | AppSpec 单一真相源：三道门 + 归属三态 + 清单，见 §3 |

三个子命令共用 `writeGuarded` 落盘通道，遵守**不静默覆盖**（源自「文件所有权」
设计原则）：目标文件已存在即拒绝生成（用户可能已手改生成物），错误信息自带放行
指引——单文件生成器（proto/store）用 `--force`，树生成器（app/domain）用
`--adopt`（重写 owned 并更新清单）或 `--check`（零写入校验漂移）。成功提示走
`IOStreams.Out`（信息性输出不污染 stderr），落盘前的 gofmt 诊断性写盘除外。

命令层为叶子命令 Options 形态（`Complete? → Validate → Run`，Run 不读 flag）：
`cli/internal/codegen` 自带 `IOStreams` 迷你版（kubectl `genericiooptions.IOStreams` 同构，
不引 k8s 依赖）与 `CheckErr` 唯一错误出口；后续扩展新子命令（如 `bald new`、
`gen crud`）一律照此模板。注意：Options 领域字段不可命名 `Out`（会遮蔽内嵌
`IOStreams.Out io.Writer`），输出路径类字段用 `OutDir`/`OutRoot`。

### 3. AppSpec 方言（应用装配的 proto 单一真相源）

```proto
message AppSpec {
  AppMeta meta = 1;                        // name/module/desc（生成标识）
  repeated ComponentSpec components = 3;   // kind/name/config_prefix（托管组件）
  CapabilitySpec capability = 4;           // provides + requires（能力声明）
  bootstrap.v1.BootstrapConfig bootstrap = 7; // bconf 契约段（唯一真相源）
  LayoutSpec layout = 8;                   // 输出根 / apiserver 目录 / Gate3
  BundleSpec bundle = 9;                   // 装配期横切链（归一化开关）
  repeated DomainSpec domains = 10;        // 业务域清单
  repeated Variant variants = 11;          // 构建期变体（build tag 分叉进声明）
  reserved 2, 5, 6;                        // 旧快捷方式（Q6 移除）
  reserved "server", "audit_backends", "bundle_normalized";
}
message Requirement { string component = 1; repeated string caps = 2; }
```

**`Requirement` 结构化是关键设计修正**（反向生成真实业务应用时暴露）：`appkit.Requires(component, caps...)` 是「组件声明对能力的依赖」对，不是扁平能力名。早期 `requires []string` 生成的 `Requires("db")` 无归属语义（组件名被当成了能力名），既无法表达 `audit.store → db` 的定位关系，也让能力校验 fail-fast 失去"缺哪个组件需要的能力"的报错价值。结构化后模板输出 `appkit.Requires("audit.store", "db")`，与手写装配一致。

### 4. 模板装配纪律（两条 P0 不变量）

生成物「编译通过但运行即坏」的装配顺序错误是本模板要防的头号风险，固化为两条纪律（并由防回归测试断言）：

1. **servers 与组件一律经 `appkit.Servers` / `appkit.Components` Option 传给 `New`**——Option 只有 `New` 消费，`New` 之后再 append 无效（servers 永不注册的静默 bug 根源）。
2. **不生成 Run 前调 `MountComponent`**——它要求运行态（`running` 在 `Run` 内才置位），装配期挂载必须走 `Components` Option。

正确形态：`appkit.New(capOpts...)` 之前完成全部 Option 组装。

### 5. 生成物骨架边界（业务填充点，非模板缺陷）

模板对以下元素留 TODO（生成器只做装配不做业务）：

| 元素 | 模板形态 | 归属 |
|---|---|---|
| 业务组件工厂（trace/db/redis 等 kind，依赖 contrib/引擎） | `buildComponent` 的 TODO | 业务/contrib 注入 |
| store/stream 审计后端（依赖 DB/Redis 桥接） | `buildAuditBackend` 的 TODO（log 开箱即用） | 业务桥接 |
| bundle 的 Authn/Authz/Metrics 注入 | seeded 链函数里显式 `bundle.Public()` + 注释指向 `bundle.Authn(…)` | 业务实例（契约没有 authn 段，模板不替业务宣布「公开」） |
| 契约 middleware 段 → 横切链 | seeded 的 `NewRouter`/`newGRPCChain` 里调 `bundle.FromMiddleware`/`FromGRPCMiddleware` | 模板固化（见 §8），业务只在 seeded 文件里改链序 |
| gateway 装配 | 注释 TODO | 落 `gatewaycontract.HTTPProvider`（接管 `server.http` 段）+ `WithHTTP(nil)` 让位；该角色**不**登记 `WithHTTPContract` |
| Registrar 注册中心、`internal/` 分层、wire、管理面端点 | 不生成 | 业务层 |

### 6. 测试策略

三层防线固化模板质量（防止「编译过但运行即崩」的盲区复发）：

1. **模板渲染锚点断言**：gofmt 必须成功 + 关键原语存在 + **装配顺序断言**（`appkit.New` 在最后一次 `capOpts = append` 之后；生成物不得含 `.MountComponent(` 调用）。
2. **消费者 module 端到端编译**：生成物在 `_example/bald`（独立 module：含 cobra/gin/grpc 依赖 + `replace ../..` 指向核心工作树）内 `go build`——核心 go.mod 保持不引入 gin/grpc。
3. **运行时冒烟**：无传输 server 的生成物真实运行 3s 存活断言（捕获 `ErrNotRunning` 等装配期崩溃）。

`cli/internal/codegen/app_test.go` 的 `exampleModule(t)` helper 负责定位消费者 module 路径：从 cwd（`go test` 恒为包目录）逐级上溯，认那份 `go.mod` 里 `module github.com/kalandramo/bald` 这一行**逐字相等**才算仓库根——不写死层数，包在树里再挪一次也不会静默失效（`cli/go.mod` 声明的是 `…/bald/cli`，前缀匹配会误判）。

### 7. 生成物的回归判据

`_example/bald` 是生成器的消费者 module：`appspec.json` 是声明的唯一真相源，`bald gen app --check` 与 `bald gen domain --check` 要求零差异，生成物在该 module 内通过 `go vet`/测试（CI 任务见 `Taskfile.yml` 的 `example-*`）。AppSpec 方言能力的活样例是 `_example/bald/_scratch/appspec.sample.json`——组件、能力依赖、bundle 归一化、审计段的完整写法都在其中，可直接 `bald gen app --spec` 生成骨架。

### 8. 契约驱动的链脚手架（两面对称）

框架侧的装配口 `appkit.WithHTTPContract` / `WithGRPCOptionsContract` 只解决「启动时谁来读 `server.*.middleware` 段」，模板必须给出**调用桥的那一次**，否则新工程又是 write-only 配置。两面在模板里的形态严格对称：

| 面 | owned（每次重生成） | seeded（生成一次、之后归用户，`kept:`） |
|---|---|---|
| HTTP | `assemble.gen.go` 出 `appkit.WithHTTPContract(apiserver.NewRouter)` | `internal/apiserver/apiserver.go` 的 `NewRouter(mw *bootstrapv1.Server_Http_Middleware) (http.Handler, func() error, error)`，体内 `bundle.FromMiddleware(mw)` + `bundle.New(bundle.Public(), opts…).Gin()` |
| gRPC | owned 的 `assemble.gen.go` 只在末尾展开 `customOptions(role)`，gRPC 钩子的登记落在那份 seeded 文件里（与 HTTP 面不同：HTTP 的 `WithHTTPContract` 是 owned 出的） | `internal/bootstrap/custom.go` 里两件事：`customOptions` 按角色出 `appkit.WithGRPCOptionsContract(newGRPCChain)`（多角色树按 `switch role` 分叉，只给有 gRPC 面的角色），同文件出 `newGRPCChain(mw *bootstrapv1.Server_Grpc_Middleware) ([]grpc.ServerOption, func() error, error)`，体内 `bundle.FromGRPCMiddleware(mw)`，业务自持的 Defaulter/Validator 挂在 bundle 链内侧 |

三条边界由模板固化，不是运行时才发现：

- **认证姿态是显式的一行**：seeded 两侧都写 `bundle.Public()` 加注释「接入认证时改 `bundle.Authn(<authenticator>)`」。契约里没有 `authn` 段，模板也不代替业务宣布「本服务公开」——把它做成配置要先加契约段，属另一轮。
- **网关角色不挂 gin 链**：`server.http` 被转码面接管时，`assemble.gen.go` 登记的是 `gatewaycontract.HTTPProvider` + `WithHTTP(nil)` 让位，**不**登记 `WithHTTPContract`；配套的，`AppSpec.bootstrap.server.http.middleware` 段也不写进该角色的契约文件（否则又是一个「写了没人读」的段）。判据在 `cli/internal/codegen/appspec_custom_test.go`：转码角色的生成物里出现 `WithHTTPContract` 即失败。
- **角色的 middleware 段从应用级继承**：`inheritMiddleware`（`cli/internal/codegen/app.go`）把 `AppSpec.bootstrap.server` 的两段 middleware 复制进每份 `configs/<app>-<role>.yaml`。此前多角色只继承地址段，角色文件里的限流没有任何路径到链上——与框架侧同一个缺陷的配置形状。

seeded 文件是 `kept:` 的（重生成不覆盖），所以链的形状必须能纯靠 `AppSpec.bootstrap` 表达，模板把 owned 与 seeded 两侧的签名绑成一对；防回归断言在 `appspec_custom_test.go`（两面 seeded 签名 + 两处登记 + 网关让位）与 `appspec_roles_test.go`（角色契约继承）。

## 理由与取舍

**决策①：为什么工具进核心 module 而不是独立 tools module？** AppSpec 生成代码在核心同 module（引用零成本）、与框架同版本（buf 版本与 proto 契约天然对齐）；独立 tools module 要跨 module import + replace + 版本协调。代价是核心 go.mod 引入 cobra——工具性质允许。

**决策②：为什么 `requires` 结构化而不是保持扁平？** 见 §3。扁平 `requires` 把 `appkit.Requires` 的 (component, caps) 语义压成单个字符串，能力校验 fail-fast 的"哪个组件缺什么能力"报错价值丢失。

**决策③：为什么生成物测试用消费者 module 而非核心 module？** 生成物 import gin/grpc/cobra（生成给用 bald 的服务），核心 go.mod 若为其加这些依赖会污染框架依赖图（P5 纪律）。`_example/bald` 已是现成的消费者依赖面（replace 指向工作树，闭环测试）。

**决策④：为什么 `gen proto` 默认不写 `go_package`？** bald 生态的 proto 生成统一走 buf managed mode（`api/proto/buf.gen.yaml` 的 `go_package_prefix`），模板写死 `go_package` 会与 managed mode 冲突或残留错误的 example 路径。需要独立 protoc 的调用方用 `--go-package` 显式指定。

**决策⑤：为什么模板留业务 TODO 而不是全自动？** 生成器的价值在"装配骨架 + 最佳实践示范"（每个原语带注释），业务（handler/wire/组件工厂/管理面）无法 proto 化也不应由框架替业务决定。全自动会让模板与业务耦合，违背框架"只做装配"的定位。

## 兼容性

纯增量：新增 `cli/cmd/bald`、`cli/internal/codegen` 与 AppSpec proto（`Requirement` 为同字段号新增消息，`requires` 字段语义从扁平变结构化——protojson 旧样本需同步，无运行时消费者存量）；`_example/bald` 移除 codegen 挂载（`user` demo 与 PATH 插件发现保留）。

**一处 breaking（链脚手架改形，见 §8）**：seeded 的 `internal/apiserver/apiserver.go` 里 `NewRouter()` 从 `func() *gin.Engine` 变成 `func(mw *bootstrapv1.Server_Http_Middleware) (http.Handler, func() error, error)`，owned 的 `assemble.gen.go` 改成经 `appkit.WithHTTPContract` 消费它。存量工程重跑 `bald gen app` 后**编译失败**（旧签名不匹配），这是有意的：静默保持旧形状等于让新加的契约段继续没人读。迁移三步——

1. `NewRouter` 收 `mw`、返回三元组，链改由 `bundle.FromMiddleware(mw)` 出，末尾 `return router, closeChain, nil`；
2. 原 `appkit.WithGRPCOptions(自建链)` 搬进 seeded 的 `newGRPCChain(mw)`，用 `bundle.FromGRPCMiddleware(mw)` 译段（业务自持的 Defaulter/Validator 仍挂在 bundle 链内侧）；
3. `customOptions` 里登记 `appkit.WithGRPCOptionsContract(newGRPCChain)`，认证姿态显式写 `bundle.Public()` 或 `bundle.Authn(…)`。

不想动 seeded 文件的工程可以留着旧形态：`WithHTTP`/`WithGRPCOptions` 仍在 API 面上，只是那两个 middleware 段不会生效（写了不报错，也不挡请求）。

## 实现现状

生成器提供 `gen proto` / `gen store` / `gen app`（含 `--spec` 方言）三类子命令，产物经 gofmt 与端到端 `go build` 验证。模板装配纪律（Option 先于 `New`、不生成 Run 前 `MountComponent`）由运行时冒烟测试断言。工具链归属独立 module `cli`（`cli/cmd/bald` + `cli/internal/codegen`）：源码检出 `cd cli && go install ./cmd/bald`，按 tag 则 `go install github.com/kalandramo/bald/cli/cmd/bald@vX.Y.Z`（该 module 零 `replace`，见摘要与风险评审 §3.4）。AppSpec 已支持反向生成真实 module（`requires` 结构化 + Bind 配置覆盖）。
