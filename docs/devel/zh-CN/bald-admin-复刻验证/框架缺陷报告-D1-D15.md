## D1 — 缓存模块 API 漂移（阻塞升级，非等价替换）

**严重度**：高（阻塞框架版本升级）

**现象**：本地 bald 已删除 `contrib/cache-redis`，但 bald-admin 仍引用
`contrib/cache-redis v0.1.0`。升级 bald 版本会直接编译失败。

**根因**：新 API **不是等价替换**——首轮分析误判为「能力全覆盖」，经对抗验证推翻：

| 差异点 | 旧 API | 新 API |
|---|---|---|
| 构造入参 | addr 字符串 | **已构造的 `goredis.UniversalClient`** |
| 连接参数 | `WithPassword`/`WithDB` | **无**（调用方自建 client，连接池/TLS 自理） |
| 底层 client | `Client()` 可取 | **不暴露**（`Close` 亦不关闭 client） |
| 键前缀 | `rediscache.Key(...)` | `WithKeyPrefix` |
| TTL/降级 | 在 redis 适配器 | 移到了 `cache/loadable` |

**证据（已重新核验）**：
- `bald/bootstrap/cache.go:31-33` — 注释载明「原 contrib/cache-redis 组件已删除
  （2026-09-18），能力被 cache/redis + cache/loadable 覆盖」
- `bald/cache/redis/redis.go:33` — `func New(client goredis.UniversalClient, opts ...Option) *Cache`
- `bald/cache/redis/options.go` — **全文只有 1 个 Option**（`WithKeyPrefix`）

**复现**：
```bash
grep -c "func With" bald/cache/redis/options.go   # → 1
grep -n "func New" bald/cache/redis/redis.go      # → 33
```

**影响面（实测 6 个文件，非计划预估的 4 个）**：`internal/bootstrap/providers.go`、
`internal/bootstrap/bootstrap.go`、`internal/apiserver/biz/v1/dict/dict.go`、
`.../secret/secret.go`、`.../e2e/t4_e2e_test.go`、`cmd/go-bald-admin/wire_gen.go`。

**已修**：`75817ad`（bald-admin，11 文件）。绕行要点——新增 `bootstrap.RedisClient`
持有底层连接（审计流需要原生 Redis 命令）；`loadable` 的 loader 是**构造期绑定**
（旧 API 是请求期传入），参数化 key 由 loader 从 key 反解。

## D2 — ServerRegistry 契约段静默失效

**严重度**：**严重**（静默失败——不报错、不中断，但配置不生效）

**现象**：配置里写了 `server.sse`（或 websocket/tcp/http3/graphql/mcp）却无对应
provider 时，该段**根本不进入遍历集合**——不报错、不打日志、进程照常启动，
但**不监听该协议**。

**根因**：同仓两种语义不对称——
- `bald/bootstrap/server.go` 的 `BuildServers` 按**已注册 provider** 枚举
  （`names` 取自 `r.providers`）；
- `bald/bootstrap/broker.go` 的 `Build` 按**契约段**枚举（`brokerSections` 表带
  `implemented` 标志）。

broker 侧有防护、server 侧没有。

**证据（已重新核验）**：
- `bald/bootstrap/broker.go:67` — 注释原话：「Build fail-fast 拒绝，
  **否则用户以为消息代理接上了、实际什么都没发生**」（该注释正是危害的自我警告）
- `bald/bootstrap/broker.go:65/68/71` — `implemented` 标志机制

**复现**（修复前的 RED）：
```bash
# 配置 server.sse 段 + 只注册 http provider
# 修复前：err=nil, len(servers)=1（静默成功，无任何提示）
# 修复后：报错 "server.sse is configured but has no implementation in this repo"
```

**已修**：`8ec75cd`（bald 仓，2 文件）。修复要点——新增 `serverSections` 表
（覆盖 Server message 的全部 **31 个 optional 段**，见 `bald/bootstrap/server.go:85-87`）
+ `validateServerSections`。

**修复时的范围界定（关键教训）**：fail-fast 必须**只针对「本仓无实现」
（`implemented=false`）**的段，**不能**同时校验「provider 是否已注册」——
后者是刻意的能力声明机制（`bald/pkg/appkit/bootstrap.go:392-396` 注释载明
「未声明的能力不注册 provider——契约段存在也无 server 消费（能力声明在代码，
是刻意的）」）。首版两条分支都 fail-fast，误伤 `pkg/appkit` 中 5 个既有测试。

## D4 — `circuitbreaker/sres` 语义与契约不符

**严重度**：中

**现象**：`sres` 是 SRE 概率式算法，`accept = (requests - K*errors)/(requests+1)`
**恒 < 1**，因此即使全成功路径也会概率拒绝；且 `State` **永不返回 `StateClosed`**
（恒 half-open）。

**影响**：调用方无法获得「已恢复」的确定性状态。需要阈值式语义的场景应改用
`hystrix`。

**证据（已重新核验锚点）**：
- `bald/circuitbreaker/sres/sres.go`（包实现）
- `bald/circuitbreaker/circuitbreaker.go:24` — `StateClosed State = iota`
  （**注意：行号已从计划文档的 22 漂移到 24**）

**复现（本会话实测）**：K=2 时，**100 次全成功路径下仍拒绝 12 次**。

**应用层绕行**：Wave 1b 改用 `hystrix`（阈值式）。

## D5 — 契约 `server.http.rate_limit` 段零消费者

**严重度**：中（违反 D2 修复所确立的 fail-fast 原则）

**现象**：契约声明了 `server.http.rate_limit` 段（rate/burst/wait 三字段），
但**无任何 Go 代码消费它**——`pkg/middleware/{gin,grpc}/` 无 ratelimit 中间件。
配了限流段却无任何效果。

**证据（双重交叉验证）**：
- `bald/bconf/proto/bootstrap/v1/server.proto:92` — `optional RateLimit rate_limit = 6;`
  （段定义在 `:69-70`）
- `grep -rn "RateLimit\|rate_limit" bald/pkg/middleware/gin/*.go bald/pkg/middleware/grpc/*.go`
  → **零命中**；且两目录文件清单中**无 ratelimit.go**

**复现**：
```bash
ls bald/pkg/middleware/gin/ | grep -i rate    # → 无输出
grep -rn "rate_limit" bald/pkg/middleware/    # → 无输出
```

**应用层绕行**：Wave 1a 走业务自持配置段 `login.rate_limit`。

**与 D2 的关系**：D2 修的是「契约段配了但无实现应 fail-fast」，而 D5 正是同一
类问题——**契约声明与实现脱节**。若 D2 的 `serverSections` 表覆盖该段，它本应
在启动时报警。**建议上游一并处理**。

## D6 — JWT 不签发 jti + 秒级时间戳 → 同秒签发产生相同 token

**严重度**：**严重**（破坏安全语义，且是静默的）

**现象**：**同一秒内对相同 claims 签发，得到字节完全相同的 token**。

**根因（两条叠加）**：
1. `toJWT` **不设置** `RegisteredClaims.ID`（即 JWT 标准 `jti`）；
2. `iat`/`nbf`/`exp` 均为**秒级** `NumericDate`；
3. 在 RSA 签名确定性（RS256 对同一输入恒等）前提下 → 同秒同 claims ⇒ 同 token。

**影响（实测两条）**：
- 连续刷新时新 access_token 与旧的**相同**（有效期不延展，客户端拿到的「新」令牌
  立刻过期）；
- 轮换出的 refresh_token 可能与**刚被消费的旧值重合**，使一次性语义失效。

**证据（已重新核验锚点）**：
- `bald/contrib/authn-jwt/jwt.go:208-221` — `func toJWT`，字段赋值清单为
  `Subject`/`Name`/`TenantID`/`Scopes`/`Roles`/`Issuer`/`ExpiresAt`——**无 `ID`（jti）**
  （核验命令须用 `jc\.ID` 精确匹配；用 `grep -E "ID|jti"` 会误匹配 `TenantID`，
  这是本报告首稿的失误，已修正）
- `bald/contrib/authn-jwt/jwt.go:204` — `jwt.RegisteredClaims`（内嵌但未用其 ID 字段）
- `bald/contrib/authn-jwt/jwt.go:296-297` — `jc.IssuedAt` / `jc.NotBefore`
  （**注意：行号已从计划文档的 298-305 漂移到 296-297**）

**复现**：
```bash
sed -n '208,222p' bald/contrib/authn-jwt/jwt.go | grep -cE "jc\.ID|\.ID ="   # → 0
# 端到端：同一秒内连续两次刷新，比较返回的 access_token 是否字节相同
```

**应用层绕行**：Wave 1d 在 `claims.Scopes` 里加随机 nonce（唯一可由业务控制的字段）。

**建议上游修复**：`toJWT` 填 `ID = uuid.NewString()`（jti），届时绕行可移除。

## D7 — `authz.Authorizer` 无热重载入口

**严重度**：高（可用性——运行期权限变更必须重启）

**现象**：运行期新增用户/改角色后，其权限**必须重启进程**才生效。

**根因**：`authz.Authorizer` 接口**只有 `Authorize` 一个方法**，
`contrib/authz-casbin` 也只暴露 `New`/`NewWithModel`/`Authorize`——**没有任何
热重载策略的入口**。

**影响（端到端实测）**：casbin 的 g 行（subject→角色绑定）在启动时经
`bootstrap.loadPolicyCSV` 从 UserStore **一次性**装载。新注册用户不在其中——
注册后立即访问受保护资源返回 **403 `ACCESS_DENIED`**，须重启才生效。
这对「注册即用」是硬伤。

**证据（已重新核验）**：
- `bald/pkg/authz/authz.go:15-20` — 接口仅 `Authorize(ctx, subject, object, action)`
- `bald/contrib/authz-casbin/casbin.go:48`（`New`）/ `:55`（`NewWithModel`）/
  `:80`（`Authorize`）—— 无策略重载方法

**复现**：
```bash
grep -nE "^func " bald/contrib/authz-casbin/casbin.go   # → 仅 New/NewWithModel/Authorize
# 端到端：注册新用户 → 立即用其 token 访问受保护资源 → 403
```

**应用层绕行**：Wave 1d-3 新增 `internal/security/authz.ReloadableAuthorizer`
装饰器（持可整体替换的内层授权器 + RWMutex），注册后调用
`bootstrappkg.ReloadPolicies()`。框架零改动。

**建议上游**：为 `authz.Authorizer` 增加可选的重载能力（如
`interface{ Authorize(...); Reload() error }` 的扩展接口）。

## D8 — 契约 Asynq 段字段面 << 实现 Option 面

**严重度**：中（导致契约驱动装配不可能）

**现象**：契约 `server.proto` 的 Asynq 段只有 **3 个字段**
（`redis_address`/`redis_password`/`redis_db`），而 `bald/transport/asynq` 的实现
有 **46 个 Option**（`WithConcurrency`/`WithQueues`/`WithStrictPriority`/各类超时…，
实测 `grep -c "^func With" options.go` = 46）。
3 字段不足以驱动真实装配——**字段比约 1:15**。

**后果**：`bald/transport/asynq` **无 contract 子包**，appkit 的契约驱动装配
（`ServerProvider` 注册表）无从覆盖，**必须走 `WithExtraServers` 逃生舱**。

**证据（已重新核验）**：
- `bald/bconf/proto/bootstrap/v1/server.proto:283-288` — Asynq 段 3 字段
- `bald/transport/asynq/options.go` — **46 个** `func With*`（`:211` `WithConcurrency`、
  `:225` `WithQueues`…）
- 逃生舱：`bald/pkg/appkit/bootstrap.go:186` — `func WithExtraServers(servers ...transport.Server)`

**复现**：
```bash
grep -c "^func With" bald/transport/asynq/options.go   # → 46
sed -n '283,288p' bald/bconf/proto/bootstrap/v1/server.proto   # → 3 字段
ls bald/transport/asynq/contract/ 2>/dev/null || echo "无 contract 子包"
```

**决策记录**：本项目选择**走逃生舱、不扩契约**——依据是计划 §R5 的既定倾向
「先记录后扩，避免为凑装配而设计契约」，且扩契约需框架发版周期。
本仓已有先例（gateway 第三服务器）。

## D9 — 任务类型名与处理器不匹配时 asynq 静默不触发

**严重度**：中（静默失败——注册成功但永不执行）

**现象**：用**无对应处理器**的类型名注册周期任务，注册**成功**，
但 asynq 消费时找不到 handler → **不触发**且**无显式日志**。

**实测对比**：
- 用 `e2e9826629`（无处理器）→ 注册成功，**等 70 秒无任何触发**；
- 用 `bald:probe`（已注册处理器）→ 正常触发两次
  （日志 `asynq probe task consumed` @22:05:00 / @22:06:00）。

**证据**：`bald-admin/backend/cmd/go-bald-admin/asynq.go`（处理器注册处）
+ 端到端验证日志（见 Wave 2.3 提交 `9ad8bd8`）。

**复现**：
```bash
# 建一个 type_name 无对应处理器的 PERIODIC 任务并启动
# 观察：启动返回 200，但 70 秒内无 "task consumed" 日志
```

**状态：未解决**（本项目内）。这是**真实的设计张力**——`CreateTask` 校验
「类型名是否有对应处理器」需要 Scheduler，而任务**定义**与**调度**在设计上是
分离的（定义可先于处理器存在，供配置预置）。**未草率加校验**，留作遗留项。

**建议**：框架层可在 `RegisterSubscriber` 时记录已注册类型，
并由 asynq 在消费未知类型时**输出显式 WARN 日志**（当前是静默丢弃）。

## D10 — `RemovePeriodicTask` 参数语义与方法名不符

**严重度**：低（但有真实踩坑）

**现象**：`bald/transport/asynq.Server.RemovePeriodicTask(taskId string)` 的参数是
**taskId（任务类型名）**，而非 `entryId`——方法内部自行反查 entryID。
方法名与参数类型（`string`）都未体现这一差异，极易误传。

**实测踩坑**：本项目首版传 `entryID`（`NewPeriodicTask` 的返回值）→ asynq 报
`periodic task not found`，且该错误以 **500** 返回（应为 400）。

**证据（已重新核验）**：
- `bald/transport/asynq/server.go:669-681` — `RemovePeriodicTask` 内部经
  `unregisterPeriodicTask(entryId)` 反查
- 对照 `:630` `NewPeriodicTask(...) (string, error)` —— **返回的是 entryID**
  （两个方法一个收 taskId、一个返回 entryID，不对称）

**复现**：
```bash
grep -n "func (s \*Server) RemovePeriodicTask" -A 12 bald/transport/asynq/server.go
```

**应用层绕行**：本项目把 `Scheduler` 接口参数改名为 `taskID` 并加注释说明。

**建议上游**：要么改名为 `RemovePeriodicTaskByType`，要么接受 entryID
（与 `NewPeriodicTask` 的返回值对称）。

## D11 — cron 与 asynq 的 cron 表达式字段数不一致；契约 `cron.seconds` 空实现

**严重度**：中（同一框架内两个调度组件语义不一致，极易混淆）

**现象（两个独立问题）**：

1. **字段数不一致**：`transport/cron.NewTimerJob` 接受 **6 字段**（含秒），
   而 `transport/asynq.NewPeriodicTask` 接受 **5 字段**（标准 cron）。
   同一框架内两个调度组件用不同字段数——写 `"*/5 * * * *"`（5 字段）给 cron 会
   解析失败，写 `"*/2 * * * * *"`（6 字段）给 asynq 也会失败。

2. **契约字段空实现**：契约 `server.cron.seconds`（`server.proto:224-227`）
   声明了「是否启用秒级精度，默认 false」，但 `WithSeconds`
   （`options.go:33-38`）是**空实现**——函数体只有注释
   「默认已启用秒级，此选项保留用于未来扩展」。故契约里配 `seconds: false`
   **不会有任何效果**（秒级始终启用）。

**根因**：
- `bald/transport/cron/server.go:64-68` 的 `NewServer` **硬编码** parser 包含
  `cron.Second`：`cron.NewParser(cron.Second | cron.Minute | cron.Hour | cron.Dom |
  cron.Month | cron.Dow | cron.Descriptor)`——秒级无法关闭。

**证据（已核验）**：
- `bald/transport/cron/server.go:64-68` — parser 硬编码 `cron.Second`
- `bald/transport/cron/options.go:33-38` — `WithSeconds` 空实现
- `bald/transport/cron/server_test.go:24/30` — 源的测试用例**全部用 6 字段**
  （`"*/10 * * * * *"` / `"0 */1 * * * *"`），佐证 6 字段是预期用法
- 对照 asynq：`expected exactly 5 fields, found 6`（Wave 2.3 实测）

**复现**：
```bash
sed -n '64,68p' bald/transport/cron/server.go    # → parser 含 cron.Second
sed -n '33,38p' bald/transport/cron/options.go   # → WithSeconds 函数体只有注释
# 端到端：cron 用 5 字段 spec → 解析失败；asynq 用 6 字段 spec → 解析失败
```

**应用层绕行**：本项目在两个装配点分别注释说明字段数差异
（`cmd/go-bald-admin/cron.go` 与 `asynq.go`）。

**建议上游**：
1. 统一两者的 cron 字段数（或在文档/API 命名上显式区分，
   如 `NewTimerJobSeconds` vs `NewTimerJob`）；
2. 让 `WithSeconds` 真正生效（或从契约中移除该字段，避免「配了无效」——
   与 D5、D2 同类的**契约与实现脱节**问题）。

## D12 — `Store.Delete` 对 0 行匹配一律 `ErrNotFound`，不区分单条/集合语义

**严重度**：中（语义错配，两个真实违反点在应用层被踩中）

**现象**：`Store.Delete(ctx, where)` 对 **0 行匹配**返回 `store.ErrNotFound`。
该语义对「按主键删单条」是正确的，但对「**按条件删集合**」是误报——

- 「删除某用户的全部收件记录」「清空某用户某方法的全部因子」这类**集合删除**，
  在集合为空（0 行）是**合法结果**，却返回 not found；
- 调用方若把该 error 透传（自然写法），用户操作会被误报失败。

**两 provider 一致（已交叉核验，非 provider 不一致）**：
- `bald/contrib/store-gorm/gorm.go:132-141` — `if res.RowsAffected == 0 { return store.ErrNotFound }`
- `bald/pkg/store/inmemory/inmemory.go:87-96` — `if len(matched) == 0 { return store.ErrNotFound }`

**文档与实现矛盾（同一次核验发现）**：
- `bald/pkg/store/store.go:233` 的 `Store.Get` 注释写「未命中返回 **(nil, nil)**」，
  但**两个 provider 实际都返回 `ErrNotFound`**（gorm `:139-145`、inmemory `:104`）。
  按注释写调用方（`if obj == nil`）会漏判 error 分支。
- `bald/pkg/store/store.go:224` 的 `Store.Delete` 注释写「**建议** where 至少含主键」——
  措辞是「建议」（可选）而非「要求」，但实现对 0 行**硬失败**。
  调用方按「建议」理解去传集合条件，即踩中本缺陷。

**复现（应用层，两个真实违反点，均已 RED→GREEN 锁住）**：

1. **消息域**：删除一条无收件记录的草稿消息 → 级联删除收件记录匹配 0 行 → 误报 404。
   （`internal/apiserver/biz/v1/message/message.go` 的 `DeleteMessage`）
2. **MFA 域**：用户禁用**本就未启用**的方法 → 按 (tenant,user) 清空匹配 0 行 →
   误报 `mfa: disable factor: store: record not found`。
   （`internal/apiserver/biz/v1/mfa/mfa.go` 的 `Disable`，Wave 1.5 遗留，
   同不变量排查发现。回归测试 `TestWave1_5_DisableIdempotent`）

```bash
grep -n "RowsAffected == 0" bald/contrib/store-gorm/gorm.go      # → ErrNotFound
grep -n "len(matched) == 0" bald/pkg/store/inmemory/inmemory.go  # → ErrNotFound
sed -n '233p' bald/pkg/store/store.go  # Get 注释「未命中返回 (nil, nil)」与实现矛盾
```

**应用层绕行**：两处调用点对集合删除**容忍 `ErrNotFound`**
（`err != nil && !errors.Is(err, store.ErrNotFound)`）；同时**保留**精确单条
删除（按 credentialID）的 `ErrNotFound` 语义——回归测试同时锁住这两面。

**建议上游**（三选一）：
1. 让 `Delete` 对 0 行返回 **nil**（删除幂等）——最符合 REST 删除语义；
2. 或新增 `DeleteAll(ctx, where) (int64, error)` 返回受影响行数，
   `Delete` 保持单条语义；
3. 至少修文档：把 `store.go:233` 的「(nil, nil)」改为实际行为，
   并把 `store.go:224` 的「建议」改为「**要求** where 唯一确定单条」——
   否则文档在**引导**调用方踩坑。

**同类问题**：D2、D5、D11.2 均为「契约/文档与实现脱节」——**本缺陷使该模式
在文档层也成立**（注释主动误导调用方，而非仅遗漏）。

## D13 — `broker` 初始化契约缺失 + `Connect()` 假成功

**严重度**：中（两个未文档化约束，均在探针实测中踩中）

**现象（两个独立问题）**：

1. **`NewBroker` 不调用 `Init`**——`addr` 只在 `Init()` 里赋值
   （`bald/broker/redis/pubsub/redis.go:66-88`）。故只
   `NewBroker(...)` + `Connect()` 会让 `b.addr` 为空 → `DialURL("")`
   → 报 **`invalid redis URL scheme:`**（错误信息极具误导性：scheme 明明给了，
   报的却是 scheme 问题）。
2. **`Connect()` 对不可达 Redis 返回 nil（假成功）**——`Connect()`
   （`redis.go:86-113`）只构造 `redis.Pool`，真正的 `Dial` 是**懒执行**
   （首次 `pool.Get()` 才连）。故 Redis 不可达时 `Connect()` 返回 nil，
   故障延迟到首次 `Publish`/`Subscribe` 才暴露。

**两个 driver 一致**：`pubsub` 与 `stream` 的 `NewBroker` 都不调 `Init`
（`pubsub/redis.go:27`、`stream/redis.go:28`）——是 `broker/redis` 的共性。

**证据（探针实测，已固化为 e2e 测试）**：
```
Init()            -> <nil>       （不连接）
Connect()         -> <nil>       ← 假成功（D13.2）
Subscribe()       -> dial tcp 127.0.0.1:6399: connect: connection refused
Publish()         -> dial tcp 127.0.0.1:6399: connect: connection refused
Disconnect()      -> 正常返回（不挂起）
```
```bash
sed -n '66,88p' bald/broker/redis/pubsub/redis.go    # Init 才设 addr
sed -n '86,113p' bald/broker/redis/pubsub/redis.go   # Connect 只建 pool
grep -n "func NewBroker" bald/broker/redis/{pubsub,stream}/redis.go  # 都不调 Init
```
回归测试：`internal/apiserver/e2e/t_w2_6_broker_e2e_test.go`
（`TestWave2_6_BrokerRequiresInit` / `TestWave2_6_BrokerDegrade`）。

**应用层绕行**：调用方必须**显式 `Init()` 后再 `Connect()`**；
且**不能信任 `Connect()` 的返回值**——须在启动期做一次真实
`Publish`/`Subscribe` 探活，或以 `Subscribe` 成功作为「已连通」判据。

**建议上游**：
1. 让 `NewBroker` 内部调用 `Init(opts...)`（或把 `Init` 语义并入构造函数），
   使 `NewBroker` + `Connect` 即可用；
2. `Connect()` 做一次 `PING` 探活并在失败时返回 error——
   当前「返回 nil 但实际未连通」会误导启动期健康检查；
3. 错误信息改进：`DialURL("")` 报 `invalid redis URL scheme:` 掩盖了
   真实原因（addr 未设置），应提示「address 未初始化，是否漏调 Init？」。

**同类问题**：**D2**（契约段静默失效）、**D5**（`rate_limit` 段零消费者）、
**D11.2**（`cron.seconds` 空实现）、**D13.2**（`Connect` 假成功）——
**「返回成功但实际未生效」是本框架最高频的缺陷模式**（4/13）。
另注：`bald/broker` 在 **appkit 零引用**——框架内**休眠组件**，
真实消费者是 `bald/transport/{redis,rabbitmq,kafka}`。

**建议上游**（框架侧根治，本项目未采纳因「不改 bald 框架」原则）：

## D16 — `transport/cron.Endpoint()` 返回无端口地址 → 注册中心装配致启动失败

**严重度**：**高**（配置即崩——启用 `registry` 段即启动失败）

**现象**：启用 `registry`（nacos）段启动 go-bald-admin 时，进程启动到注册阶段
即失败退出：

```
Error: address scheduler: missing port in address
Usage:
  go-bald-admin [flags]
```

错误信息**不指向 cron**，也不说明是 endpoint 格式问题——`address scheduler`
是 `net.SplitHostPort` 对无端口地址的原生报错文本，排查者需自行推断
`scheduler` 从何而来（实测：追到 cron 的 endpoint）。

**根因（三段链路，已逐段核实）**：

1. `bald/transport/cron/server.go:160` —— `Endpoint()` 返回
   `fmt.Sprintf("%s://scheduler", KindCron)`，即 **`cron://scheduler`**。
   cron 是**进程内调度器**（无监听端口），该返回值是**描述性字符串**，非
   可注册地址。
2. `bald/pkg/appkit/appkit.go:621` 的 `buildInstance()` 遍历 `a.servers` 收集
   `s.Endpoint()`（`if ep := s.Endpoint(); ep != ""`），**非空即收进
   `ServiceInstance.Endpoints`**——不校验格式。（同文件 `:651` 的
   `waitForEndpoints()` 也调 `Endpoint()`，但它只判 `:0`，对本缺陷无影响。）
3. `bald/registry/nacos/registry.go:105` 的 `Register()` 对每个 endpoint
   `url.Parse` 后取 `u.Host` 调 `net.SplitHostPort`——对 `"scheduler"`
   （无端口）返回错误，`Register` 直接返回该错误 → **应用启动失败**。
4. **停机同样受阻**：`registry.go:160` 的 `Deregister()` 有**同一段**
   `net.SplitHostPort(u.Host)`——即便启动被绕过，停机注销也会撞同一错误
   （两处对称，见 `grep -n SplitHostPort` 的 105/160）。

**复现（最小、无外部依赖）**：

```bash
# 1) 错误文本逐字来自 SplitHostPort（Go 原生）
cat > /tmp/r.go <<'EOF'
package main
import ("fmt";"net")
func main() {
    _, _, err := net.SplitHostPort("scheduler")
    fmt.Println(err)
}
EOF
cd /tmp && go run r.go
# 输出：address scheduler: missing port in address  ← 与启动错误逐字一致

# 2) endpoint 来源
grep -n "scheduler" bald/transport/cron/server.go
# → 160: return fmt.Sprintf("%s://scheduler", KindCron)

# 3) 收集点不校验格式
grep -n "s.Endpoint()" bald/pkg/appkit/appkit.go
# → 621: buildInstance    （if ep := s.Endpoint(); ep != "" { eps = append(eps, ep) }）
# → 651: waitForEndpoints （只判 ":0"，对本缺陷无影响）

# 4) 消费点报错（Register 与 Deregister 两处对称）
grep -n "SplitHostPort" bald/registry/nacos/registry.go
# → 105: Register      （host, port, err := net.SplitHostPort(u.Host)）
# → 160: Deregister    （同一段，停机同样失败）
```

**影响面（同类 endpoint 排查，实测对比）**：

| transport | `Endpoint()` 返回 | 注册后果 |
|---|---|---|
| `cron` | `cron://scheduler` | **无端口 → 启动失败**（本缺陷） |
| `asynq` | `asynq://<redis_addr>` | 有端口（Redis 地址）——不崩，但把**依赖地址**当**自身服务地址**注册，语义可疑 |
| `mcp` | `""` | 空串被 `ep != ""` 过滤 → 安全 |
| `http3` | `s.Addr` | 视配置（显式端口则正常） |

即 **cron 是唯一必崩的**；asynq 虽不崩但注册语义同样值得商榷。

**归族**：与 D14（`audit.backends` provider 未注册 → 启动失败）同属
**「配置即崩」类**——但 D14 的错误信息指明了缺失的 provider（可操作），
本缺陷的错误信息（`address scheduler: missing port`）**不指明来源**，
排查成本更高。

**建议上游（三个可选修法，按推荐度排序）**：

1. **`buildInstance` 过滤不可注册的 endpoint**（推荐）：收集时校验格式
   （`net.SplitHostPort` 可解析或 scheme+host 合法），跳过进程内组件
   （cron 等无监听端口的 transport）。这与 `ep != ""` 的现有过滤意图一致，
   只是把「非空」收紧为「可注册」。
2. **`cron.Endpoint()` 返回空串**：与 `mcp` 的现有做法对齐（`return ""`），
   让上层既有过滤生效。代价：丢失「该 server 存在」的可观测性。
3. **`Register` 跳过非法 endpoint 而非中止**：容错性更好，但会掩盖配置错误
   ——不推荐（与项目「fail-fast 优于静默」的原则相悖）。

**验证说明**：本缺陷来自真实启动尝试（`go run ./cmd/go-bald-admin` +
`registry.type=nacos`），非静态阅读推断；根因链的每一段均以 file:line 锚点
核实，最小复现命令可直接执行并输出与启动错误逐字一致的文本。

## D17 — 框架自有 proto 契约未发布到 BSR → 下游无法经 buf 引入 `bald.store.v1`

**严重度**：中（阻塞契约复用；非启动崩溃，有绕行路径）

**现象**：bald 在 `bconf/buf.yaml` 中**声明**了 BSR 模块名
`buf.build/kalandramo/bald-bconf`，但该模块**从未发布到 BSR**——
下游（如 bald-admin）无法通过 `buf.yaml` 的 `deps` 引入框架自有的
`bald/store/v1/store.proto`（含 `PagingRequest`/`PaginationRequest`/
`FilterExpr` 等分页过滤契约）。

**根因（三段链路，已逐段核实）**：

1. `bald/bconf/buf.yaml:3` —— 模块声明存在：
   ```yaml
   version: v2
   modules:
     - path: proto
       name: buf.build/kalandramo/bald-bconf
   ```
   但 `name:` 仅是**本地模块标识**，不构成发布。发布需显式 `buf push`。
2. **仓库无任何发布动作**：`grep -rn "buf push" bald/`（含
   `.github/workflows/`、`Makefile`、`Taskfile*`、`*.md`、`*.sh`）**零命中**；
   `bald/.github/workflows/ci.yml` 无 `buf push` 步骤。
3. **BSR 侧确实不存在**（三次实测，非瞬时网络故障——同批次对照
   `buf.build/gnostic/gnostic` 拉取成功，证明网络正常）：
   ```
   $ buf dep update    # 在 deps 含 buf.build/kalandramo/bald-bconf 的模块内
   Failure: resource with name "kalandramo/bald-bconf" was not found
   EXIT=1              # 三次尝试一致
   ```

**后果**：框架把「分页/过滤/排序契约」定义为**单一真相源**
（`bald/bconf/proto/bald/store/v1/store.proto` 头注：「形状以 bald-crud 的
pagination/v1 为准……剥离 gnostic OpenAPI 注解，仅依赖 protobuf WKT」），
下游却**无法经 BSR 消费**。这直接影响了 go-wind-admin 复刻场景：

- 源 go-wind-admin 的 `List` 入参用 `pagination.PagingRequest`
  （`buf.build/tx7do/pagination`，55 处 import）；
- bald 自有 `bald.store.v1.PagingRequest` 形状**刻意与之一致**
  （store.proto 头注自述），本应是「不引入第三方 pagination 也能对齐源契约」
  的正解；
- 但模块未发布 → 下游只能**二选一**：引第三方 `tx7do/pagination`
  （与框架契约形成两套并行分页类型），或**手工复制** store.proto
  （破坏「单一真相源」，且框架演进后必然漂移）。

**复现（最小、可直接执行）**：

```bash
# 1) 模块声明存在
cat bald/bconf/buf.yaml
# → modules[0].name: buf.build/kalandramo/bald-bconf

# 2) 仓库无发布动作（零命中即证据）
grep -rn "buf push" bald/ --include="*.yml" --include="*.yaml" \
    --include="*.md" --include="*.sh"
# → （无输出）

# 3) BSR 侧不存在（对照实验：同批 gnostic 可拉取）
mkdir -p /tmp/p/probe/v1 && cd /tmp/p
cat > buf.yaml <<'EOF'
version: v2
modules: [{path: .}]
deps:
  - buf.build/kalandramo/bald-bconf
  - buf.build/gnostic/gnostic
EOF
printf 'syntax="proto3";\npackage probe.v1;\n' > probe/v1/x.proto
buf dep update
# → Failure: resource with name "kalandramo/bald-bconf" was not found
#   （gnostic 可正常解析 → 排除网络故障）
```

**影响面（同类「框架契约发布」排查，实测对比）**：

| 框架自有 proto 契约 | 本地声明 | BSR 发布 | 下游可引入 |
|---|---|---|---|
| `bald.store.v1`（bconf） | ✅ `bald-bconf` | ❌ **未发布** | ❌（本缺陷） |
| `bootstrap.v1` 等其余 bconf 契约 | ✅ 同模块 | ❌ 同上 | ❌ 同上 |

即**整个 `bconf` 契约模块**都不可经 BSR 消费，非单文件问题。

**归族**：与 D3（transport README 路径漂移）同属**「文档/声明与事实不符」类**
——声明了模块名，但发布这一环缺失，读者据 `buf.yaml` 会误以为可用；
严重度低于 D2/D6（无静默失败），但**阻塞面广**（所有下游契约复用）。

**建议上游（三个可选修法，按推荐度排序）**：

1. **发布 `bconf` 到 BSR 并纳入 CI**（推荐）：补 `buf push` 步骤
   （tag 触发），使 `buf.build/kalandramo/bald-bconf` 真实可解析。这样
   下游 `deps` 一行即可复用框架分页契约，与源 `tx7do/pagination` 保持
   同形，避免两套并行类型。
2. **改为 Go 侧复用**：既然 `bconf/gen/go` 已生成 pb
   （`bald/bconf/gen/go/bald/store/v1/store.pb.go` 存在），下游可直接
   `import "github.com/kalandramo/bald/bconf/gen/go/bald/store/v1"`，
   proto 侧则不 import。代价：失去 `buf generate` 链路一致性
   （下游 proto 无法引用该类型，只能 Go 层用）。
3. **在 `bconf/README` 明确「本模块未发布，下游请用方式 2」**：
   最低成本，至少消除「声明与事实不符」的误导。

**本次处置（bald-admin 侧，2026-09-20）**：
按用户裁定「没有依赖就引入」，bald-admin 已引入 `buf.build/gnostic/gnostic`
与 `buf.build/tx7do/pagination`（见 `bald-admin/backend/api/buf.yaml`）。

`bald-bconf` 后可回收为框架自有契约。

**验证说明**：本缺陷来自真实 `buf dep update` 尝试（三次），非静态阅读推断；
