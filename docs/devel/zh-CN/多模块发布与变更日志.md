# 多模块发布与变更日志

bald 仓库里每个 Go module 独立发布：根模块 tag 是 `vX.Y.Z`，子模块是 `<目录>/vX.Y.Z`（例如 `bconf/v0.14.0`）。90+ 个 module 靠手工同步版本会反复出现三类问题：

- 改了模块忘了打 tag（漏发）；
- tag 只有版本号，说不清这一版包含什么；
- A 用到了同批发布的 B 的新 API，A 的 `go.mod` 仍写着 B 的旧版本，下游 `go get A@新版本` 编译失败。

`bald release` 把发布拆成四个可单独检查、可重放的步骤。所有写操作默认关闭，先看输出再执行。

## 四步流程

### 1. plan：算版本

```bash
task release-plan
# 等价：go run ./cmd/bald release plan
```

对每个 module 取「最近 tag..HEAD」的提交，按文件归属过滤（同一文件只属于最深的 module，`cobramcp/examples/*` 的改动不会算到 `cobramcp`），得到：

- 哪些 module 需要发版；
- 当前版本、下一版本、bump 等级；
- 该版本的提交列表（也是变更日志的来源）；
- 计划内模块的 `go.mod` 里需要归位的内部 `require`。

结果同时写入 `.bald/release-plan.json`（`.bald/` 已在 `.gitignore`），供后三步复用。`--json` 把计划打到 stdout，便于脚本消费。

### 2. sync：依赖归位

```bash
task release-sync              # 只看会改什么
task release-sync -- --write   # 真正写入 go.mod
```

只改计划内模块的 `go.mod`：把对同批发布模块的 `require` 升到本轮版本。不发版的依赖保持原样，发布范围不会因为一条 `require` 无限扩散。已经是目标版本的条目跳过，所以重复执行是幂等的。

### 3. changelog：写变更日志

```bash
task release-changelog              # 只看将写入的内容
task release-changelog -- --write   # 写入 CHANGELOG.md
```

新版本插在文件头部说明之后、历史版本之前；同一模块的同一版本已存在时直接拒绝，避免重复条目。

### 4. tag：打标签

```bash
git add -A && git commit -m "chore: 发布 <模块列表>"
task release-tag                  # dry-run，打印将创建的 tag
task release-tag -- --apply       # 在 HEAD 创建 lightweight tag
task release-tag -- --apply --push # 同时推送到 origin
```

tag 指向 HEAD，与仓库既有 tag 一样是 lightweight。Go proxy 按 tag 解析版本，推送后即可 `go get`。

`bconf/v*` tag 还会触发 `.github/workflows/publish-bconf.yml`：把 proto 契约推送到 BSR，使 Go 侧与 proto 同 tag 发布。其他模块没有额外流水线。

## 版本规则

提交遵循 Conventional Commits，同一模块取所有提交里最高的等级：

| 提交 | 效果 |
|---|---|
| `feat: ...` | minor |
| `fix:` / `perf:` / `refactor:` / `revert:` / 其他类型 | patch |
| `type!:` 或 body 含 `BREAKING CHANGE:` | 1.x+ 升 major；0.x 升 minor |
| `docs:` / `chore:` / `test:` / `ci:` / `style:` / `build:` | 不单独触发发布 |
| 模块第一次发布 | `v0.1.0` |

只含上述「不触发」提交的模块不会出现在计划里，也没有 tag。merge 提交不参与判断。

## Tag 守卫

`--apply` 前依次检查：

1. 工作区干净（tag 只能覆盖已提交内容）；
2. 当前 HEAD 相对计划记录的 HEAD，只允许增加 `CHANGELOG.md` 与 `go.mod` 的改动——也就是发布提交本身；出现其他文件说明计划已过期，需重新 `plan`；
3. 目标 tag 不存在（防止重复发布）；
4. `--push` 必须与 `--apply` 同时使用。

守卫检查在任何 tag 创建之前完成；不满足时直接停止。

## 发布范围

- 不发布 `_example/`（消费者示例）与 `cobramcp/examples/*`（演示 module）；它们只参与文件归属判断。
- `contrib/*`、`log/*`、`transport/*` 等可选 Provider 与核心模块一视同仁，有提交就进入计划。
- 没有历史 tag 的可发布模块首次发布固定 `v0.1.0`。

## 一次完整发布

```bash
# 业务改动已提交，工作区干净
task release-plan
task release-sync -- --write
task release-changelog -- --write
git add -A && git commit -m "chore: 发布 <模块列表>"
git push origin main
task release-tag -- --apply --push
```

## 常见问题

- **sync 报 “require … is neither …”**：计划里的版本和 `go.mod` 当前值对不上（计划生成后又改过依赖），重新 `task release-plan`。
- **changelog 报 “已包含 …”**：该版本已写过条目。确认是重复执行还是版本号算错；不要手工改历史条目来绕过检查。
- **tag 报 “HEAD 比计划多出非发布改动”**：计划之后提交了别的改动。重新 `plan`，让提交列表与版本重新对齐。
- **只想补发一个模块**：对该模块做一次会触发发布的提交后重新走完整流程；不要跳过计划直接 `git tag`，否则 `go.mod` 归位与变更日志会和 tag 脱节。
