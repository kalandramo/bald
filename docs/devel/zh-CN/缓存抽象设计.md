# bald 缓存抽象：后端无关 KV 契约 + 回源组合器

> 适用包：`bald/cache`（契约）、`bald/cache/{local,redis,loadable}`（实现与组合器，各自独立 module）
> 关联文档：`AppKit FromBootstrap 约定装配.md`（CacheRegistry 契约装配）、`数据存储设计.md`（store 层与缓存的关系）、`Bald 指标设计.md`（同为契约装配家族）
> 参考实现：onex/pkg/cache（对比评审，见《理由与取舍》）
> Last updated: 2026-09-16

## 摘要

bald 的缓存设计分两层：**契约层**（`cache.Cache`）与**组合层**（`cache/loadable`）。契约层定义后端无关的 KV 抽象——`string` key + `[]byte` value + TTL，零序列化耦合，零外部依赖；实现层（`local` freecache / `redis` go-redis）各自独立 module 并经 `CacheRegistry` 契约装配。组合层在本轮补齐第一件：`loadable` 回源组合器——Get miss 时经 singleflight 合并并发回源并回填，业务侧省去「查缓存 → miss → 查库 → 写缓存」样板，同时根治缓存击穿。

与 onex/pkg/cache 的核心差异：**契约层不放泛型**（序列化责任留在调用方，`[]byte` 边界清晰）；**回源必须合并并发**（singleflight，onex 的 LoadableCache 缺失此件导致击穿时并发 miss 全部打到 loader）；**不做无失效广播的 L2**（多节点本地脏读是已知坑，短 TTL 只是掩盖）。

## 设计

### 1. 契约层：`cache.Cache`（既有，本轮零改动）

```go
type Cache interface {
    Get(ctx context.Context, key string) ([]byte, error)          // miss 返回 ErrNotFound
    Set(ctx context.Context, key string, value []byte, ttl time.Duration) error // ttl=0 永不过期
    SetNX(ctx context.Context, key string, value []byte, ttl time.Duration) (bool, error) // 防击穿/分布式锁原语
    Delete(ctx context.Context, key string) error
    Has(ctx context.Context, key string) (bool, error)
    GetMulti(ctx context.Context, keys []string) ([][]byte, error) // 单次往返；missing 处 nil + ErrNotFound
    SetMulti(ctx context.Context, items []Item) error
    Close() error
}
```

契约层纪律：`string` key 直白可调试（redis-cli 可按 key 排查）；`[]byte` value 把序列化责任留在调用方（框架不替业务做编解码决策）；`SetNX` 提供分布式锁原语但不做锁语义（跨进程协调由业务组合）。

### 2. 组合层：`cache/loadable` 回源组合器（本轮新增）

```go
// LoadFunc 从数据源加载 key 对应的值（通常是 DB 查询）。
// 返回错误时 Get 透传错误且不回填缓存。
type LoadFunc func(ctx context.Context, key string) ([]byte, error)

func New(backend cache.Cache, loader LoadFunc, opts ...Option) *Cache
func WithTTL(ttl time.Duration) Option // 回填默认 TTL，0=永不过期
```

**Get 关键路径（防击穿核心）**：

1. `backend.Get` 命中 → 直接返回（命中路径零额外开销）
2. miss（`errors.Is(err, cache.ErrNotFound)`）→ `singleflight.Group.Do(key)` 同 key 并发合并为一次 loader 调用
3. loader 成功 → `backend.Set` 回填（`WithTTL` 默认 TTL）→ 返回值
4. loader 失败 → 错误透传，**不回填**（不留脏数据，下次请求自然重试）

**透传语义**：`Set/SetNX/Delete/Has/SetMulti` 透传 backend；`GetMulti` 逐 key 走 Get 路径（Get 会回源则 GetMulti 也回源，语义一致，any miss → `ErrNotFound` 对齐契约）；`Close` 透传 backend（「拿到什么关什么」）。

### 3. 组合器与装配的关系

loadable **不进 CacheRegistry**：Registry 装配的是后端实例（local/redis → `app.Cache(type)`），组合器由业务代码显式构造——对齐「配置驱动参数，代码声明能力」分工。典型用法：

```go
c := loadable.New(app.Cache(rediscontract.Type), loadFromDB, loadable.WithTTL(5*time.Minute))
```

## 理由与取舍

**决策①：为什么选择 singleflight 而非 SetNX 锁做回源合并？** 进程内合并零 RTT 开销，无需额外 key 与 TTL 协商。跨进程合并（多副本同时 miss）留给业务用契约层 `SetNX` 原语自行组合——框架不预设分布式锁语义，因为它带活锁/租约续期等复杂度，不属于本层职责。

**决策②：为什么 loader 失败不回填（也不做负缓存）？** 防穿透的负缓存需要「空值标记」一等公民——契约层加 `Empty bool` 或哨兵字节串，哨兵值会污染 `[]byte` 的数据语义（业务合法存空值时无法区分）。违背「契约不动」承诺，砍掉，留给未来契约演进。loader 失败不回填意味着穿透场景每次都打到源——由业务在 loader 内部自行决定空值策略（返回空 `[]byte` 也会被回填，等价于业务自定义负缓存）。

**决策③：借鉴 onex 什么、规避什么？**

| onex 设计 | bald 取舍 |
|---|---|
| 装饰器组合模式（L2/Chain/Loadable/Noop 正交组合） | 借鉴——loadable 即组合模式的 P1 落地 |
| LoadableCache 的 loader 回填语义 | 借鉴并修正——回填要 singleflight 合并（onex 缺失，击穿时并发 miss 全部打到 loader） |
| 泛型 `Cache[T]` + `any` key（MD5 hash） | 规避——key 语义不透明、序列化耦合进契约层 |
| L2Cache（ristretto + 远程，无失效广播） | 规避——`Del` 只清本节点本地，其他节点脏读直到 TTL；根治需要失效广播（Pub/Sub），复杂度高，需求未实证，列入不做清单 |
| cacheserver（集中式缓存微服务） | 规避——那是 onex 的业务服务（secret 集中管理），网络 RTT 抵消本地缓存收益，与 bald「进程内契约装配」哲学冲突 |
| `GetWithTTL` 两次 RTT | 规避——bald 契约无此方法；需要 TTL 感知的场景由后端原生能力承担 |

**不做清单**（当前显式不做，理由留档防 YAGNI 争议回潮）：负缓存（决策②）、L2 两级缓存（无失效广播的设计是已知坑，带广播的版本等真实多副本高 QPS 读需求）、`typed` 泛型便利层（纯便利可随带）、契约装配（组合器非后端）。

## 兼容性

纯增量，无破坏：契约层与 local/redis 实现零改动；loadable 是新增独立 module，不进 CacheRegistry，不触碰 bconf 契约。
