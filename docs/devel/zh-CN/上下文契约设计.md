## 摘要

`pkg/contextx` 提供 bald 框架在 `context.Context` 中存取请求级元信息的便捷函数——**统一五个标准键**（user / username / trace_id / request_id / tenant_id），供 `pkg/middleware` 的 gin/grpc 子包与业务 handler 共同引用，避免各处重复定义私有 context 键（键不一致导致的"写进去读不出"是最常见的 context 隐性 bug）。

## 设计

五个标准键，每个 `With`/`From` 配对：

```go
// 用户身份
WithUserID(ctx, userID)          / UserIDFromContext(ctx) string
WithUsername(ctx, username)      / UsernameFromContext(ctx) string

// 可观测性
WithTraceID(ctx, traceID)        / TraceIDFromContext(ctx) string
WithRequestID(ctx, requestID)    / RequestIDFromContext(ctx) string

// 多租户
WithTenantID(ctx, tenantID)      / TenantIDFromContext(ctx) string
```

读取缺失一律返回空串（不 panic、不区分"未设置"与"设置为空"）。

### 键的来源与消费

| 键 | 写入方 | 消费方 |
|---|---|---|
| user_id / username | 认证中间件（`ContextWithAuthClaims` 同步写入） | 业务 handler、审计、授权 subject 推导 |
| trace_id / request_id | 可观测中间件（`RequestID`/`Observability`） | 日志（`log.ContextWithAttrs` 挂载）、跨服务透传 |
| tenant_id | 认证中间件（Claims.TenantID） | `pkg/store` 多租户查询自动注入隔离条件 |

### 与 `authn.AuthClaims` 的关系

`ContextWithAuthClaims(ctx, claims)` 把完整 Claims 注入 context（`authn.AuthClaimsFromContext` 可读回），**同时**把 `Subject`/`Name`/`TenantID` 同步写入 contextx 的扁平键——下游不 import `authn` 也能取到用户身份（如 store 层取 tenant_id），避免"要读身份就得依赖认证包"的耦合。

## 理由与取舍

**决策①：为什么独立成包而不是并入 `pkg/authn`？** contextx 是传输/认证/存储共用的基础设施（trace/request id 与认证无关），独立成包让 `pkg/store`、`pkg/middleware`、业务三方都可引用，避免依赖倒挂。

**决策②：为什么只做字符串键？** 元信息都是标量标识（ID/名称），字符串足够且零依赖；结构化数据（完整 Claims、span）各自走自己的 context 键（`authn` 包内私有键、otel span 在 trace 上下文）。

**决策③：为什么缺失返回空串而非 error？** 元信息是"有则用之、无则降级"的旁路数据（如审计 subject 可为空、多租户查询可跳过隔离），空串让消费方零负担判断；需要强制存在的场景由业务自己校验。

## 兼容性

纯增量：新增 `pkg/contextx` 包，现有包（中间件、store）逐步迁移到统一键，无破坏。

## 实现与过渡

| 步骤 | 内容 | 验证 |
|---|---|---|
| 1 | 五个 `With`/`From` 配对 | 单测：RoundTrip、缺失返回空串 |
| 2 | `authn.ContextWithAuthClaims` 同步写入 contextx 键 | 单测：认证后 store/业务可读 |
| 3 | 中间件/日志/多租户消费方接入统一键 | e2e：链路中 trace_id/tenant_id 贯通 |
