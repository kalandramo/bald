## 摘要

AppKit 是 bald 的**运行期生命周期编排器 + 段驱动装配引擎**。它不做组件构造：
契约段到实例的翻译由各域 Provider 完成（`bootstrap` 的配置/日志/服务器构造、
`contrib/*` 与 `*/contract` 的后端 Provider）；AppKit 只负责回答三个问题——
**装什么**（声明 + 计划）、**以什么顺序装**（阶段/优先级/拓扑）、**怎么拆**
（停机逆序 + 效应账本）。

三条承诺：

1. **一份声明面**：`MustServe(ctx, opts...)` 是唯一入口；配置驱动的部分全部
   进契约，代码表达不了的能力经 Option/Provider 声明。
2. **计划先于副作用**：`Compile` / `--plan` / `Doctor` 用同一份声明产出可打印、
   可 diff 的计划；装配错误在启动前暴露。
3. **拆得回去**：启动期写入（全局句柄、注册中心、组件）都记在效应账本里，
   停机与任何失败路径都逆序回放。

## 1. 边界：谁拥有什么

| 归 AppKit | 不归 AppKit |
| --- | --- |
| 计划编译（`Plan` IR）、段路径末者胜、阶段/优先级/拓扑排序 | 组件构造（`bootstrap.ConfigProvider`、`bootstrap.ServerProvider`、各后端 `contract.AppProvider`） |
| 生命周期（启动、注册、停机、失败回滚） | 组件实现（transport、log、cache、database、broker…） |
| 能力声明（`WithHTTP`/`WithGRPC`/`WithHealth`…） | 业务路由/handler、拦截器链内容、迁移模型 |
| 效应账本、组件热插拔、业务域/变体 | 协议层健康/就绪判定（归 `health` + 装配层） |
| 资源面 `Key[T]`、注册中心运行期编排 | 配置源读取与合并（归 `bootstrap/config`） |

依赖方向：`appkit → bootstrap / bootstrap/config / log / health / transport /
registry / bconf`，无反向依赖。

## 2. 装配模型：声明 → 计划 → 应用

### 2.1 Provider 是唯一的装配单元

```go
type Provider interface {
	Option                                   // 可直接作为 MustServe 变参
	Segments() []string                      // 消费的契约段路径
	Plan(ctx, PlanScope) ([]Node, error)     // 纯函数：只读契约/声明
	Build(ctx, ApplyScope, Node) (any, Cleanup, error) // 唯一允许副作用
}
```

- `Segments()` 声明**精确段路径**（`database` / `database.sql` / `server.http`）。
  同一路径**末者胜**：后声明的 Provider 接管（`std.Standard()` 的默认后端因此
  可被业务 Provider 覆盖）；不同路径并存。
- `Plan` 不得 I/O、不得构造实例——`Compile` 与真实启动调用的是同一个 `Plan`。
- `Build` 只在「声明的段实际出现在契约里」时执行（段缺失 = 跳过，合法）；
  产物按顶层段落资源面（`registry` 段为 `registry.Registrar`，六资源域为
  `map[string]any`，`audit` 为 `auditor`，`server` 为 `[]transport.Server`）。
- 框架自有后端集合 = `std.Standard()`：`StandardServerProvider`（http/grpc）+
  `StandardAuditProvider` + `StandardLoggerProvider`。其余域由业务按需挂载。

内置 Provider 与契约段清单见《Bald 声明式装配设计》。

### 2.2 Node 与阶段

`Node` 是计划的原子单位：`Key`（资源键，全局唯一）、`Kind`、`Segments`、
`Phase`、`Priority`、`DependsOn`、`TeardownAfter`、`Reload`、`EffectName`、
`Origin`、`Opaque`（逃逸舱标记）。

| 阶段 | 内容 |
| --- | --- |
| `PhaseConfigure` | 配置层与 `app` 元数据（无业务副作用） |
| `PhaseBootstrap` | 阶段 B 资源：logger、registry、tracer、metrics、database、cache、storage、audit、ai、workflow、broker |
| `PhaseWire` | 业务域接线（域 `Wire`/`ApplyNode`） |
| `PhaseServe` | 服务器构建与启动 |
| `PhaseDrain` | 停机钩子与服务器 drain |
| `PhaseTeardown` | 效应账本逆序回放、组件 Dispose |

阶段内排序：Kahn 拓扑（`DependsOn`）→ `(Priority, Key)`。优先级常量是声明面的
一部分，第三方可自选数值：

```text
Logger 10 · Registry 20 · Tracer 30 · Metrics 40 · Database 50 · Cache 60
Storage 70 · Audit 80 · AI 90 · Workflow 100 · Broker 110
```

同名节点冲突（I4）：默认编译错误；恰好一个节点带 `Override: true` 与
`Reason` 时该节点胜出。程序化接管（如 `appkit.Registrar(impl)`）就是这样进入
计划的——覆盖是显式的、可在 `--plan` 里看到的。

### 2.3 计划可检视：Compile / --plan / Doctor / 缓存

- `Compile(ctx, opts...) (*Plan, error)`：纯编译，不构造、不写文件、不改全局。
- `--plan`（text）/ `--plan-format=json`：打印计划后以 0 退出，发生在任何
  副作用之前。CI 用它做装配回归。
- `Doctor(ctx, opts...)`：计划 + 装配漂移检查（`App.Drift()`）。
- `WithPlanCache(path)`：启动时把计划按 `(role, input)` 记为基线，`doctor`
  据此报告装配变更；缓存只是观测基线，不是执行依据。
- `WithOpaqueBudget(n)`：逃逸舱节点预算，超预算产出警告（不阻断）。

### 2.4 L3 段覆盖检查

契约里出现、但本次装配没有任何 Provider 消费的顶层段，启动期**直接报错**并
列出段名与修复提示。豁免出口只有 `WithUnimplementedSegments(...)`（且条目必须
是真实契约字段路径，拼错在计划期报错）。server 的非内置子段同规则：没有
`server.<proto>` Provider 接管即报错。

## 3. 入口

| 入口 | 适用 | 行为 |
| --- | --- | --- |
| `MustServe(ctx, opts...)` | 生产 main | `Serve` + 失败记日志 + 非零退出 |
| `Serve(ctx, opts...) error` | 测试 / 自管退出 | 同上但不退出 |
| `NewApp(opts...) *App` | 需要自管生命周期、多实例、自定义装配时序 | 不消费 Domains/Providers 计划，业务自行 `Run` |
| `NewHarness() *App` | e2e | 轻量装配容器 |

**默认走 `MustServe`。** 它内化：`--config` 解析 → 契约两遍预装载（第一遍
文件/远程层解析 `app.name`；第二遍以 `app.name` 派生 env 前缀并全量重合并）→
装配 → `Run`（信号处理内建）。

`NewApp` 是逃生路径：不跑计划、不跑 L3、不消费 Domains；需要这些语义就不要
选它。

## 4. 能力声明（代码声明，配置表达不了）

| Option | 作用 |
| --- | --- |
| `Providers(ps...)` | 挂载 Provider（Provider 本身也是 Option，可直接变参传） |
| `WithHTTP(handler)` | 声明 HTTP 业务面（`server.http` 段据此构建） |
| `WithGRPC(register, unary...)` | 声明 gRPC service 与拦截器链 |
| `WithGRPCOptions(fn)` | 运行期求值的拦截器链（`PhaseServe` 时调用一次） |
| `WithGatewayRegister(fn)` | gateway 转码面能力（`server.http.driver` 选模式） |
| `WithExtraServerFunc(fn)` | 契约形状表达不了的服务器的通用逃生舱 |
| `WithHealth(h, opts...)` | 挂健康/就绪探针（`WithProbePaths` / `WithHealthPollInterval`） |
| `Bind(prefix, protoMsg)` | 把 proto 子消息的 flag 注册进 FlagSet |
| `Registrar(impl)` | 显式注册中心实例（接管 `registry` 段，计划中可见 Override） |
| `WithRole(role)` / `OnRole(role, opts...)` | 多角色装配与按角色分叉 |
| `WithVariantDecls` / `WithVariantImpl` | 构建期变体（按 build tag 命中增量） |
| `WithConfigFile` / `ConfigLayers` / `RemoteConfig` / `WatchConfigFile` | 配置装载面 |
| `StrictContract(business...)` | 契约键白名单校验（未知键启动即报） |
| `OnConfigChange(fn)` | 配置热更新全量回调 |
| `BeforeStart` / `AfterStart` / `BeforeStop` / `AfterStop` | 四段生命周期钩子 |
| `Servers(...)` | 直接注入已构造的服务器 |
| `StopTimeout(d)` | 服务器 Stop 阶段超时（钩子各有独立超时） |

## 5. 生命周期（`App.Run`）

```text
Resolve（能力解析 fail-fast）
  → BeforeStart 钩子
  → 组件 Start（注册序）
  → PhaseBootstrap/Build（阶段 B Provider 循环）
  → PhaseWire（业务域 Wire/ApplyNode）
  → 服务器构建（PhaseServe）并并发 Start
  → waitForEndpoints（:0 解析真实端口，超时 5s）
  → Registrar.Register
  → AfterStart 钩子
  → 首次协调（Reconcile）
  → 等待信号 / 服务器崩溃 / ctx 取消
  → Deregister
  → stopAll：效应回放 → BeforeStop → 服务器 Stop（并发）→ AfterStop → 组件 Dispose 逆序
```

失败路径全部收敛到同一回滚：`waitForEndpoints` / `register` / `afterStart` /
组件启动失败都经 `stopAll`（含效应回放）。**装配链任何一步失败，全局句柄恢复
装配前的值，已构造资源逆序释放。**

### 效应账本与可逆性

- 装配期（配置层、Provider 产物）**不可逆**：变更 = 重启；同名注册冲突直接报错
  （装配笔误应 fail-fast）。
- 运行期（组件、注册中心、日志句柄）**可逆**：每次写入记一条 Effect，停机/
  失败逆序回放。`TeardownAfter` 允许节点声明「我要最后一个拆」（审计尾批、
  指标 flush）。运行期挂载 `Registry.Mount` / `MountComponent` 返回幂等 undo——
  与装配期 `Register` 的「不可逆、重名报错」是刻意分开的两套语义。
- 组件热插拔：`MountComponent` / `UnmountComponent`，与 Effect 共用停机编排。

### 热更新

`OnConfigChange` → 副本试装载（`proto.Clone`）→ `Validate` → 整契约原子落盘 →
按 `ReloadReconcile` 节点逐条协调。坏配置记日志并保留旧契约。段不支持热更新
（如 database/registry）的节点标 `ReloadRestart`，变更需重启。

细粒度响应走 `OnKeyChange(key, fn)`（仅该 key 新旧值确实不同才触发，基线是首次
加载值）；需要「收敛到期望态」而不是「响应一次事件」的，用 `Reconcile(name, fn)`
做 diff-apply——失败不回滚、下次协调自然补齐。分发顺序固定：全量回调 → key 订阅
→ 协调器。

## 6. 业务域与变体

`Domain` 是「每域包导出一个声明值」的一等 Option：

```go
appkit.MustServe(ctx, std.Standard(), authv1.Domain, dictv1.Domain, ...)
```

槽位：`Declare`（计划期声明节点）、`Wire`（装配期自我接线）、`ApplyNode`
（声明节点的执行点）、`Routes`/`RouteTable`（REST 路由与可检视清单）、
`Services`（gRPC service 注册）、`Reconcile`（可协调节点）。清单由生成物
（`domains.gen.go`）承载——禁止 `init()` 自注册，import 树即清单。

变体（`WithVariantDecls`/`WithVariantImpl`）表达构建期增量：声明与实现同源
生成，计划里以 `VariantPatch` 呈现。

## 7. 选项速查之外的两个约定

1. **配置命名空间由 `app.name` 派生**（`MustServe` 路径）：`app.name` 决定 env
   前缀与多环境文件名，因此它是必填项；两遍预装载消解了「用配置决定读哪些
   配置」的自指。
2. **能力声明与契约段必须一致**：`WithGRPC` 声明了但契约没有 `server.grpc`，
   对应 flag 变更不产生效果——这是刻意的（避免「配置说开了、没人实现」）；
   L3 检查兜住反方向（契约有段、代码无消费者）。

## 8. 最小用法

```go
func main() {
	opts := []appkit.Option{
		std.Standard(),                        // http/grpc/audit/logger 默认后端
		storegorm.AppProvider(),               // database.sql 段 → GORM
		appkit.ConfigFile("configs/app.yaml"),
		appkit.WatchConfigFile(true),
		appkit.StrictContract(),               // 未知契约键启动即报
		appkit.WithHTTP(router),
		appkit.WithGRPC(registerService),
		appkit.WithHealth(healthChecker),
		appkit.WithGRPCOptions(newInterceptors), // 拦截器链由业务自持
		appkit.WithRole("api"),
	}
	appkit.MustServe(context.Background(), opts...)
}
```

完整可运行示例：`_example/bald`（由 `bald gen app --spec` 生成装配骨架，
`internal/bootstrap/custom.go` 承载生成器表达不了的接线）。装配声明、生成物、
`--plan` 基线由同一份 AppSpec 派生，改声明不改手写代码。

配套契约（同一角色一份 yaml）驱动地址/TLS/日志/元数据；`_example/bald` 的
`configs/` 由 AppSpec 的 bootstrap 段派生，Gate 校验其键与 bconf 契约一致。

## 9. 防坑要点

| 坑 | 规则 |
| --- | --- |
| 全局句柄写入不可回滚 | 一切全局写入走 Effect；`UndoEffects` 在 BeforeStop 之前执行 |
| 注册端口未就绪 | `waitForEndpoints` 等真实端口；`:0` 不会注册 `scheme://:0` |
| 注册中心多后端静默覆盖 | registry 单选：两个 registry 子段同时触发即计划期报错 |
| 停机顺序错 | 用 `DependsOn`/`TeardownAfter` 表达，不手写排序表 |
| 段声明了没人消费 | L3 检查 fail-closed；豁免必须显式且路径真实 |
| Provider Build 碰 App | `Build` 只能读 `ApplyScope.App` 的资源面，不得写入 |
| 热更新半截配置 | 副本试装载 → Validate → 原子落盘；坏配置保留旧契约 |
