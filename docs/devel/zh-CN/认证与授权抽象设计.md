# bald 认证与授权抽象：零引擎耦合的 P7 双接口 + P9 传输中立归一化

> 适用包：`pkg/authn`、`pkg/authz`
> 关联文档：`路由注册与绑定设计.md`（gin 侧 `AuthnMiddleware`/`AuthzMiddleware` 接入）、`grpc-gateway 配置与 transcoding.md`（gRPC 侧 `AuthnInterceptor`/`AuthzInterceptor`）、`框架契约总览.md`（§9 中间件依赖倒置表）、`架构演进路线.md`（§0.5 / P7）
> 参考实现：go-lulu `plugins/security/authn`、onexstack `pkg/authz`（对比后不照搬其 casbin 直耦）、osbuilder `middleware/grpc/authz.go`
> Last updated: 2026-09-02
> Status: Accepted

## 摘要

bald 提供认证（`pkg/authn`，谁在调）与授权（`pkg/authz`，能不能调）两个**零引擎耦合**的抽象包：核心只定义接口与身份结构，不 import 任何具体验签库/策略引擎（JWT / OIDC / API Key / Casbin / RBAC 一律外置为桥接子模块）。传输层（gin/grpc 中间件）依赖倒置接入——中间件构造期注入 `Authenticator`/`Authorizer` 实例，核心不持有任何实现。

**最重要的承诺：核心抽象零第三方依赖，认证器/授权器是业务策略，不进 appkit 通用 Registry。** 任何调用方只 import `pkg/authn`/`pkg/authz` 都不会拖进一个具体认证实现。

## 背景与动机

P7（架构演进路线 §0.5）落地前，bald 只有 `pkg/middleware` 的校验/可观测拦截器接口，认证（谁在调）与授权（能不能调）尚无统一抽象，`_example` 无法演示登录/认证/权限拦截。参考实现的取舍：

- go-lulu `plugins/security/authn` 的 `AuthClaims` 是**强类型结构**（非弱类型 map），字段对齐 OIDC 标准声明——值得照搬，保证 proto-first / 类型真相源。
- onexstack `pkg/authz` 直接在核心耦合 `gorm-adapter`/`casbin`——不照搬，策略引擎应外置。
- osbuilder `middleware/grpc/authz.go` 的 `Authorize(subject, object, action)` 三元组签名——采纳，与审计三元组同源。

## 设计

### 1. `pkg/authn`：认证抽象 + 身份结构

```go
// AuthClaims 是认证通过的统一身份声明（字段对齐 OIDC 标准声明 + 多租户/权限扩展）。
type AuthClaims struct {
    Subject   string    // 主体标识，必填
    TenantID  string    // 租户标识；非空时经 pkg/store 多租户机制自动隔离数据
    Name      string    // 展示名（可选）
    Scopes    []string  // 细粒度授权范围（"user:read"）
    Roles     []string  // 粗粒度角色（"admin"）
    ExpiresAt time.Time // 过期时间；零值=永不过期
    Issuer    string    // 签发者（审计/路由用）
}

// Authenticator 认证器接口；具体实现（JWT/OIDC/API Key/Basic）外置为桥接子模块。
type Authenticator interface {
    Authenticate(ctx context.Context) (*AuthClaims, error)  // 从请求 ctx 抽凭证并校验（含过期）
    AuthenticateToken(token string) (*AuthClaims, error)    // 直接校验 token 字符串（非传输场景/测试）
}
```

**关键行为：过期校验下沉到 `Authenticator` 接口。** 实现契约要求 `ExpiresAt` 非零且早于当前时间时返回 error；传输层拦截器不再重复判断 `Expired()`——避免"每层各查一遍"的双重判定漂移。

context 注入与读取：

```go
func AuthClaimsFromContext(ctx context.Context) *AuthClaims
func ContextWithAuthClaims(ctx context.Context, c *AuthClaims) context.Context
// ↑ 同步写入 contextx 的 user/tenant 键，供 pkg/store 多租户与业务 handler 读取
func (c *AuthClaims) HasScope(scope string) bool
func (c *AuthClaims) HasRole(role string) bool
func (c *AuthClaims) Expired() bool
```

token 抽取与传递：

```go
// TokenExtractor 从请求 context 抽取原始 token（Bearer header / gRPC metadata / cookie
// 的具体形态由 gin/grpc 桥接层实现，核心不感知传输细节）。
type TokenExtractor interface { Extract(ctx context.Context) (string, error) }
func ContextWithToken(ctx context.Context, token string) context.Context
func TokenFromContext(ctx context.Context) string
```

### 2. `pkg/authz`：授权抽象 + 传输中立归一化

```go
// Authorizer 授权判定接口；具体实现（Casbin/RBAC/硬编码规则）外置为桥接子模块。
type Authorizer interface {
    // (allowed, error)：
    //   allowed=false 且无 error → 明确拒绝（拦截器映射 403）
    //   error != nil → 判定过程出错（拦截器映射 500）
    Authorize(ctx context.Context, subject, object, action string) (bool, error)
}

func Func(func(...) (bool, error)) Authorizer // 普通函数适配
func AllowAll() Authorizer                    // 开放接口/公开服务
func DenyAll() Authorizer                     // 默认拒绝，需显式放行
```

**P9 归一化（`normalize.go`）：REST 与 gRPC 共用同一策略空间。** 授权判定基于 `(subject, object, action)`，其中 subject 从 `authn.AuthClaims` 取，object/action 由拦截器从请求推导。若 REST 用 `/v1/secret/*` 命名、gRPC 用 `SecretService.GetSecret` 命名，同一策略就要双写——M6.8 CR Issue4 的根因。归一化函数把两者收归同一资源/动作空间：

```go
// gRPC FullMethod "/go.bald.admin.v1.SecretService/GetSecret" → object "secret"
func DefaultGRPCObject(fullMethod string) string
// gRPC FullMethod 方法段前缀 → action（Delete→delete / List→list / Create/Update/Set/Put→write / 其余→get）
func DefaultGRPCAction(fullMethod string) string
// HTTP 路径 "/v1/secret/123" → object "secret"（去 /v1 前缀取首个资源段）
func DefaultHTTPObject(path string) string
// HTTP 方法 → 小写动作（与 gRPC 动作空间对齐）
func DefaultHTTPAction(method string) string
```

拦截器构造期可用 `ObjectResolver`/`ActionResolver` 函数类型自定义推导（返回空串则用默认规则），使业务可覆盖"私有资源段"等特殊路径。

### 3. 中间件依赖倒置接入

```go
// gin 侧（pkg/middleware/gin）：
AuthnMiddleware(authn.Authenticator, opts...)   // 认证失败 → 401；成功注入 AuthClaims
AuthzMiddleware(authz.Authorizer, opts...)      // 拒绝 → 403；出错 → 500
// gRPC 侧（pkg/middleware/grpc）：
AuthnInterceptor(authn.Authenticator, opts...)
AuthzInterceptor(authz.Authorizer, opts...)
```

两个中间件都支持 `SkipPaths`/`SkipMethods` 选项（`/healthz`、`/metrics`、`/ping` 等公开路径豁免，含通配符）。

## 理由与取舍

**决策①：为什么核心不持有认证器/授权器实例、不进 appkit Registry？** 认证器是业务策略（用哪个 IdP、签多久由业务定），与传输/存储插件（服务器、注册中心）性质不同。注册表只收纳"框架知道如何装配"的插件；认证器由业务在 bootstrap 层构造后经中间件构造器注入。核心保持"知道接口、不认识实现"。

**决策②：为什么 `Authenticator` 要分 `Authenticate(ctx)` 与 `AuthenticateToken(token)`？** `Authenticate` 从请求 ctx 抽凭证（中间件主路径）；`AuthenticateToken` 给非传输场景（CLI 校验、测试、内部服务调用）直接验串。两者共用同一过期校验契约。

**决策③：为什么授权做归一化而不是各传输层各写各的？** 归一化让策略只写一份（`secret` + `get`），双传输同源。代价是默认规则有假设（`v1` 前缀、`Service` 后缀、方法名前缀推导）——业务可经 `ObjectResolver`/`ActionResolver` 覆盖，默认值在文档与代码注释里写死。

**决策④：为什么 `AllowAll`/`DenyAll` 进核心？** 它们是"零策略"的两个极端（开放接口/默认拒绝），不依赖任何引擎，放核心让中间件开箱可用（不注入 Authorizer 时默认 DenyAll，fail-closed）。

## 兼容性

纯增量，无破坏：新增 `pkg/authn`、`pkg/authz` 两包，现有包不动；中间件新增 `Authn*`/`Authz*` 构造器（与既有 `Observability`/`Audit` 中间件并列），无存量调用受影响。

## 实现与过渡

| 步骤 | 内容 | 验证 |
|---|---|---|
| 1 | `pkg/authn`：`AuthClaims` + `Authenticator` + context 注入/读取 | 单测：过期校验、HasScope/HasRole、context RoundTrip |
| 2 | `pkg/authz`：`Authorizer` + `Func` + `AllowAll/DenyAll` + 归一化函数 | 单测：四组归一化映射、DenyAll fail-closed |
| 3 | `pkg/middleware/{gin,grpc}`：`Authn*`/`Authz*` 依赖倒置接入 + `SkipPaths` | 单测：401/403/500 映射、公开路径豁免、subject 传递 |
| 4 | `bald-authn-jwt`（首个范本桥接子模块） | e2e：登录签发 + 拦截校验 |
