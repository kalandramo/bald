# bald 错误模型：零依赖核心包 + 可选 gRPC 桥接子包，不可变 Error 骨架补齐 Message 与双向传输

> 适用包：`pkg/berrors`（新增）、`pkg/berrors/grpcerr`（新增）、`pkg/berrors/httperr`（新增）
> 关联文档：`路由注册与绑定设计.md`（§4 的 `web.Error` 提案由本设计取代，web 层经 `httperr.StatusCode` 取状态码）、`服务端设计.md`
> 参考实现：go-lulu `errors`（`WindError`）、onexstack `pkg/berrorsx`（`ErrorX`）、kratos `api/errors`
> Last updated: 2026-08-29
> Status: Accepted

## 摘要

我们提议为 bald 新增 `pkg/berrors` 错误模型包：**核心包零依赖**（不 import gRPC、net/http、kratos、gin），提供不可变的 `Error` 类型（传输中立 `Code` + 稳定 `Reason` + 用户 `Message` + i18n `Details` + 可选 `cause` 与调用栈）、按 `Reason` 匹配的 `Is`、工厂函数与标准库 `errors` 桥接；gRPC 双向转换（`status.Status` + `errdetails.ErrorInfo`）放在 `pkg/berrors/grpcerr` 子包、HTTP 状态码映射（`CodeToHTTP`/`StatusCode`）放在 `pkg/berrors/httperr` 子包，**两个边界桥接子包只在传输边界引入，核心包始终保持零传输依赖**。

**最重要的承诺：核心包零依赖，任何场景（纯 HTTP、gRPC、CLI、测试）都能 import `pkg/berrors` 而不会拖进一个传输框架。** 这个承诺与 bald 的底座哲学一致——`pkg/log` 已是先例：核心零依赖、默认 nop、用户装配期注入。

设计的出处是对两个现有实现的合取：go-lulu `errors` 贡献了零依赖、不可变 builder、按 `Reason` 匹配、栈捕获；onexstack `errorsx` 贡献了 `Message` 字段与 gRPC 双向闭环（`GRPCStatus`/`ErrorInfo`/`FromError`）。我们取两家之长，并把 gRPC 耦合从核心剥离成可选子包。

## 背景与动机

**两个现有实现各有一半正确，但都缺另一半。** 我们上一轮对比了 go-lulu `errors` 与 onexstack `errorsx`，结论是互补的：

go-lulu `WindError` 的骨架是对的——**零依赖 + 不可变 builder** 让错误类型可以安全地作为 sentinel 常量被派生：

```go
var ErrOrderNotFound = errors.NotFound("ORDER_NOT_FOUND")

// go-lulu：返回新实例，ErrOrderNotFound 保持原样。
return ErrOrderNotFound.WithDetails(map[string]string{"id": id})
```

但它缺两块：没有面向用户的 `Message`（只有 `Reason` + `Details`，前端必须做 i18n 模板才能给用户看）；gRPC 方向是半通的——没有 `GRPCStatus()`，传输时要调用方手写 `codes.Code(wErr.Code)`，且**从 gRPC 收到的错误无法反向解析**，跨服务语义在接收端丢失。

onexstack `ErrorX` 补上了这两块：`Message` 字段直接带用户文案；`GRPCStatus()` 自动附 `errdetails.ErrorInfo{Reason, Metadata}`，`FromError` 能把 gRPC status 解析回 `ErrorX`。但它把整个核心包绑死了 Kratos + gRPC，`Code` 直接是 HTTP 状态码，而且 builder 是**可变**的——sentinel 被 `WithMetadata` 就地污染是真实 bug 源：

```go
// onexstack：就地修改，sentinel 被污染，后续所有调用方都带上了上一次的 id。
return ErrOrderNotFound.WithMetadata(map[string]string{"id": id})
```

**一句话给问题定性：bald 需要一个"go-lulu 的骨头 + errorsx 的血肉"——零依赖、不可变、带 Message、gRPC 双向闭环的错误模型，并且不能因为 gRPC 能力而让核心包背上任何依赖。**

这不是凭空发明。Kratos 生态的 `api/errors` 已经证明"错误类型实现 `GRPCStatus()`、携带 `ErrorInfo`"是 Go 微服务的既定路径；go-lulu 证明"零依赖核心 + 边界转换"同样可行。我们的工作是把两者在 bald 的依赖纪律下合并。

## 设计

从最小的错误类型讲起，然后加构建器、匹配、HTTP 映射；gRPC 能力单独成节，因为它决定了核心包的依赖边界。

### 1. Error：四个字段 + 两个可选附加物

```go
package errors

// Error 描述一个业务失败。所有字段均可为空。
type Error struct {
    Code    uint32            `json:"-"`       // 传输类别，与 gRPC codes.Code 1:1，见 Code* 常量
    Reason  string            `json:"reason"`  // 领域稳定标识，如 "ORDER_NOT_FOUND"，errors.Is 按它匹配
    Message string            `json:"message"` // 可展示给最终用户的简短文案
    Details map[string]string `json:"details"` // i18n 动态变量，如 {"id": "42"}
    cause   error             `json:"-"`       // 包装的底层错误（error 链）
    stack   []uintptr         `json:"-"`       // 失败点调用栈，日志收集用
}
```

**边界：**
- `Code` 用 `uint32` 而不是 `codes.Code`，核心包因此不依赖 gRPC；`Code` 取值与 gRPC 协议 1:1（`CodeNotFound = 5` 等），见附录。
- `Reason` 是不可变契约：永不本地化、永不翻译；它决定 `errors.Is` 的匹配结果。
- `Message` 与 `Details` 分工：`Message` 是一句完整可展示的话（"订单不存在"），`Details` 是前端做 i18n 模板的动态变量。两者都写也不冲突。
- `cause` 与 `stack` 是附加物：裸 `New` 不带，由 builder 补上。

### 2. 构造：工厂函数优先，New 兜底

```go
// 常用传输类别工厂：BadRequest / NotFound / AlreadyExists / PermissionDenied /
// ResourceExhausted / FailedPrecondition / Unauthenticated / Internal /
// Unimplemented / Unavailable / DeadlineExceeded
if order == nil {
    return errors.NotFound("ORDER_NOT_FOUND")
}
// 需要用户文案时链上 WithMessage：
return errors.NotFound("ORDER_NOT_FOUND").WithMessage("订单 %s 不存在", id)
```

`New(code, reason)` 只留给工厂之外的场景。

### 3. 不可变 builder：sentinel 永远安全

所有 `With*` 方法返回新实例，接收者绝不被修改：

```go
func (e *Error) WithMessage(format string, args ...any) *Error
func (e *Error) WithDetails(details map[string]string) *Error
func (e *Error) WithCause(cause error) *Error
func (e *Error) WithCode(code uint32) *Error

// sentinel 派生是安全的：
var ErrOrderNotFound = errors.NotFound("ORDER_NOT_FOUND")
return ErrOrderNotFound.WithDetails(map[string]string{"id": id}) // 新实例，原变量不变
```

栈捕获发生在第一个 `With*` 调用时（`runtime.Callers`），幂等、延迟到真正派生的时刻。`StackTrace()` 格式化输出供日志收集。

**边界：** `WithDetails` 浅拷贝 `Details` map（共享底层），安全的前提是它整体替换 map 而不是就地改键；后续若新增就地修改方法必须改深拷贝。

### 4. 匹配与标准库桥接

```go
// Is：两个 Error 按 Reason 相等匹配；Code/Message/Details/cause 故意忽略。
// 这样跨服务时——同一个"订单不存在"在 A 服务可能是 NotFound、在 B 服务被包装成
// Internal——errors.Is 依然命中，因为匹配的是稳定业务标识。
func (e *Error) Is(target error) bool

// 包级桥接：本包遮蔽标准库 errors，重导出最常用函数，调用方无需别名。
func Is(err, target error) bool { return stderrors.Is(err, target) }
func As(err error, target any) bool
func Unwrap(err error) error
func Join(errs ...error) error

// FromError：从任意错误链提取 *Error，找不到返回 (nil, false)。
func FromError(err error) (*Error, bool)
```

### 5. HTTP 状态码：外置到 `httperr` 桥接子包

HTTP 映射**不放在核心包**。核心包只持有传输中立的 `Code`（`uint32`，与 gRPC `codes.Code` 1:1），
`Code → HTTP status` 的权威映射（grpc-httpjson-transcoding / Envoy 规范，17 码全表）放进 `pkg/berrors/httperr` 子包，返回 `int`，不依赖 `net/http`：

```go
w.WriteHeader(httperr.CodeToHTTP(wErr.Code))   // 未知码兜底 500，绝不产生误导性 2xx
```

`httperr` 额外提供 `StatusCode(e *errors.Error) int`（`CodeToHTTP(e.Code)`）与反向 `HTTPToCode(status int) uint32`。
**刻意不实现为核心包的方法**：若把 `StatusCode()` 放在 `*Error` 上，核心包会反过来 import `httperr`（循环依赖），
也违背「核心包零 net/http/gin 依赖」的承诺。`web` 层在边界用 `httperr.StatusCode(e)` 取状态码（见 `路由注册与绑定设计.md` §3.4）。

> 设计意图：`grpcerr`（gRPC 边界）与 `httperr`（HTTP/gin 边界）是两个**对等**的桥接子包，
> 都只在对应传输边界被 import，核心包 `pkg/berrors` 始终零 gRPC/net/http/gin 依赖。

### 6. gRPC 双向闭环 + HTTP 映射：两个独立子包，边界引入

核心包**不实现** `GRPCStatus()`、也不持有 `StatusCode()`——那都是传输依赖，会破坏零依赖承诺。
转换能力按协议分到两个子包：

```go
package grpcerr // gRPC 边界

// ToStatus：把 *errors.Error 转成 gRPC status，附 errdetails.ErrorInfo{Reason, Details}。
func ToStatus(err error) *status.Status

// FromStatus：把 gRPC status 解析回 *errors.Error（从 ErrorInfo 恢复 Reason/Details）。
func FromStatus(st *status.Status) error
```

```go
package httperr // HTTP/gin 边界

// CodeToHTTP：Code → HTTP 状态码（未知码兜底 500）。
func CodeToHTTP(code uint32) int

// HTTPToCode：HTTP 状态码 → Code（因正向多对一，取语义最贴切者；未知兜底 Unknown）。
func HTTPToCode(status int) uint32

// StatusCode：*errors.Error → HTTP 状态码，替代核心包方法（防循环依赖）。
func StatusCode(e *errors.Error) int
```

- gRPC server 拦截器在边界调 `grpcerr.ToStatus(err)` 收口，`status.Error(...)` 透传。
- gRPC client 收到错误调 `grpcerr.FromStatus` 恢复结构化 `*errors.Error`，`errors.Is` 依然按 Reason 命中。
- kratos 的 `api/errors` 同样实现 `GRPCStatus()` + `ErrorInfo`，所以 `FromStatus` 天然能解析 Kratos 错误；反过来 `ToStatus` 产的 status 也能被 Kratos 客户端理解。跨生态语义互通。
- HTTP 侧（gin）在 `web.ErrorResponse` 用 `httperr.StatusCode(e)` 还原状态码，不再依赖核心包方法。

### 7. 改造前 vs 改造后对照

| | 现状 / 参考实现 | 引入 pkg/berrors 后 |
|---|---|---|
| 核心依赖 | go-lulu 零依赖 ✓；errorsx 绑 Kratos+gRPC ✗ | 零依赖（两侧都要的） |
| 用户文案 | go-lulu 无 Message；errorsx 有 | 有 `Message` |
| builder 安全性 | go-lulu 不可变 ✓；errorsx 可变 ✗ | 不可变（取 go-lulu） |
| gRPC 发送 | go-lulu 边界手写；errorsx 内置 ✓ | `grpcerr.ToStatus` 边界收口 |
| gRPC 接收 | go-lulu 丢失；errorsx 内置 ✓ | `grpcerr.FromStatus` 恢复 |
| HTTP 码表 | go-lulu 内置 ✓；errorsx 靠 kratos | `httperr` 子包（取 go-lulu，核心零依赖） |
| 匹配语义 | go-lulu 按 Reason ✓；errorsx 按 Code+Reason | 按 Reason（取 go-lulu） |
| 栈捕获 | go-lulu 有 ✓；errorsx 无 | 有（取 go-lulu） |

## 理由与取舍

**决策①：为什么核心零依赖，gRPC 单独拆子包？**
这是全设计的承重墙。bald 的底座承诺是"任意场景可复用"——一个纯 HTTP 服务、一个 CLI 工具、一个单元测试，都不该为了一个错误类型背上 gRPC。`pkg/log` 已经立了先例（核心零依赖、后端注入）。拆子包后，核心包 0 个外部依赖，`grpcerr` 只在用 gRPC 的项目里被 import，成本精确落到使用处。被放弃的方案：把 `GRPCStatus()` 直接放在核心类型上（errorsx 的做法）——省 20 行，但核心包从此依赖 grpc + genproto，且任何不使用 gRPC 的调用方也被迫链接它们。

**决策②：为什么 `Code` 是传输中立 `uint32`，而不是 HTTP 状态码？**
一个错误要能在一个请求里以 HTTP 形态出去、在下一个服务里以 gRPC 形态进来。`Code` 保持与 gRPC `codes.Code` 1:1，HTTP 码只是它的一次投影（`CodeToHTTP`）。反过来（errorsx 的 `Code int` 即 HTTP 码）会让 gRPC 方向必须依赖 kratos 的转换表——我们把"传输类别"这个概念握在自己手里，而不是外包给第三方。被放弃的方案：直接用 `codes.Code` 类型——省一次转换，但核心包立刻依赖 gRPC，违反决策①。

**决策③：为什么不可变 builder？**
可变 builder（errorsx）的 bug 真实存在：sentinel 常量被 `WithMetadata` 就地污染后，所有调用方共享同一份 metadata，跨请求串数据。不可变（clone + 整体替换 Details）把"共享 sentinel"从雷区变成安全区。代价是每次派生多一次小分配——业务错误构造不是热路径，可忽略。被放弃的方案：直接复制 go-lulu 的浅拷贝 clone——正确，但我们保留同样的注释警告：若未来新增就地修改方法必须改深拷贝。

**决策④：为什么 `Is` 只比 `Reason`，不比 `Code`？**
`Code` 是易变的传输分类：同一个业务失败在不同服务、不同时刻可能被标成 `NotFound` 或 `Internal`（包装后）。`Reason` 才是稳定契约。errorsx 比 `Code + Reason` 双等，让匹配语义混入了易变维度，跨服务时不可靠。被放弃的方案：比全部字段——`Details` 每次派生都不同，sentinel 匹配直接失效。

**决策⑤：为什么 `Message` 和 `Details` 并存，而不是只留一个？**
`Message` 满足"直接给用户看一句完整的话"（错误码表的默认文案）；`Details` 满足"前端做 i18n 模板"（动态变量替换）。两个消费方，两种载体。只留 `Details`（go-lulu）逼着所有服务端去写前端模板；只留 `Message`（简化版）丢失结构化变量。并存不冲突。

**决策⑥：为什么不直接照搬 go-lulu 整个包？**
我们不是从零造轮子，但 bald 需要 `Message`（go-lulu 没有）和 gRPC 反向解析（go-lulu 没有）。直接 vendor go-lulu 的包意味着把它的两个缺口也搬进来，再在外部打补丁——不如在一个我们自己的包内把模型定义清楚。被放弃的方案：直接依赖 go-lulu/errors 并在外面加 wrapper——wrapper 破坏 `errors.Is` 链和 `ErrorInfo` 透传，得不偿失。

**决策⑦：为什么错误模型独立成包，而不是留在路由文档的 `web.Error`？**
路由设计文档 §4 提的 `web.Error` 是"web 层的最小桥"。但错误是跨协议的概念（HTTP + gRPC），它不该属于 web 层。独立成 `pkg/berrors` 后，gRPC 侧（`grpcerr`）与 HTTP 侧（`httperr.StatusCode`）都引用同一个模型，HTTP handler、gRPC handler、job、CLI 共享同一套错误语义。**本设计 Accepted 后，路由文档 §4 的 `web.Error` 提案由 `pkg/berrors` 取代；HTTP 边界状态码经 `httperr.StatusCode(e)` 取得（不在核心包上挂方法，以避免循环依赖）。**

## 兼容性

**这是纯增量变更，无破坏。** 具体承诺：

1. 新增 `pkg/berrors`、`pkg/berrors/grpcerr`、`pkg/berrors/httperr` 三个包，现有包一律不动。
2. `pkg/log` 已确立的"包名遮蔽标准库"先例同样适用于 `pkg/berrors`（`errors` 包名遮蔽标准库 `errors`，桥接 `Is/As/Unwrap/Join`），调用方无需改 import。注意与 go-lulu 相同的限制：**`New` 不桥接**（本项目 `New(code, reason)` 与标准库 `New(string)` 签名冲突），需要标准库 `New` 时别名 import。
3. 路由设计文档 §4 的 `web.Error` 尚未落地（文档 Draft/Accepted 状态，无代码），由 `pkg/berrors` 取代是替换而非迁移，零存量代码受影响。

**已知代价（诚实列出）：**
- 每次 `With*` 派生多一次 `runtime.Callers` 栈捕获 + 一次小分配（`clone`）。栈捕获只在首个子构建器触发且幂等；业务错误构造不是热路径。
- 核心包 0 依赖的代价是：用 gRPC 的项目必须显式 import `grpcerr` 并在拦截器/客户端收口各写一行转换——比 errorsx 的"开箱即用"多 2 行样板。这是决策①的明码标价。
- `Error()` 输出格式（`code: %d, reason: %s; cause: %v`）是日志可读性取向；`Message` 不混入 `Error()`，需要展示时取字段而非字符串——避免日志串被多语言文案污染。
- HTTP 映射放在 `httperr` 子包（而非核心包方法）的代价是：web 层取状态码需 `httperr.StatusCode(e)` 而非 `e.StatusCode()`——多一次包前缀，但核心包保持零循环依赖、零 net/http 依赖。这是决策①在 HTTP 侧的对称延伸。

### A. `pkg/berrors` API 清单（草案）

```go
// errors.go
type Error struct { /* 见 §1 */ }
func New(code uint32, reason string) *Error
func BadRequest(reason string) *Error          // + NotFound/AlreadyExists/PermissionDenied/
func (e *Error) Error() string                 // ResourceExhausted/FailedPrecondition/Unauthenticated/
func (e *Error) Is(target error) bool          // Internal/Unimplemented/Unavailable/DeadlineExceeded

// builder.go
func (e *Error) WithMessage(format string, args ...any) *Error
func (e *Error) WithDetails(details map[string]string) *Error
func (e *Error) WithCause(cause error) *Error
func (e *Error) WithCode(code uint32) *Error
func (e *Error) StackTrace() string

// code.go
const CodeOK uint32 = 0; /* ... CodeUnauthenticated = 16 */

// bridge.go
func Is(err, target error) bool
func As(err error, target any) bool
func Unwrap(err error) error
func Join(errs ...error) error
func FromError(err error) (*Error, bool)

// httperr/httperr.go  （HTTP/gin 边界，核心包不依赖此子包）
```

```go

if order == nil {
    return nil, errors.NotFound("ORDER_NOT_FOUND").WithMessage("订单 %s 不存在", id)

// HTTP 层（web.WriteResponse 内）：经 httperr 取得状态码，核心包不挂方法

st := grpcerr.ToStatus(err)   // grpc status + ErrorInfo{Reason, Details}

if wErr, ok := errors.FromError(grpcerr.FromStatus(st)); ok {
```

### C. FAQ

**为什么包名遮蔽标准库 `errors`？** Kratos `api/errors`、grpc `errors` 都是同样的惯例；桥接 `Is/As/Unwrap/Join` 后调用方只 import 一个包。代价与 go-lulu 相同：`New` 不桥接，需要标准库 `New` 时别名 import。

**和 Kratos `api/errors` 是什么关系？** 平行实现，通过 `grpcerr.FromStatus`（Kratos 错误也带 `ErrorInfo`）互转。不依赖它，因为 Kratos 的包自带 gRPC 依赖，违反核心零依赖。

**为什么栈捕获只在 `With*` 时发生，`New` 不捕获？** `New` 常用于包级 sentinel 定义（不是失败现场）；失败现场是派生 `With*` 那一刻。延迟到派生时捕获，正好拿到真实调用点，且避免每次 `New` 都付 `runtime.Callers` 的代价。

**`Message` 进不进 `Error()` 字符串？** 不进。`Error()` 是给日志看的（`code/reason/cause`），`Message` 是给用户看的（字段直接取）。混进 `Error()` 会让日志被多语言文案污染，且 `Error()` 字符串无法结构化消费。
