# bald 装配层评估：诊断、目标设计与路线图

> 评估对象：`kalandramo/bald`（框架，多 module）与其 reference example `kalandramo/bald-admin`。
> 评估日期：2026-10-15。基线提交：bald `2ad7222`（main，与 origin 同步）、bald-admin `0535551`。
> 本文回答三个问题：装配层是否合理、缺陷深度是否由 bald 框架模块导致、以及「业务聚焦写业务」这个愿景如何落地。

## 0. 一句话结论

**装配复杂度的主要来源是框架结构，不是示例用法。** 三条结构性缺陷最硬：框架没有「业务域」这个一等概念（`AppSpec` 里没有域字段，生成物把业务入口留成 TODO 桩）；13 份资源注册表逐行同构、而本可消除它们的泛型 `appkit.Registry[T]` 全仓零引用；「契约段 → 消费者」靠人工枚举表维系，且**静默漏消费已经发生**（`script` 契约段全仓零消费者，配了不报错）。

按四条验收判据的当前裁决：**① 新增业务域只动 3 个文件、零装配修改 —— 不成立**（实测下界 7 个文件、其中装配 4 个）；**② 装配行数不随域数量增长 —— 不成立**（每个业务域约 14 处装配引用）；**③ 业务代码不 import 装配层 —— 实质成立**（业务层对 `appkit`/`bootstrap`/`internal/**` 零依赖），但口径需钉死；**④ 新服务 30 分钟跑起来 —— 无任何计时证据**。

目标形态可收敛到 **3 条语句、0 个必填 Option、0 个必须理解的框架概念**，appkit 默认可见面从 **147 个导出符号降到约 34 个（-77%）**。代价是 breaking（每处已在 §5 列出迁移动作）。

### 1.2 行数口径（重要纠正）

本机 `Get-Content` 默认按非 UTF-8（GBK）解码这些含中文的源文件，UTF-8 中文字节被错拼时会**吞掉行尾 LF**——同一个 `appspec_gen.go`，真实 368 行会被读成 316 行（实测：文件 368 个 `0x0A` 字节，`Get-Content -Raw` 只数出 316 个 LF）。`Select-String` 的行号同样漂移。

**本次所有行数/行号一律使用 UTF-8 安全通道**（`[System.IO.File]::ReadAllLines/ReadAllText`、`git grep`、ripgrep、`find /c /v ""`）。权威基线：

## 2. 现状实测

### 2.1 框架侧：装配面有多大，其中多少是用户必须理解的

`pkg/appkit` 对外可见 **147 个导出符号**（`go doc -all` 权威计数：func/method 125、type 15、const 5、var 2；`type` 计数已独立核对为 15）。按处置视角分组：

| 组 | 数量 | 内容 |
|---|---|---|
| 入口与生命周期 | 23 | `New`/`FromBootstrap`/`Run`/`BeforeStart`… |
| 配置 | 19 | `ConfigFile`/`RemoteConfig`/`ConfigLayers`/`StrictContract`/`WithConfigNamespace`… |
| 协议面与健康检查 | 14 | `WithHTTP`/`WithGRPC`/`WithGatewayRegister`/`WithProbes`… |
| **资源域注册表与访问器** | **45** | 13 张注册表（`New*Registry`/`Register`/`MustRegister`/`Build`）与 12 个 `X()/Xs()` 访问器 |
| **自研机制** | **26** | `Effect`/`Components`/`Provides`/`Requires`/`OnKeyChange`/`Reconcile`/`ReconcileCtx`… |
| 运行期挂载 / 测试装置 / 泛型注册表 | 17 | `MountComponent`/`UnmountComponent`/`NewHarness`/`Registry[T]`… |
| 可观测与审计的后端装配 | 3 | `Auditor`/`StartMetricsServer`/`WithLogDecorators` |

三个可直接量化的问题：

1. **机制层占 appkit 的 23.6%**：`capability.go` 95 + `component.go` 116 + `effect.go` 92 + `keywatch.go` 91 + `mount.go` 194 + `reconcile.go` 367 = **955 行 / 4,052 行**。这套自研原语（能力声明 S1、组件生命周期 C1、效应账本 T1、运行期挂载 A1、key 级热更新 R1/R1-2）普通业务用户一个都用不到，却与日常 API 平铺在同一个包面里。
2. **6 个能力胶水文件逐行同构、纯转发**：`ai.go` 78 + `broker.go` 77 + `cache.go` 74 + `database.go` 78 + `storage.go` 76 + `workflow.go` 74 = **457 行**（占 11.3%），唯一决策是 Effect 注册位置；它们把「注册表 → 构建 → 存字段 → 提供访问器」这四步在六个域上抄了六遍。
3. **15 组同义双拼名**：`Bind`(`appkit.go:224`) ↔ `WithBind`(`bootstrap.go:450`)、`Provides` ↔ `WithProvides`、`Effect` ↔ `WithEffect`、`Reconcile` ↔ `WithReconcile`、`Components` ↔ `WithComponents`、`AfterStart`(`appkit.go:345`) ↔ `WithAfterStart`(`bootstrap.go:244`)…… 30 个导出名承载 15 个语义。且这套「同一个机制在两个入口各导出一次」**本身也没做齐**：有 `AfterStart`/`WithAfterStart`，却没有 `WithAfterStop`——这本身就是增量式设计的痕迹。

**注册表面（判据 ② 的要害）**：13 张注册表形状完全一致（`type XProvider func(...)` + `type XRegistry struct{ mu; providers map[string]XProvider }` + `NewXRegistry` + `Register` + `MustRegister` + `Build`），用户最小成本 3 行/表（`New` + `MustRegister` + `With*Registry`），13 域全用约 39 行。更关键的是**两张手工枚举表**：

- `bootstrap/database.go:77-86` `databaseSections`——8 个引擎段，注释 `:69-71` 自陈：「新引擎在 bconf 加段后**在此追加**（编译期漏加 = 该段配置静默无消费，由『契约字段须全有消费者』审查兜底）」。
- `bootstrap/server.go:100-141` `serverSections`——32 个段，只有 `http`/`grpc` 标记 `implemented: true`。

**而这句自陈的后果已经实现**：`BootstrapConfig` 声明了 15 个顶层段（`bconf/proto/bootstrap/v1/bootstrap.proto:26-71`），其中 `script` 段**全仓零消费者**——`git grep -E 'ScriptRegistry|WithScriptRegistry|scriptSection|WithScript'` 命中 **0**，`bootstrap/` 与 `pkg/appkit/` 下无 `script*.go`。用户配了 `script:` 段，框架静默忽略、不报错、不告警。**「靠人工审查兜底」这条防线已被证明是失效的。**

一个反直觉的对照：框架里**已经有**消除这 13 份拷贝的抽象——`pkg/appkit/registry.go:18` 的泛型 `Registry[T any]`，但它在全仓（含测试、示例、cmd）**零引用**。抽象建好了没人用，拷贝留在原地。

### 2.2 示例侧：装配路径有多长

`bald-admin` 从 `main.go:27` 到服务器起来 = **24 跳 / 19 个装配文件 / 3,787 行**（占非生成非测试代码 **20.7%**）。其中 6 个核心装配文件 2,400 行。值得注意的细节：

- 19 个装配文件里注释 1,392 行 = 非空行的 **40%**——这不是啰嗦，是**脚手架的自我解释成本**：一个没有文档就读不懂的装配层。
- `cmd/bald-admin/app/` 20 个文件的定性：纯装配 4、**挟带业务决策 8**、演示/适配 2、测试 6。限流/熔断/重试阈值（`app/options/options.go:93-110`、`app/builders.go:20-111` 读 `login.rate_limit.*`/`login.breaker.*`/`login.retry.*`）、审计后端集合（`app/audit.go:183`）、cron 表达式（`app/cron.go:44-46`）、SSE 安全语义（`app/sse.go:118-142`）、令牌 TTL、桶名——**业务决策住在装配目录**。
- 业务种子数据 369 行写在装配根（`internal/bootstrap/bootstrap.go:457-826` 的 seed + seedPolicies），占该文件 40%。
- 仓库唯一一条机械化守卫只锁一条边界：`internal/apiserver/layering_invariant_test.go:34-69`（biz 非测试文件不得 import `internal/bootstrap`），且它用的是**子串匹配**而非解析 import，还显式跳过 `_test.go`——即这条唯一守卫本身也偏弱。

**新增一个业务域的真实成本**（git 实证，非推导）：`89f14e5 feat(permgroup)` 动了 **8 个文件**——biz 325 行、handler 136、model 55、e2e 测试 322，加上装配侧的 `bizset.go`、`server.go`、`bootstrap.go`、`wire_gen.go`。注意这个提交里**没有 proto**（契约先行），也就是说这 8 个文件全是「契约已有、接线新加」的成本。按域规模不同，全栈域（如 `dict`）触碰 15–17 个文件，其中装配 6–7 个。

判据 ①「零装配修改」为什么不可能，机制上很清楚：不注册 bizset 字段编译不过、不挂 `server.go:46` 路由进不来、不建 store 与 AutoMigrate 跑不起来、不写策略行（`bootstrap.go:614-826`）新域恒 403。

### 2.3 生成器侧：它固化了示例的复杂度，还是落后于它

`cmd/bald` 实际只有 **3 个子命令**（`gen proto` / `gen store` / `gen app`）；`appspec` 不是子命令，是 `gen app --spec` 模式。

| 子命令 | 产物 | 装配占比 |
|---|---|---|
| `gen proto <name>` | 1 文件（package + service + 4 message），**0 个 Go 函数** | 0% |
| `gen store <name>` | 1 文件 10 行（struct + `KeyOf<Name>`），无落点约定（默认写 CWD），**零测试** | 0% |
| `gen app <name>` | 1 文件 96 行，函数 `main`/`newApp`/`buildBundle`/`buildServers`；`buildServers` 从未被调用（死代码） | **100%** |
| `gen app --spec` | 1 文件 `package main`，11 个函数（`serveRunE`/`buildComponent`/`buildAuditBackend`/`applyAuditors`/`reconcileAudit`…） | **≈100%**（业务仅 6 处 TODO 注释） |

三个必须记下的问题：

1. **生成器是示例装配的删减副本**：`appspec_gen.go` 的 `reconcileAudit`(:227) / `auditBackendComponent`(:264) / `buildAuditBackend`(:294) / `applyAuditors`(:309) 与示例 `cmd/bald-admin/app/audit.go:133/55/101/32` **同名同形**。示例里的装配复杂度不只是被模仿，是被**固化进了用户的起点**。
2. **副本还漏掉了后来补的修复**：模板的 `Dispose`（`appspec_gen.go:282-289`）只从 map 删除、**不 Close 后端**；而 `audit.go:82-90` 的注释明写不收尾的后果——「每次热更新泄漏一个 goroutine + 1024 容量 chan，且已入队事件被静默丢弃」。模板也没有 `audit.go:178-193` 的值域白名单。
3. **生成物走的是被取代的旧装配路径**：模板 emit `bconf.NewBootstrap()` + 手写 `appkit.Bind`×3 + `appkit.New(capOpts...)`（`appspec_gen.go:81,124-127,175`），而示例已迁到 `appkit.FromBootstrap`（`assembly.go:616`）并把这些样板内化。生成器**比参考示例旧一代**，因此也拿不到 `FromBootstrap` 路径上的契约一致性 fail-fast。

**声明面与契约面严重不匹配**：`AppSpec` 只有 6 个字段（`meta`/`server`/`components`/`capability`/`audit_backends`/`bundle_normalized`），而 `bconf` 已契约化了 15 个段。缺 `log`/`registry`/`database`/`cache`/`storage`/`tracer`/`metrics`/`middleware` 的声明能力 → 这些装配只能手写，**装配复杂度无法声明化**。且声明字段并不保证有消费者：`ServerSpec.gateway`（`appspec.proto:52`）在 `internal/codegen` 里 grep `Gateway` = **0 命中**，是死声明——声明了不生成任何接线，文档却称「模板 TODO 改为生成该接线」。

**契约校验的闸门造好了，却没接进生成物**：`bconf` 的 `FindUnknownKeys`（`bconf/unmarshal.go:41`）由 `bootstrap/config/config.go:240-247` 在 `StrictContract` 开启时消费，框架面入口是 `appkit.WithStrictContract`（`pkg/appkit/bootstrap.go:298`）；但 `StrictContract` 在 `internal/codegen` 里 **0 命中**——生成物从不 emit 它。后果：用户照抄 `docs/guide` 里的 `http.addr`（正确键是 `server.http.addr`），运行期被 `DiscardUnknown: true`（`bconf/unmarshal.go:151-153`）**静默吞掉**，本该拦住它的那道门在生成物里根本没接线。

**膨胀是线性的、可证**：加一个能力要同步改 4 处——proto 字段 + `appspecData` 手工转发（`appspec_gen.go:342-349`）+ `runGenAppSpec` 6 字段转写（`app.go:241-248`）+ 模板条件块与测试锚点（`app_test.go:111-120`）。组件 kind 是字符串 switch（`appspec_gen.go:198-210`），取值清单只存在于 proto 注释；配置键是裸字符串（`:120,124-125,130`），与 `bconf` 契约无编译期关联。

**测试覆盖不足**：现有测试只断言字符串锚点 + 能否编译 + 一条 3 秒存活冒烟（`app_test.go:41,111,177`），不覆盖 gateway、多 kind、真实端口、生成物目录结构、声明字段是否全被消费；`gen store` 零测试。

### 2.4 四条判据的裁决

| 判据 | 裁决 | 证据 |
|---|---|---|
| ① 新增业务域只动 3 文件、零装配修改 | **不成立** | permgroup 实证 8 文件（装配 4）；全栈域 15–17 文件（装配 6–7）；`bizset.go:39`/`server.go:46` 是不改就编译不过/路由不进来的硬耦合 |
| ② 装配行数不随域数增长 | **不成立** | 21 域在 6 个装配文件中共 282 处域相关引用 ≈ 14 处/域；`assembly.go:274-288` 与 `servers.go:66-102` 是逐 service 手工登记 |
| ③ 业务不 import 装配层 | **实质成立**（口径需钉死） | 业务层对 `pkg/appkit`/`bootstrap`/`internal/**` **零条**；依赖 `pkg/store`(19 文件)/`berrors`(11)/`pkg/contextx`(5) 属业务 API 层 |
| ④ 新服务 30 分钟跑起来 | **无证据** | 无任何计时实测；仅文档「30–60 行样板」的说法 |

判据 ③ 的口径按以下三层钉死（本文采此口径，后续以此验收）：**业务 API 层**（`pkg/store`、`pkg/contextx`、`berrors`、生成的 `storev1` 契约、能力包的公开接口）——允许；**装配层**（`pkg/appkit/**`、`bootstrap/**`、任何 `internal/**`、注册表与契约段 provider 类包）——违规；**能力实现层**（`cache/loadable`、`contrib/authn-jwt`、`oss/minio`、`oss/s3`）——允许但应有意识。

## 3. 归因：缺陷深度是否由 bald 框架模块导致

**结论：主要由框架结构导致（可修）；示例放大了它（不必修）；另有一组是有意取舍（不该改）。**

### 3.1 框架结构必须改

| # | 框架缺陷 | 硬证据 | 命中判据 |
|---|---|---|---|
| F1 | **不存在「业务域」一等概念** | `AppSpec` 无域字段；生成物把业务入口留 TODO 桩（`appspec_gen.go:109` HTTP、`:214` `func registerGRPCService(s *grpc.Server) {}`） | ①（核心） |
| F2 | **注册表抽象没被抽出** | 13 张表逐行同构；`appkit.Registry[T]`（`pkg/appkit/registry.go:18`）全仓零引用 | ② |
| F3 | **每新增资源域需同步改 7 处** | registry 文件 / `bootstrapSpec` 字段 / `With*Registry` / `build*` / 阶段 B 调用 / Effect 注册 / AppKit 字段与访问器 | ② |
| F4 | **手工段枚举表 + 已发生的静默漏消费** | `bootstrap/database.go:77-86`（注释自陈）、`bootstrap/server.go:100-141`；**`script` 段零消费者** | ②（+ 隐性正确性） |
| F5 | **双入口 + 15 组双拼，且双拼不齐** | `New`(`appkit.go:373`) vs `FromBootstrap`(`bootstrap.go:460`)；15 组同义名；`AfterStop` 无对应 `WithAfterStop` | ④ |
| F6 | **唯一必填 Option 源于内部自指** | `WithConfigNamespace`(`bootstrap.go:265`) 缺则 `:640-645` 直接报错；自指论证见 `appkit.go:56-66` | ④ |
| F7 | **内部时序约束外泄为逃生舱** | `WithGRPCOptions`(`:199`)、`WithExtraServerFunc`(`:239`) 注释自陈；而根因已由「server 构造延后到 Run 期」根治（`:533-543` + `wiring_order_test.go:27-65`）——**根因修了、舱留着** | ④ |
| F8 | **codegen 生成旧装配路径且落后于示例** | `internal/codegen/app.go:52`、`appspec_gen.go:175` 均产 `appkit.New(...)`；模板漏掉 `Dispose` 的 Close 修复 | ④（生成物即用户起点） |

### 3.2 示例（bald-admin / _example）导致 —— 框架无需改

| # | 现象 | 为什么框架不用改 |
|---|---|---|
| E1 | 注释占装配非空行 40%（1,392/3,787） | 脚手架自述文档，不是可执行装配 |
| E2 | 演示物冒充业务（`demo.heartbeat` 5s 心跳、`*/30` cron 探针、`bald:probe` handler）约 230 行 | 示例为演示「全接一遍」 |
| E3 | 21 域 + 9 个可选后端全接、审计三后端双轨（`app/audit.go` 204 + `app/audit_wiring.go` 146） | 示例定位，不是框架要求 |
| E4 | 业务种子数据 369 行写在装配根（占 `bootstrap.go` 40%） | 数据内容属应用 |

### 3.3 混合归因（框架缺钩子 + 示例选错落点）—— 框架要补钩子

**业务能力策略住在装配层**：`cmd/bald-admin/app/builders.go:20-111` 构造 `buildLoginLimiter`/`buildLoginBreaker`/`buildLoginRetrier`，读的是业务配置段 `login.rate_limit.*`/`login.breaker.*`/`login.retry.*`（`builders.go:38-48`、`:71-82` 的注释即配置 schema），在 `assembly.go:508-522` 注入业务对象。登录限流/熔断/重试阈值这些**业务决策**因此住在装配目录。

**框架缺的是钩子，不是门面**：业务层其实已经只持有注入点——`biz/v1/auth/auth.go:107/112/117` 是三个**端口字段**（`ratelimit.Limiter` / `circuitbreaker.CircuitBreaker` / `*retry.Retrier`），经 `Set*`（`auth.go:195-213`）注入；构造在装配层。所以：

- **不需要再加一层注入门面**（那只会多一个中间层）；
- **要改的是落点**：让业务域自持「读自己的配置段 → 构造自己的能力 → 持有自己的端口」，即 `Domain.Wire(app)` 钩子。补上之后，装配层不再出现 `login.rate_limit.*` 这类业务阈值；
- **真正可改的是端口所有权**：`ratelimit.Limiter`（`ratelimit/ratelimit.go:25`）与 `circuitbreaker.CircuitBreaker`（`circuitbreaker/circuitbreaker.go:56`）是接口，业务依赖它们无妨；但 `retry.Retrier` 是**具体结构体**（`retry/retry.go:46`），业务即使想用端口也做不到——**裁决 3：加** `retry.Doer` 端口接口（1 个接口 + 1 处断言）。这是**唯一**一处为判据 ③ 加代码的地方。

### 3.4 有意取舍 —— 不改

`stopAll` 五阶段停机、显式注册不用 `init()`（`registry.go:6-8`、`registrar.go:13-15`）、能力声明 fail-fast（`capability.go:45-94`）、`Ais()` 返回副本（`ai.go:72-77`）、审计旁路不阻断（`mount.go:176-193`）——这些代价已被论证并接受，本文不动。

**唯一被本评估推翻的既有取舍是「两条装配入口并存」**（原判为可接受取舍）：它的代价已从「多一套 Option 类型」恶化成「15 组双拼 + 生成器产旧路径 + 用户必须先自答『我在哪条路径上』」，而收益（e2e 复用 `newApp`）可由 `NewApp` 单独保留。**代价 > 收益，改为单入口。**

## 4. 目标设计

### 4.1 单一入口与目标 `main.go`

```go
// cmd/user-service/main.go —— 用户手写；新增业务域时永不修改。
package main

import (
	"context"

	"github.com/kalandramo/bald/bootstrap/std"
	"github.com/kalandramo/bald/pkg/appkit"
)

func main() {
	appkit.MustServe(context.Background(), std.Standard())
}
```

用户写 **3 条语句**（2 个 import + 1 次调用）、需要理解的框架概念 **0 个**（无 Option、无注册表、无机制名、无必填命名空间）。带业务域的版本由生成器产出，形态是同一次调用后面追加域声明值：

```go
func main() {
	appkit.MustServe(context.Background(),
		std.Standard(),
		authv1.Domain, dictv1.Domain, // ... 每域一个声明式值（生成物维护）
	)
}
```

设计约束：**唯一入口**（`MustServe`，内部完成 `--config` 解析 → 契约装载 → 命名空间解析 → 段驱动装配 → 信号处理 → `Run`）与**唯一 Option 类型**（`BootstrapOption` 消失）。`NewApp` 保留为测试/e2e 用的第二构造器，但它不是第二条装配路径。

**裁决 6：单入口必须提供 `AfterStop`——判定为遗漏，非有意取舍。** 证据：前身项目 go-wind 两个都在（`go-wind/app.go:105` `WithBeforeStop`、`app.go:116` `WithAfterStop`），且有测试钉死排序「BeforeStop → Server.Stop → AfterStop」（`go-wind/app_test.go:341-358`），插件示例亦在用；bald 的 `New` 路径同样有 `AfterStop`（`appkit.go:351`），**只有 `FromBootstrap` 路径缺**（`bootstrap.go:243` 有 `WithAfterStart`、`:403` 有 `WithBeforeStop`，无 after-stop）——移植时丢了一个。影响：`stopAll` 五阶段是「效应回放 → BeforeStop → Server.Stop → AfterStop → 组件 Dispose 逆序」（`appkit.go:621-666`），缺这一项使声明式路径的用户拿不到**阶段 3** 这个槽位（「所有 server 已停、组件仍可用」时刷指标 / drain / 注销后记日志），只能错位使用 `WithBeforeStop`（在停 server **之前**跑）或组件 `Dispose`（在 AfterStop **之后**跑、语义是收尾组件），两者都不等价。补法是纯增量、不破坏，但必须同时补一条**停机阶段序测试**——当前 12 段停机序只有 2 个不变量被测试钉住。

### 4.2 注册表收敛：段驱动单一 Provider（候选 A 选定）

```go
// pkg/appkit —— 唯一注册抽象
type Provider interface {
	// Segments 声明本 provider 消费的契约段路径（如 "server.http"、"database.sql"、"logger"）。
	Segments() []string
	// Build 在段存在时构建；段缺失返回 (nil, nil, nil) 表示跳过。
	Build(ctx context.Context, cfg *bootstrapv1.BootstrapConfig, app *App) (any, Cleanup, error)
}

func Providers(ps ...Provider) Option // Go 里类型与函数不能同名：接口叫 Provider，构造器叫 Providers
```

框架侧循环改为段驱动：

```go
present := contractSegments(cfg)   // 由 protobuf 反射枚举，不手写
for _, p := range registeredProviders {
	if !anyPresent(present, p.Segments()) { continue }   // 段缺失 → 跳过
	...Build...
}
if missing := present.Minus(covered); len(missing) > 0 {
	return fmt.Errorf("contract declares segments with no provider: %v", missing)
}
```

三个机制要点：**枚举表消失**（段名由 provider 自持，存在性由 `cfg` 的 protobuf 反射给出——`BootstrapConfig` 已具备完整反射能力，`databaseSections`(:77-86) 与 `serverSections`(:100-141) 两张手工表都可删除）；**fail-fast 加强**（见下）；**每新增资源域 = 1 个 provider 文件 + 1 行注册**，框架内 7 处同步点只剩 1 处，且那一处在用户/contrib 侧。

候选 B（把 `Registry[T]` 升为唯一实现、13 份变薄壳）**是 A 的真子集**：它省约 700 行框架代码、让死机器复活，但 7 处同步点与两张手工段表都还在、用户侧仍是 39 行 `New`+`MustRegister`、`script` 型静默依然检测不到。故选定 A，并把 B 作为 A 的落地步骤之一（先收成 `Registry[T]`，再换成段驱动循环，可分两批发布）。

fail-fast 四层：

| 层 | 今天 | 目标 |
|---|---|---|
| L1 段存在但 provider 未注册 | 报错 | 同语义保留（错误信息列出已注册 provider 及其段） |
| L2 provider 注册但段缺失 | 跳过（合法） | 同语义保留 |
| L3 段存在且**无人实现** | **静默**（`script` 实证） | **新增：启动报错**，列出未覆盖段 |
| L4 段名拼错 | 无检测 | 由 L3 覆盖（拼错 ⇒ 该段无人覆盖） |

唯一取舍：契约允许声明「框架尚未支持」的段（`server` 的 30 个未实现段、`script`）。折中为 `StrictSegments` 默认开（fail-closed）+ `WithUnimplementedSegments(...)` 显式白名单。

#### 具体入口：`bootstrap/std`（`MustServe` 的第二个参数即它）

`std.Standard()` 返回 1 个 Option，内含框架**自有**后端：`server.http`、`server.grpc`、`logger`(slog)、`config`(file+env)、`tracer`+`metrics`(otel)、`audit.log`。第三方后端（nacos/etcd/loki/minio/asynq/gateway…）仍走各自 `*/contract` 显式 import——这保住了「未 import 的后端零编译成本、依赖图可见」的原有哲学，只是把「13 个 registry 构造 + 39 行 `MustRegister`」换成 1 个 Option。**裁决 1：引入**——接受「`std` 一旦被 import 即拉入 http/grpc/otel 全部依赖」这一代价，换取判据 ④ 的装配面收敛。

### 4.3 业务域一等概念 `Domain`（判据 ① 的前置）

域包导出一个 `appkit.Domain` 值（含 `Wire(app) error`、路由/服务注册、迁移、`ConfigKeys` 等钩子），生成物产出 `domains_gen.go` 聚合清单。**Go 没有运行期包发现，导入清单必须有承载者**——从手写文件变成生成物是唯一可行路径；仓库已有同向先例（`_example/bald/register_grpcgw.go`），但它的导入仍需手写，正是本设计要消除的残余。不选 `biz` 包内 `init()` 自注册：与 `pkg/appkit/registry.go:6-8` 明确写下的「不做 init() 自注册」哲学冲突。

**裁决 4：`Domain` 契约落点进 `AppSpec`。** `appspec.proto` 新增 `repeated DomainSpec domains`；`DomainSpec` 至少含 `name` / `proto_package` / `service`（用于从 proto 派生路由与授权策略）/ `model` / `config_keys`（把业务配置段的归属写进声明）。生成期校验：name 唯一、`service` 与 `api/protos` 中实际存在的 service 匹配。这样声明面只有一处域清单，与 §4.6 的 `domains` 字段同源。

`Domain.Wire` 同时解决 §3.3 的混合归因：`builders.go` 里那三个读业务配置段的 builder 移进 auth 域包，装配层不再出现业务阈值。

**接缝裁定（本文档记录为架构裁定）**：appkit 侧接受「域声明值」作为 Option（**不新增注册表式 API**），生成物只产出「一次 `MustServe` 调用 + 域清单」，`assemble.gen.go` / `domains.gen.go` 与 `Domain` 值直接对接。理由：判据 ① 要求清单由生成物承担，判据 ② 要求框架侧不因域增长而变厚；把域清单做成 appkit 的注册表会同时违反两者。

**回归生成语义**（三态归属）：`owned` 覆盖 / `seeded` 已存在即跳过并输出 `kept:` 而非报错 / `user` 永不触碰；同时修掉 `appspec_gen.go:357-362` 在 gofmt 失败时**越权直写**（无 `--force` 也截断重写）的缺陷。

**验收脚本**（取代现在「字符串锚点 + 能否编译 + 3 秒存活」）：

1. sha256 白名单比对，含**「手写装配文件集合为空集」**这条断言；
2. 装配行数差 == 域数，且手写装配 diff 为空；
3. 生成物内置 `layering_invariant_test.go` 的不变量（并把守卫从子串匹配升级为 AST 匹配）；
4. 端到端计时：`T0 → 生成 → tidy → build → 起服务 → curl /readyz 200 → curl /v1/demo 200 → SIGTERM exit 0 → T1`，要求 `T1-T0 ≤ 1800s`（判据 ④ 的度量口径）。

| B9 | `AppKit` 更名 `App` | 全部 | 机械替换 | 2 |
| B10 | L3「无人消费段」fail-fast 默认开启 | 框架 + 用户契约 | 契约里的未实现段（`script` 等）删除或加白名单 | 1 |

### 5.2 批次顺序（哪些必须同批）

- **批 1（零用户破坏）**：13 张表内部收成 `Registry[T]`；引入 `pkg/audit.Compose` 并由 appkit 调它；L3 段覆盖检查**先做成告警**（让 `script` 静默立刻可见而不破坏构建）；建立 `pkg/appkit/mech` 且**原名保留为 alias**。批 1 结束即可核验：`script` 被报出来、13 份样板收敛、机制可 import 但旧名未删。
- **批 2（必须原子同批）**：B1+B2+B3+B4+B5+B9，外加两个 codegen 模板（`internal/codegen/app.go`、`appspec_gen.go`）与 bald-admin、contrib 的迁移。理由：入口合并、双拼合并、注册表收敛、机制下沉**共享同一个 `Option` 类型改动**，拆开会出现两次 Option 迁移；模板不同批发新会生成编译不过的代码。
- **批 3**：B6+B7 + `Domain` 一等概念（判据 ① 的前置，硬依赖生成器骨架）。

### 5.3 用户迁移动作

`main.go` 改 `MustServe`；删除全部 `NewXRegistry`/`MustRegister`/`WithXRegistry`；15 组双拼机械替换；机制相关加 `mech` 前缀；`X()/Xs()` 访问器改 `Resource(segment)`；审计器显式注入（不再依赖全局 `GetAuditor()`）；契约里的未实现段删除或白名单；删掉 `WithConfigNamespace`（env 名不变）。

**第 5 项的验证门（批 3 前置，未验证不得开工 B6）**：先确认 `bootstrap/config.Store` 是否支持「在已装载的合并树上追加一层 env 而不整体重建」。做法：读 `bootstrap/config/config.go` 的层模型（`Layer` / `merged`）与 `Load` 路径，找是否存在「追加层 + 重算」入口。若不存在，该项自动升级为 breaking（`config` 包需要新 API），B6 必须与 `config` 变更同批发布。

原始问题（保留以便回溯，逐条见下）：

1. **`bootstrap/std` 是否引入**：把装配从 39 行压到 1 行，代价是 `std` 一旦被 import 就拉进 http/grpc/otel 全依赖。倾向引入，但这是「判据 ④ 便利」与「最小依赖图」之间的取向选择。
2. **L3 的缺省严格度**：默认报错会拦住「契约先行」工作流（声明了尚未实现的段就起不来）；默认告警会重演 `script` 的静默。本文选 fail-closed + 显式白名单。
3. **`retry.Doer` 端口是否加**：1 个接口 + 1 处断言，只服务 1 个业务文件（`auth.go:117`），但不加则业务永远绑死 `*retry.Retrier` 具体实现。
4. **`Domain` 的契约落点**：加进 `AppSpec`（改 `appspec.proto`）还是新增 `domain.proto`。
5. **两遍配置合并的底层可行性**（用于消除 `WithConfigNamespace` 必填）：需确认 `bootstrap/config.Store` 支持追加一层而不重建。**此项未验证，标为待验证**——D1 自己也未验证到底层。
6. **`AfterStop` 无 `WithAfterStop`**：遗漏还是有意？影响双拼合并后的语义对齐。
7. **`gen proto` 是否升级**为带 `google.api.http` + buf.validate 的 CRUD 六件套；是否删除「模板模式」（无 `--spec`，属破坏性变更）；`--module` 是否落地（现状被丢弃，`app.go:142`）。
8. **证据文件是否归档进仓库**：五份原始证据现在 `%TEMP%\bald-eval\`，可能被清理。
