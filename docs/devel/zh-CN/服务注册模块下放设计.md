# 服务注册模块下放设计

> Title: 服务注册抽象自 `pkg/registry` 下放为顶层独立 module，后端自 `contrib/registry/*` 上移为 `registry/<backend>`
> Author(s): kalandramo
> Last updated: 2026-09-17
> Status: Draft（设计待评审；实现已按本文落地，2026-09-17，未提交）

## 摘要

我们把服务注册抽象从主模块的 `pkg/registry` 下放为顶层独立 module
`github.com/kalandramo/bald/registry`，并把四个后端实现从
`contrib/registry/{etcd,consul,nacos,kubernetes}` 上移到 `registry/<backend>`。
**最重要的承诺：注册中心后端的依赖图里不再有主模块**——为四个接口 require
gin/grpc/cobra/otel 这件事，到此为止。

契约代码零改动。`registry.go` 的 51 行原样搬家，`inmemory/` 变成同 module 子包。
破坏性变更只有 import 路径本身，消费者全部在自家仓库内。

## 背景与动机

### 注册中心后端为了四个接口，拖进整个主模块

这是最硬的一条证据。etcd 后端的契约包这样写：

```14:17:bald/contrib/registry/etcd/contract/contract.go
import (
	"context"
	"fmt"
	"time"

	bootstrapv1 "github.com/kalandramo/bald/bconf/gen/go/bootstrap/v1"
	registry "github.com/kalandramo/bald/pkg/registry"

	etcd "github.com/kalandramo/bald-registry-etcd"
)
```

它只需要 `serviceInstance` / `Registrar` / `Discovery` / `Watcher` 四个名字。
但它 import 的路径属于主模块，于是 `go.mod` 里必须写：

```5:9:bald/contrib/registry/etcd/go.mod
require (
	github.com/kalandramo/bald v0.0.0
	github.com/kalandramo/bald/bconf v0.1.0
	go.etcd.io/etcd/client/v3 v3.7.1
)
```

`v0.0.0` 不是版本，是个占位符——它靠 replace 兜底：

```29:31:bald/contrib/registry/etcd/go.mod
replace github.com/kalandramo/bald => ../../..

replace github.com/kalandramo/bald/bconf => ../../../bconf
```

kubernetes 后端连占位符都写成了完整的伪版本
（`github.com/kalandramo/bald v0.0.0-00010101000000-000000000000`）。
四个后端累计 18 处 import `bald/pkg/registry`，每一处都把主模块的整棵依赖树
（gin、grpc、cobra、otel、bald-crud/viewer）挂到自己的依赖图上。
nacos 后端 go.mod 的 indirect 列表里躺着 prometheus / grpc / lumberjack，
它们与 nacos SDK 毫无关系——那是主模块的行李。

顺带一提，四个后端的 module 名现在是分裂的：etcd / consul / kubernetes 用平铺的
`github.com/kalandramo/bald-registry-*`，只有 nacos 用了
`github.com/kalandramo/bald/contrib/registry/nacos`（见
`bald/contrib/registry/nacos/go.mod` 第 1 行）。没有理由，就是没统一过。

### 这违反了我们自己写下的布局判据

指标域的决策记录里已经把判据写死了：

```296:296:bald/docs/devel/zh-CN/Bald 指标设计.md
**决策③：后端为什么放顶层子模块而不是 contrib/？** 对齐布局判别：独立 go.mod = 可独立发布的桥接模块，且契约（零依赖）与后端（重依赖）必须物理隔离，否则 transport 六模块会被迫传递引入 client_golang/otel/datadog-go。contrib/ 语义是「接根模块运行期框架」，这三者不接任何框架，只是 SDK 桥接。
```

拿这把尺子量 registry：契约只 import `"context"`，后端只实现契约、不 import
appkit/bootstrap/transport——**它是纯 SDK 桥接，它不属于 contrib/**。
同族能力早已全部落在顶层：`cache/{local,redis}`、`broker/{kafka,rabbitmq,redis,rocketmq}`、
`log/{loki,sentry,aliyun,tencent,charm}`、`metrics/{prometheus,otel,datadog}`、
`retry`、`oss`、`encoding`。只有 registry 例外：契约在 `pkg/`，后端在 `contrib/`。

### 这个例外还锁住了一处架构债

《模块依赖关系.md》记着三类 Registry 不能进 bootstrap 的原因：

```21:21:bald/docs/devel/zh-CN/模块依赖关系.md
说明：`pkg/appkit` 无独立 go.mod，归属主模块；appkit 直接 import `bootstrap/config`（Store 内核），即主模块经 bootstrap 间接获得 Store 能力——与「bootstrap 是装配+配置装载唯一 module」的定位一致。六域客户端 Registry（Database/Cache/Storage/Ai/Workflow/Broker）2026-09-15 自 appkit 迁入 bootstrap（仅依赖 bconf 契约，零新增模块依赖）；appkit 保留 `With*Registry` Option、阶段 B 调 Build、实例存 AppKit 字段与访问器。Tracer/Metrics/Registrar 三类 Registry 因依赖根模块包（otel、pkg/registry）留在 appkit——迁入会造成 bootstrap→根模块循环依赖。
```

`pkg/appkit/registrar.go` 的包注释把同一件事说得更直白：

```4:6:bald/pkg/appkit/registrar.go
// 位置说明：必须放 appkit（主模块）——Provider 签名引用 pkg/registry 的
// Registrar（主模块），若放 bootstrap module 会形成
// bald⇄bald/bootstrap 的模块循环（appkit import bootstrap module）。
```

循环的成因不是 otel 那类第三方依赖，而是**我们自己的包路径**：bootstrap 想认识
`registry.Registrar`，就得 require 主模块。契约一旦独立成零依赖 module，
这条约束立刻消失——Registry 与 Database/Cache 等六域的分界从"能不能"变回"该不该"。

## 设计

### 目标形态：契约一层、后端一层、装配不动

```
registry/                 module github.com/kalandramo/bald/registry        零依赖
├── go.mod
├── registry.go           ServiceInstance / Registrar / Discovery / Watcher（原样搬）
└── inmemory/             同 module 子包（零依赖，不单独建 module）

registry/etcd/            module github.com/kalandramo/bald/registry/etcd
├── go.mod                require registry + bconf + go.etcd.io/etcd/client/v3
├── registry.go  watcher.go  service.go  options.go
└── contract/contract.go  契约段 → options 映射 + Provider
registry/consul/          module .../bald/registry/consul
registry/nacos/           module .../bald/registry/nacos
registry/kubernetes/      module .../bald/registry/kubernetes
```

契约 module 的 `go.mod` 只有两行（module 声明 + go 指令），go.sum 为空：

```go
module github.com/kalandramo/bald/registry

go 1.27.1
```

后端 module 的依赖声明变成真实的、可解析的版本：

```go
module github.com/kalandramo/bald/registry/etcd

go 1.27.1

require (
	github.com/kalandramo/bald/bconf v0.7.0
	github.com/kalandramo/bald/registry v0.1.0
	go.etcd.io/etcd/client/v3 v3.7.1
)

replace github.com/kalandramo/bald/registry => ../../registry

replace github.com/kalandramo/bald/bconf => ../../bconf
```

### 契约代码零改动，只有 inmemory 的落位需要解释

`registry.go` 从头到尾只 import `"context"`，`inmemory` 只 import 契约本身。
搬家不需要动一行实现代码。`inmemory` 留在契约 module 内作普通子包，理由是对照
`cache/local`：后者独立成 module 是因为它依赖 freecache（三方库必须隔离），
而 inmemory 零依赖——同 module 子包的依赖代价为零，没有拆分的必要。

### 装配层与运行期一行不改

`appkit.RegistrarRegistry` 的 Provider 签名、`FromBootstrap` 的阶段 B 构造、
启动后 Register / 停机前 Deregister / Effect 回放 cleanup 的时序全部保持原样，
唯一的改动是 import 路径。这是本设计能"一次改完、不搞过渡期"的底气。

### 改造前 vs 改造后

| | 改造前 | 改造后 |
|---|---|---|
| 契约位置 | `pkg/registry`（主模块） | `registry/`（独立 module，零依赖） |
| 后端位置 | `contrib/registry/*` | `registry/<backend>`（对齐 cache/broker） |
| 后端 module 名 | `bald-registry-etcd` / `bald/contrib/registry/nacos`（分裂） | 统一 `bald/registry/<backend>` |
| 后端 require | `bald v0.0.0` + `replace ../../..` | `registry v0.1.0`（真实版本） |
| 后端依赖图 | 主模块全家 | registry + bconf + SDK |
| RegistrarRegistry 位置 | 被主模块循环锁死在 appkit | 循环消失，可评估迁 bootstrap |

## 理由与取舍

### 我们没选"只下放契约、后端留在 contrib/registry"

这个方案能让后端摆脱主模块依赖，收益的大头拿到了。我们仍然不选它：契约在顶层、
实现在 contrib，与 cache / broker / log / metrics 的形态不一致，query "注册中心后端放哪"
会永远得到两个答案。目录形态的一致性比省几个 `git mv` 值钱。

### 我们没选"把目录挪到 registry/ 但不建 go.mod"

Go 的模块边界只认 go.mod。顶层目录不含 go.mod，就仍然是主模块的一部分——
依赖隔离收益为零，同时破坏了"顶层目录 = 独立 module"的既有约定（cache、broker、
log、metrics、retry、oss、encoding 无一例外）。这是看起来做了事、实际什么都没做。

### 我们没选"在主模块保留 type alias 做兼容垫片"

`pkg/registry` 的三个接口用别名指向新 module 是可行的，但我们查了消费者：
主模块内 7 个文件（appkit 5 个 + inmemory 2 个，其中 2 个是测试）、`_example` 2 处、
`bald-admin` 1 处（`backend/cmd/probe/main.go`）。全部在自家仓库，一次改完。
为不存在的第三方消费者留一个永久垫片，是拿长期成本换短期便利。

### 我们没选"顺带把 RegistrarRegistry 迁进 bootstrap"

循环约束消失后这件事确实可做了，但它有独立的判断要素：bootstrap 要不要多认识一个
运行期契约、`WithRegistrarRegistry` 的签名怎么改、测试怎么分家。混在一起做会让 review
失去焦点。本文只解除约束，不消费它。

### 我们没选"复用 kratos 的 registry 抽象"

2026-09-06 已删除 kratos 桥接路线（kratos contrib 的 nacos 还有 SDK v1/v2 分裂坑），
抽象面改为对齐 go-wind 的 Registrar + Discovery + Watcher。不重开。

### 我们没选"保持现状，因为 registry 还没被真实业务用起来"

Discovery / Watcher 目前确实没有消费方，这是事实。但"没人用"不是"可以放错位置"的理由——
恰恰相反，**趁没有消费方时做破坏性迁移，成本最低**。等 bald-admin 或别的项目接上
client-side LB 之后再动，就要背上兼容包袱。

## 兼容性

**这是破坏性变更，我们直说。** 主模块已发布 v0.6.1，因此主模块下一个版本是 v0.7.0。

| 变更 | 性质 | 代价 |
|---|---|---|
| `github.com/kalandramo/bald/pkg/registry` → `.../bald/registry` | breaking（import 路径） | 主模块 7 处 + `_example` 2 处 + bald-admin 1 处 |
| `.../bald/pkg/registry/inmemory` → `.../bald/registry/inmemory` | breaking（import 路径） | 同上清单内 |
| `bald-registry-{etcd,consul,kubernetes}` → `bald/registry/<backend>` | breaking（module 路径 + 伪版本依赖） | 零消费者：v0.0.0 伪版本靠 replace 兜底，从未发布 |
| `bald/contrib/registry/nacos` v0.1.0 → `bald/registry/nacos` | breaking（已发布 module 改路径） | **bald-admin 是真实消费者**（require v0.1.0），需同步 |
| 契约与接口语义 | 无变化 | 零 |

四个后端里只有 nacos 发过 tag（`contrib/registry/nacos/v0.1.0`），且它是
bald-admin 的真实依赖——这是本次唯一跨仓库的破坏点，必须连带处理，不能只改本仓。
etcd / consul / kubernetes 没有发过版，改名的代价仅限本仓内。

影响面（已全仓搜索确认，无遗漏）：

- 主模块：`pkg/appkit/` 的 `registrar.go`、`bootstrap.go`、`appkit.go`、
  `registrar_test.go`、`appkit_test.go`，以及 `pkg/registry/inmemory/` 的
  `inmemory.go`、`inmemory_test.go`——共 7 个文件各 1 处，合计 7 处。
- `_example`：`bald/main.go`、`bald/register_nacos_disabled.go`（后者只 import appkit，
  随 appkit 的路径变更一起编译通过，无需改动）。
- `bald-admin`：`backend/cmd/probe/main.go`（import 1 处）+ `backend/go.mod`
  （`contrib/registry/nacos v0.1.0` → `registry/nacos v0.1.0`）。
- `docs/`：见「实现与过渡」第 4 步。

迁移路径不设灰度、不做双写：import 路径要么改要么不改，没有中间态。
自家仓库一次改完，比留两套路径更安全。

## 实现与过渡

### 第一步：目录迁移与 import 改写（不动任何版本号）

1. `git mv pkg/registry registry`；`git mv contrib/registry/{etcd,consul,nacos,kubernetes} registry/`
   （命令在仓库根执行；PowerShell 下先 `New-Item` 目标父目录，避免批量 Move-Item
   的目录嵌套坑）
2. 新建 `registry/go.mod`（两行，见「设计」）；四个后端 go.mod 改 module 路径与
   require，replace 指向 `../../registry` 与 `../../bconf`
3. 主模块 `go.mod` 增加 `replace github.com/kalandramo/bald/registry => ./registry`
   与 require（本地联调阶段版本写 `v0.0.0`，第二步换真实 tag）
4. 改写清单内的 import；`_example` 必须同步（它是本地 replace，不跟随就编译不过）。
   bald-admin 不受影响：它依赖的是真实 tag `contrib/registry/nacos v0.1.0`，
   该 tag 指向的旧 commit 里目录还在，模块路径照常可解析——它的适配是第二步的独立动作，
   不是本次落地的前置条件。
5. 验证（每处都要跑）：

```
registry/                 go build ./... && go vet ./...
registry/etcd|consul|nacos|kubernetes/
                          go build ./... && go test ./...
根模块                    go build ./... && go test ./pkg/appkit/...
_example                  go build ./...
```

### 第二步：发版与 require 升真实版本

顺序不可倒置（子模块 tag 先于消费者 require）：

1. 打 tag：`registry/v0.1.0`、`registry/{etcd,consul,nacos,kubernetes}/v0.1.0`
2. 主模块 require `registry v0.1.0`，replace 保留本地开发
3. `_example` 的 require 升真实 tag；bald-admin 的同步可选、时点自定（旧 tag
   `contrib/registry/nacos v0.1.0` 仍可解析，不会被强制 break）。tag 未被 proxy
   收录时用 `GONOSUMDB='github.com/kalandramo/bald,...'` 绕过 sumdb 延迟，既有惯例

### 风险与对策

- **最大风险是漏改一处 import**，表现为编译错误而非静默问题——`go build ./...`
  在四个 module 加根模块各跑一遍即可穷尽。
- 模块数量从 N 到 N+5，发布链路多一轮 tag 与 require 升级。这是这次取舍里唯一
  无法消除的成本，接受。
- 隐性成本：本地 `replace` 不跨 module 传递——主模块 require 图多一个子模块，
  所有以本地 replace 引入主模块的下游模块都要补一条对应 replace（本次 10 个）。
  发版后这些 replace 按 bconf 的既有做法保留，但今后每从主模块切出一个子模块，
  都要重复缴这笔税。
- 契约处于 0.x：`Discovery` / `Watcher` 的形状还可能随首个消费方调整。
  独立发版会让这类调整有版本号可循，比藏在主模块里更可见。

## 附录

### FAQ

**为什么契约 module 不把 inmemory 一起拆成独立 module？**
inmemory 零依赖，拆出去只增加一个 module 和一轮 tag，不带来任何隔离收益。
`cache/local` 独立的原因（freecache 是三方依赖）在这里不成立。

**主模块还要不要 require registry？**
要。`pkg/appkit` 是注册生命周期的驱动方，必须认识 `registry.Registrar`。
但方向变成 主模块 → registry（零依赖），不再有环。

**`pkg/registry` 这个名字会不会被外部用户依赖？**
主模块 v0.6.1 已发布，理论上会。我们已确认自家两个仓库（bald、bald-admin）
是全部消费者；若有第三方用户，本次变更随主模块 v0.7.0 的 release notes 说明。

**这算不算"contrib 收缩"的开始？**
不算。contrib 的语义（接根模块运行期框架）没有变，`authn-jwt`、`authz-casbin`、
`audit-{store,stream}`、`store-gorm`、`database/{gorm,mongodb}`、
`observability-otlp`、`cache-redis` 都实现根模块契约并接入运行期编排链，
它们留在 contrib 是正确的。变的是 registry——它本来就不该在那儿。

3. **模块级连带被本文低估**：本地 `replace` 不跨 module 传递，主模块的 require 图
   新增 `registry` 后，**所有以 `replace github.com/kalandramo/bald => ..` 引入主模块
   的模块**都会报 `updates to go.mod needed`，必须补一条
   `replace github.com/kalandramo/bald/registry => ../../registry`。实际补齐 8 个
   （`transport/{webrtc,tcp}`、`contrib/{store-gorm,observability-otlp,authz-casbin,
   authn-jwt,audit-stream,audit-store}`）加 `_example` 两个。这条成本对任何
   "从主模块切出子模块"的改动都成立，应进入迁移检查单。
