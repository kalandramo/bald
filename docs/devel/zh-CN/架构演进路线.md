# bald 架构演进路线

> 基于同仓库 5 个项目的横向对比（bald / go-lulu / onexstack / go-crud / osbuilder），提炼出的架构设计与落地优先级。
> 结论：**bald 当前架构方向正确（proto 为唯一契约、核心零后端耦合），与 go-lulu 理念最接近**；本文给出补齐差距的演进路线。

---

## 0. 五项目定位速读

| 项目 | 定位 | 与 bald 关系 |
|------|------|--------------|
| **bald** | 全栈微服务框架，proto 为唯一契约与类型真相源 | 本体 |
| **go-lulu** | 极简可组合"积木盒"框架，核心零外部依赖 | **理念最接近**：生命周期骨架 + builder 注册表 + proto 配置 |
| **onexstack** | 可复用后端基础设施库（类 k8s component-base） | 参考：泛型仓储、IOptions、Server 抽象 |
| **go-crud** | 泛型 Repository 统一驾驭 8 种存储引擎的 DAL | 参考：多 module 隔离、分页/过滤引擎、数据权限 |
| **osbuilder** | onexstack 技术栈的 Go 项目脚手架 CLI | 参考：工程化（kubectl 风格 CLI、Task 组合、代码生成） |

## 0.5 设计约束与分层契约（评审判据）

本节是演进路线能否成立的**判据**：任何新 P 项（含 P2.3 扩列子模块）都必须满足下列约束，否则视为破坏架构。它不是模块清单（模块见 §3），而是边界与数据流。

### 0.5.1 核心包禁止依赖清单

bald 核心（`pkg/appkit`、`pkg/store`、`pkg/berrors`、`pkg/conf`、`pkg/config`、`pkg/server`、`pkg/registry`、`pkg/middleware`、`pkg/log`）**不得直接 import** 下列类别，需要时一律走"桥接子模块 + `FromXxx` 适配器 + 依赖倒置接口"：

| 禁止直接依赖 | 原因 | 允许的接入方式 |
|------|------|------|
| `gorm.io/gorm` 及驱动 | 引擎耦合 | `bald-store-gorm` 子模块实现 `Queryable[T]`，核心只依赖 `pkg/store` 抽象 |
| `net/http` / `google.golang.org/grpc` | 传输耦合 | `pkg/server` 定义 `Server` 接口，具体实现或桥接在子模块 |
| `go.opentelemetry.io/otel*` | 可观测耦合（P5） | `pkg/middleware` 仅定义接口，OTel 实现由调用方注入 |
| `cel.dev/cel-go`、`protovalidate` | 校验耦合（P5/P6） | `pkg/middleware` 仅定义 `MessageValidator`，实现由调用方注入 |
| `github.com/go-kratos/kratos`（核心逻辑） | 框架绑定 | 仅 `pkg/registry` 的 `FromKratos` 桥接可引用，且为单向（kratos→bald） |
| `golang-jwt/jwt*`、`casbin`、`keyfunc`(JWKS) | 认证/授权引擎耦合（P7） | `pkg/authn` 仅定义 `Authenticator`+`AuthClaims` 抽象，`pkg/authz` 仅定义 `Authorizer` 接口；jwt/oidc/casbin 实现外置为 `bald-authn-*`/`bald-authz-*` 子模块 |

**判据**：新增一个 P 项时，若它让核心包出现上表任一行 import，则该 P 项设计不合格，必须下沉到桥接子模块或改为接口注入。认证/授权/多租户（P7/P8）同样适用：核心只定义接口与 `AuthClaims`（proto）契约，具体验签/策略引擎不得进入核心。

### 0.5.2 桥接子模块接入契约

任何 `bald-store-*` / `bald-*-register` 子模块（独立 `go.mod`）必须遵守：

1. **实现抽象**：至少实现 `pkg/store` 的 `Queryable[T]` + `DBProvider[T]`（或对应包的同构接口）；认证/授权类子模块实现 `pkg/authn.Authenticator` / `pkg/authz.Authorizer`。
2. **自注册协议**：通过 `init()` 调 `pkg/appkit.RegisterXxx`（或 `pkg/registry.RegisterAuthenticator`/`RegisterAuthorizer`），命名 `MustRegisterXxx` 在重复/冲突时 `panic`；业务侧 `import _ ".../register"` 即插即用，核心 `main` 不手写注入。
3. **单向依赖**：子模块可 import 核心，核心**不得** import 任意具体子模块（防止全家桶回吸）。
4. **传输中立**：子模块内部可依赖引擎，但对外暴露的仍是核心抽象类型，不含 `net/http`/`grpc` 类型泄漏。

### 0.5.3 请求生命周期分层（数据流）

演进各 P 项的编排锚点如下，P0/P1 的"为什么这样切"以此为准：

```
main
 ├─ appkit.Bind(prefix, opt)        注册业务 flag（四源键一致）
 ├─ config.Load(v, msg)             viper 四源合并 → 写回 confv1 指针
 ├─ appkit.Run
 │   ├─ 注册表装配：import _ 触发的 init() 把 Server/Provider 装入 Registry[T]
 │   ├─ BeforeStart → loadConfig（实时读 confv1，不缓存 addr 快照）
 │   ├─ Server.Start（并发，errgroup）   ← P0 分阶段停机的前置
 │   ├─ waitForEndpoints（轮询 Endpoint()）
 │   └─ 信号/errgroup 触发 stopAll：
 │        BeforeStop(独立超时) → Server.Stop(cancel) → AfterStop(独立超时)
 └─ Server 处理请求
      └─ Store[T].ListWithPaging(req)
           └─ translate → detectStrategy → 引擎 Queryable[T].Where/Sort/Page
                └─ 桥接子模块（gorm/mongo/...）翻译为原生查询
```

关键点：`confv1` 指针在 `loadConfig` 后才被写回，故 `Server.Start`/`Endpoint`/`GatewayServer` 后端地址必须**实时读** `cfg.GetAddr()`，不得缓存构造期快照（详见 `pkg/server` 注释约定）。

### 0.5.4 可逆性与隔离边界

- **`init()` 自注册是不可逆全局副作用**：`MustRegisterXxx` 冲突即 `panic`，属有意为之（早发现装配错误）；测试需隔离注册表时，应覆盖 `Registry[T]` 实例而非依赖全局。
- **分页策略可切换但语义不可静默降级**：`translate` 对不支持的逻辑（如 `FilterExpr.Type=OR`）直接报错，不允许降级为 `AND`（见 CR 修复记录），保证组合查询语义不被悄悄改写。

## 1. 共识：bald 已走对的路（保持不变）

1. **Proto 单一真相源**（配置/API/请求/前后端类型全由 proto 生成）。
   - 同 go-lulu（`bootstrap/conf/proto/bootstrap/v1/*.proto`）+ go-crud（`api/protos/pagination/v1`）。
2. **核心零后端耦合（P5）**：registry/config 走 `FromKratos` 桥接；`pkg/store` 泛型仓储 + 后端 `DBProvider` 注入，引擎留独立子模块（已落 `bald-store-gorm`）。
   - 同 onexstack `pkg/store`（Store[T]+DBProvider）+ go-crud 多 module 隔离。
3. **函数式 Option DI，不用 wire/fx/dig**：四项目均手写 DI，bald 一致。
4. **依赖倒置的中间件/拦截器**：`pkg/middleware/{gin,grpc}` 仅定义接口，校验/可观测实现由调用方注入。

## 2. 差距与演进路线（按优先级）

### P0 — 生命周期编排（对照 go-lulu `app.go:268-414`）

**现状**：bald `pkg/appkit` 已有 `Run` + errgroup 并发 + 信号停机，但缺乏分阶段优雅停机与崩溃级联。

**目标**：补齐与 go-lulu 对齐的生命周期：
- 分阶段 `BeforeStop → Server.Stop → AfterStop`，各阶段独立超时 context。
- `Stop` 只发 cancel 不直调 Stop（防双重停止）。
- hook 安全 recover。

**产出**：`pkg/appkit` 增强 `Run` 的分阶段停机骨架（参考 go-lulu `app.go:347-397`）。

---

### P1 — 全局 builder 注册表 + init 自注册（对照 go-lulu `bootstrap/builder.go`）

**现状**：bald 后端（registry/config/store）由调用方在 `main` 里手写注入，无插件注册表。

**目标**：引入 `bald.RegisterXxx` 注册表，插件 `init()` 自注册，业务按需 `import _` 即插即用（如 `import _ "github.com/kalandramo/bald-store-gorm/register"` 自动把 GORM Provider 装进默认 Store 工厂）。

**价值**：避免"全家桶"，与 P5 一致；与 go-lulu `RegisterXxxBuilder`/`MustRegisterXxxBuilder` 同构。

---

### P2 — 存储层增强（对照 go-crud / onexstack `pkg/store`）

已落地：`Store[T]` + `DBProvider[T]` + `Queryable[T]` + `where` + inmemory + `bald-store-gorm`。
待增强（按收益排序）：

0. **分页策略内聚**（go-crud `pagination/paginator.go`）：`Page/Offset/Token` 三策略已抽成命名 `Paginator` + `detectStrategy` [已落 P2.1]。
1. **DTO↔Entity Mapper**（go-crud `gorm/repository.go:46`）：`Mapper[DTO,Entity]` 双向映射（反射 `CopierMapper`）已落地 [已落 P2.2]。
2. **桥接子模块扩列**：`bald-store-mongo`、`bald-store-ent`、`bald-store-redis`（各自独立 go.mod，复用 `pkg/store` 抽象）—— ⏸️ 暂不新建（见 §0）。
3. **数据权限/审计下沉 DAL**（go-crud `viewer/data_scope.go` + `audit/context.go`）：`Viewer` 五级数据范围 + `Auditor` 无侵入 Context 注入。建议作为可选插件（**P9**，业务强需求再落地）。

### P3 — 横切关注点细化

- **日志门面**：bald `pkg/log` 已有最小接口；对齐 go-lulu `log/global.go` 的全局回退（默认 nop）+ 适配器外置（slog/zap）。
- **错误模型**：bald `pkg/berrors` 已有 `Error{Code,Reason,Details}` + `grpcerr`/`httperr` 桥接；对齐 go-lulu `errors.WindError`（Is/Unwrap/栈）+ 跨 gRPC/HTTP 映射，核心包不耦合网络库。
- **可观测性中间件**：onexstack `pkg/middleware/{gin,grpc}/observability.go` 的 traceparent/request-id 注入 + OTel 集成，可作为可选插件挂载（依赖倒置，核心不钉 cel-go/otel）。

### P4 — 工程化与脚手架（对照 osbuilder）

- **kubectl 风格可扩展 CLI**：`bald` 根命令下挂子命令（已落 `user` 演示），未来支持 PATH 插件发现，让用户扩展与框架命令共存。
- **Task 组合式流水线**：`bald` 的构建/发布任务拆为可组合单元（已在用 go-task `Taskfile.yml`，沿用）。
- **代码生成脚手架**：配置驱动 + 嵌入模板，一键生成"项目骨架 / CRUD handler / proto stub"，复用 osbuilder 范式（P4，长期）。

### P7 — 认证与授权（authn / authz）（对照 go-lulu `plugins/security/authn` + onexstack `pkg/authz` + osbuilder 拦截器模板）

> 注：P5（核心零后端耦合）、P6（请求校验分层）已在其他改动中落地，见 §0 总表；本文档 §2 原列 P0-P4，本次补齐 P7/P8。

**现状**：bald 现有 `pkg/middleware` 仅定义了校验/可观测拦截器接口，认证（谁在调）与授权（能不能调）尚无统一抽象；`_example` 有 `user` 子命令 demo，但无登录/认证/权限拦截 demo。

**目标**：沿用"依赖倒置 + 核心零耦合"，把认证授权拆成**核心抽象**与**桥接实现**两层：

1. **核心抽象 `pkg/authn`**（借鉴 go-lulu `plugins/security/authn/engine.go`，零引擎依赖）：
   - `Authenticator` 接口：`Authenticate(ctx) (*AuthClaims, error)` / `AuthenticateToken(token) (*AuthClaims, error)` / `CreateIdentity` / `CreateIdentityWithContext`。
   - `AuthClaims` 标准结构：`Subject` / `TenantID` / `Scopes []string` / `Roles []string`（proto 定义，作为上下文真相源候选；与 go-lulu `claims.go` 的 `ClaimFieldScope` 对齐）。
   - `context.go`：`ContextWithAuthClaims` / `AuthClaimsFromContext` 注入与提取（与 go-lulu `authn/context.go` 同构）。
   - **核心不依赖** jwt/casbin/oidc 任何库。
2. **授权接口 `pkg/authz`**（借鉴 osbuilder `middleware/grpc/authz.go` 模板）：仅定义 `Authorizer` 接口 `Authorize(subject, object, action string) (bool, error)`；Casbin/RBAC 策略引擎作为**可选桥接子模块**，核心不 import casbin（对照 onexstack `pkg/authz` 直接耦合 `gorm-adapter`/`casbin`，不照搬）。
3. **拦截器依赖倒置**（与 P3 一致）：`pkg/middleware/{gin,grpc}` 新增 `AuthnInterceptor(authn.Authenticator)` / `AuthzInterceptor(authz.Authorizer)`，从 context 取 `subject`+`object=FullMethod`+`action=CALL`（同 osbuilder 模板）。拦截器支持 `SkipPaths` 选项（探针/公开路径豁免，见下）。
4. **参考边界（对照 onexstack `pkg/token`）**：该包可借鉴其**思想**但须规避其**反模式**：

   | 维度 | 借鉴 / 规避 | 理由 |
   |------|------|------|
   | 公开路径豁免 `skipPaths`（`/healthz`、`/metrics`、`/ping` 等 + 通配符 `*`） | ✅ 借鉴 | 直接吸收为 `pkg/middleware` 拦截器的 `SkipPaths` 选项 |
   | JWT 算法白名单校验（强制 `SigningMethodHMAC`，防 `alg=none`） | ✅ 借鉴 | 纳入 `bald-authn-jwt` 子模块的验签逻辑 |
   | 包级全局 `config` + `sync.Once` + `Init/Reset` | ❌ 规避 | 与 bald 函数式 Option DI（P1/P5）冲突；全局 state 测试隔离脆弱，`Reset` 是测试补丁反模式 |
   | 核心直接 `import gin` 并把 `ctx.(*gin.Context)` 类型断言写进解析逻辑 | ❌ 规避 | 违反 §0.5.1 核心零传输耦合；token 解析用纯 `string`，请求提取由 `pkg/middleware/{gin,grpc}` 各自在桥接层完成 |
   | `Reset()` 硬编码默认密钥 | ❌ 规避 | 生产遗漏 `Init` 即用此密钥签发，高危；bald 必须显式要求密钥，不允许默认值 |
   | `claims` 用 `jwt.MapClaims`（弱类型） | ❌ 规避 | 与 bald proto-first / 类型真相源冲突；`AuthClaims` 须为强类型 proto 结构（对齐 go-lulu `claims.go`） |

   > 一句话：onexstack `token` 是"务实但耦合严重"的实现（gin + 全局 state + 弱类型 claims 塞进核心），仅取其 skipPaths 与算法校验两点思想，其余作为反面教材规避。
5. **桥接子模块**（独立 go.mod，`import _` 注册到 `pkg/registry` 的 `RegisterAuthenticator`）：
   - `bald-authn-jwt`、`bald-authn-oidc`（go-lulu `authn/oidc` 用 JWKS+RS256 验签）、`bald-authn-apikey`、`bald-authn-basic`。
   - `bald-authz-casbin`（可选，Casbin model/adapter 外置）。

**价值**：认证/授权机制可插拔；业务换 IdP（自建 JWT ↔ 企业 OIDC）只换子模块，核心与 handler 不动；与 P1 注册表、P5 零耦合一致。

**产出**：`pkg/authn`（抽象+context）、`pkg/authz`（接口）、`pkg/middleware` 两个拦截器、`bald-authn-oidc`（首个范本）、`_example/bald` 新增 `login` 子命令演示签发+拦截校验。

### P8 — 多租户支持（Tenant Isolation）（对照 onexstack `pkg/store/where` Tenant/RegisterTenant）

**现状**：bald `pkg/store/where.go` 已有 `Where`/`Filter`，但每次查询需业务手写租户条件，易漏（越权风险）；无全局租户上下文提取机制。

**目标**：直接借鉴 onexstack 的 `RegisterTenant(key, valueFunc)` 模式（与 bald 现有 `Where` 同构，改动最小），融入 `pkg/store`：

1. **全局租户注册**：`pkg/store.RegisterTenant(key string, valueFunc func(ctx) string)`。
2. **自动注入**：`Where.T(ctx)` 在构造条件时自动把 `key = valueFunc(ctx)` 追加到 Filters；`Store.ListWithPaging` 的 `translate` 阶段合并租户条件与业务 `FilterExpr`（租户列优先、不可被业务覆盖，防越权）。
3. **与 AuthClaims 联动**：`valueFunc` 默认从 `authn.AuthClaimsFromContext(ctx).TenantID` 取值（P7 已注入）；非多租户应用不注册即无租户列，零开销。
4. **桥接子模块**若需按租户分库/分 schema，`bald-store-gorm` 可在 `applyWhere` 后叠加 `tenantID` 路由（可选）。

**价值**：租户隔离下沉 DAL，handler 无感知；避免"漏写租户条件导致跨租户数据泄漏"类高危 bug；与 P2 存储层、P7 认证天然衔接（认证出 TenantID → 存储自动隔离）。

**产出**：`pkg/store` 的 `RegisterTenant` + `Where.T` + `translate` 合并逻辑；`_example/bald user` 演示多租户过滤。

## 3. 架构总览（演进后目标态）

```
bald (核心, 零后端依赖)
├── pkg/appkit        生命周期编排(分阶段停机/崩溃级联)        [P0]
```

## 4. 落地优先级建议

| 优先级 | 任务 | 依据 | 风险 |
|--------|------|------|------|
| **P0** | 生命周期分阶段停机 | go-lulu app.go | 低，纯增强 |
| **P1** | builder 注册表 + init 自注册 | go-lulu builder.go | 中，需约定注册协议 |
| **P2.1** | 分页三策略内聚 | go-crud paginator | 低 |
| **P2.3** | 扩列 store 桥接子模块 | go-crud 多 module | ⏸️ 暂不新建（见 §0） |
| **P3** | 日志/错误/可观测对齐 | go-lulu/onexstack | 中，涉及既有包 |
| **P4** | 脚手架/CLI 插件 | osbuilder | 高，长期 |
| **P5** | 核心零后端耦合 | 多项目共识 | 低，已落 |
| **P6** | 请求校验分层 | proto buf.validate + 拦截器倒置 | 低，已落 |
| **P7** | 认证与授权（authn 抽象 / authz 接口 / 拦截器 / 桥接子模块） | go-lulu authn + osbuilder 拦截器模板 | 中，需定 AuthClaims proto 与注册协议 |
| **P8** | 多租户支持（RegisterTenant + Where.T 自动隔离） | onexstack pkg/store/where | 低，与现有 Where 同构 |
| **P9** | 数据权限/审计下沉 DAL（Viewer 五级范围 + Auditor） | go-crud viewer/audit | 低，业务强需求再落地 |

**原则**：保持"核心零后端耦合"，所有引擎/插件/可观测实现均外置子模块，核心只定义接口与 proto 契约。认证/授权/多租户同样遵循：核心只定义 `Authenticator`/`Authorizer`/`RegisterTenant` 抽象与 proto 契约，jwt/oidc/casbin 等具体引擎外置为桥接子模块。

## 5. 横向经验速记

- **多 Module 隔离**是四项目的共同选择（go-crud 8 引擎各自 go.mod、bald-store-gorm 独立 go.mod）——避免大仓后端耦合，**bald 坚持下去**。
- **Proto-first 配置**是 go-lulu/go-crud/bald 共识——YAML 只是载体，proto 是契约。
- **手写函数式 DI** 优于 wire/fx——四项目零使用重框架，bald 一致。
- **依赖倒置拦截器/中间件**——核心不钉具体库（protovalidate/otel），由调用方注入。
- **验证类 demo 要接进可运行路径**（如 `bald user` 子命令），不能仅单测——本次落地即靠 demo 暴露 inmemory `Count(nil)` 空指针。
