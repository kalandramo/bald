# 架构改进路线图

> 本文档基于 2026-08-29 对 bald 架构的全面评估，汇总当前设计已确认合理的前提下，
> 仍需在中长期演进中处理的 5 项改进点（编号 P1–P5），并给出落地优先级与建议方案。
>
> 评估结论：**bald 分层清晰、契约优先、依赖方向正确，已达可落地生产的质量，无需推翻重来。**
> 本文档仅记录"从合格到优秀"的演进项。

---

## 总体结论速览

| 编号 | 问题 | 优先级 | 性质 | 当前是否阻塞 |
|---|---|---|---|---|
| P1 | 配置双轨制（conf proto ↔ options）长期维护成本，全栈 proto 化后 options 应废弃 | 中期 | 重构 | 否 |
| P2 | `validation` 反射方法命名约定易拼写错且静默 skip | 短期 | 健壮性 | 否（**已修复**） |
| P3 | `errors` 包遮蔽标准库 `errors` | 可选 | 命名隐患 | 否 |
| P4 | `web` 强绑定 gin，不支持 `http.Handler` 等 | 可选 | 取舍 | 否 |
| P5 | 远程配置源（nacos 等）直接 require 进核心 go.mod | 短期 | 依赖熵 | 否（**已修复**） |
| P6 | 请求参数校验：规则应与 proto 契约同源，且核心不绑定校验库 | 中期 | 架构收敛 | 否（**已落地**） |

设计亮点（已确认合理，不改动）：三层配置分工、接口契约优先、并发生命周期处理、传输中立错误模型、零依赖可注入日志、文档完整度。

## P1：消除配置双轨制的平行默认值

### 现状
- `server` 层当前消费 `options`（`SecureServingOptions` / `GRPCOptions` / `log.Options`）。
- 框架级配置经 `conf` 解析为 `confv1.*` proto 后，再经 `ToSecureServing` / `ToGRPCOptions` / `ToLogOptions` 回灌到 options。
- 因此**框架级配置的默认值存在两份真相源**：`conf.NewBootstrap()` 的 proto 默认值 + `options.NewXxxOptions()` 的 Go 默认值。
- 二者靠注释约定"严格一致"，改一处不会编译报错，漂移风险随版本累积。

### 影响
- 默认值漂移是**静默**的：某次只改了 `options` 默认值，proto 侧不变，行为在"用 proto 路径"与"用 options 路径"下分叉，且难以察觉。

### 建议方案（渐进，已在《proto 配置契约设计》阶段 2 规划）

> 关键前提更新（2026-08-29）：bald 已确定**全栈 proto 驱动**——框架配置、业务配置、
> API 接口、请求参数、前后端类型定义均由 proto 生成，proto 是全仓唯一契约与类型真相源。
> 因此 `options` 作为"proto → Go struct 兼容层"的存在理由已瓦解，onexstack 仅为**借鉴实现**
> 而非需要对其 `IOptions` 契约保持对齐的外部约束。**结论：`pkg/options` 应整体废弃。**

1. 让 `server` 层直接消费 `confv1.*` proto 消息，删除 `pkg/options` 整层（含 `ToXxx` 桥接）。
2. flag 绑定从 `opt.AddFlags()` 下沉到 `pkg/conf`：新增 `conf.BindFlags(msg proto.Message, fs *pflag.FlagSet)`，
   遍历 proto 字段描述符把每个可配置字段注册成命令行 flag（复用现有键路径约定，如 `http.addr`）。
3. 校验统一收口到 proto：`protoc-gen-validate` 注解生成 `Validate()`，取代手写 `options.Validate()`。
4. TLS Smart Mode（`loadResource`/PEM/Base64/CA 等运行时视图逻辑）从 `options.TLSOptions`
   迁为纯函数 `conf.ResolveTLS(cfg *confv1.TLS) (*tls.Config, error)`，不进入 proto 注解。
5. `conf.NewBootstrapFromOptions` 等迁移期桥接在 server 改造完成后删除。

### 已落地：默认值注入（protoc-gen-defaults 集成，方案 B）
- 已把 `protoc-gen-defaults` 的 `defaults/defaults.proto` 引入 `api/proto/defaults/`，
  并在 `buf.gen.yaml` 追加 `protoc-gen-defaults` 插件条目；二进制由 Makefile `proto-config`
  目标在 PATH 缺失时按 `.bingo/protoc-gen-defaults.mod` 的 pin 版本 `go install`，
  **不进入 bald 核心 go.mod**（与 P5 治理原则一致）。
- `api/proto/bald/config/v1/{config,server,log}.proto` 已加 `(defaults.value)` 注解，
  生成的 `*.pb.defaults.go` 提供 `Default()`：零值字段注入 `:443`/`10s`/`tcp`/`:9090`/`info`/`console` 等，
  且 `Bootstrap.Default()` 递归初始化 `http`/`grpc`/`logger`/`tls` 子消息。
- `conf.NewBootstrap()` 已改为 `cfg := &confv1.Bootstrap{}; cfg.Default()`，仅对无法注解的
  `app.id`(hostname)、`app.name/version`、`log.output_paths`(repeated) 做 post-process。
- 原 `conf.go` 中 7 个标量默认值常量已删除（双真相源减半，单一事实源收敛到 proto 注解）。
- 约束（来自插件）：`repeated`/`map` 不支持注解注入；`Default()` 仅在字段为零值时注入，
  与「未配置即默认」语义一致。

### 本期（P1 第一步）完成边界
- **已完成**：框架级默认值的「唯一真相源」收敛到 proto 注解（protoc-gen-defaults 注入）。
  测试基准（`conf_test.go`）已改为以 proto 契约为准，不再以 `options.NewXxxOptions()`
  的默认值作镜像，切断测试层的隐性双基准。
- **已完成（P1 阶段 2，2026-08-29）**：废弃 `pkg/options` 整层，server 直消费 `confv1.*` proto。
  全栈 proto 化后 options 已是多余二次翻译，无保留必要（onexstack 仅为借鉴、非对齐约束）。
  执行清单（均已落地）：①`http_server.go`/`grpc_server.go`/`gateway_server.go` 的 opts 字段改为
  直接读 `confv1.Http`/`confv1.Grpc`；②TLS 逻辑迁 `conf.ResolveTLS`（Smart Mode：文件/PEM/Base64）；
  ③flag 绑定改 `conf.BindFlags`（遍历 proto 描述符，替代 `options.AddFlags`）；
  ④`appkit.Bind` 支持 `proto.Message` 类型；⑤删 `ToXxx`/`NewBootstrapFromOptions` 与 `pkg/options`，
  重做并发安全（`-race`）回归全绿。
  收益：彻底消解 proto↔options 双真相源、server 与配置来源解耦、类型全仓唯一。
  说明：校验当前仍用手写 `conf.Validate`（未引入 `protoc-gen-validate`），属后续可选增强，
  不在本次范围内。

### 验收
- `go test -race ./...` 全绿，`NewBootstrap()` 注入的默认值与 proto 注解声明严格一致。
- `pkg/options` 已删除，server 直接消费 `confv1.*` proto（`NewHTTPServer`/`NewGRPCServerWithRegister` 签名已变）。
- 端到端冒烟：proto 路径（`config.Unmarshal` → `conf.NewBootstrap` → server 直接读）行为正确
  （已有 `conf_test.go`/`appkit_test`/`bind_test`/`server_test` 与 `_example/bald` 覆盖）。

## P2：`validation` 反射分发的拼写错误静默化 —— ✅ 已修复（2026-08-29）

### 原状（已修复）
- `pkg/validation` 通过反射查找 `ValidateXxxRequest` 方法名约定进行校验分发。
- `Register` 时对未匹配的方法仅 `klog.V(4).Infof` 提示，**不返回 error**，拼写错误在运行时静默跳过。
- 影响：业务开发者拼错方法名（如 `ValidateUserRequst`）导致校验**完全不生效且无报错**，
  等同于「以为有校验、实际没有」。

### 修复方案（已落地，采用「返回 error」而非引入第三方校验库）
- `Register` 现在返回 `error`：只要方法名以 `Validate` 开头，即视为「声明了校验意图」，
  此后**任何一项**约定不满足都返回 error（方法名≠请求类型名、第二参数非指针、
  返回值非 error、签名不符），不再静默 skip。
- `NewValidator` 签名由 `NewValidator(any) *Validator` 改为 `NewValidator(any) (*Validator, error)`，
  迫使调用方处理注册失败（编译期即可见）。
- 传 `nil` 仍合法（表示「没有校验器」），但语义显式。

### 验收（已通过）
- 新增 `TestRegister_TypoMustError`：三种错误形态（方法名拼写错误 / 第二参数非指针 /
  返回值非 error）均断言返回 error 且错误信息包含具体原因。
- 新增 `TestRegister_NonValidateMethodIgnored`：非 `Validate` 前缀的方法被忽略且不报错。
- `go test -race ./...` 全绿。

### 未采纳的替代方案及原因
- **迁移到 `go-playground/validator/v10`**：它会把规则放进 Go struct tag，
  与 bald「proto 是全栈唯一契约」的方向相悖（等同于在 Go 侧再造一份规则真相源）。
  字段级规则应由 proto 注解承载，见下方 P6。

## P3：`errors` 包遮蔽标准库 `errors` —— 已完成（2026-08-29）

### 现状（改造前）
- 原 `pkg/errors` 重导出 `Is/As/Unwrap/Join` 但刻意不导出 `New`，文档已说明设计意图。
- 业务代码已用别名 `berrors "pkg/errors"` 规避，但**包名本身遮蔽了标准库 `errors`**。

### 影响
- 新贡献者容易 `import "pkg/errors"` 后误以为拿到标准库 `errors.New`，或反之在框架内想用标准库时被遮蔽。属于长期可维护性隐患，非功能缺陷。

### 方案（已落地）
- 将包重命名为 `berrors`（与示例别名一致），框架内对标准 `errors` 不再遮蔽。
- 重命名范围：`pkg/errors` → `pkg/berrors`（含子包 `grpcerr`），同步更新所有代码/注释/go.mod 引用（server / web / middleware / errors 自身 / _example）。
- 保留 `Is/As/Unwrap/Join` 对标准库的原样转发，业务无感知。

### 验收（已通过）
- 全仓 `go build ./...` / `go test ./...` 通过；`grep -r "pkg/errors"` 在 `.go` 中归零（go.mod 无残留）。

## P3 补强：HTTP 边界桥接拆为对称子包 `pkg/berrors/httperr`（2026-08-29 已完成）

### 背景
P3 改名后，核心包 `berrors` 仍内联了 `Error.StatusCode() int` 方法（HTTP 映射）。
这违反「核心包零 net/http 依赖」的契约——一旦 `StatusCode()` 存在，核心包就与 HTTP 传输耦合，
也让「对称桥接」不彻底（gRPC 侧早已有 `grpcerr` 子包，HTTP 侧却还赖在核心包）。

### 方案（已落地）
- 新建 `pkg/berrors/httperr`（与 `grpcerr` 对等）：提供纯函数
  `CodeToHTTP(code uint32) int` / `HTTPToCode(status int) uint32` / `StatusCode(e *berrors.Error) int`。
- 刻意不 import gin：gin 边界函数留在 `pkg/web` 侧（`response.go`、`middleware/gin`），
  错误包家族不反向依赖 web 框架；状态码用标准库 `int` 而非 `http.StatusCode`，
  进一步把 `net/http` 隔离在子包内部、不牵连上层。
- 核心包 `errors.go` / `code.go` 注释改为指向 `httperr` 子包；**移除 `Error.StatusCode()` 方法**
  （这是循环依赖根因：核心包若保留该方法会反向依赖 httperr 子包）。
- 迁移边界调用：`pkg/web/response.go`、`pkg/middleware/gin/{authn,authz}.go` 三处
  `e.StatusCode()` → `httperr.StatusCode(e)`。

### 关键坑：test 包循环依赖
`errors_test.go`（package errors）曾 import `httperr`，而 `httperr` import `berrors`，
Go 的 test 包 import 也计入依赖图 → `import cycle not allowed in test`。
修复：把 `StatusCode` 断言从 `errors_test.go` 移到 `httperr_test.go`
（`TestStatusCode` 覆盖 `StatusCode(berrors.NotFound(...)) == 404`），`errors_test.go` 不再 import httperr，
核心包测试只验证传输中立模型。

### 最终形态
```
pkg/berrors/        # 核心：传输中立错误模型，零 gRPC/net-http/gin 依赖
├── grpcerr/        # gRPC 边界桥接（依赖 gRPC）
└── httperr/        # HTTP/gin 边界桥接（仅依赖标准库 int）
```

### 验收（已通过）
- `go build ./...` / `go test ./pkg/berrors/... ./pkg/web/... ./pkg/middleware/...` / `go vet` 全绿；
- `errors_test` 与 `httperr` 无循环依赖（StatusCode 断言在 `httperr_test.go`）。

## P4：`web` 层强绑定 gin —— 已完成（2026-08-29，仅文档化）

### 现状
- `pkg/web` 直接消费 `*gin.Context`，不支持标准库 `http.Handler` 或 echo/fiber。
- grpc-gateway transcoding 的复用通过 build tag 隔离 gin 路由，已规避冲突。

### 影响
- 若目标是"通用微服务框架"，HTTP 入口绑定单一 web 框架限制了接入方。当前 gin 选型成熟主流，**可接受**，属有意取舍。

### 方案（已落地，仅文档化、不动代码）
- 不做抽象重构（避免过度设计），仅在《路由注册与绑定设计.md》§7 补充**选型决策声明**：
  HTTP 入口层选用 gin 为默认实现是有意为之；`pkg/server.HTTPServer` 仍封装标准库 `net/http`
  （底座零框架耦合），仅业务处理流水线消费 `*gin.Context`；不抽象 `web.Context` 接口；
  gRPC/grpc-gateway 复用同一 biz 层，故不影响 gRPC 生态接入。

### 验收（已通过）
- 《路由注册与绑定设计.md》§7 已补充选型决策说明。

## P5：远程配置源依赖移出核心 go.mod

### 现状（已确认：桥接设计本身正确，仅需清理残留依赖）
- **桥接模式与 registry 完全对称，且已落地**：`config.FromKratosSource(src kratosconfig.Source)`
  把 kratos 的 `config.Source` 适配成 bald 的 `RemoteSource`（`pkg/config/source.go`），
  与 `registry.FromKratos(r kratosregistry.Registrar)` 思路一致。
  kratos contrib/config 下已实现 `etcd/consul/nacos/apollo/polaris/kubernetes` 等后端，
  全部实现 `config.Source`，可直接喂入 `config.FromKratosSource`——**零重复造轮子**。
- 框架核心只依赖 kratos 核心库的 `config.Source` 接口，`source.go` 注释也明确要求
  「用户自行引入具体 contrib 后端」。
- **唯一反模式**：核心 `go.mod` 却直接 `require` 了
  `github.com/go-kratos/kratos/contrib/config/nacos/v3` 与 `github.com/nacos-group/nacos-sdk-go`，
  导致即使不用远程配置也会拉取 nacos SDK——这与 registry 侧「只依赖核心接口、不钉后端」的治理**不一致**。

### 影响
- 增加核心模块的体积、CVE 表面积与构建时间；违反"最小依赖"原则（与设计意图及 registry 治理相悖）。

### 建议方案（短期，低风险）——已落地
- 从核心 `go.mod` 删除 `contrib/config/nacos/v3` 与 `nacos-sdk-go` 两行，`go mod tidy` 后核心只留 `kratos/v3` 核心库。
- 原 `pkg/config/integration_test.go`（带 `//go:build integration`）整体迁移到**独立子模块**
  `tests/integration/`（拥有自己的 `go.mod`，`replace` 指向本地 bald，自行 require nacos），
  并改为外部测试包 `package integration_test`、只调用公开 API（`config.Load` / `config.FromKratosSource`）。
  这样 nacos SDK 完全不进入框架核心依赖图。
- `_example/bald` 若需保留 nacos 演示，可在该示例目录用独立 go.mod 或 `-tags remote_nacos` 自行 require nacos SDK。

### 验收（已验证）
- 核心 `go.mod` 不含任何 contrib/config 后端与 nacos-sdk-go；
  `go build ./...` 与 `go test ./...` 全部 PASS，无 nacos 拉取。
- 独立子模块 `cd tests/integration && go mod tidy && go vet -tags integration ./...` 通过，
  需真实 nacos 时 `go test -tags integration -run Nacos -v` 可连远程配置中心验证桥接。

### 同范式推广：`_example` 拆为独立 module（2026-08-29 已落地）

与 `tests/integration` 同一范式：`_example/go.mod`（module `github.com/kalandramo/bald/example`，
`replace github.com/kalandramo/bald => ..`），覆盖 `bald` 与 `bald-gin` 两个入口。

**为什么必须拆**：`_example` 需要 `grpc-gateway/v2`、`cel-go`（protovalidate）等重依赖。
放在核心 module 里会让这些依赖进入核心依赖图，所有使用 bald 的项目被迫传递依赖它们。
拆分后核心 `go.mod` 只留 `kratos/v3` 等最小集合（顺带清掉了 `chi`、`nacos` 等）。

注意 `replace` 的相对路径取决于 `go.mod` 所在层级：
`_example/` 是一级用 `..`，`tests/integration/` 是两级用 `../..`。

**重要认知：Go 工具链忽略 `_` 前缀目录**
`_example` 以下划线开头，**不参与**核心的 `go build ./...` / `go test ./...`，
也**不被 `go mod tidy` 扫描**。后果：
1. 核心 `go build ./...` 通过 ≠ example 能编译——example 的编译错误长期被掩盖；
2. `go mod tidy` 拉不进 example 的依赖（所以「跑 tidy 就能编 example」是错的）；
3. 验证必须用显式路径：`cd _example && go build ./...`。

**拆分后立即暴露的 3 个真实缺陷**（此前从未被编译过，一直在仓库里）：
1. `register_grpcgw.go` 缺 `net/http` import；
2. `greetService` 未嵌入 `UnimplementedGreetServiceServer`（protoc-gen-go-grpc 的
   `require_unimplemented_servers` 要求），无法注册；
3. **`pkg/server.GatewayServer` 的设计缺陷**：`register` 回调硬编码 `*http.ServeMux`，
   但 grpc-gateway v2 用 `runtime.ServeMux`，根本无法接入。
   已改为 `register func(ctx, conn) (http.Handler, error)`——让业务自建 mux 并交回
   `http.Handler`，核心因此**无需依赖 grpc-gateway**（依赖倒置，与 P6 拦截器同构）。
   顺带修复 `register` 失败时 `conn` 未关闭的连接泄漏。

**端到端冒烟（首次真正跑通 grpcgw）**：
```
name="world" -> OK: hello, world
name=""      -> ERR: rpc error: code = Unknown desc = code: 3, reason: EMPTY_NAME
```
证明 `ValidatorInterceptor` → `pkg/validation` 分发器 → `ValidateGreetRequest` 全链路生效。

**挂载 grpc-gateway 后回归 e2e 时又暴露 2 个真实框架 bug（2026-08-29 修复）**：

1. **`GRPCServer` 缓存了 `addr` 快照，与 `cfg` 指针不同步**
   `NewGRPCServerWithRegister` 在构造时 `addr: cfg.GetAddr()` 存成字段，而
   `appkit.BeforeStart` 的 `Unmarshal` 在**构造之后**才把 env/flag 覆盖后的地址写回
   `bootstrap.GetGrpc()`（同一指针）。结果 `Start`/`Endpoint` 读的是旧快照，HTTP server
   因实时读 `cfg.GetAddr()` 正确、gRPC server 却仍监听配置默认值（如 `:9090`），
   `Endpoint()` 返回的也是旧地址 —— 客户端按 `Endpoint()` 连接必然连错端口。
   修复：删除 `addr` 字段，`Start`/`Endpoint` 全部实时读 `s.cfg.GetAddr()`。

2. **`GatewayServer` 在构造期固化后端地址 + Start/Stop 死锁**
   旧 `NewGatewayServer(addr string, ...)` 在构造时 `grpc.NewClient(addr)`，把后端地址
   锁死在构造期（config 尚未加载，env 覆盖无效 → 网关永远连 `:9090`）。
   改为接收 `*confv1.Grpc` 指针，并把 `conn` 与 handler 的构建**延迟到 `Start`**——
   此时 config 已就绪，实时读 `backend.GetAddr()`，env/flag 覆盖生效。
   延迟过程中若 `Start` 在持 `mu` 锁期间进入阻塞的 `Serve`，会与 `Stop`（`mu.Lock()`
   才能调 `Shutdown`）构成死锁：Stop 等 Start 释放锁、Start 等 Stop 调 Shutdown。
   修复：`Start` 仅在建立 conn/register/attach 阶段持锁，attach 完**立即释放锁**再进
   `Serve`；`HTTPServer` 新增 `attachHandler`（延迟挂载业务 handler，保留 `/healthz`
   `/readyz` 探针）。

3. **`config.Load` 的 `BindPFlags` 把零值 flag 压过 env/文件（2026-08-29 修复）**
   `v.BindPFlags(opts.Flags)` 会把所有 flag（含用户未传的零值）写进 viper override 层，
   按 viper 语义（flag > env > 文件）压过环境变量与本地文件，导致
   「只 `t.Setenv` 不设 flag」时 env 覆盖完全失效。修复：`bindViperBasics` 改为仅对
   `flags.Changed == true` 的 flag 调 `BindPFlag`，未传的 flag 不进 override 层。
   语义变为「flag 被显式设置才覆盖 env/文件」，符合运维预期且对测试（t.Setenv）友好，
   `pkg/config` 测试全绿无回归。

## P6：请求参数校验分层（声明式注解 + 命令式 Go，依赖倒置）

### 背景
请求入参已由 proto 生成（`_example/bald/proto/greet.proto` → `baldv1.GreetRequest`）。
因此「字段级校验规则」也应与契约同源，而不是在 Go 侧另建一份规则真相源
——这与 P1 阶段 2 废掉 `pkg/options` 是同一条原则的延续。

参照 `miniblog/internal/apiserver/pkg/validation` 的实际用法，确认了**分层是对的、
但内层实现不应照搬**：

| 层 | miniblog（onexstack）实现 | bald 决策 |
|---|---|---|
| 外层分发（请求类型 → 校验方法） | 反射找 `ValidateXxxRequest` | **借鉴**，保留（P2 已修复静默 skip） |
| 内层规则（字段 → 规则） | Go `Rules map[string]ValidatorFunc` | **不借鉴**，改用 proto 注解 |
| 复杂逻辑（跨字段/查库/权限） | 手写 Go | **借鉴**，接 `web.Validator[T]` 或 `ValidateXxx` |

不照搬 `Rules` map 的原因：它靠**字段名字符串**匹配 + `value.(string)` 类型断言，
在 proto 生成的结构体上有两个硬伤——
① 改 proto 字段导致 Go 字段名变化 → 规则静默失效（`if !ok { continue }`）；
② 同名字段类型不同 → 类型断言 panic。
而 proto 注解天然由描述符承载映射，无字符串失配、无类型断言。

（补充事实：miniblog 也并非纯自研，`post.go` 直接 import 了第三方 `ozzo-validation`
做 URL 校验；且 onexstack 的 `ValidRequired` 对非指针字段调 `IsNil()` 会 panic。）

### 已落地（2026-08-29）

**1. proto 注解（契约层）**——`_example/bald/proto/greet.proto`
```proto
import "buf/validate/validate.proto";

message GreetRequest {
  string name = 1 [(buf.validate.field).string = {
    min_len: 1, max_len: 32, pattern: "^[A-Za-z0-9_-]+$"
  }];
}
```
- `buf.yaml` 新增 dep `buf.build/bufbuild/protovalidate`（仅引入 proto 定义）。
- **不需要代码生成插件**：普通 `protoc-gen-go` 即可，注解作为扩展选项留在描述符里，
  运行时由 `protovalidate.Validate(msg)` 读取。这与 PGV（protoc-gen-validate）不同。
- 已验证：`buf build` 通过；生成产物 `greet.pb.go` 中可见 `buf/validate` 引用，注解确实进入描述符。

**2. 拦截器依赖倒置（方案 B）**——`pkg/middleware/grpc/validator.go`

核心包**不绑定任何校验库**（与 P5「核心只依赖接口、实现外置」一致）：
```go
type MessageValidator func(ctx context.Context, rq any) error

func ValidatorInterceptor(validate MessageValidator) grpc.UnaryServerInterceptor
```
调用方按需要注入：
```go
// (a) protovalidate：读取 proto 注解（需 go get buf.build/go/protovalidate）
grpcmw.ValidatorInterceptor(func(ctx context.Context, rq any) error {
    msg, ok := rq.(proto.Message)
    if !ok { return nil }
    return protovalidate.Validate(msg)
})

// (b) pkg/validation 分发器：复杂命令式逻辑，框架自带零外部依赖
v, err := validation.NewValidator(myValidator{})
grpcmw.ValidatorInterceptor(v.Validate)

// (c) 串联：先跑注解规则，再跑复杂逻辑
```

**为什么不把 protovalidate 直接写进拦截器**：它内嵌 CEL 引擎（`cel-go`），
是较重的运行时依赖；把它钉进核心 go.mod 会与 P5 治理相悖，且让不用 protovalidate
的用户被迫拖入 cel-go。依赖倒置后，核心 go.mod **零新增依赖**（已验证
`go.mod`/`go.sum` 中无 protovalidate / cel-go）。

**3. 顺带消灭的隐患**：旧实现 `ValidatorInterceptor(validation.NewValidator(nil))`
会得到一个「看似注册了、实际什么都不校验」的校验器，`_example/bald/main.go` 正是这么用的。
改造后 nil 就是 nil、语义可见，且拦截器的 nil 回调有回归测试。

**4. example 接线**：`register_grpcgw.go`（`-tags grpcgw`）用 `init` 注入真实校验器
`greetRequestValidator.ValidateGreetRequest`，演示「注解规则 + 手写逻辑」两层串联。

### protovalidate Go 运行时已接入（2026-08-29）

在 `_example` 独立模块内 `go get buf.build/go/protovalidate`（v1.3.0）。
**核心 go.mod 仍未引入 protovalidate / cel-go / grpc-gateway**（已验证）。

`register_grpcgw.go` 的完整接线：
```go
// init：预热 protovalidate 实例（预编译 CEL，注解写错在启动期就暴露）
protoValidator, err := protovalidate.New()

// 拦截器回调：先跑注解规则（廉价、可共享），再跑手写逻辑（查库/权限）
greetValidator = func(ctx context.Context, rq any) error {
    if msg, ok := rq.(proto.Message); ok {
        if err := protoValidator.Validate(msg); err != nil {
            return mapValidationError(err)   // → berrors.BadRequest("INVALID_ARGUMENT")
        }
    }
    return v.Validate(ctx, rq)   // pkg/validation 分发器，处理注解表达不了的逻辑
}
```
- 用 `protovalidate.New()` 预热实例而非每次 `Validate(msg)`：预编译 CEL 表达式，
  且让「注解编译错误」在进程启动期暴露（fail fast），而非第一个请求才炸。
- 错误映射 `mapValidationError`：protovalidate 默认累积全部违规，
  聚合后转 `berrors.BadRequest("INVALID_ARGUMENT")`——与 `conf.Validate` 收集全部问题风格一致。
- **两层不重复**：手写校验器改为只做注解表达不了的判断（依赖外部状态的保留字检查），
  非空/长度/格式全交给注解，避免同一规则在两处各写一遍（双真相源）。
