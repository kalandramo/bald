# go-bald-admin 设计文档

> 配套 `需求文档.md`。本文档规定基于 bald 重构 `go-wind-admin/backend` 的**具体依赖选型**与模块设计。
> 核心原则：**所有能力必须经由 bald 实现或桥接**，业务不直连引擎。

## 1. 整体架构

```
bald/examples/go-bald-admin/          (独立 go module: github.com/kalandramo/bald/examples/go-bald-admin)
├── go.mod                            replace github.com/kalandramo/bald => ../../bald
│                                    replace .../bald/contrib/store-gorm => ../../contrib/store-gorm
│                                    replace .../bald/contrib/authn-jwt => ../../contrib/authn-jwt
├── api/protos/                       (从源项目搬运并精简的 .proto，业务契约)
├── gen/                              (protoc 生成代码)
├── internal/
│   ├── conf/                         (业务配置 proto → bald pkg/conf 生成)
│   ├── entity/                       (GORM 实体 / DTO，实现 store.Entity 约束)
│   ├── data/                         (仓储层：store.NewStore[T](baldgorm.NewGormProvider))
│   ├── biz/                          (业务逻辑层，含 authz 策略 / data scope 注册)
│   ├── server/                       (gRPC + HTTP 服务注册，复用 appkit + middleware)
│   └── bootstrap/                    (appkit.Run 入口、注册表装配)
└── docs/
```

- **模块边界**：`go-bald-admin` 独立 go.mod，绝不在 `bald` 核心 go.mod 添加业务/引擎依赖（P5）。
- **启动范式**：复用 `bald/_example/bald/main.go` 的 `appkit.Run` + `register_grpcgw.go` 模式。

## 2. 依赖选型（逐项决策）

| 能力域 | 源项目依赖 | bald 选型 | 决策理由 |
|--------|-----------|----------|----------|
| 核心框架 | `go-wind-toolkit`/`gow` | **bald 核心** | 本次重构目标即验证 bald |
| 配置管理 | 自研 viper 封装 | **bald `pkg/conf`**（proto-first） | 配置/类型单一真相源，viper 四源已由 bald 封装 |
| 认证 | `pkg/jwt`（golang-jwt 自封装） | **`bald/contrib/authn-jwt`** | 实现 `authn.Authenticator`，HS256 白名单，无硬编码密钥 |
| 授权 | `pkg/authorizer` + 自研 RBAC | **bald `pkg/authz.Authorizer`** + 业务 RBAC 实现 | 核心仅定义接口（避免 casbin 入核），业务侧桥接 RBAC |
| 数据访问 | `ent` (entgo.io/ent) | **`bald/contrib/store-gorm`** + GORM 实体 | 核心零耦合；GORM 桥接已落地，泛型 `Store[T]` 同构 ent 的 Repository |
| 分页 | 自研 | **bald `pkg/store` 三策略** | Page/Offset/Token 已由 P2 落地 |
| 多租户 | 中间件手动注入 | **`store.RegisterTenant` + `Where.T(ctx)`** | P8 下沉 DAL，查询自动隔离 |
| 数据权限 | 自研 Viewer | **`store.RegisterDataScope`** | P9 五级范围函数注入 |
| 任务队列 | `asynq`（Redis） | **MVP：本地 goroutine + 接口抽象**；后续桥接 `bald/contrib/task` | 首期不在核心引入 Redis 强依赖；保留 `TaskRunner` 接口 |
| 对象存储 | `minio-go`（OSS） | **业务侧 `pkg/oss` 抽象 + minio 桥接**（位于 example 内） | OSS 非 bald 核心能力，example 内自管 |
| 缓存 | `redis-go` + `HExpire` | **MVP：进程内 `ristretto`/map；后续 `bald/contrib/store-redis`** | Redis 8.0 专有命令暂不在核心支持，降级为本地缓存 |
| 服务注册 | `etcd`/`consul` | **MVP：单进程，不做注册中心** | 验证阶段不需要；后续桥接 |
| 链路追踪 | `jaeger` + otel | **bald `pkg/middleware` 依赖倒置 + 可选 otel 桥接** | P3 已预留，otel 不入核 |
| 依赖注入 | `google/wire` | **bald 函数式 Option（`appkit.Registry` + `init` 自注册）** | P1 注册表范式，不用 wire（与路线共识一致） |
| gRPC-Gateway | `grpc-gateway` | **复用 bald `_example` 的 `register_grpcgw` 范式** | 传输中立，核心不钉 grpc-gateway |
| 代码生成 | `gow` + `buf` + `protoc-gen-*` | **bald `codegen` 子命令 + buf** | P4 已落地；复用源项目 `buf.gen.yaml` |

### 2.1 明确**不采用**的依赖
- ❌ `ent`：以 GORM 实体 + `bald-store-gorm` 替代（图式关系在业务层用外键/关联查询表达）。
- ❌ `kratos`：以 bald `appkit` + gin/gRPC 原生替代。
- ❌ `google/wire`：以 bald 注册表 + 函数式 Option 替代。
- ❌ 源项目 `pkg/jwt`、`pkg/authorizer`、`pkg/middleware/auth`、`pkg/middleware/ent`：
  由 `bald-authn-jwt` + `bald/pkg/authz` + `bald/pkg/middleware` 替代。
- ❌ `casbin`：不进核心；RBAC 用 `authz.Authorizer` 函数式实现（如需规则引擎，业务侧桥接）。

### 2.2 依赖引入位置
- **bald 核心 go.mod**：不新增任何上述引擎依赖（保持零耦合）。
- **`go-bald-admin` go.mod**：仅引入 `gorm`/`glebarez-sqlite`/`golang-jwt`/`minio-go` 等业务侧桥接所需（经 contrib 传递或直引）。
- **`bald/contrib/*`**：已有 `store-gorm`、`authn-jwt` 各独立 module；如需 Redis/Task 桥接，新增 `bald/contrib/store-redis`、`bald/contrib/task`。

## 3. 关键模块设计

### 3.1 认证授权（P7）
```
server/grpc:
  middleware grpc Authn(authenticator) → Authz(authorizer)  // 依赖倒置注入
authn.Authenticator 实例 = baldjwt.NewJWTAuthenticator(secret, issuer)
authz.Authorizer 实例 = biz.NewRBACAuthorizer(permissionRepo)  // 业务实现
```
- 登录接口（`authentication` 服务）调用 `authenticator.IssueToken(claims)` 签发 JWT。
- 中间件把 Bearer → `authn.ContextWithToken` → `Authenticate` → `ContextWithAuthClaims`。
- 过期校验下沉 `Authenticator`（契约已要求校验 `ExpiresAt`）。

### 3.2 多租户 + 数据权限（P8/P9）
```
bootstrap 初始化：
  store.RegisterTenant("tenant_id", store.DefaultTenantFunc)   // 显式开启
  store.RegisterDataScope(biz.CurrentUserScope)               // 仅本人
  store.RegisterDataScope(biz.DeptScope)                       // 本部门（按 claims 角色）
```
- `ListWithPaging`/`Get`/`Delete` 经 `mergeTenant`+`mergeDataScope` 自动拼接条件。
- `AuthClaims` 携带 `TenantID`/`Roles`/`Scopes`，供 scope 函数与 authorizer 使用。

### 3.3 数据层（P2）
```
entity.User 实现 store.Entity 约束（主键、表名）
provider := baldgorm.NewGormProvider[User](db, func(u *User) string { return u.ID })
repo := store.NewStore[User](provider)
// 业务调用 repo.ListWithPaging(ctx, where, opts)
```
- 迁移：`provider.Migrate` 走 GORM AutoMigrate。
- 分页策略：`detectStrategy` 自动识别 Page/Offset/Token。

### 3.4 配置（proto-first）
- 业务配置 proto 放 `api/protos/<domain>/config`，经 `make proto-config` 生成到 `internal/conf/gen`。
- 加载：`config.Load` 四源合并；flag 经 `appkit.Bind` 注册。

## 4. 与 bald 核心的联动验证
- 每次核心改动后，在仓库内执行 `cd bald/examples/go-bald-admin && go build ./... && go test ./...`
  验证真实业务无回归（这是"用 go-wind-admin 验证 bald"的核心价值）。
- e2e 覆盖：登录（401→token）→ 访问受限接口（403 越权）→ 跨租户查询隔离。

## 5. 风险与缓解
| 风险 | 缓解 |
|------|------|
| GORM 表达力不及 ent（图遍历/边查询） | 业务层用关联查询 + 分批；首期 MVP 不移植深图查询 |
| Redis 8.0 专有命令 | 缓存 MVP 降级本地；后续 `bald/contrib/store-redis` 再评估 |
| asynq 任务语义 | 抽象 `TaskRunner` 接口，MVP 本地实现，后续桥接 |
| proto 搬运量大（97 个） | 按 M0–M4 增量搬运，先 authentication/permission 跑通范式 |
