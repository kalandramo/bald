# go-bald-admin 设计文档

> 配套 `需求文档.md`。本文档规定基于 bald 重构 `go-wind-admin/backend` 的**具体依赖选型**与模块设计。
> 核心原则：**所有能力必须经由 bald 实现或桥接**，业务不直连引擎。

## 0. 实现契约：外部依赖禁止虚假实现

本范例是"用真实业务验证 bald 框架"的载体，**任何外部依赖都不得用手写桩、内存占位、硬编码或
模拟实现蒙混**，必须接入真实、可运行、可验证的依赖。该契约优先于一切"先跑通范式"的简化诉求。

### 0.1 禁止项（硬性约束）
- **禁止 fake / mock / stub 充当外部依赖**：数据库、缓存、消息队列、认证后端、第三方 API 等
  外部系统，不得用内存 map、固定返回值、空接口、打印日志代替。
- **禁止硬编码返回值**：handler / service 不得对"受限资源""机密""用户"等本应从存储读取的领域对象
  返回写死的字符串或常量（如 `content: "top-secret-value"` 之类演示占位）——必须经由 `store` 等
  真实 DAL 读写。
- **禁止占位式桥接**：`InitBridges` / bootstrap 中不得留"待接入"的空壳；依赖必须构造出
  可工作的真实实例并注入。
- **禁止为绕过工具链而牺牲真实语义**：M0-M4 的"纯 Go 手写、避开 protoc"只是生成方式选择，
  **不等于**可用假实现替代真实能力；M5 已确认 proto+buf 为正式契约来源。

### 0.2 允许的简化（须显式标注且真实可跑）
- **SQLite 内存库**作为零外部依赖的真实数据库是**允许的**（它仍是真实的 GORM+DAL 读写路径，
  非内存占位）；外部 PostgreSQL/MySQL 仅在其环境具备时再切换 driver（见 M4.2 / M6）。
- **内存 RBAC 角色映射**作为授权策略引擎是允许的（策略本身即业务数据，非外部依赖）；但
  角色/权限来源若需求要求落库，则须经 `store` 真实加载（M2 已落 RoleStore）。
- 任何上述简化，必须在里程碑记录中明确标注"真实路径"与"待接真实外部依赖项"，不得静默伪装成完成。

### 0.3 当前偏差清单（须逐步消除）
| 位置 | 现状 | 性质 | 处置 |
|------|------|------|------|
| `handler/gin/auth.go` `GET /secret/:id` 返回 `content:"top-secret-value"` | 硬编码演示值 | 违反 §0.1 | **已消除(M6.3)**：改经 `biz`→`store` 读真实 Secret 实体(`model.Secret`+`SecretStore`) |
| `grpc/secret.go` `GetSecret` 返回 `"top-secret-value-for-"+id` | 硬编码拼接 | 违反 §0.1 | **已消除(M6.3)**：统一经真实 DAL，跨租户检索被 store 隔离为 NotFound |
| `internal/security/rbac` 内存静态 RBAC 表 | 内存假实现 | 违反 §0.1 | **已消除(M6.1)**：改由 `internal/security/casbin` 桥接 casbin(策略 `rbac_*.conf/csv`) |
| `bootstrap.openDB()` 非空 DSN 仅给指引、不接 driver | 占位桥接 | 受 §0.2 允许（无 DB 环境） | 待 M6 外部 DB 真实切换接 PG/MySQL driver 验证 |
| `M1` 内存用户表（admin/alice） | 已落地 `UserStore`（SQLite） | 已消除 | 无需处置 |

> 校验：`go test ./...` 中涉及外部依赖的用例必须走真实传输/真实 DAL（如 gRPC 真实连接、SQLite 真实
> 读写），不得用 fake client 或 in-memory double 替代；新增虚假实现视为回归。

## 1. 整体架构

分层**参考 `osbuilder` 脚手架模板**（`osbuilder/internal/osbuilder/tpl/project`，clean/onion 分层），
并按 bald 约定做三处偏差（见 §1.1）。源项目 `go-wind-admin/backend` 是单 admin 服务 + gRPC-gateway 双协议，
故采用「按服务名 `apiserver` 分顶层、服务内再按层拆分」的范式（与 osbuilder `internal/apiserver` 同构）。

```
bald/examples/go-bald-admin/                          (独立 go module)
├── go.mod                              replace github.com/kalandramo/bald => ../../bald
│                                      replace .../bald/contrib/store-gorm => ../../contrib/store-gorm
│                                      replace .../bald/contrib/authn-jwt => ../../contrib/authn-jwt
├── api/protos/<domain>/<svc>.proto     (从源项目搬运精简，业务契约)
├── gen/go/...                          (protoc 生成代码)
├── cmd/
│   └── go-bald-admin/main.go           (入口：appkit.Run + 注册表装配)
├── configs/                            (yaml 配置，viper 四源加载)
├── internal/
│   ├── apiserver/                      (单 admin 服务，双协议 gRPC + gin(grpc-gateway))
│   │   ├── server.go                   (appkit.Server 装配：注册 gRPC/gin handler)
│   │   ├── ginserver.go                (HTTP 传输，复用 bald pkg/middleware/gin)
│   │   ├── grpcserver.go               (gRPC 传输，复用 bald pkg/middleware/grpc)
│   │   ├── biz/                        (业务逻辑/use case)
│   │   │   └── v1/<domain>/<domain>.go (按 领域+版本 组织，如 biz/v1/permission/permission.go)
│   │   ├── handler/                    (传输层适配器，薄壳)
│   │   │   ├── gin/<domain>.go         (HTTP handler → 调 biz)
│   │   │   └── grpc/<domain>.go        (gRPC handler → 调 biz)
│   │   ├── model/                      (GORM 实体，对应 osbuilder model；实现 store.Entity 约束)
│   │   ├── store/                      (数据访问：store.NewStore[T](baldgorm.NewGormProvider))
│   │   └── pkg/
│   │       ├── conversion/             (model ↔ proto 映射，对应 osbuilder pkg/conversion)
│   │       └── scope/                  (P9 数据权限 DataScope 函数注册)
│   ├── bootstrap/                      (appkit 注册表：RegisterTenant/RegisterDataScope/Authenticator/Authorizer)
│   └── conf/                           (业务配置 proto → bald pkg/conf 生成)
└── docs/
```

- **模块边界**：`go-bald-admin` 独立 go.mod，绝不在 `bald` 核心 go.mod 添加业务/引擎依赖（P5）。
- **启动范式**：复用 `bald/_example/bald/main.go` 的 `appkit.Run` + `register_grpcgw.go` 模式；
  注册表装配在 `internal/bootstrap` 内完成（替代 osbuilder 的 `wire`）。

### 1.1 与 osbuilder 模板的分层偏差（必须保留，因 bald 原则）
| 维度 | osbuilder 模板 | go-bald-admin（bald 约定） | 理由 |
|------|---------------|---------------------------|------|
| 依赖注入 | `google/wire` (`wire.go`) | 框架插件发现用 `appkit.Registry`(核心原生)；**业务对象装配 M6.4 改 `google/wire`** | bald **核心不内置** wire；业务层用 wire 做装配(与源项目同构),仅接管业务层,不替代核心注册表 |
| 授权 | `casbin` | `authz.Authorizer` + 业务 RBAC 实现（M0-M5 验证用） | bald **核心不内置** casbin，但业务层可把 casbin 作为 `authz.Authorizer` 的真实实现（P7 仅约束核心不钉死授权引擎）；源项目 `go-wind-admin/backend` 即用 casbin，落地时优先复用 |
| 基础设施 | `onexstack`（Store/Server/错误） | `bald` 自有 `pkg/store`/`pkg/appkit`/`pkg/berrors` | 本次目标即验证 bald |
| 实体层名 | `model` | `model`（沿用 osbuilder 命名，非 `entity`） | 与模板对齐，降低迁移认知成本 |
| 转换层 | `pkg/conversion` | `pkg/conversion`（沿用） | 与模板对齐 |
| 配置 | 自研 viper | `bald pkg/conf`（proto-first） | 配置单一真相源 |
| 多服务 | apiserver/jobserver/mqserver/mbctl 多二进制 | 仅 `apiserver` 单服务双协议 | 源项目 admin 是单服务 |

### 1.2 领域分层映射（osbuilder → bald）
- `osbuilder internal/apiserver/biz/v1/user` ⇔ `go-bald-admin internal/apiserver/biz/v1/<domain>`
- `osbuilder model/user.gen.go` ⇔ `go-bald-admin model/<domain>.go`（GORM 实体）
- `osbuilder store/user.go` ⇔ `go-bald-admin store/<domain>.go`（`store.NewStore[T]` 封装）
- `osbuilder pkg/conversion/user.go` ⇔ `go-bald-admin pkg/conversion/<domain>.go`
- `osbuilder handler/gin|grpc/user.go` ⇔ `go-bald-admin handler/gin|grpc/<domain>.go`（薄适配）


## 2. 依赖选型（逐项决策）

| 能力域 | 源项目依赖 | bald 选型 | 决策理由 |
|--------|-----------|----------|----------|
| 核心框架 | `go-wind-toolkit`/`gow` | **bald 核心** | 本次重构目标即验证 bald |
| 配置管理 | 自研 viper 封装 | **bald `pkg/conf`**（proto-first） | 配置/类型单一真相源，viper 四源已由 bald 封装 |
| 认证 | `pkg/jwt`（golang-jwt 自封装） | **`bald/contrib/authn-jwt`** | 实现 `authn.Authenticator`，HS256 白名单，无硬编码密钥 |
| 授权 | `pkg/authorizer` + 自研 RBAC | **bald `pkg/authz.Authorizer`** + 业务 RBAC 实现 | 核心仅定义接口（避免 casbin 入核），业务侧桥接 RBAC |
| 数据访问 | `ent` (entgo.io/ent) | **`bald/contrib/store-gorm`** + GORM 实体 | 核心零耦合；GORM 桥接已落地，泛型 `Store[T]` 同构 ent 的 Repository |
| 分页 | 自研 | **bald `pkg/store` 三策略** | Page/Offset/Token 已由 P2 落地 |
| 多租户 | 中间件手动注入 | **`store.RegisterTenant` + `Where.T(ctx)`** | P8 下沉 DAL，查询自动隔离 |
| 数据权限 | 自研 Viewer | **`store.RegisterDataScope`** | P9 五级范围函数注入 |
| 任务队列 | `asynq`（Redis） | **MVP：本地 goroutine + 接口抽象**；后续桥接 `bald/contrib/task` | 首期不在核心引入 Redis 强依赖；保留 `TaskRunner` 接口 |
| 对象存储 | `minio-go`（OSS） | **业务侧 `pkg/oss` 抽象 + minio 桥接**（位于 example 内） | OSS 非 bald 核心能力，example 内自管 |
| 缓存 | `redis-go` + `HExpire` | **MVP：进程内 `ristretto`/map；后续 `bald/contrib/store-redis`** | Redis 8.0 专有命令暂不在核心支持，降级为本地缓存 |
| 服务注册 | `etcd`/`consul` | **MVP：单进程，不做注册中心** | 验证阶段不需要；后续桥接 |
| 链路追踪 | `jaeger` + otel | **bald `pkg/middleware` 依赖倒置 + 可选 otel 桥接** | P3 已预留，otel 不入核 |
| 依赖注入 | `google/wire` | **bald 函数式 Option（`appkit.Registry` + `init` 自注册）**（M0-M5 验证用） | P1 仅约束核心不内置 DI 框架；业务层可选用 `google/wire` 做装配 |
| gRPC-Gateway | `grpc-gateway` | **复用 bald `_example` 的 `register_grpcgw` 范式** | 传输中立，核心不钉 grpc-gateway |
| 代码生成 | `gow` + `buf` + `protoc-gen-*` | **bald `codegen` 子命令 + buf** | P4 已落地；复用源项目 `buf.gen.yaml` |

### 2.1 明确**不进 bald 核心**的依赖（业务层可按需采用）
> 以下均指"bald 核心 go.mod 不引入",不表示业务项目不能用。go-bald-admin 是验证 bald 范式的最小
> 业务,故 M0-M5 直接用了核心提供的等价抽象;若真实项目(如源项目 `go-wind-admin/backend`)依赖这些
> 引擎,在 `go-bald-admin` 业务层桥接即可(满足 §0 真实依赖契约)。
- ❌ `ent`：**核心**不引入;以 GORM 实体 + `bald-store-gorm` 替代（图式关系在业务层用外键/关联查询表达）。业务层仍可按源项目风格保留 ent。
- ❌ `kratos`：**核心**不引入;以 bald `appkit` + gin/gRPC 原生替代。
- ❌ `google/wire`：**核心**不内置;业务层装配可选用 wire(见 §1.1),范例用 `appkit.Registry` 仅因核心已给等价机制。
- ❌ 源项目 `pkg/jwt`、`pkg/authorizer`、`pkg/middleware/auth`、`pkg/middleware/ent`：
  由 `bald-authn-jwt` + `bald/pkg/authz` + `bald/pkg/middleware` 替代(核心层契约)。
- ❌ `casbin`：**核心**不引入;RBAC 用 `authz.Authorizer` 实现,业务层可桥接 casbin 作为该接口的真实实现(源项目即用 casbin,优先复用)。

### 2.2 范例定位（M6 决策基线）
`go-bald-admin` 是 **bald 框架的能力验证载体**,而非 `go-wind-admin/backend` 的复刻。M6 对成熟库的态度:
- **接**:源项目已用、且能消除 §0 偏差的成熟库——`casbin`(授权)、`go-redis`(缓存,单测 `miniredis`)、
  `google/wire`(业务装配,M6.4 确认采用,见 M6 段职责边界;框架发现仍用 `appkit.Registry`)、
  `bald-authn-jwt` 非对称支持(M6.5:RS256/ES256,签发持私钥/验签持公钥,经同一 `jwt/v5` 库)。
- **不接**(无业务场景 / 会混淆 example 定位):`asynq`(无异步任务)、`minio`(无文件)、`ent`(已选
  `bald-store-gorm` 路线,混用 ORM 致乱)、`opa`(策略即业务数据,用 casbin 足够)、kratos 全家桶(与
  `appkit`+gin/gRPC 原生定位冲突)。これら属"未来可选",非 M6。
- **核心约束**:所有桥接落在 example 的 `go.mod`(业务层),经 `authz.Authorizer` / `store` 等接口注入,
  **绝不**写进 bald 核心(呼应"核心不钉死"原则)。

### 2.2 依赖引入位置
- **bald 核心 go.mod**：不新增任何上述引擎依赖（保持零耦合）。
- **`go-bald-admin` go.mod**：仅引入 `gorm`/`glebarez-sqlite`/`golang-jwt`/`minio-go` 等业务侧桥接所需（经 contrib 传递或直引）。
- **`bald/contrib/*`**：已有 `store-gorm`、`authn-jwt` 各独立 module；如需 Redis/Task 桥接，新增 `bald/contrib/store-redis`、`bald/contrib/task`。

## 3. 关键模块设计

### 3.1 认证授权（P7）
```
server/grpc:
  middleware grpc Authn(authenticator) → Authz(authorizer)  // 依赖倒置注入
authn.Authenticator 实例 = baldjwt.NewJWTAuthenticator(secret, issuer)
authz.Authorizer 实例 = biz.NewRBACAuthorizer(permissionRepo)  // 业务实现
```
- 登录接口（`authentication` 服务）调用 `authenticator.IssueToken(claims)` 签发 JWT。
- 中间件把 Bearer → `authn.ContextWithToken` → `Authenticate` → `ContextWithAuthClaims`。
- 过期校验下沉 `Authenticator`（契约已要求校验 `ExpiresAt`）。

### 3.2 多租户 + 数据权限（P8/P9）
```
bootstrap 初始化：
  store.RegisterTenant("tenant_id", store.DefaultTenantFunc)   // 显式开启
  store.RegisterDataScope(biz.CurrentUserScope)               // 仅本人
  store.RegisterDataScope(biz.DeptScope)                       // 本部门（按 claims 角色）
```
- `ListWithPaging`/`Get`/`Delete` 经 `mergeTenant`+`mergeDataScope` 自动拼接条件。
- `AuthClaims` 携带 `TenantID`/`Roles`/`Scopes`，供 scope 函数与 authorizer 使用。

### 3.3 数据层（P2）
```
entity.User 实现 store.Entity 约束（主键、表名）
provider := baldgorm.NewGormProvider[User](db, func(u *User) string { return u.ID })
repo := store.NewStore[User](provider)
// 业务调用 repo.ListWithPaging(ctx, where, opts)
```
- 迁移：`provider.Migrate` 走 GORM AutoMigrate。
- 分页策略：`detectStrategy` 自动识别 Page/Offset/Token。

### 3.4 配置（proto-first）
- 业务配置 proto 放 `api/protos/<domain>/config`，经 `make proto-config` 生成到 `internal/conf/gen`。
- 加载：`config.Load` 四源合并；flag 经 `appkit.Bind` 注册。

## 4. 与 bald 核心的联动验证
- 每次核心改动后，在仓库内执行 `cd bald/examples/go-bald-admin && go build ./... && go test ./...`
  验证真实业务无回归（这是"用 go-wind-admin 验证 bald"的核心价值）。
- e2e 覆盖：登录（401→token）→ 访问受限接口（403 越权）→ 跨租户查询隔离。

## 5. 风险与缓解
| 风险 | 缓解 |
|------|------|
| GORM 表达力不及 ent（图遍历/边查询） | 业务层用关联查询 + 分批；首期 MVP 不移植深图查询 |
| Redis 8.0 专有命令 | 缓存 MVP 降级本地；后续 `bald/contrib/store-redis` 再评估 |
| asynq 任务语义 | 抽象 `TaskRunner` 接口，MVP 本地实现，后续桥接 |
| proto 搬运量大（97 个） | 按 M0–M4 增量搬运，先 authentication/permission 跑通范式 |

## 7. 里程碑落地记录

### M0（脚手架，已落地）
- 独立 go module `examples/go-bald-admin`，`replace` 指向本地 `../../bald` 及 `../../contrib/{authn-jwt,store-gorm}`。
- `cmd/go-bald-admin/main.go`：`appkit.Run` 范式 + cobra `FParseErrWhitelist.UnknownFlags=true`（appkit 自解析 flag）+ PATH 插件发现。
- 双协议启动验证：HTTP `:8080` 健康检查 + gRPC `:9090`，`servers=2`。
- `internal/bootstrap`：`InitBridges(ctx)` 占位（M1 接入认证/授权）。

### M1（认证授权 P7，已落地，2026-08-30）
目标：跑通 P7 认证授权范式（登录签发 JWT、受保护接口 401/403），**不搬运 97 个 proto**——
用纯 Go 业务层验证中间件范式，避免 buf 工具链/联网阻塞（与"先跑通范式"里程碑精神一致）。

新增模块：
- `internal/security/rbac/rbac.go`：实现 `authz.Authorizer` 接口（RBAC 内存角色映射）。
  - 权限点 = `object:action`，其中 object 由路径归一化（取 `/v1` 后首段资源名，如 `secret`/`auth`），action = HTTP 方法小写。
  - 默认拒绝；subject 为空（未认证）即拒绝。
- `internal/apiserver/biz/v1/auth/auth.go`：登录校验 + `bald-authn-jwt.IssueToken` 签发；内存用户表（admin/alice，角色 admin/viewer）。
- `internal/apiserver/biz/v1/secret/secret.go`：受限资源业务（Get/Delete）。

**M6.5 JWT 非对称(✅ 已完成 · 从第二批提前)**
- **Why**:原 `bald-authn-jwt` 仅 HS256(对称),签发与验签共用一把密钥。对称密钥一旦分发给任一
  下游(网关/微服务),该节点即可伪造 token——验签权与签发权无法分离。非对称(RS256/ES256)使
  签发方独占私钥、验证方只持公钥,是 JWT 进入多服务/多租户/企业 OIDC(JWKS)生态的门槛能力,
  也直接消除 `bootstrap.go` "密钥不应存进程内存常量"的隐患(私钥可进 KMS/HSM)。
- **How(只动 `bald-authn-jwt` 桥接子模块,核心 `pkg/authn` 零改动)**:
  - `jwt.go` 重构为 Option 构造:`WithHMACSecret` / `WithRSAKeys(priv,pub)` /
    `WithECDSAKeys(priv,pub)` / `WithSigningAlg` / `WithAllowedAlgs` / `WithIssuer` /
    `WithLeeway`;算法按注入密钥自动推断(HMAC→HS256,RSA→RS256,ECDSA→ES256)。
  - 验签 `keyfunc` 按 token 头 `alg` 选对应公钥,拒绝 `alg=none` 与密钥错位;白名单 `WithValidMethods`
    防算法混淆。`authn.AuthClaims` 经内部 `jwtClaims` 桥接类型与 `jwt.RegisteredClaims` 互转,不污染核心。
  - `Signer` 接口(`IssueToken`)供 auth biz 依赖(而非裸密钥);`Authenticator` 实现 `authn.Authenticator`
    验签。仅注入公钥的验签方调用 `IssueToken` 返回错误(无法伪造)。
- **范例接入**:`bootstrap.InitBridges` 启动时 `authnjwt.GenerateRSA(2048)` 生成密钥对,构造
  `Signer`(私钥,注入 auth biz `Login`)+ `Authenticator`(仅公钥,注入 gin/grpc 拦截器)两个独立实例,
  演示签发/验签权解耦。`InitBridges` 加幂等保护(避免重复生成密钥对破坏闭环)。
  生产应从 KMS/固定 PEM 加载密钥(重启后旧 token 仍有效、私钥可进 HSM)。
- **wire**:`authbiz.New` 改收 `authnjwt.Signer`;`wire.go` 的 `provideSigner()` 返回
