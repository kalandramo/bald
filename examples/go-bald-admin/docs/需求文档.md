# go-bald-admin 需求文档

> 目标：以 `bald` 框架重构 `go-wind-admin/backend`（基于 `gow`/`go-wind-toolkit` 脚手架的后台管理系统），
> 作为 bald 的官方落地范例，验证 P0–P9 各项能力在真实业务下的可用性。
> 本文件是范围与验收基线；具体技术选型见同目录 `设计文档.md`。

## 1. 背景与目标

- **源项目**：`go-wind-admin/backend` 是一个 Go 微服务后台管理系统，含 553 个 Go 文件、97 个 proto，
  业务域覆盖 admin / authentication / permission / identity / dict / audit / storage / task / internal_message / redis_cache。
- **重构目的**：验证 bald 框架（核心零耦合 + 桥接子模块）能否承载真实后台管理系统的全部横切与业务需求，
  重点验证 P7（认证/授权）、P8（多租户）、P9（数据权限）在真实场景下的落地。
- **约束**：重构后的包**必须全部基于 bald 实现**（认证走 `bald-authn-jwt`、存储走 `bald-store-gorm` 等
  contrib 桥接），不再使用源项目的 `ent` / `kratos` / `wire` / 自研 jwt / 自研 authorizer。

## 2. 功能需求

### 2.1 业务域（MVP 优先，按依赖排序）
| 域 | 源 proto | bald 落地说明 |
|----|----------|--------------|
| authentication | `authentication/service` | 登录/登出/刷新令牌，走 `bald-authn-jwt` |
| permission | `permission/service`（13 个 proto） | 角色/菜单/权限点，RBAC 授权走 `authz.Authorizer` |
| identity | `identity`（16 个 proto） | 用户/组织/岗位，业务 CRUD |
| dict | `dict` | 数据字典，业务 CRUD |
| admin | `admin`（36 个 proto） | 系统配置类业务 CRUD |
| storage | `storage/service` | 文件/对象存储元数据，业务 CRUD + OSS 桥接 |
| audit | `audit`（9 个 proto） | 操作审计日志，走 bald 审计注入 |
| task | `task` | 异步任务（源用 asynq），首期可用内存/本地实现 |
| internal_message | `internal_message` | 站内信，业务 CRUD |
| redis_cache | `redis_cache` | 缓存抽象，首期用 `bald-store-gorm` 的 Redis 缓存或旁路 |

### 2.2 横切需求（bald 能力验证点）
- **认证（P7）**：Bearer JWT 校验、令牌签发（`bald-authn-jwt`），`AuthClaims` 强类型注入 context。
- **授权（P7）**：RBAC 模型，基于 `authz.Authorizer` 接口；**不引入 casbin 到核心**，业务侧可桥接。
- **多租户（P8）**：通过 `store.RegisterTenant("tenant_id", store.DefaultTenantFunc)` 显式开启，
  查询自动注入 `tenant_id` 条件。
- **数据权限（P9）**：通过 `store.RegisterDataScope` 注入"仅本人/本部门/全部"等范围条件。
- **存储（P2）**：统一 `store.Store[T]` 泛型仓储，GORM 桥接 `bald-store-gorm`，三策略分页（Page/Offset/Token）。
- **配置（proto-first）**：框架与业务配置均以 proto 生成（bald `pkg/conf`），viper 四源合并。
- **生命周期（P0）**：`appkit.Run` 三阶段优雅停机；`pkg/appkit` 注册表统一管理 server/provider/middleware。
- **可观测（P3）**：日志/错误/链路依赖倒置，接入 `bald` 生态（otel 可选桥接）。
- **CLI/代码生成（P4）**：复用 `bald` 的 `codegen` 子命令生成 proto/store；kubectl 风格插件发现。

### 2.3 协议与接口
- 同时暴露 **gRPC** 与 **HTTP（grpc-gateway transcoding）**，复用 bald `_example` 的 register 范式。
- API 由 proto 生成，与源项目 `api/protos` 保持业务契约一致（字段语义对齐，可简化非必要字段）。

### 2.4 部署与运维
- 支持本地（SQLite + 内存）一键跑通 e2e，作为验证基线。
- 生产形态用 PostgreSQL + Redis（源项目要求 Redis 8.0+，因使用 `HExpire`/`HSETEX`）；
  缓存命令若必须，需在选型中明确替代方案。

## 3. 非功能需求
- **零核心耦合**：`go-bald-admin` 是独立 go module，经 `replace => ../../bald` 引用核心，
  不向 `bald` 核心 go.mod 引入任何业务/引擎依赖。
- **可测试**：每个业务服务具备单元 + e2e（参考 `bald/_example/bald/greet_e2e_test.go`）。
- **文档一致**：proto 注解驱动 OpenAPI/Swagger（buf 生成），复用源项目 `buf.*.gen.yaml` 配置。

## 4. 验收标准
1. `go build ./...` 在 `bald/examples/go-bald-admin` 下通过（独立 module）。
2. `go test ./...` 全绿，含至少一个 gRPC-gateway e2e（登录→带令牌访问受限接口→多租户隔离生效）。
3. P7/P8/P9 均有可演示路径：未认证返回 401、越权返回 403、跨租户查询被隔离。
4. 不出现 `ent` / `kratos` / `wire` / 源项目 `pkg/jwt` / `pkg/authorizer` 的直接依赖。
5. 与 bald 核心改动联动：修改核心后在本范例一键验证无回归。

## 5. 范围与里程碑
- **M0 脚手架**：module 建立、proto 搬运、appkit 启动、gRPC+HTTP 双协议跑通（对标 `_example/bald`）。
- **M1 认证授权**：authentication + permission 落地 P7。
- **M2 多租户+数据权限**：identity/admin 落地 P8/P9。
- **M3 业务域补齐**：dict/storage/audit/task/internal_message。
- **M4 部署与文档**：e2e、OpenAPI、README。

## 6. 风险与开放问题
- 源项目深度依赖 `ent`（图式 ORM + 代码生成）与 `asynq`（Redis 任务队列），重构需替换为
  `bald-store-gorm` + 自有任务抽象，存在查询表达力差异（见设计文档选型章节）。
- `redis_cache` 依赖 Redis 8.0 专有命令，需确认 bald 生态是否提供等价缓存桥接或降级方案。
