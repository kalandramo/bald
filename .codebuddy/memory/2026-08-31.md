## bald vs GoWind 设计哲学对比（分析任务，无代码改动）
对比了 bald 与 https://www.gowind.cloud/framework/intro.html 的「设计哲学」（积木式架构/分层职责/零外部依赖）。
- 核心结论：GoWind=生态型积木（核心<500行仅依赖 x/sync、plugins 100+ 适配器独立 go.mod、bootstrap YAML+SPI init() 自注册"零代码装配"）；bald=固执己见融合型（gin/grpc/viper/otel-API/kratos 焊进核心，berrors 零依赖，grpc-gateway 不进核心，桥接复用 kratos 生态，proto-first）。
- 哲学逐条兑现度：组合优于继承=两者一致；接口优于实现=bald 部分兑现（领域边界接口 vs GoWind 全领域插件）；零外部依赖=bald 有意相反；零隐藏魔法=各有张力（GoWind 的 SPI init() 隐式注册 vs bald 的显式全局 SetLogger/SetAuditor）。
- 本质差异：扩展模型（插件 SPI 广度 vs 接口桥接+范例反哺深度，P9 模式）、装配（YAML 声明式 vs Go Options+appkit 显式）、配置真相源（YAML vs proto）、传输（22+ 广度 vs HTTP/gRPC/gateway 语义深度对齐）。

## bald 架构下一步优化提案（咨询，未动代码）
基于 GoWind 对比短板 + 坑清单（坑集中在「装配期错误」）提出 P10-P13：
- **P10 横切关注点 Bundle**（优先级最高）：`pkg/middleware/bundle` 门面一次构造双传输产出（`b.Gin()` / `b.GRPCChain()`），链序（Error最外/Authn→Audit→Authz）由框架固化，依赖走构造器注入（`SetAuditor` 全局退化为兜底），内置 P9 归一化默认。零破坏（散装路径保留）。
- **P11 contrib 晋升管道**：go-bald-admin 的 `internal/cache`、`internal/security/casbin`、`internal/observability` 三件套收编为 `contrib/cache-redis`、`contrib/authz-casbin`、`contrib/observability-otlp`（独立 module，照 store-gorm 模式——store-gorm 已验证独立 go.mod 路线）。规则：internal 桥接存活两个里程碑即晋升 contrib。
- **P12 AppSpec + 装配 codegen**：proto 从「配置真相源」扩到「拓扑真相源」，P4 CLI 生成 main 装配骨架（appkit.Servers + bundle + config 绑定），对标 GoWind YAML 声明式但保编译期类型检查。分两步：先生成 config 绑定再生成装配。代价大放最后。
- **P13 卫生项**：`bald/go.mod:72` 孤儿 replace（require 无 bald-store-gorm 却 replace）应删；`freeAddr` 等 e2e 工具收进 `pkg/testkit`。
- 明确不做：可换 HTTP 栈抽象（毁 pkg/web 深度）、运行时 YAML 拓扑、追协议广度、彻底消灭全局状态（audit 已双路径，otel 全局是 Go 惯例）。
- 关键判断：bald 优化方向是「把正确装配从文档知识变成框架保证」，不是学 GoWind 积木化。

## Cordis 论文（时空可组合性）对 bald 的启发（咨询，未动代码）
论文《A Programming Paradigm for Spatiotemporal Composability》（arXiv:2608.25512，北大+DeepSeek-AI，Cordis 元框架形式化，源自 Koishi）。核心：把效应系统/共效应系统从静态分析提升为运行时机制——时间可组合性=可逆效应（卸载零残骸）、空间可组合性=响应式共效应（依赖图变化安全传播）；Cordis 三层=核心库（效应追踪+ctx.set/get+生命周期状态机）/组件加载器（声明式配置+增量协调+HMR）/领域层。DeepSeek Harness 万物皆插件（连 agent-loop 都是插件）。
- **用论文语言诊断 bald**：坑清单全部命中两类失效——`SetLogger/SetAuditor/RegisterTenant/RegisterStoreProvider` 是**不可逆效应**（纯全局写入无逆操作，`pkg/store/tenant.go:40` 已验证无 Unregister）；InitBridges 顺序坑/issueToken nil panic 是**共效应失效**（依赖未声明未解析）。bald 已在**进程级**实现 temporal（P0 三阶段停机），**组件级完全缺失**。
- **新增四个优化方向**（与前次 P10-P13 衔接）：
  - **T1 效应账本**：appkit 从钩子集合升级为可逆操作台账（`appkit.Effect(name, undo)` 登记逆操作，Stop 逆序回放）；收益=e2e 测试隔离（t.Cleanup 回放账本全局归零）。最小改动。
  - **S1 能力声明与解析**：bundle/contrib 组件声明 Provides/Requires，启动期拓扑排序+缺依赖 fail-fast（替代运行时 nil panic）；P10 bundle=S1 第一子集。
  - **C1 Server⊂Component 统一**：trace provider/metrics exporter/StreamAuditor/审计 DB 等散装全局统一为 `Component{Start,Dispose}` 纳入 appkit 生命周期，停机顺序按依赖图（logger 最后死）；「trace 忘 shutdown 丢批」变结构保证。
  - **R1 增量协调**：WatchConfigFile/OnConfigChange 升级为期望态 vs 实际态 diff-apply（热切 auditor 后端/日志级别/casbin 策略/OTLP endpoint），细粒度 key 订阅非全量 reload。P12 拆两半：codegen 静态 + reconcile 运行时。
- **能力扩展（agent-native 差异化）**：可逆工具注册表（P1 Registry 升级+效应账本）、自修改审计（agent 挂工具=AuditEvent 天然追踪）、管理面 API 变更可回滚。定位=「被验证的运行时可重组服务框架」，Go 侧 agent harness 底座。
- **明确不学**：Go 动态加载/HMR（编译语言认命，只做配置态重组）、形式化证明（bald 元定理=BUG-1/3/4 式契约回归测试）、通用元框架化（吸收机制不改 opinionated 定位）、万物皆插件教条（blessed stack 依赖不可换性）。
- 合并路线：P10 bundle→P11 contrib→T1 账本（与 P10 并行：组装正确性 vs 拆卸正确性）→C1 Component→R1 协调→远期 agent-native。

## 架构优化第五批落地（A1 运行时可逆挂载，2026-08-31）

- **`pkg/appkit/mount.go`** 三层原语：
  - `Registry[T].Mount/Unmount`：装配期 `Register`（不可逆 init() 语义）的运行期对偶——可逆挂载、undo 幂等（sync.Once）、同名冲突报错不覆盖。语义分开的理由：装配期错误 fail-fast（panic 合理）、运行期变更必须可回滚（账本语义）。
